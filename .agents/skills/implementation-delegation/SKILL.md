# 実装委任の選定

決めるのは**モデル・effort・/code-review 強度**の3つ。「Opus 5 / high」という判断の形で渡し、起動は人間が手動で指示する。

**対象: $ARGUMENTS** —— issue 番号の後に `codex` / `claude` があればその提供元だけ、無ければ両方。§1〜§3 は提供元非依存 —— 同じ判断を §4 / §5 の表に写すだけ。ティアの対応は**価格で揃える**(§5 の対応表): 主力 = Opus 5 ↔ Sol、廉価 = Sonnet 5 ↔ Terra、上位 = Fable 5 ↔ Sol / xhigh。

## 出力

提供元ごとに次の形だけ。根拠の再説明・スキル本文の繰り返し・伺い(「投げてよいか」等)は書かない:

- 実装: <モデル / effort> —— 既定から上げ下げしたときだけ理由1行
- /code-review: <モデル / effort> —— 実装より上げたときだけ、静かな失敗面を1行
- (あるときだけ)委任前に埋めた穴、渡す文面の特記

## 1. 選定

軸は**失敗コスト**(挙動不変リファクタ、ドメイン不変条件、セキュリティ境界、床)と**仕様の明確さ**(issue に完了条件・触るファイル・不変条件が書き切れているか)。

| | 仕様が明確 | 仕様が曖昧/探索的 |
|---|---|---|
| **失敗コストが高い** | 上位ティア / high | `/grilling` で曖昧さを解消してから再判定(初回上限 xhigh) |
| **失敗コストが普通** | 主力ティア / medium | 主力ティア / high |
| **機械的・反復的** | 廉価ティア / low〜medium | ——(曖昧なら廉価ティアに出さない) |

**既定は主力ティア / medium。上げる理由を言えるときだけ上げる**: 床に触る(権限・封じ込め・ブランチ規律・不変条件の執行点)/ 既存テストが旧挙動を assert している(仕様変更かバグかの区別を委任先が付ける)/ スキーマ変更の判断を含む。

### max は再試行

`max` は初回の実装・`/code-review` では選ばない。初回の上限は `xhigh` であり、仕様の曖昧さは
compute で埋めず、`/grilling`・issue の補完・分割のいずれかで解消してから選び直す。

`max` を使う入口は次の2つだけ:

- 人間がその実装または review に `max` を明示指定した。
- 同じ完了条件とスコープのタスクを `xhigh` で完走した後、test・review・外部正本のいずれかが
  局所修正では閉じない推論上の失敗を具体的に示し、その同じタスクを再試行する。

仕様不足、必要情報の欠落、tool / environment の失敗、usage limit による中断は `xhigh` の推論不足ではない。
それぞれ原因を直して同じ強度で再開する。`max` を選ぶ出力には、明示指定か、先行する `xhigh` の
失敗を1行で記す。局所修正で閉じる通常の finding や、単に「難しい」「静かに壊れうる」
「念のため」は入口にならない。

## 2. /code-review 強度

- **実装難度ではなく、間違いの現れ方で決める。** 上げるのは失敗が**静か**な面 —— 記録の汚染、開くだけのセキュリティ窓、挙動不変のはずの逸脱など、テストが緑のまま動いて見える方向。fail-closed に**うるさく**壊れる面(スキーマ拒否で止まる、受け入れ基準の赤で見える)は実装と同モデルで足りる。上げるときは「この間違いはどう静かに壊れるか」を issue ごとに1行 —— この1行が言えたときだけ、初回は `xhigh` まで上げる。静かな失敗面は `max` の入口ではない。パターン踏襲の実装を強くレビューする逆転も、この軸から自然に出る(migration 等、見所が1点なら下げてよい)。
- **実装と同じ提供元・設定が既定。** review は実装よりトークンが少ないことだけを理由に上げない。上の1行が書けるときだけ1段上げ、判断が割れるなら同じ設定に置く。別系列レビューは残量に余裕があるときの任意の上乗せ。
- **Codex**: モデルも effort も動かせる。spawn 時は必ず両方渡す(model だけでは compute budget が確定しない)。エージェントファイル側の設定は spawn 時より強いので、都度指定するならファイル側で固定しない。
- **Claude Code**: 強度の上下はモデルで行う(effort は親を継ぐ)。上げる=上位モデル —— Opus 5 実装なら /code-review を Fable 5 に。effort が動かないことは実装と同モデルに揃える理由にならない。
- **インライン実行する構成だけはモデルも effort も動かさない**(effort はプロンプトにレンダリングされキャッシュが飛ぶ)。
- **上げられないときは issue 本文で埋める**(発動条件はトークン残量と、リポジトリの `/code-review` が別物に差し替わっているときの2つだけ): 不変条件をテストファイル名で列挙する / 判断の分岐を PR 本文に書かせる。

### 2.1 ponytail-review

`実装 → ponytail-review → tests → /code-review → tests` が出発点。外すのは人間が外すと言ったときだけ。**モデル/effort の選定対象ではない** —— 実装スレッド内でインライン・実装と同設定で流すので、出力に行を作らない。/code-review は ponytail-review が入っても下げない。ponytail 系はプラグインで、スキル一覧・skills ディレクトリ・作業ログに見えないことは不在の証拠にならない。ADR が意図的に長い形を要求する箇所はテストで釘付けか確認し、釘が無い決定だけ渡す文面で1行名指しする。

## 3. issue 文面

- **issue 本文が発注書。** 完了条件・触ってよいファイル・不変条件(テストファイル名)を issue に書いてから投げる。薄ければプロンプトではなく issue を書き足す。
- **読む鎖の確認**: スキル → `CONTEXT.md`/ADR、`AGENTS.md` → issue の引き方、issue 冒頭 → ADR 番号。切れていたらその場所を直す(プロンプトで埋め合わせない)。
- 大型リファクタは「挙動不変+既存テスト green」を完了条件に単独スライス。モジュール新設2つ以上なら分割不足。相互依存スライスは分けない(分けてよいのは順序依存だけで、前提として issue に書く)。
- **発注書ファイルは既定では書かない** —— `/tdd #<issue>` で足りる。別立てするのは issue に書くべきでないその回限りの事情(スコープ制限 / 適用スキルの絞り込み / ADR が正本のときの読む順序)だけ。

## 4. Claude(鮮度 2026-08。世代が変わっていたら `claude-api` で更新し、このファイルも書き換える)

| モデル | 向くタスク |
|---|---|
| **Fable 5** | 一発で解けていない難問、長時間の自律実装。既定 `high`。1リクエストが数分〜十数分走るので待ち方を先に決める |
| **Opus 5** | 主力。複数ファイル実装・大きめリファクタ・床。既定 `high`、要求の厳しい作業だけ `xhigh` |
| **Sonnet 5** | 既存パターン踏襲、テスト追加、定型配線。既定 `high` |
| **Haiku 4.5** | rename、機械的置換、大量読み取り |

Max 席では Fable も他モデルと同じ週次 usage limit を共有(上限50%)。

## 5. Codex(GPT-5.6、鮮度 2026-08。世代が変わっていたら Web 検索で更新)

対応は**価格で揃える**(Sol $5/$30 ≈ Opus 5 $5/$25、Terra $2.5/$15 ≈ Sonnet 5 $3/$15、Luna $1/$6 ≈ Haiku $1/$5)。能力序列だけを見ると Sol は Fable 5 と同クラス(Artificial Analysis / Vals、2026-08)だが、値段が Opus 5 と同じなので主力に置く。OpenAI 自身の位置づけは「Sol = 最重要、Terra = 日常」で、その日常帯はこの表では Sonnet 5 の帯に写す。

| モデル | Claude 側の相方 | 向くタスク |
|---|---|---|
| **Sol / xhigh** | Fable 5 | 一発で解けていない難問、床。`max` は §1 の再試行だけ。`ultra` は effort の延長ではない別枠 orchestration mode —— 選ぶ前に効果を検証 |
| **Sol** | Opus 5 | 主力。複数ファイル実装・大きめリファクタ。既定 `high`(OpenAI 既定は medium だが Opus 5 の既定 `high` に揃える) |
| **Terra** | Sonnet 5 | 既存パターン踏襲、テスト追加、定型配線。既定 `high` |
| **Luna** | Haiku 4.5 | rename、機械的置換、大量処理 |

effort: `none`〜`max`。low=軽作業、medium=標準、high=既定、xhigh=難所、max=`xhigh` の推論不足が実証された再試行(または人間の明示指定)。

## 6. 委任先の前提

- **Claude Code**: スキル・MCP・指示ファイルが効くが、スキルが差し替わっていることがある —— 特定の呼び方を前提にせず issue 本文で埋める(§2)。
- **Codex App**: skill 発見は `.agents/skills` / `~/.agents/skills`。対話できるので、人間応答待ちのステップに「確認不要」と書き添えない。
