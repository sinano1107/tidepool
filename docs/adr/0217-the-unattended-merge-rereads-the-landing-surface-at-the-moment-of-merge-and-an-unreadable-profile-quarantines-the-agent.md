# 無人 merge は merge の瞬間に着地の面を読み直し、読めない profile は agent の quarantine に落とす

**Status 追記: 帰結が別 issue に回した「解決できてダイヤルを持たない profile」の枝は ADR 0228 で閉じた** —— 組み込みは work を実行しないので、その枝に届くのは registry の無い盤面だけになる。決定4 の「組み込みを上書きするエントリの削除は今日どおり許す」は、work の参照について狭まった。

**Status 追記: 帰結の「PR 単位の手段は GitHub で PR を閉じることだけ」は ADR 0229 で手段として効くようになった — 閉じた PR はキューから外れ、決定5 の観測も閉じた PR を読む**

2026-10-09 の grilling(issue #1392、発端は #1359 / ADR 0196 の帰結)で決定。`auto_if_ci_green` の無人 merge キューに
入った PR は、その後ダイヤルが取り下げられても、workspace に保護が付いても、CI が緑になれば盤面が無人で merge していた。
merge の直前に読み直していたのは付帯子と異議の門(ADR 0105 決定4)だけだった。調べた経路は #1392 に置く。

## 決定

1. **無人 merge は merge の瞬間に着地の面を読み直す。** 述語は「いま着地しても、この PR は無人 merge キューに入るか」で、
   保護・ダイヤル・risk flag から面を決める判定を1つにし、キュー投入時と merge 時の両方がそれを呼ぶ。ADR 0196 決定2 の
   とおり、無人 merge の背後にある判断は常設の設定だけである。行為の瞬間にその設定が取り下げられていれば、盤面にその
   merge を執行する根拠は無い。ADR 0088 が危険な値の付与に確認を求めても、取り下げが効かなければ片側だけの門になる。
   ダイヤルだけを読み直す案は、保護(ダイヤルに依らない資源側の不変条件)を素通りさせるので退けた。読む点は CI を
   読む前と、CI を読んだ後に盤面の名義で行為する直前 — 緑なら merge、赤なら merge question — の2点である(後者は
   issue #1644 で merge の直前から広げた。question も盤面の名義の行為で、そこで人間が merge と答えれば盤面が執行する)。
   門も同じ2点で読む。赤の枝でも読むのは、merge question を立てること自体が門を待つからで(ADR 0092)、回答時の検証に
   任せると修理が push する前の CI で問うことになる。門と違うのは結果だけである — 門に当たった PR はキューに残り、面が
   変わった PR はキューから外れる。
2. **面が変わった PR は、変わった先の面へ渡す。** `escalate`・保護・risk flag なら、キューから外して盤面の名義で merge question を
   立てる(いま開けば立つ question と同じ形 — 推奨は merge、回答時の CI 検査がそのまま効く)。`external` なら、キューから
   外し、外した事実を盤面の名義の event としてタスクに残す。question を立てないのは `external` が「盤面は問わない」宣言
   だから(ADR 0079 決定2)、黙って外さないのは ADR 0105 決定3「無言で消える経路は残さない」と同じ穴になるからである。
   締める向きだけが問題で、緩める向き(`escalate` で開いた後に `auto_if_ci_green` へ)は開いた question が残るだけなので、
   読み直しは PR をキューへ入れることはしない。CI が赤の PR では、question 面へ渡すときに立てるのは CI 赤の question
   (推奨は hold)である — 求める判断は「赤でも merge するか」で、面の変化はその判断を変えない。`external` への変化は
   赤でも同じく event を残して外す。
3. **profile が読めなければ、ダイヤルを推測せず agent を quarantine に落とす。** 着地の2点 — PR を開く時点と、無人 merge
   キューの PR に CI を読んだ後で行為する瞬間 — で authority profile が解決できない(agent の削除・定義の破損)とき、
   読めないダイヤルを `external` とも `escalate` とも扱わない。前者は盤面が何もしない fail-open(今日の挙動)、後者は `external` を宣言した人間に問わないはずの question
   を立てる。欠陥は PR ではなく registry にあるので、求める判断は「merge するか」ではなく「registry を直せ」であり、その形は
   既存の agent 名の quarantine である。開く時点では PR を開く前に解決し、失敗は着地の失敗として返す(直した後に retry で
   開く)。キューの側では PR をキューに残してスキップし、直った後の tick が本当のダイヤルで決める。解決の失敗と、解決
   できてダイヤルを持たない profile(組み込みの reviewer profile)は区別する。
4. **解除の検査と削除の扉は、同じ「着地を待つ完了タスク」を数える。** agent 名の quarantine の解除は「registry に戻った、
   またはその名前に依存するものが無い」で通るが、依存に数えていたのは未着手タスクだけだった。done のタスクは Edit で
   付け替えられないので、そのままでは registry を直さずに解除でき、次の tick でまた落ちる。そこで両者に、その agent の
   profile を読んで着地を待つ完了タスク(PR をまだ開いていないもの、キューにいるもの)を数えさせる。扉の外で registry から
   消した場合の修理はエントリを戻すことである。組み込みを上書きするエントリの削除は今日どおり許す(名前は組み込みへ
   落ちて解決し続ける — ADR 0117 決定2)。
5. **quarantine 中に盤面の外で merge された PR は、quarantine 回答の受理直前に観測する。** スキップされた PR は ADR 0079
   決定3 の merge 失敗時の検査に届かないので、観測しなければ解除の検査が永久に通らない。回答時の検証が正しさを担い走査は
   快適性のため、という ADR 0079 の線に乗せ、60秒面も遅い走査も広げない。

## Considered options

- **registry 編集の側でキューを掃除する** — 扉の外の編集(registry repo の直接編集)を取りこぼす。merge の瞬間に読む形は
  経路を問わない。
- **読めない profile は merge question に倒す(fail-closed)** — 決定3 の理由で退けた。
- **2点目を merge の直前に限る** — CI 赤の question は人間が判断するので害が無い、という読み。`external` の PR に盤面が
  問い、回答しだいで執行するので退けた(issue #1644)。

## 帰結

- 解決できてダイヤルを持たない profile は、共有した判定の中で `external` と同じ枝を通る。組み込みを上書きするエントリを
  キューの PR があるうちに消すと、その PR は event を残してキューから外れる。その枝の当否は別 issue で扱う。
- 人間が個別の PR を止める盤面の手段は増えない。ダイヤルと保護は agent / workspace 単位で、決着したタスクは Edit も
  cancel も拒む。PR 単位の手段は GitHub で PR を閉じることだけである。
