# 着地 question の通知は回答の面へ開かず盤面へ導く

2026-10-02 の triage / grilling(issue #828)で決定。push 通知の deep-link は、着地 question を含むすべての
question を単体の回答ビューへ開いていた。単体ビューは `landing` 注釈を持たないため、回答不能な着地 question も
通常のカードとして出て、merge は押した後に拒否される。ただし、より根の深い問題は回答不能かどうかに関係ない。
ADR 0092 決定4 は merge 判断をログの流し読みの後ろに置いたが、push の経路はすべての着地 question でこの順序を
飛ばしていた。コードを読んだ観測は #828 のコメントにある。

## 決定

1. **着地 question は通知するが、その通知は回答の面へ直接開かず、盤面へ導く。** 決定4 の「merge の前に、その
   背後の決定を読む」は triage 画面の並びではなく、着地の判断そのものの規則である。だから、どの面から人間を
   呼んでも成り立たなければならない。「着地を待つものがある」という知らせは残し、判断は流し読みの後ろに残す。
2. **線は「盤面が自分から人間を呼ぶ面」に引く。** 人間が自分から入る面(管理 MCP の回答)は
   この線の外にあり、回答不能なものは決定5 の回答時検証が止める。盤面は、人間が流し読みを済ませたかを状態として
   持たない。フローは WebUI の道筋であり、Triage session が開くのは操舵が始まってからだからである。この線を
   強制するには判定の根拠から作る必要がある。そもそも決定4 が防ぎたいのは、流し読みを飛ばす道筋を盤面が作る
   ことであり、人間の明示の判断を止めることではない。
3. **行き先は盤面のルート(`/`)とする。** 先例は human task の通知。triage タブを直接開く deep-link は新設しない
   — それが要るという観測が無い。
4. **単体ビューは、着地 question を開かれても回答カードを出さない。** 「merge の判断は triage で」と書いて盤面へ
   導く。単体ビューの存在理由は push からの1問だけの回答であり、決定1 で push から着地 question へ入る道が
   無くなるので、そこで答えさせる理由も無くなる。

## 退けた案

- **単体ビューで `blocked_by` を見て、回答不能なときだけ merge を出さない** — 回答不能なものは防げるが、回答可能な着地
  question はすべて決定4 の順序を飛ばしたまま残る。
- **着地 question を個別通知から外す** — 「着地を待つものがある」という知らせまで落とし、Quiet hours の通知対象
  (question タスク)に例外を1つ増やす。
- **着地 question は triage でしか答えられないと盤面が強制する** — 決定2。
