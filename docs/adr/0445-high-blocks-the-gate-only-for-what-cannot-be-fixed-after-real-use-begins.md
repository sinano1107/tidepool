# high は実運用の後に直せないものだけで門を塞ぐ

2026-11-28 の triage(#1879 の残量の見直し)で決定。門(#1879)を置いた 2026-10-13 以降、`priority:high` は約 750 件起票され約 700 件
閉じたが、open は 70 件前後から減らず、その 63 件はこの 7 日の起票だった。見直しの懸念は全件起票し、確かめていない疑いも基準に
当たれば high にし、spec を割った ticket が high を引き継ぐので、直してレビューするたびに同じ領域から high が出ていた。open の 69 件を
「実運用の後に直したら何が失われるか」で読み直すと、残るのは 17 件だった。振り分けの表は #1879 のコメントに置く。

## 決定

1. **high のテストは5つにする。** ADR 0244 決定2 の4つを置き換える。
   - 実運用の後に直すと、既にある行・登録物の backfill か意味の付け替えが要る。既存の表・列の形の変更はここに含む。実運用の後に
     migration と backfill を書く手間を避けるため、予想できるものは先に入れる。足すだけの変更でも、既存の行に値が無いことを食い違い・停止として読む形はここに当たる。
   - 記録の書き手(decision log・event・episode・usage・PR 決着・transcript 由来の欄)が、後から再構成できない事実を落とすか取り違える。
   - 初回の運用で repo・財布を壊す。
   - 門の1周の観測を嘘にする。
   - 初回の運用で走る agent に届く文が、定義の欠けや事実の誤りで判断を変えうる。
   疑いは、事実ならこの5つに当たるときだけ high にする(ADR 0244 決定2 の疑いの扱いはこの範囲で残す)。「信頼を壊す」と
   「自律的に動く最適化プロセスの実装と誤り」はテストから外す —— 前者は範囲が決まらず、後者は初回の運用で動かさないプロセスの
   欠陥まで門に入れていた。
2. **人間が門の運用で避けると決めた操作でしか起きない欠陥は high にしない。** どの操作を避けるかは門の運用をする人間が持ち、
   この ADR と `docs/agents/triage-labels.md` には列挙しない。避けるのをやめるときは、その操作が理由で下げた issue を先に high へ
   戻して読み直す。
3. **spec を割った ticket は spec の priority を引き継がない。** ticket ごとに決定1 のテストを当てる。spec は、high の ticket が
   残る間だけ high に置く。
4. **門の確認からベンチマークを外す。** ADR 0244 決定6 の「自律最適化プロセスの隔離環境での様子見」と、ADR 0298 決定9 の
   「初回走行は門の前」をやめる。ADR 0298 決定9 の理由は「実運用でも初回の meta-review は真っ先に動く」だったが、初回の meta-review は
   人間が起こす扉(ADR 0300 決定2)で、初回の運用ではそれを使わない。ベンチマーク(#1880)は門の後に置く。ADR 0298 追記の決定1 が
   退けたのは門の観測を手順書に移す案で、この決定とは別である。

## Considered options

- **門の条件2(high が空)を外し、委任の1周だけで門を開く** —— high ⇔ #1879 の blocker の機械判定(ADR 0244 決定5)を捨てる理由が
  無い。テストを絞れば条件2 は満たせる。
- **実運用の後は migration を書く前提にして、表の形の変更を high から外す** —— migration を書く・整備する手間が実運用の後に
  積み上がる。予想できるものは先に入れる。
- **初回の運用で避ける操作をこの ADR に列挙する** —— 操作の選び方は使い方の方針で、tidepool は汎用である(#1879 の Round 2 と同じ線)。
