# agent 名は専門性の連続性を運ぶ — 編集は洗練に限り、転生は新名で

2026-07-15 の grilling(レビュー差し戻し時にプロンプトが変わっていたら失敗原因が分析できないのでは、という問い)で決定。前提として、修理タスクと self RCA は失敗当時ではなく**現在の** agent 定義で走る(per-use 解決 — ADR 0009/0011 の線)。修理は新しい作業であって失敗の再現実験ではなく、定義変更がまさにその欠陥の修正(Condensation の成果)だった場合、当時の壊れた定義で修理を走らせるのは自傷になる。ただしこの安全性は「現在版が常に当時版の改良である」ことに依存する。そこで:

決定: **agent 名は専門性の連続性を担う。定義の編集は洗練(refinement)に限り、転生(repurposing — developer を reviewer に書き換えるような専門性の別物化)は禁止。専門性を変えるときは新名で作成し、旧名は削除する。**

帰結・執行:

- 「洗練か転生か」は機械判定不能なので構造強制はしない。執行は人間のゲートに置く: agent 発の変更は PR の diff レビュー、人間発の変更は WebUI(issue #54)の編集面の注意書き。
- 旧名削除の余波は既存の agent quarantine が受け止める(その名前宛ての未着手タスクだけが止まり人間を呼ぶ)— 転生と違い、事故が静かに進行しない。
- 新名作成は ADR 0017 により frontmatter を埋めるだけ(空本文が正規形)— 転生禁止が不便を生まない土台。
- 「reviewer は常に reviewer」の**権限面**はこの教義に依存しない — read-only は task 型がコード定数 profile で強制し(ADR 0013)、役割の付け替えは盤面ポインタ(default agent / Auditor)の差し替えで表現される。この教義が守るのは残りの半分、**専門性の散文の連続性**である。

Considered options:

- **失敗当時の定義を復元して修理を走らせる(版の焼き込み + 過去版 spawn)** — 修理が「壊れていたかもしれない定義」の再現実行になる。per-use 解決の哲学に反し、registry を過去に巻き戻して spawn する新しい実行モードを要する。分析に必要なのは当時版で「走ること」ではなく「読めること」(ADR 0020)。
- **転生を許容し、分析は版記録だけで支える** — 名前が同一性を運ばなくなり、「self = 歴史的事実」の意味論(当時の自分と今の自分が同種の worker であること)が壊れる。deckhand → tako(ADR 0017)は名前の維持より削除 + 新名を選んだ前例。
