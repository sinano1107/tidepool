# 異議由来の修理タスクは異議されたタスクの子である

issue #178 で決定。triage コミットが登録する修理タスクは元タスクへの構造的参照を一切持たず、
手掛かりは title の `repair: <元 title>` 文字列だけだった — 同じ関数が並べて登録する RCA
review が `parent_id` と workspace を明示的に渡しているのと非対称である。修理タスクにも
`parent_id`(= 異議されたタスク)を張る。

根拠は、**worker が他タスクを読む手段が存在しない**こと。MCP の verb は6本
(`get_current_task` / `list_agents` / `complete_task` / `log_decision` / `decompose` /
`escalate`)で、任意のタスクを引くものは無い。purpose に元タスクの ID を書いても worker は
その番号で何も引けず、人間向けの目印にしかならない。帰属だけが文脈を運ぶ配線である —
ADR 0045 の実装スコープ項目3(親の decision log を review 限定から全子に開放)が入れば、
子である修理タスクは元タスクの判断の全記録と決着済み子の handoff を受け取る。CONTEXT.md の
Decompose が修理タスクに与えた役割(「異議 → 修理タスク → assignee 自身の再計画」= agent が
decompose 済みの木の組み替え)にも、木の中に居ることが素直に対応する。

この形は review の指摘から生まれる修理タスク(CONTEXT.md の Review: 「レビューの指摘は review
タスクの分解子としての修理タスクになり」= 元タスクから見れば孫)と一見ずれるが、両者は1つの
規則の帰結である — **修理タスクは、修理を要求した記録が乗っているタスクの子である**。review の
指摘はその review 自身の decision log に乗り、異議は `raiseObjection` が異議されたエントリの
タスク(= 元タスク)に append する。人間が出した異議であっても修理タスクが「人間」ではなく元
タスクに付くのはこのためで、要求を運ぶ記録は元タスクの上にしか存在しない。

代償は自覚の上で受け入れる。元タスクの子である以上、同じ親の下の RCA review が失敗 question を
出して人間が abandon と答えると、ADR 0006 のカスケードが修理タスクごと cancel する — 人間
自身が出した異議の指示が、無関係な RCA の失敗で消える。ただしこれは修理タスクが作る問題では
なく RCA review 群が今日既に互いに持っている露出であり、しかも ADR 0006 の根拠(「decompose の
子は全員 `based_on_decision` で1つの判断に紐づく」)は `based_on_decision` を持たない異議由来の
子には成り立たない。カスケードの射程の見直しは issue #180 が引き取る。同型の露出 — in_progress
な元タスクに子が生えて ADR 0003 の不変条件が元タスクの完了を塞ぐこと — は issue #181。

Considered options:

- **purpose にタスク ID を書くだけ(帰属を持たせない)** — abandon カスケードと held から修理
  タスクを構造的に隔離できる。しかし worker はその ID で何も引けないため、必要な文脈はすべて
  purpose の焼き込みが運ぶことになり、焼き込みが唯一の生命線になる。ルート review が対象を
  purpose の散文で運ぶ先例(CONTEXT.md の Review)はあるが、ルート review は「完了タスクを
  前提としない独立監査」であって対象タスクが盤面に存在しない場合を含む — 元タスクが必ず存在
  する修理タスクとは事情が違う。
- **子にした上で ADR 0006 のカスケード範囲を先に絞る** — 事故を構造的に塞げるが、決着済み ADR の
  改訂であり、かつ RCA review が今日既に晒されている問題でもある。#178 の解決を待たせる筋合いが
  ないため issue #180 として独立させた。
