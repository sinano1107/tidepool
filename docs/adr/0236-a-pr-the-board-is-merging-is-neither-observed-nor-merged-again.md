# 盤面が merge している PR には観測も執行も手を出さない —— 執行の記録は執行した経路が持つ

2026-10-10 の grilling(issue #1759、#1798 を含む)で決定。盤面が PR の決着を書く経路は、執行する側(無人 merge の
tick、人間の `merge` 回答)と、観測する側(quarantine 回答前の観測 —— ADR 0217 決定5、遅い走査と回答受理直前の
バックストップ —— ADR 0079 決定3)に分かれる。どちらも GitHub の読み取りや merge を await しており、その間にもう一方が
同じ PR を決着させうる。実測では、1つの PR に決着の event が2件残った。merge の await 中に観測が割り込むと、盤面自身の
merge に `pr_merge_observed` と `pr_merged` が1件ずつ残る。60秒を超えた tick に次の tick が重なった場合も同じだった。
窓と実測は #1759 に置く。

## 決定

1. **同一プロセス内の競合では、盤面が執行した merge は必ず `pr_merged` として残る。** 執行と観測を区別して綴るのは、
   正典の主張を記録から確かめるためである(ADR 0079 決定4)。窓が狭いことは、この区別を崩してよい理由にならない。
2. **執行する経路は、その PR に処理中の印を持つ。** 印のキーは workspace と PR 番号の組で、盤面のプロセスの中
   (`Landing`)に置く。無人 merge の tick は PR を処理する間、人間の `merge` 回答は merge を呼ぶ直前から
   決着を書き終えるまで、印を持つ。対象は無人 merge キューと merge question の両方の面である。
3. **印の付いた PR には、観測も執行も手を出さない。** 観測する経路と重なった tick は、その PR を飛ばす。印の付いた
   PR への人間の `merge` 回答は「いま merge 中」として拒まれ、question は開いたまま残る。観測は印を、自分の await が
   終わった後、決着を書く直前に確かめる。
4. **「外せたときだけ event を書く」は重ねない。** 決定3 のもとで、キューから外す経路はすべて、印を持つ側か、印を見て
   飛ばす側にある。この安全網は印が漏れたときに重複を1件にまとめるが、残る1件の kind が正しい保証はない。2件残る
   ほうが、記録の上で食い違いに気づける。

飛ばされた PR は、quarantine 回答の受理の時点でまだキューに残る。registry が戻っていない分岐ではこれが着地待ちに
数えられ、回答は拒まれる。ただしこの分岐では tick が profile を解決できず、PR に印を付けられない。拒まれるのは、
await の途中で registry が壊れた場合に限られる。

プロセスが落ちた場合は、決定1 の範囲に入らない。merge が返った後、決着を書く前に落ちると、再起動後の観測が盤面自身の
merge を観測として記録する。印を DB に持っても、merge が GitHub に届いたかは分からないので、この経路は別に扱う(#1820)。

## Considered options

- **先に外した側の event だけを残す(外せたときだけ書く)** —— 1か所の変更で重複は消える。しかし merge の窓では
  盤面の merge が観測として残り、決定1 を破る。
- **quarantine 回答前の観測を、registry が戻っていない分岐だけで走らせる** —— 窓はほぼ閉じる。ただし await の途中で
  registry が壊れた場合が残り、tick の重なりも塞がらない。
- **tick を重ねない(前の tick が走っている間は次を飛ばす)** —— tick 同士の重なりだけを塞ぐ。観測との競合には別の仕組みが
  要り、仕組みが2つになる。
- **印を DB の列に持つ** —— 決着を書く経路はすべて1プロセスの中にあるので、DB に持つ利点がない。プロセスが落ちると印が
  残り、片づける起動時の処理が要る。
