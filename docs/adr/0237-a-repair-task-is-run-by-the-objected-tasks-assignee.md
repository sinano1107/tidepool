# 異議由来の修理子は異議されたタスクの assignee が走らせる

2026-10-10 の grilling(issue #1773)で決定。triage の Commit が異議を束ねて登録する修理子は、workspace を元タスクから
写すのに assignee を写さず、pickup の時点の既定 agent に解決されていた。同じ登録の RCA は assignee を意図して決めている
(self は書いた worker、auditor は Auditor ポインタ)のに、修理子だけ理由が無かった。CONTEXT.md の「異議 → 修理タスク →
assignee 自身の再計画」とも読み違えられていた。測定は #1773 に置く。

## 決定

1. **異議されたタスクが work なら、修理子の assignee はその assignee 列から写す。** 列は pickup で解決済みの名前を持つ
   (ADR 0233 決定2)ので、写すのは元タスクを走らせた agent である。異議されたエントリの書き手ではない(書き手を名指す
   のは self RCA)。review の空の列は Auditor ポインタへの参照なので写さない(ADR 0233 決定3)。
2. **写す名前は束ねる時点で人間の登録と同じ assignee の門に通し、通らなければ空で登録して、写さなかった名前と理由を
   修理子の登録 event に残す。** 元タスクが着地し終えると、その agent は削除の扉に数えられず(異議の大半は着地済みのタスクに打たれる)、shadow が外れて組み込みに
   解決されることもある。そのまま写すと pickup で agent 名の quarantine に落ち、名前が組み込みなら Auditor に解決される
   review まで止まる —— ADR 0228 が扉で防いだ事故と同じ形である。
3. **列が `human` なら `human` を写す。** 修理子は human タスクになる。人間が自分の手でした判断への異議は、元タスクを
   担った者に戻る —— 決定1 と同じ線で、例外を作らない。
4. **異議の効果は2つである。** 修理子による fix-forward と、元タスクが未決着なら、待っている子の決着後に統合復帰した
   assignee が修理子(purpose が異議されたエントリと方向コメントを運ぶ)を読んでする再計画である。修理子は付帯子なので
   (ADR 0049)、元タスクは修理子を待たず、異議された分解の子も止まらない。即時に計画を捨てる経路は #1582 が引き取る。

根拠は文脈ではない —— 元タスクの文脈は帰属が運ぶ(ADR 0046)。異議は「この agent のこの判断」への方向コメントであり、
agent を専門性で選び分ける盤面(ADR 0019 / 0031)では、既定 agent に落とすと人間が選んだ専門から外れた agent が直す。
着地のダイヤルと削除の扉の数えも元の agent の側に揃う。review の修理の宛先をレビュー対象の実行者に置く先例(ADR 0013)
とも同じ向きである。

## Considered options

- **今どおり既定 agent に任せる** —— 分解の子も親の assignee を継がないが、分解の子は親の agent が宛先を選んだ結果で、
  修理子には宛先を選ぶ判断の主がいない。
- **門を通さず写し、解決の失敗は quarantine に任せる** —— 決定2 の事故を残す。
- **門を通らなければ Commit を拒む** —— 無関係な agent の削除が人間の異議を束ねられなくする。
- **`human` は写さず既定 agent に任せる** —— 規則に例外が増え、しかもブランチを持たない human タスクの下の work は
  pickup で workspace の quarantine に落ちる(#1796、#1773 の実測)。
