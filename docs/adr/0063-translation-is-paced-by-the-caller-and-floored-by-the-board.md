# 翻訳の流量は呼び出し元が決め、盤面はホストの資源を守る床だけを持つ

issue #224 で決定。ADR 0062 が1件あたりの費用を扱ったのに続いて、**「訳をそえる」1回が
何件を立てるか**の線を引く。

## トグルの単位は1件ではなかった

`ui_kits/tidepool-webui/triage-screen.jsx` の log skim のスイッチは、`renderedLogEntries`
の**全件**に対して `runTranslate` を `await` なしで一斉に発火する。コード自身のコメントが
"one switch covers a whole morning's worth of entries" と書いている。

同じ「訳をそえる」でも、3つのスイッチは形が違う。

| | 場所 | 対象 | 呼び出しの形 |
|---|---|---|---|
| 1 | question カード | そのタスクの purpose と各 item の title / detail(選択肢とおすすめは訳さない) | POST 1本、サーバ側で fragment を逐次 |
| 2 | **decision log の見出し** | **いま描画されている全エントリ** | **POST N本を並列** |
| 3 | handoff の中 | その doc の各セクション本文(見出しは機械的に復元) | POST 1本、サーバ側で section を逐次 |

1 と 3 は**1つの読み物**を訳すスイッチで、内部で複数の fragment に割れても
`translateHandoff` / `translateQuestion` がサーバ側で逐次に回し、全体が揃うか throttled かの
どちらかで返る(「a handoff reads as one coherent unit」)。2 だけが件数の決まっていない
集合への fan-out であり、しかも並列である。

### 実測(2026-08-10)

- **CLI プロセス 1本の peak RSS は ~300MB。ADR 0062 の削減後も変わらない**(302MB)。
  トークンを 87% 削ってもプロセスの重さは動かない。
- **本番 Pi は 4 コア / 3,791MB、うち利用可 ~2,980MB。** 単純計算で**10本前後で OOM**
  する。盤面本体と worker session が同じ Pi のメモリを分け合っており、worker は sonnet で
  もっと重い。
- **`src` のどこにも同時実行の制限がない。** `defaultExec` は素の `execFile` である。
- **公開経路は Tailscale Funnel で、ブラウザとの間は HTTP/2**(`curl` で ALPN を確認)。
  HTTP/1.1 の「1オリジン6接続」という偶然の防壁は効かない。
- コストの単位も N 倍である。50件のトグル on は、ADR 0062 の前で **$0.82**、後で **$0.11**。

issue #224 が「1件 $0.03〜0.05」と書いた数字は、人間が実際に押すボタン1回の値段として
1〜2桁小さかった。人間側の体感「訳がなかなか出ない」の正体もここにある。

## 決定

**1. 流量を決めるのは呼び出し元である。** `webui/app.jsx` の `translateTarget` ——
kit へ `onTranslate` として渡される seam —— を同時2本の門でくるむ。kit は今までどおり
N 本呼び、門が並ばせる。

置き場所をここに選ぶ理由は3つ。(a) この門は**3つのスイッチ全部**が通るので、log skim
だけ並列という不揃いが seam の位置で自動的に解消される。(b) kit 側(`runTranslate`)に
置くと、面の見た目を持つはずの kit が「このホストが何本まで CLI を立てられるか」を知る
ことになる。守っているのは Pi のメモリであって画面ではない。(c) kit 単体プレビューには
`onTranslate` が渡らないため門も存在しないが、そこでは翻訳自体が起きないので問題に
ならない —— 「流量制御は kit の性質ではなくアプリの性質」という線を引くことになり、
それが正しい。

**2. 盤面は床を持つ。上限2、待ちは30秒で諦める。** `ClaudeTranslationClient` が同時に
立てる CLI プロセスを2本までに絞る。上限値は 300MB × N と Pi の空き ~2,980MB から
来ているが、盤面本体と worker が同じメモリを分け合うため安全側に 2 を採る。

**この床はペーサーではない。** 決定1 により呼び出し元が既に2本までしか投げないので、
床は常に空いており待ち時間はゼロである。床が効くのは**第2の呼び出し元**(別タブ、
スマホと PC の同時閲覧、将来の別経路)が現れたときだけで、そのときの待ちも翻訳1件ぶん
(~7秒)に収まる。

**待ちに上限を置くのは、HTTP のタイムアウトに依存しないためである。** 50本を一斉に
投げてサーバ側で並ばせる設計なら、最後の1本は3分待つ —— Node の `server.requestTimeout`
(既定300秒)にも Tailscale Funnel 側の未知のタイムアウトにも、いつか当たる。それらは
盤面が決めた値ではなく、将来黙って変わりうる外部の値である。盤面が自分で決めた秒数で
諦めれば、その依存は消える。諦めた答えは既存の `error` 状態で描かれる
(`TpTranslationNote` が `result.message` をそのまま出す)ので、UI に新しい状態は要らない。
30秒という値は「翻訳数本ぶんの待ちは許すが、分の単位は許さない」という意味である。
決定1 が守られている限りこの上限には決して当たらず、**当たったときは呼び出し元の
行儀が崩れた証拠として人間に見える**。

**3. 進行状況はスイッチの隣に数字1つで出す。** 50件なら3分かかるので、行ごとの「…」
だけでは動いているのか詰まっているのか区別がつかない。集計を置く場所は既にある ——
throttled の注記が同じ場所に1つだけ出る設計で、その理由も書かれている(「a real skim
can have many unread entries; N identical notes would just be noise」)。同じ判断が
進行状況にもそのまま当てはまる。新しい配線は要らない: kit は `logTranslations` と
`renderedLogEntries` を既に持っている。プログレスバーは採らない —— 滑らかに見せる装置は
7.4秒に1件という粗い進み方に向かず、止まったときに止まって見えない。

**4. 途中でスイッチを戻したら、未送信分はキャンセルし、送信済みは走らせきる。**
送信済みを止めない理由は、止めても払い済みのトークンが戻らないうえに
`translation_cache` へ保存されず、**次に同じエントリを訳すとき満額をもう一度払う**から
である。走らせきれば結果はキャッシュに入り、次のトグル on は無料になる。未送信分を
止める理由は、人間が「もういい」と言ったからである。

キャンセルは `logTranslateRequested` からもキーを消さなければならない。あの ref は
fold/reveal での再要求を防ぐためのものだが、キャンセルした分を残したままにすると
スイッチを入れ直しても二度と要求されず、**行が `loading` の「…」のまま永久に固まる**。

**5. プリフェッチもバッチもしない。** 表示要求されたエントリだけを、要求されたときに
訳す。今の設計は「決して読まれないエントリには一円も払わない」を保証しており、
decision log は盤面が回るほど増えるので、先読みは**読まれない訳文への支払い**を新設する
ことになる —— issue #224 が問題視した構図を別の形で作り直す。バッチ化(複数エントリを
1コールにまとめる)は、キャッシュのキーが `source_hash` 単位でなくなるか、バッチ内の
1件の失敗が全体を落とすかのどちらかを招く。

再訪の条件を書き残す: 7.4秒 × 2並列が問題として観測されたときである。そのときまず
測るべきはコストではなく「同時に何件表示されるか」であり、削るべき固定費は1件あたり
1〜1.5秒の CLI プロセス起動時間である。

## Consequences

**床が守るのは「この Pi のメモリ」という具体的な資源であり、上限2 はホスト固有の値
である。** 盤面が別のホストへ移れば適正値は変わる。今は registry や設定から動かせる
値にしない —— 動かせる値にした瞬間、それは permission を広げる設定と同じ性質(ADR 0061)
を持ち、門を誰にするかという別の問いが生える。痛みが観測されたら考える。

**50件のトグル on は3分かかるようになる。** 直列より速く(逐次なら6分)、OOM しない
代わりに、一斉に飛んでいた頃より1件目以降の到着が遅れる。決定3 の数字はその待ちを
人間が読めるようにするためのものである。

## Considered options

- **WebUI 側だけで逐次化する** —— 呼び出し元が1つである今日は成立するが(CONTEXT.md:
  翻訳は WebUI 専用)、将来別の経路が増えれば同じ穴がまた開く。守っている資源が
  ホストのメモリである以上、床は資源の側に要る。
- **サーバ側だけで並ばせる(呼び出し元は一斉に投げたまま)** —— 最後の1本が3分待ち、
  HTTP のタイムアウトという外部の不確定要素に寄りかかることになる。決定2 のとおり。
- **床が埋まっていたら待たずに即「今は無理」を返し、呼び出し元が再試行する** ——
  再試行の責任がクライアントへ乗り、スイッチの状態管理が一段複雑になる。決定1 が
  守られている限り床は空いているので、その複雑さを買う理由が無い。
- **上限なしで待つ** —— 本 ADR が消したかった依存がそのまま残る。
- **進行状況をプログレスバーで出す** —— 決定3 のとおり。
- **送信済みの翻訳も中断する** —— 払った金を捨て、次回に満額をもう一度払う。
