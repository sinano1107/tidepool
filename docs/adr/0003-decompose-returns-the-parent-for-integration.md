# Decompose returns the parent for integration; a task with unfinished children cannot complete

`decompose` は1コールで「理由 + 子タスク群」を受けて原子的に処理し、親をスロットから外す(escalate と同型)。親はその時点では完了せず、全子が done/cancelled になった後にキューへ復帰し、統合セッションが完了基準の全体を確認してから `complete_task` する。このため「未完了の子を持つタスクは完了できない」が completeTask の不変条件になっている。完了イベントは実際に基準が満たされた時にのみ流れる(decision log が嘘をつかない)。

Considered options:

- **独立完了型** — 子登録後すぐ親を done にし、子は独立タスクとして流す。最も単純だが、親の完了基準が満たされる前に「完了」が記録され、分解時の見落としを誰も検証しない。
- **保留完了型** — complete_task 時に完了記録だけ残して親を todo に戻し、全子完了で自動 done。統合検証のセッションが構造的に存在せず、「todo だが完了記録済み」という紛らわしい中間状態を導入する。
- **復帰型(採用)** — 親セッションがもう1回走るコストを払う代わりに、子の成果が出揃った状態での検証・反復分解の機会が保証される。CONTEXT.md の「分解された作業の品質は統合点で判断するのが最良」とも一致する。

復帰そのものに専用機構はない: 子は常に親より後の sort_key で末尾に登録されるため、derived blocked が外れれば通常のキュー順で親が選ばれる。先頭へのジャンプもしない — 人間がボード上で親より上に並べた作業があるなら、その順序を尊重する(question への回答が親を先頭に送るのは人間の操舵行為だから、という対比)。
