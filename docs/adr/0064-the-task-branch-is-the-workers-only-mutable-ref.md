# タスクブランチは worker の唯一の可変 ref である

issue #234 のグリリング(2026-08-10)で決定。実運用テストで、worker が Tidepool の checkout した
`task/<id>` から別ブランチへ移動する挙動が観測された。終了時の HEAD 確認だけで「タスクブランチ以外を
変更できない」という境界を本当に保証できているかを測り、必要なら強化する、というのが元の射程である。

## 測定 —— 現行実装の境界

issue が挙げた4ケースの答えは、コードを読めば確定する(実験は現行実装の再確認にしかならない)。

| ケース | remote-backed | purely-local |
|---|---|---|
| 1. 別ブランチのまま終了 | 捕まる —— `releaseTree` の HEAD 検査(`src/workspace.ts:357`) | 捕まる(同じ) |
| 2. 保護ブランチを変更してタスクブランチへ戻る | 捕まる —— `parkOnProtectedBranch` の位置一致検査(`src/workspace.ts:400`)。ローカルがリモートより先行 | **素通り** —— `isRemoteBacked` で早期 return(`src/workspace.ts:395`)。ADR 0053 決定3 の着地(ff-only)まで無防備で、着地判断が `hold` なら永久に捕まらない |
| 3. 別の非保護ブランチを変更 | 素通り | 素通り |
| 4. `git update-ref` 等で ref を直接変更 | 対象が保護ブランチなら2と同じ、他は素通り | 素通り |

加えて、**現行実装には静かな潜在バグが1つある**。worker が
`git update-ref refs/remotes/origin/<保護> <自分のタスクブランチの先端>` を撃ってから escalate または
失敗すると:

1. 非 mergeBack の解放は `refreshWorkspace` を呼ばない(`src/workspace.ts:624` の `if (mergeBack)`)
2. `parkOnProtectedBranch` が偽の ref へローカル保護ブランチを ff し、**位置一致検査も通る**
   —— 比較の両側が同じ偽値なので一致する
3. 次の pickup の fetch が `refs/remotes` を真の値に戻す
4. **その次のタスク**の解放で位置検査が落ち、無実のセッションに quarantine が誤帰属する

## 決定

**タスクブランチは worker の唯一の可変 Git ref である。** pickup 時に workspace の全 ref のスナップ
ショットを取り、slot 解放時に比較して、自分のタスクブランチ以外が1つでも動いていれば workspace を
quarantine する。

### 1. 見張るのは `refs/*` 全部。除外は自分のタスクブランチ1本のみ

タグも stash も remote-tracking ref も含む。荷重が今日かかっているのは保護ブランチ(ローカルと
remote-tracking)と `refs/heads/task/*` だけだが、**列挙は黙って古くなる** —— #234 が書かれた時点で
荷重を持っていたのは保護ブランチ1本で、ADR 0053 が祖先のタスクブランチを統合幹(fork 元 / merge back
先)にした瞬間に増えた。CONTEXT.md が付帯子を「列挙ではなく補集合」で定義したのと同じ理由である。

名前で範囲を切れないもう1つの理由が ADR 0023 にある。`branch` は**参照**であって fork 事実ではない
ので、今日 non-protected なブランチは registry のエントリが編集された瞬間に保護ブランチになる。範囲を
名前で切ると、床の切り方が registry の状態に依存する —— ADR 0013 の「床はデータの状態に依存しない」の
反対側に立つ。

引き受けるコストは、git の道具が残す一時 ref(`refs/stash`、`refs/bisect/*`、`git worktree add` が
作るブランチ)である。いずれも道具を使い終えて片付けなかった場合にだけ残り、「セッションが終わったのに
git に持ち越しがある」は規律の側に倒す(WIP コミットが拾えない場所に成果が残っている状態でもある)。

### 2. 集合そのものの一致を要求する —— 移動・削除・新規作成すべてが違反

削除が最も静かな破壊である。タスクブランチは決着後も削除されず「そのタスクが産んだ差分の恒久記録」で
あり続ける(CONTEXT.md の Review)ので、`git branch -D task/<兄弟>` は監査記録を消し、痕跡をどこにも
残さない。移動だけを見る綴りはこれを通す。

新規作成を許すと、規則が「既にどの ref があったか」に依存する分岐を持ち、その分岐自体が抜け道の在り処に
なる。集合一致は1つの述語で済む。worker がスクラッチブランチを必要とする理由も無い —— 実験も試行錯誤も
自分のタスクブランチ上でできて、WIP コミットで退避される。

違反時のメッセージは**動いた ref を名指しする**。quarantine の確認 question の本文に載り、人間の修理
手順がそのまま読める形になるためで、ハッシュだけを比べて「どれかが動いた」としか言えない実装は選ばない。

### 3. 逃げ道は作らない —— ホスト上の人間の手作業も違反として扱う

セッション中にホスト上の同じ checkout でブランチを作れば、それが人間の手であっても quarantine が立つ。
線は既に一部引かれている: `parkOnProtectedBranch` は今日すでに「帯域外の手作業でローカルの保護ブランチが
分岐している」ことを quarantine 事由にしている(`src/workspace.ts:401`)。本決定はそれを全 ref へ広げる。

`refs/human/*` のような除外名前空間は**成立しない**。この不変条件は git の最終状態だけを見る(issue の
Non-goal —— コマンドの列挙禁止ではなく状態の不変条件で守る)ので、盤面には ref を動かしたのが人間か
worker かを区別する手段がない。**逃げ道は必ず両方に開く。**

誤検知のコストは低い。確認 question は1択で、動いた ref が並ぶ。踏んだ人間は自分がやったと即座に分かり
30秒で答えて解除でき、作った ref は消えない(盤面は検知するだけで巻き戻さない)。窓は pickup→release の
間だけである。

### 4. 盤面自身の書き込みはスナップショットを取り直す(再基準化)

**盤面はセッション実行中に、同じ workspace の ref を書く**。すべて人間面から入るので slot=1 でも並行する。

| 経路 | 動く ref | 条件 |
|---|---|---|
| `src/registry.ts` registry の fetch(registry 読み取りのたび) | `refs/remotes/*` | registry clone が workspace 登録されている |
| `src/registry-write.ts` push(remote-backed の registry 着地) | `refs/remotes/*` | 同上 |
| `src/registry-write.ts` `update-ref`(purely-local の registry 着地) | `refs/heads/<REGISTRY_BRANCH>` | 同上 |
| `src/github.ts` PR 昇格の push | `refs/remotes/*` | 任意の workspace |
| `src/human-verbs.ts` `mergeTaskToProtected`(purely-local の着地 question への回答) | `refs/heads/<保護>` | 任意の workspace |

タスクA の着地 question に人間が答えた瞬間にタスクB が同じ workspace で走っていれば、B の解放で不変
条件が落ちる —— 無実のセッションの quarantine である。したがって**盤面が workspace の ref を書いたら、
その時点でスナップショットを取り直す**。

`refs/remotes/*` を検査対象から外して「盤面は使う直前に必ず fetch する」に頼る案も採らなかった。安全性が
**コード全体に散った性質**に依存し、将来 fetch を挟まない読み口が1つ足された瞬間に静かに崩れるためで、
ADR 0052 が「宣言を clone の実態から推測しない」を選んだのと同じ形の危険である。再基準化の**呼び忘れは
静かに壊れない** —— 忘れた経路は誤検知として quarantine を立て、registry の fetch は読み取りのたびに走る
ので即座に露見する。

### 5. 検査の位置 —— pickup の最後と、`releaseTree` の直後

```
pickup (prepareWorkspaceAtPickup):
  宣言の突き合わせ → refreshWorkspace → ensureTaskBranch
  → スナップショット           ← ここ。worker に手渡した瞬間の状態が基準になる

release (releaseWorkspace):
  releaseTree                  ← HEAD 検査 + WIP コミット(自分のタスクブランチへ)
  → スナップショット比較        ← ここ。worker のセッションが終わった直後
  → refreshWorkspace / merge back / parkOnProtectedBranch   ← 盤面が他の ref を書き始める
```

`refreshWorkspace` が `refs/remotes` を動かすので、スナップショットは fetch の**後**でなければならない。
比較は盤面自身の書き込みの**前**でなければならない —— 順序を誤ると盤面が自分の不変条件を踏んで自分を
quarantine する。

**WIP コミットは撃つ。** issue 本文の「WIP の通常処理を続けない」から意図的に外れる。WIP コミットの
着地先は worker の唯一の可変 ref であり、不変条件と直交する。成果を失わなければ人間は `git log` で
worker が何をしたかを読める。そして解除の検証は `verifyWorkspaceClean`(ツリーがクリーン)なので、
退避を飛ばすと人間は ref を戻すだけでなく worker の残骸の処分まで判断しないと答えられなくなる。WIP
コミットは元々「エージェントの善意に依存しない機械的退避」であって、内容の正当性の承認ではない。

### 6. スナップショットは `workspace_state` の列に置く

制約が3つある —— 盤面の再起動を跨ぐこと(watchdog / 再起動の失敗経路も `releaseWorkspace` を通る)、
盤面が取り直せること、そして **worker が書ける場所であってはならない**こと。

`refs/tidepool/snapshot` のような git の ref に置くのは**自己矛盾**である(不変条件の基準を、その不変
条件が見張っている相手が書ける場所に置くうえ、決定2 の集合一致の下ではその ref 自身が検査対象に入る)。
イベント payload は、追記専用の監査ログを「今の状態」の保存に使うことになり、しかも再基準化のたびに全 ref
の写像が積まれてタスクブランチは削除されないので単調に育つ —— イベント履歴は判断と観測の記録であって
状態のキャッシュではない。`workspace_state` は既に「workspace 単位の、盤面側が持つ状態」(`needs_human`)
のテーブルであり、意味論が一致する。キーが workspace 名なのも、再基準化の5経路が「どのタスクが走って
いるか」ではなく「どの workspace を触ったか」しか知らないことと合う。

値は `git for-each-ref --format='%(objectname) %(refname)'` のソート済み出力をそのまま1本のテキストと
して持つ。比較が文字列比較で済み、決定2 が要求する「動いた ref の名指し」が行差分でそのまま取れる。

**スナップショット未設定(NULL)の分岐は書かない。** 移行の瞬間に `in_progress` なタスクは高々1つで、
当たっても quarantine が1枚立って人間が30秒で答えるだけである。一方 `NULL = 検査スキップ` は静かな穴で、
将来 pickup を経ない解放経路が足されたときその経路では不変条件が黙って走らなくなる。分岐を書かなければ
NULL は自然に「基準と現在が一致しない」= 違反に落ち、fail-closed 側に倒れる(ADR 0028 の「fail-closed は
可視化とセット」と同じ姿勢)。

### 7. quarantine の解除条件は拡張しない

ref が元へ戻っていることは要求しない。既存の検証条件(registry に存在し、ツリーがクリーンで、盤面の
状態パスと重ならない)が測っているのは「**資源が使えるか**」であって「原因が取り消されたか」ではない
—— ツリーが dirty な workspace は次のタスクを走らせられないが、ブランチが1本増えた workspace は完全に
使える。

そして復旧を要求すると、人間の正当な修理が「**動いた ref のほうが正しいので、そのまま受け入れる**」で
あるケースを塞ぐ。解除後にスナップショットを取り直す必要も無い —— 次の pickup が常に新しい基準を取る
ので、古い基準が残って同じ quarantine が再発することはない。

## なぜ今か —— 観測された痛みは1件も無い

正直に置く。**「他の ref を書き換えた worker」の観測は今日まで1件もない。** #234 自身の観測(別ブランチ
への移動)はケース1であり `releaseTree` が既に捕まえる。#228 の観測(自分のタスクブランチへの
`git merge --ff`)は本不変条件の下で**合法**であり、しかも ADR 0053 決定1 が fork 元を系譜から決めた
以上、あの操作をする**動機そのものが消えている**(ADR 0053 決定4 が「検知しない」と決めたのはこの
理由による。本 ADR とは重ならない —— 土台の移動を捕まえるには保護ブランチとの merge-base の不変性が
要り、それは ADR 0023 が降りた「fork 事実の記録」へ一歩戻る)。

「observed pain over speculation」を素直に適用すれば、答えは「足さない」に倒れる。それを打ち消したのは
**壊れ方の静かさ**である。

- **ADR 0053 が保護ブランチ以外の ref にも盤面の正しさの荷重をかけた。** 祖先のタスクブランチは統合幹で
  あり、worker がそれを動かせば親の統合復帰は嘘の土台の上に立つ。しかも動かされたことはどこにも現れない
  —— #228 が見つかったのは worker が自分で decision log に書いたからである
- **その構造はまだ一度も実運用を通っていない。** #220 / #228 の実環境動作確認は ADR 0053 の実装**前**の
  観測であり、「痛みが観測されていない」の一部はそれを反映しているにすぎない
- **観測された2件は同じ族である。** 個別の操作は違っても、「worker が自分の git 状況を自力で修復する」
  という挙動は短い試行の中で2回出ている
- **既存の潜在バグを1つ閉じる**(上の `refs/remotes` 偽造 → 無実の次セッションへの誤帰属)

判断基準は件数ではなく、ADR 0023 が毎回解決を選び ADR 0052 が宣言と実態のずれを quarantine にしたときと
同じ「静かには壊れないか」である。素通りするケースの壊れ方は、親の統合復帰が誤った土台の上で成功し、
誰も気づかない、という形をとる。

## Considered options

- **保護ブランチだけを守る**(issue のケース3 が明示的に問う分岐)—— ADR 0023 が宣言した境界(保護
  ブランチは「worker が直接書き込んではならない対象」)をそのまま執行するだけなので、新しい主張を
  1つも足さない。しかし ADR 0053 の下では祖先のタスクブランチが保護ブランチと**同じだけ荷重を持つ**
  ため、守れる範囲が今日の正しさに届かない。
- **荷重のある ref だけを列挙する**(保護ブランチ + `refs/heads/task/*`)—— 誤検知面がほぼ無く、人間の
  スクラッチブランチも registry clone の衝突も起きない。決定1の「列挙は黙って古くなる」と ADR 0023 の
  「`branch` は参照」の2点で退けた。
- **`git switch` / `git checkout` をコマンド allowlist で禁止する** —— issue の Non-goal がそのまま
  理由である。`REVIEW_BASH_WRITE_DENIALS`(`src/claude-worker.ts`)が review 専用に留まっている経緯と
  同じく、`sh -c` で抜けられる。守りたいのは操作の列ではなく最終的な Git 状態である。
- **`refs/remotes/*` を見張らず、park の直前に必ず fetch する** —— 再基準化の経路が5から2へ減り、
  「remote-tracking ref は盤面のキャッシュであって誰の領土でもない」という筋も通る。決定4 の理由で
  退けた(不変条件の文が literally true でなくなり、安全性がコード全体に散った性質に依存する)。
- **セッション中は盤面自身の書き込みを直列化する** —— ADR 0052 が並行着地を「黙って上書きせず、再試行
  可能な失敗にする」形にしている姿勢とは整合する。しかし slot=1 で常に何かが走っている以上、registry
  編集がしょっちゅう拒まれる。
- **違反したセッションでは WIP コミットも撃たない**(issue 本文の文言)—— 決定5 の理由で退けた。
- **quarantine の解除に ref の復旧を要求する** —— 決定7 の理由で退けた。
- **現行の境界で走らせ続け、実際に他の ref が動く事件が出てから設計する** —— この repo の
  observed pain over speculation の既定の答えであり、真剣に検討した。「なぜ今か」の4点で退けた。
