# abandon が破棄するのは計画ではなく、失敗タスクが乗っている分解判断

issue #180 で決定。ADR 0006 の abandon カスケードは失敗タスクの親の**未決着の子を全部** cancel する
(`src/tasks.ts:1141-1153`)— 「全部」に条件は無い。しかし 0006 の根拠2 はこう綴られている:

> decompose の子は全員 `based_on_decision` で1つの判断に紐づく — 1子の放棄はその判断の前提を壊すので、
> 残りの子を盲目に走らせるより判断ごと無効にして親の統合セッション(ADR 0003 と同型)に再計画させる
> 方が一貫する。

`based_on_decision` を刻むのは `decomposeTask` だけである(`src/tasks.ts:1576`)。異議由来の RCA review と
修理タスク(ADR 0046)、layer 1 の完了時レビュー、escalate が登録する question は**いずれも持たない**。
共有する分解判断が無いのだから「1子の放棄がその判断の前提を壊す」という論理がそもそも当てはまらず、
カスケードがそこへ届いているのは射程の切り忘れである。具体的には、独立監査である `rca (auditor)` が、
当事者レビューである `rca (self)` の失敗に連座して消える — CONTEXT.md が「独立レビューは対象の判断に
利害を持たない距離が価値」と綴るまさにその独立性が、カスケードによって連座している。

盤面は既にこの区別を一級市民として持っている。ADR 0047 の年表は、分解判断に基づく子を
`decision.children` に入れ、そうでない子を `child_outside_the_decomposition` として名指しで別に綴る。
**worker の面では区別されているのに、cancel の側だけが区別を持っていなかった。**

## 決定

**1. abandon が無効にするのは「親の子ぜんぶ」ではなく「失敗タスクが乗っている分解判断」である。** 倒れるのは
失敗タスクのサブツリーと、**同じ `based_on_decision` に乗る兄弟**のサブツリーだけ。失敗タスクがどの分解判断
にも乗っていなければ、倒れるのは自分のサブツリーだけである。CONTEXT.md の「計画ごと破棄」は
**判断ごと破棄**へ言い換える — 「計画」を保ったまま範囲だけ狭めると、用語集の「計画」がどこを指すのか
読み手が特定できなくなる。

**2. 綴りは「`failed` の判断と一致する兄弟」であって「判断を持つ兄弟」ではない。** 後者(issue #180 の
選択肢1)は巻き添えの向きを裏返すだけで、同じ事故を作る — T が A・B に分解されて blocked のまま、
異議由来の `Ra` / `Rb` / 修理タスクが子として足され、`Ra` の失敗に abandon と答えると、**生きている
分解計画 A・B のほうが消えて `Rb` が生き残る**。

実装の罠を記しておく: 条件は「`failed` が判断を持ち**かつ**兄弟がそれと一致する」でなければならない。
`sibling.based_on_decision === failed.based_on_decision` と素直に書くと JS では `null === null` が真なので、
判断を持たない失敗タスクが判断を持たない兄弟を全部掃く — 直したはずのバグが復活する。SQL の
`NULL = NULL` はたまたま偽になるため、この罠は JS 側に移した瞬間に開く。

決裁権外の子(承認 question 経由で実体化する子)は判断を持ち越す — `PendingChildSpec.based_on_decision`
(`src/tasks.ts:141`)が「承認された子は通常の分解兄弟と同じ出自を保つ」ために焼き込まれており、承認
question **自身**も `based_on_decision` を持つ(`src/tasks.ts:1566`)。したがって狭めた射程の下でも、
承認済みの子は自分の判断と共に倒れ、未回答の承認 question も兄弟として巻き込まれる — 今日の「巻き
込まれた未回答 question を含む」がそのまま保たれる。例外は要らない。

**3. held も同じ範囲へ狭める。そして2つの範囲は常に一致していなければならない。** failure question だけが
持つ「親の親のサブツリーを凍らせる」広い段は、0006 の根拠3 が明言するとおり**カスケードを安全にする
ためだけに**存在する(「held が兄弟の新規着手も防ぐため、回答時のカスケードは todo のタスクにしか
触れない」)。射程が狭まればその正当化は非一致の兄弟について消える。

ただし held をゼロにする(一般 question と同じ段に落とす)ことはできない — `Ra` の失敗 question が
開いている間に同じ判断に乗る兄弟 `A` が pickup されて `in_progress` になり、そこへ abandon が着弾すると、
**走っているセッションを cancel することになる**。したがって held はカスケードの範囲を**厳密に覆う**。
2箇所に別々に綴ると片方だけ変えた瞬間に穴が開くので、両者は1つの範囲定義から導く。これを不変条件
として持つ。

**held の集合はカスケードの対象集合そのもの — 一致する兄弟「自身」を含む。** 今日の `HELD_IDS_CTE`
(`src/tasks.ts:1892`)は held ルートの**子から下**を集める形をしており、ルート自身は入らない。今日は
ルートが `plan` なので兄弟はその子として held に入っているが、ルートを
`{failed} ∪ {一致する兄弟}` へ素直に差し替えると兄弟自身が集合から落ち、子孫だけが held に残る —
兄弟が pickup されて `in_progress` のまま abandon が着弾する、この決定が禁じたその穴が、範囲の
不一致ではなく CTE の形から入ってくる。`failed` 自身は held ではなく未回答の子(failure question)に
よって blocked なので、この配慮が要るのは兄弟だけである。

**4. 人間が読む文面(`abandonConsequence`、`src/watchdog.ts:48`)は規則と件数を運ぶ。** 分岐条件は
`parent_id` の有無ではなく「失敗タスクが判断に乗っており、かつその判断に乗る未決着の兄弟がいるか」に
変わる。広い側の文面は「この分解判断を破棄する — このタスクの残りと、同じ分解判断から生まれた N 件の
兄弟 — 親を先頭復帰させて再計画させる」。件数を入れるのは、兄弟1つと7つでは人間の答えが変わりうる
一方、1語で運べて30秒の回答を膨らませないため。

焼き込みは嘘にならない: 一致する兄弟の集合は question の登録から回答までの間に変化しない(held が
彼らを凍らせており決着できない)。人間 decompose だけは blocked な親にも子を足せるが、それは別の判断
に乗るので一致しない。

**5. `based_on_decision` を `tasks` の列にする(今は `task_registered` イベントの payload にしかない)。**
狭めた範囲は SQL で表現される必要があり、`HELD_IDS_CTE` は `nextSlotTask` / `listQueue` が毎ポーリング
通す経路である。`events` にはインデックスが1本も無く、追記のみで単調に育つテーブルへの join を盤面の
心拍に埋めるのは避ける。そもそも `tasks` は既にイベント列の**射影**であり(`status` / `handoff_doc` /
`pr_number` はどれもイベントから導かれる現在値)、登録時に確定して二度と変わらない
`based_on_decision` が射影に無いことのほうが例外だった。既存行は `task_registered` イベントから
backfill する。ADR 0047 の `history`(未実装)も子ごとに同じ値を読むため、これは共有の決定である。

**6. ADR 0006 は supersede しない。** 0006 の核(「安全弁任せ」でも「人間の手作業」でもなく破棄する)は
生きており、根拠2 は今回はじめて正しく適用されるだけである。倒れるのは射程の綴り方だけなので、
0006 は元の trade-off の記録として無傷で残す。

## 効果

- **親の先頭復帰の条件は変えない。** 今日のコードは `unblockTarget = plan` としつつ「plan が `todo` かつ
  未決着の子を持たない」ときだけ先頭挿入する。判断ごと破棄でも、破棄によって親の最後の未決着の子が
  消えたなら再計画のため先頭に戻すのが筋で、消えていないなら親はまだ blocked のまま — 既存の条件式が
  両方を自然に表現している。実装時に「直す」対象ではない。
- **ADR 0046 の代償を解消する。** 0046 は修理タスクを元タスクの子にした代償として「同じ親の下の RCA
  review が失敗 question を出して人間が abandon と答えると、カスケードが修理タスクごと cancel する」を
  自覚の上で受け入れ、射程の見直しを issue #180 に引き渡していた。修理タスクは `based_on_decision` を
  持たないので、本 ADR の下では倒れない。0046 の代償段落は**編集しない** — 決定時点で受け入れた代償の
  記録として無傷に保つ。
- **`assertNoGatingQuestion`(`src/tasks.ts:1882`)のコメントの前提が偽になる。** 門の**挙動**は正しいまま
  だが(failure question は狭めた射程でも宙に浮く)、「abandon はその計画を丸ごと cancel する」という
  綴られた前提は成り立たない。実装時に改める。
- **issue-backed の確定的失敗(`src/scheduler.ts:245`)も同じ規則に乗る** — こちらの失敗タスクはキュー
  先頭のタスクであり、分解の子であることもルートであることもあるが、規則はそのまま読める。

## Considered options

- **`based_on_decision` を持つ兄弟を掃く(issue の選択肢1)** — 決定2。巻き添えの向きが裏返るだけ。
- **現状維持 — 連座を「計画ごと破棄」の許容コストとして受け入れ、0006 に射程として書き足す
  (issue の選択肢3)** — この立場を採ると 0006 の根拠2 は射程の説明として使えなくなり、根拠1
  (「兄弟間の依存エッジが無いので選択的に止められない」)だけで支えることになる。根拠1 は独立監査に
  対して弱い — `Rb` が `Ra` の成果物に依存していないことは**構造的に**言える。
- **カスケードだけ狭め、held は広いまま据え置く** — held は超集合なので安全側に倒れており、間違った
  結果は生まず、払うのは待ち時間だけ。issue が報告した害は cancel であって凍結ではない、という最小変更の
  立場。ただし連座を凍結という形で払い続けることになり(`Rb` は人間が quiet hours 中に眠っている間ずっと
  slot に入れない)、0006 の根拠3 が held の広さを説明しなくなるので別の根拠を新たに立てる必要がある。
- **`based_on_decision` を events から都度導出する(スキーマ変更なし)** — diff は小さいが、インデックスの
  無いテーブルへの join を pickup ポーリングに埋め、ADR 0047 の実装でも同じ join を書くことになる
  (`EventRow` の生の payload が2箇所に露出する)。
- **文面に兄弟の title を列挙する** — 最も正直だが question の文脈が長くなり、キュービューが既に持って
  いる情報を複製する。件数で足りる。
