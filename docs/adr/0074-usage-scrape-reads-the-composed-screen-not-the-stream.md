# 使用量の読み取りは PTY ストリームではなく合成後の画面を読む — @xterm/headless による端末エミュレーション

ADR 0028 のスクレイプは PTY の生バイトストリームをバッファし、ANSI を除去してラベル(`Current session` 等)を文字列検索していた。しかし fullscreen TUI は**再描画時に差分描画を行う** — 前フレームと一致する前置きをカーソル移動(例: `\e[17C`)でスキップし、差分だけを流す。Pi では `Current week (Fable)` の per-model 行がデータ到着の遅れにより**後続の再描画にのみ**現れるため、ラベル全文がストリーム上に一度も存在せず、fable ペース線(ADR 0030)は本番で一度も効いたことがなかった(issue #323、2026-08-13 に Pi・CLI 2.1.221 で生バイト列まで実測)。根本原因は「ストリームを画面だと思って読んでいた」ことにある。そこで読み取りを**端末エミュレーションに転換する**: scraper は PTY データを headless 端末(`@xterm/headless`、PTY と同一の cols/rows)へ適用し、確定時に**合成後の画面テキスト**を返す。画面上にはラベルが必ず全文存在するため、パーサのラベル検索は差分描画の切れ方に依存しなくなる。

**キャプチャ確定条件も同時に変える。** 旧実装はパネルヘッダ出現後 500ms 静穏で確定し、breakdown 再描画を意図的に切り捨てていた(fable 行が初回描画に含まれる Mac 実測に基づく前提で、Pi では成り立たない)。新しい確定条件は**静穏窓の延長一本**: 再描画が続く限り確定を延ばし、実測した再描画間隔より長い静穏で確定する。fable 行の出現は確定条件にしない — Pro プランでは fable 行の不在が正常な姿であり(ADR 0030)、fable 待ちは Pro での毎回タイムアウトか「遅い Max」との混同を生む。静穏窓・タイムアウトの値は Pi 実測で決める(スクレイプ所要時間は数秒延びるが、毎時1回に対しては誤差 — ADR 0028 が 663ms→2.7秒を誤差と断じたのと同じ理路)。静穏窓の延長には安全床を敷く: **タイムアウト時、パネルマーカーが既に描画済みならその時点の合成画面でベストエフォート確定する**(null にしない)。旧実装ではタイムアウト経路は 500ms 静穏が必ず先に発火するため実質到達不能だったが、延長により「再描画が止まらない」入力で初めて到達可能になり、そこで null に倒すと fable の取り逃しより悪い session / week の全体 fail-closed へ退行する。パネルが一切描画されていないタイムアウトは従来どおり fail-closed。

**意味論は一切変えない。** これは ADR 0028 / 0030 が要求する入力の忠実性を回復する決定であり、session / week の fail-closed、fable の「不在 = 個別制限のないプラン」、just-in-time ポーリング、実行中タスク不干渉はすべてそのまま。parseUsage の入力契約だけが「生キャプチャ(ANSI 除去はパーサの責任)」から「合成後の画面テキスト」へ変わる。実機キャプチャのフィクスチャは**生バイトのまま**保持し、テストは本番と同じ合成→パース経路を通す — 生バイトこそが一次証拠であり、合成後テキストで保存し直すと今回のバグを検出できないテストに退化する。Pi の差分描画キャプチャ(断片入り)を新たにフィクスチャへ加え、「差分入力から fable が読めること」を回帰テストにする。

Considered options:

- **キャプチャ窓の延長だけ**(エミュレーションなし) — 30秒まで延ばしてもラベルは `Fable)` 断片でしか流れないと実測済み(issue #323)。窓延長は必要条件ではあるが単独では解にならない。
- **断片・位置ベースの復元** — 生ストリームから断片やカーソル座標で行を復元する。今回の断片(`\e[17C Fable)`)は前フレームとの一致長に依存した偶然の形で、次の差分は別の切れ方をする。差分アルゴリズムの出力を場当たりで追うことになり、#79 型の破損を機構として温存する。
- **自前ミニ VT パーサ**(依存追加なし) — CUP/CUF/ED/EL/alt-screen 程度で 400〜800 行、加えて DECSTBM・pending wrap・CJK 全角セル・チャンク境界分断などの落とし穴。依存 0・現役メンテ(VS Code のターミナル永続化と同じ基盤)の本物が約 2MB で手に入る以上、合理性がない。
- **非公式 API 直叩きの再考** — ADR 0028 で「一度も成功しなかった」実績により却下済み。状況の変化は観測されていない。

Consequences:

- 依存が1つ増える(`@xterm/headless`: pure JS・依存 0・install スクリプトなし。Pi armv8 でもファイル展開のみ)。生産側の node-pty と `pty.onData → term.write` で直結する正規ペア。
- `term.write` は非同期のため、合成は async 側(scraper)に置く。parseUsage は同期の純テキストパーサのまま — 「scraper は画面を観測し、parser はテキストを読む」という分業。合成処理はヘルパーとして切り出し、テストが生フィクスチャを再生するのにも使う。
- TUI が描画機構を変えるリスクは残る(ADR 0028 の「PTY 駆動の脆さ」)が、差分描画・レンダラ差・書式の揺れのうち**描画由来**の破損源はエミュレーションが構造的に吸収する。書式(ラベル文言)変更は従来どおりスクレイパー破損イベントとして扱う。
