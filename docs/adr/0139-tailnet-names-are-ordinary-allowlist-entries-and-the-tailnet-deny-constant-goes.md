# tailnet 名は Domain allowlist のふつうの値であり、tailnet deny の定数は外す

2026-09-21 の grilling(issue #793)で決定。**ADR 0036「ネットワークフィルタは多層の一枚へ格下げ」節と、ADR 0072 決定1 の
「床の deny 側(`DENIED_TAILNET_DOMAINS`)はコード定数のまま常勝」、決定2 の IP リテラル拒否の理由、決定5 の優先関係 canary を
supersede する。** 両 ADR の他の部分は生きている。実測(deny あり / なし / 許可リスト非空 / `strictAllowlist` なしの4形)は
issue #793 のコメントに置く。

`deniedDomains: ["*.ts.net", "raspberrypi"]` を支えていた根拠は3つとも立たなくなっていた。持ち出し先とされた同居の
context-vault はトークン無しの書き込みに 401 を返し(ADR 0036 の #150 追記が自分で測っている)、worker に token を渡す経路は
設計上無い(cwd 外の読み取りは床が拒む — ADR 0033 / 0038)。
egress は ADR 0072 以降は既定 deny で、#152 で観測した「dot 無しの短縮名が allowlist の手前を通る」穴も現行 CLI では
deny を抜いても再現しない。残る働きは「人間が明示確認つきで `allowed_domains` に書いた tailnet 名を黙って拒む」だけで、
これは2つの害を持つ — ADR 0034 が予約し ADR 0072 決定1 が形の根拠に引いた「tailnet は allowlist で個別に開ける」を
データでは行使不能にし、しかも registry と worker 向け文面(実効リストは deny を引かない)が「開いている」と言う宛先を
proxy だけが 403 にするので、ADR 0072 が潰した 403 リトライの形を再現する。

## 決定

1. **`DENIED_TAILNET_DOMAINS` を外す。** tailnet 名は他のドメインと同じく ADR 0072 決定3 の取引(開けた先へ持ち出せる、
   受容は workspace 単位・`allowed_domains_set` の確認つき)に乗る。ネットワークの床は既定 deny の側にあり、定数は
   床ではなく opt-in への拒否権だった。人間面を守る主機構は credential で、tailnet は信頼境界ではない(ADR 0036)ので、
   開けた worker が人間面に届いても返るのは 401 である。
2. **tailnet 名を「確認で買えないもの」の類に入れない。** 裸の `*` は姿勢の全放棄、IP リテラルは下の理由で、
   どちらも人間が読んだ綴りと受容した範囲が一致しない。tailnet 名は読んだとおりの1ホストを指す。導入者の tailnet に
   無防備なホストがありうることは事実だが、それは決定3 の取引そのもので、tailnet だけを別扱いにする線は引けない。
3. **IP リテラル拒否は残し、理由を差し替える。** 旧理由(名前パターンの deny をデータが名指しで迂回する穴)は定数と
   一緒に消える。残る理由: 決定3 の取引は「そのドメインの**運営者**へ持ち出す」ことの受容であり、IP は運営者を
   名指さない(持ち主は変わり、CGNAT 帯は tailnet ごとに別の機械を指す)— 綴りが人間の受容した相手を固定しない。
4. **封じ込め canary の tailnet 相は2宛先とも残し、優先関係の canary は外す。** 不変条件は宛先定義(worker は人間面に
   届かない — ADR 0034 / 0036)なので canary の問いは変わらず、執行機構の記述だけが既定 deny に替わる。短縮名の穴を
   いま塞いでいるのは `strictAllowlist` ですらなくベンダーの既定挙動で、コードで釘打ちできない — 版上げで黙って戻らない
   ことを固定できるのは canary だけである。`deniedDomains > allowedDomains` を測る行(deploy-pi 3a(7))は主語を失う。

## 検討して採らなかった案

- **拒否を文法ガードへ移す(`*.ts.net` 配下を `allowed_domains` で拒否)** — 嘘の経路は消えるが、ADR 0034 の予約を
  撤回する根拠が決定2 のとおり無い。
- **値を導入者の設定へ移す** — 既定 deny の上で導入者の deny が働くのは、導入者自身が書いたワイルドカード allow から
  例外を削るときだけで、その需要は観測されていない。読み手のいない設定面は作らない。
- **現状維持** — 1環境のホスト名が製品コードの定数に残り、上の嘘の経路も残る。

## 範囲外

Codex 経路には deny の層が元から無く、写す対象も消えた。Codex の proxy で dot 無し名が allowlist を素通りしないかは
未測定で、#794 の観測に足す。
