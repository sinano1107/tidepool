# worker の外部到達は workspace 単位のドメイン許可リストで開ける: 既定は全閉、開ける判断は registry 編集時の人間が引き受ける

issue #309 の grilling(2026-08-13)で決定。実環境動作確認 第3段(ADR 0052 の段取り)で、依存を持つリポジトリの worker が `npm install` を完走できないことが判明した — サンドボックスのネットワークはベンダー proxy の**既定 deny**(headless では許可リスト外への CONNECT が `403 blocked-by-allowlist`)であり、盤面が書く `deniedDomains` はその上に**さらに**塞ぐ層でしかなかった。ADR 0033 の「ネットワークは現状のまま開放」は bind について #146 で覆ったのに続き、egress についても事実ではなかったことになる。帰結は3つ観測された: 依存を持つ workspace では `node_modules` の事前配置なしに実作業ができない、`package.json` を変更するタスクは原理的に不可能、そして worker は制限を知らされていないため自力で `npm install` を撃って 403 リトライで watchdog まで CPU を焼く(実測13分・77% CPU、2セッションで計 $4.3)。

## 決定

**1. 開け方は workspace 単位の registry フィールド `allowed_domains` とし、コード定数の許可リストは空に保つ。** 既定は今日の姿のまま全閉で、開くのは人間がその workspace のエントリに明示したドメインだけ(入口既定閉・opt-in — skill 許可リストと同じ意味論であり、ADR 0034 が tailnet の将来開放に予約したのと同じ形)。これは許可リスト4本目で、`review_allowed_commands` に続いて**データが床に触れる2つ目のフィールド**である。したがって統治は同型に写す: 床の deny 側(`DENIED_TAILNET_DOMAINS`、checkout 設定ガード)はコード定数のまま常勝、門は PR ではなく人間面 — credential + 危険な値の明示確認(理由コード `allowed_domains_set`、ADR 0061)— で、文法ガードが「綴りが人間の読んだ範囲を越えない」ことを守る。

**2. 文法ガードはドメイン名構文のみを通す。** スキーム・パス・空文字・裸の `"*"` を拒否し、`*.example.com` 形のサブドメインワイルドカードは許す。裸の `"*"` を確認つきでも許さないのは、全開放が封じ込めの姿勢そのものの放棄であり、データ値ではなくコード変更で表明すべき決定だからである(「確認で買えないものがある」— registry 保護剥奪と同じ線)。**IP リテラルも同じ理由で拒否する** — 床の tailnet 遮断は名前パターン deny であり(proxy は CONNECT のホスト文字列で濾す。CIDR は表現できない — issue #152 の実測)、`allowed_domains` に IP を書けることは registry データが ADR 0036 の床を名指しで迂回できることを意味する。データが床に勝つ唯一の穴になるので、文法で塞ぐ。

**3. ドメインを開けることは持ち出し経路を開けることであり、その受容の単位は workspace、判断の瞬間は registry 編集時である。** 開けたドメインの運営者(および同ホストの無認証 POST 面)へは、その workspace の内容と注入される盤面文脈を能動的に送り出せる — worker は npm token を持たないので publish は閉じているが、リクエストに載せる経路は残る。この残余は無条件には受容しない(workspace は公開 GitHub リポジトリとは限らず、private もありうる)。受容するのは人間が workspace 単位で開けたときだけで、private / 機微な workspace は閉じたままにし、依存はホスト側の `node_modules` 事前配置(第3段で実測済みの回避 — `package-lock.json` の一致確認つきコピー)で賄う。ホスト配置は恒久の**最適化経路**として残る — 機構ではない。

**4. worker には網の姿を伝える。** WORKER_PROTOCOL に英語で1段落 — egress は既定 deny であること、この session で開いているドメインの実効リスト(定数 + workspace エントリから導出。閉なら「無い」と明言)、許可外への取得はリトライせず諦めること。403 無限リトライの失敗の形はこの行動側の通知に畳み込み、盤面側の検知・矯正機構は作らない(観測1回に対して過剰)。

**5. ベンダー意味論は2点とも実機で確認してから頼る。** `strictAllowlist: true` を明示して fail-closed をコードで釘打ちする(headless の自動 deny はベンダー既定依存)ことと、`deniedDomains > allowedDomains` の優先関係 — 後者は公式ドキュメント由来で**インストール済み CLI ではまだ測っていない**。tailnet 遮断がこの決定を生き延びるかはこの優先関係そのものなので、deploy-pi のサンドボックス e2e スモークに canary を2本足す: 許可ドメインへの到達が通ること、そして **allowedDomains が設定された状態で tailnet 名が依然拒否されること**(優先関係の canary)。いずれも「設定が黙って捨てられていない」control の同居つき(#146 のパターン)。

**6. 初適用は tidepool 自身のエントリに `allowed_domains: ["registry.npmjs.org"]`。** npm は metadata もタルボールも単一ホストで完結し、tidepool は公開リポジトリなので決定3の取引は軽い。他エコシステムは必要とする workspace が現れた時点でそのエントリに足す(`DENIED_TAILNET_DOMAINS` と同じ「既知のものを列挙する」姿勢)。

**射程外を2つ明記する。** ブラウザバイナリ(Playwright CDN)は開けない — ホスト準備の姿勢に従う(system ブラウザは `~/` 外にありサンドボックスから読める。`PLAYWRIGHT_BROWSERS_PATH=0` なら `node_modules` 配置に相乗りできる。サンドボックス内で**実行**できるかは未検証で、必要になった日の別 issue)。またサンドボックス内でのブラウザ使用自体は問題ない — 封じ込めはツールの列挙ではなく宛先で効いており(ADR 0034)、ブラウザの到達面は curl と同一である。ただし WebFetch の「GET-only だから開けたまま」の理屈は転用できない(ブラウザは POST を撃てる)— 正当化は宛先の閉じ込めのほうにある。

## Considered options

- **(b) 依存解決をホスト責務と明示するだけ** — 封じ込め面積ゼロ増だが、`package.json` を変更するタスクが原理的に不可能で、v1 の目的地「エージェントが tidepool 自身を開発する」と正面衝突する。閉じた workspace 向けの最適化経路としてだけ生き残る(決定3)。
- **(c) 盤面が pickup 前に依存を用意する(`prepare_command`)** — 一見穏当だが、registry で最も危険なフィールドになる:「盤面として素のホストで任意コマンドを実行せよ」であり、work タスクが `package.json` に仕込んだ install スクリプトを次の pickup で盤面が非サンドボックスで実行する**2セッション洗浄経路**が開く(ADR 0033 が checkout 設定ガードで塞いだ形の、より太い再来)。`--ignore-scripts` は native モジュールを壊す。しかもタスク中の依存変更は救えず、結局本決定が要る。private workspace の依存需要が観測された日に固有の decision として起こす将来経路 — その本丸は host 実行の安全性である。「盤面が機械的にアクセスするが worker には解放されないソース」の設定面はその日まで一緒に寝かせる(今日は読み手が存在せず、消費者のない設定は嘘の面になる)。
- **グローバルなコード定数で `registry.npmjs.org` を全 workspace に開ける** — 決定3の受容が workspace 単位で下せなくなり、private workspace が選んでいない持ち出し経路を背負う。
- **持ち出し残余の無条件受容(WebFetch 残余と同じ線)** — workspace の内容は公開リポジトリとは限らない。受容は人間の workspace 単位の判断に移した。
- **裸の `"*"` を明示確認つきで許す** — 姿勢の放棄はデータ値で表明させない。
