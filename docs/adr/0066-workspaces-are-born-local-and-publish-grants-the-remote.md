# 盤面は GitHub 上に repo を作らない — workspace はローカルに生まれ、`publish` が remote 正本を与える

issue #212 のグリリング(2026-08-12)で決定。#209 の machine user 対応から派生した議論で、`createWorkspace` の `create` モードが `gh repo create <name> --private --add-readme` を **tidepool-bot のトークンで**撃っていることが判明した(`src/github.ts:264-266`)。`src/github.ts:246` のコメントが明記するとおり owner を省いた bare name は**認証ユーザ**に解決されるので、この扉から生まれる repo の owner は tidepool-bot であってユーザーではない。

CONTEXT.md の GitHub identity は「**GitHub 上の名義は執行者を表し、判断の帰属は盤面の記録が正典**」と書くが、執行者と所有者は別である。実務上も bot の資格情報は Pi 上のトークンファイル1つであり、それを失ったとき失われるのは**ユーザー自身の成果物**になる。

## 調査で確定した制約(すべて実測)

1. **他人の個人名前空間には repo を作れない。** bot のトークンで `sinano1107/foo` は作成できない。「盤面が作る」と「ユーザーが所有する」は個人アカウントのままでは両立しない。
2. **github.com に org 作成 API は無い。** REST の Orgs エンドポイントは list / get / update / delete のみで、org は Web UI でしか作れない。盤面が org を自動生成する道は存在しない。
3. **org 名はグローバルに一意。** 固定名を前提にできず、名前はどこかで宣言されるほかない。
4. **org のメンバーであることとアクセスがあることは別。** base permission が `none` ならメンバーでも repo にアクセスできない。org の価値は「付与がゼロになる」ではなく「**N 個の付与が1つの設定になる**」。
5. **今日の運用は既に「N 個の付与」の形である。** `tidepool-bot` は `sinano1107/tidepool-registry` に repo 単位の collaborator(push)として入っており、`sinano1107/tidepool` には入っていない。既存 repo の owner は両方とも `sinano1107`(人間)で、bot 名前空間の repo は1つも無い。既存 org は4つあるがいずれも tidepool 向きではない。

## 決定

### 1. 新規作成は GitHub に触れない。名前は据え置き、意味を狭める

`create` モードは `mkdir` + `git init -b main` + 初期コミット + 登録になる。GitHub に一切出ないので、所有権の問いがこの扉から発生しない。`repo` を書かないため、生まれる workspace は構造的に purely-local である(ADR 0052 決定3 の宣言モデルにそのまま乗る)。盤面の GitHub 身元(ADR 0024)を要求しないので、identity を持たない盤面でも作成できる。

**モード名は `create` のまま据え置く。** 判別軸は変わらない — 3モードは「checkout がこのホストにあるか / repo が GitHub にあるか」の2軸で切られ、`create` の前提は「どちらも無い」である。変わるのは前提ではなく、前提が成立したとき盤面が何をするかだけである。`create-local` という綴りも検討したが、`-local` が意味を持つのは対になる remote 直作成の動詞が存在するときに限られ、本 ADR はその動詞を作らない。将来必要になれば `create-and-push` のように合成そのものを名前にできるので、今 接尾辞で身構える理由がない。

**したがって ADR 0052 と issue #57 の本文にある「create モード」は、GitHub に repo を作る旧い動詞を指す。** 名前を据え置いた代償はこの一点であり、ここに明記することで払う。

`git init -b main` の `-b` は**明示が必須**である。ホストの `init.defaultBranch` は盤面の管理下になく、`master` の環境では初期ブランチ名が保護ブランチの既定(`main`)とずれて `ensureTaskBranch` が pickup 時に落ちる。初期コミットが要るのは同じ理由で、空リポジトリには `main` が存在しない(`src/workspace.ts:142-149`)。

### 2. remote 正本は `publish` が与え、宛先の repo は人間が用意する

purely-local → remote-backed という遷移には、今日**扉が1枚も無い**。`repo` は `updateWorkspace` の編集対象外(`notes` / `protected` / `review_allowed_commands` のみ)であり、遷移は registry の手編集でしか起こせない。`publish` が与えるのはこの扉であって、repo の作成はその中の1ステップですらない — 盤面は repo を作らない。

**引数は宛先の repo URL である。** 人間が GitHub 上に空 repo を作り(個人名前空間でよい)、bot を collaborator に招待し、その URL を渡す。盤面がするのは `git remote add origin <url>` と `git push --atomic --all`(決定6)と registry エントリへの `repo` の書き込みだけで、**GitHub 上に新しく作るものが1つも無い**。この非対称が本 ADR の要である: 執行者としての名義(ADR 0024)は残り、所有者としての立場だけが盤面から消える。

宛先が人間の入力であることは副次的な利点も持つ。合成 root の env 1行に宛先を置く設計では、その1行の誤りが以後の全 publish を黙って別の場所へ着地させるが、毎回人間が打つ値ならその形の静かな誤りは起こらない。盤面は宛先の所有者を検証しない — 打ち間違いは人間の入力の範疇であり、bot に write 権限が無ければ push が落ちるだけである。

### 3. 動詞名は `publish`。「昇格」は使わない。「バックアップ」は誤り

盤面には既に3つの「昇格」がある — PR 昇格(タスク成果 → PR。CONTEXT.md の Cancel / Objection、ADR 0053 / 0060 / 0064 / 0065)、ADR 0052 決定3 の `repo` 欄の昇格、ADR 0029 の e2e の昇格。4つ目を足すと、どの文書を読んでいるかで語の指す先が変わる。`publish` は git の語彙で remote へ出すことを指し(private repo でも成立する — publish ≠ public)、既存語と衝突しない。

**「ローカル workspace を GitHub にバックアップする」という表現は撤回する。** バックアップは「正本は手元、写しが向こう」だが、ADR 0052 の下では向きが逆である — リモートが正本になり、ホスト上の checkout はキャッシュへ**格下げされる**。この動詞が起こすのは複製ではなく、fork 元も休止位置も着地の形も同時に切り替わる**状態遷移**である。

### 4. `publish` はセッションと並行してよい — ADR 0064 の再基準化テーブルの6行目

`publish` は `remote add` と `push` しか打たず、**checkout を動かさない**。したがって ADR 0064 の「盤面は走っているセッションの checkout を動かさない」の線は無傷である。一方 `refs/remotes/origin/*` を**新規作成**するので、再基準化しなければ無実のセッションが解放時に quarantine へ落ちる。ADR 0064 決定4 のテーブルに `publish` の行を足し、**push したブランチの行だけ**を外科的に取り直す。

ADR 0064 は「書いた ref はどの経路でも1本に確定している」と書いているが、`publish` は初めて複数本を書く経路になる。記述は「**N 本だが確定している**」へ改訂される — 外科的再基準化の機構(全 ref を撮り直さない)はそのまま効く。push した先は盤面が知っているからである。

並行を許すのは、CONTEXT.md が既に「人間面から入る書き込みは slot の外から来るので**常にセッションと並行しうる**」と書いており、`publish` がその族に属するためである。セッションの途中で宣言が反転するが、ADR 0053 は着地の形を**完了時に**解決するので矛盾しない — PR の base はいま push した保護ブランチであり、それはタスクブランチが切られた地点そのものである。ADR 0052 決定7 の休止位置の追従も、publish 直後はリモートとローカルの保護ブランチが一致しているので no-op になる。

### 5. `publish` は4つを拒み、失敗時は `remote add` を巻き戻す

- **既に remote-backed な workspace**(エントリが `repo` を持つ)。この拒否がリトライの意味も確定させる。
- **registry clone 自身**(`resolvesToRegistryClone` — `src/workspace.ts:276`)。purely-local な盤面でこれを通すと、workspace エントリは remote-backed を宣言し合成 root は purely-local を宣言する。**ADR 0052 が quarantine と定めた「2つの宣言の食い違い」を人間の扉が製造する**ことになる。`RegistrySelfUnprotectError`(ADR 0013)と同じ形の、確認では買えない拒否である。
- **GitHub 身元(ADR 0024)を持たない盤面**。push できないので、外部効果を1つも起こさないうちに落とす。要求するのは `github` クライアントではなく `githubAuth` である —— `publish` が GitHub へ出るのは git の push 1本だけで、API は ADR 0067 の probe(あれば撃つ)にしか使わない。
- **checkout に既に `origin` が在る workspace**(実装時に追加 — issue #285 やること5)。エントリが `repo` を持たないのにこれが起きているなら、それは帯域外の手作業が作った ADR 0052 のずれ状態であり、pickup でどのみち quarantine に落ちる。`publish` が上書きして辻褄を合わせる形は採らない。**この拒否は下の巻き戻しの線も引いている** —— 自分が `remote add` した場合しか `remote remove` しないので、publish が足していない remote は決して消えない。

**git リポジトリでないパス**は決定7 の門が先に弾くので、`publish` の側では起こらない。

**失敗時は `git remote remove origin` で巻き戻す。** 案1で最も起きる人為ミスは「repo は作ったが bot の招待を忘れた」であり、そのとき経路は `remote add`(ローカル・成功)→ `push`(失敗)→ registry コミット未実行 を辿る。残るのは「clone に remote があるのに宣言が無い」= ADR 0052 が quarantine と定めたずれそのものである。`remote add` はローカル操作なので巻き戻しは確実で、失敗した publish は痕跡を残さない。

**外部効果と registry コミットの間に `await` を挟んではならない。** `authedGit` も `commitToRegistry` も `execFileSync` であり、Node が単一スレッドである以上、await を含まない publish はイベントループに対して不可分になる — pickup が中間状態を観測できない。`createWorkspace` が「外部効果が先、registry コミットが最後」を採れたのは「途中失敗が残すのは registry が知らない孤児だけ」だったからだが、`publish` の対象は**既に登録済み**の workspace なので、その根拠は引き継げない。旧 `create` モードだけが `github.createRepository` を await していた点も、決定1 でその呼び出しごと消える。

### 6. `publish` が送るのは全ブランチ。完全性は主張しない

`git push --atomic --all`(`refs/heads/*`)。publish 以前のタスクブランチも連れて行く。

**`--atomic` は必須である**(実装時に追加 — issue #285 やること2)。2番目に起きやすい人為ミスは GitHub UI の「Add a README」で、そのとき `main` だけが non-fast-forward で落ち、`task/*` は宛先に存在しないので**成功する**。非 atomic だと publish は失敗扱いで決定5 の巻き戻しを撃つのに、人間の「空のはずの repo」にはタスクブランチが載ったまま残り、**「失敗した publish は痕跡を残さない」がリモート側で破れる**。サーバ側 atomic push は git 2.4+ で GitHub も対応している。タスクブランチは決着後も削除されない**差分の恒久記録**であり(CONTEXT.md の Review)、保護ブランチだけを送ると、workspace は「remote 正本を持つ」と宣言しながら恒久記録の唯一の在処が盤面自身がキャッシュと呼ぶものになる。publish 以降のタスクのブランチは完了時の PR 昇格が押すので、範囲の選択が決めるのは publish 以前の履歴を連れて行くかだけである。

送るのは**その瞬間にローカルにあるブランチ集合の忠実な転写**であって、履歴の完全性ではない。盤面は ref の永続台帳を持たない — ADR 0064 のスナップショットは pickup→release の窓の中だけの一時的な基準である。セッションの外で人間がブランチを消していれば、それは publish の時点で存在せず、送りようがない。**欠落の報告もしない**: event log からタスクブランチ名を導けるので検知自体は可能だが、消えたブランチに対して人間が取れる行動は無く、状態遷移の動詞を監査の動詞に変えることになる。タグは送らない(ドメイン上の意味を持たないため)。

### 7. `register` の門は「git リポジトリであること」を検証する

`registerExistingCheckout`(`src/workspace-create.ts:299`)は今日 `originUrl(path)` を読むだけで、そのパスが git リポジトリかを検証しない。doc コメントはこれを意図と書いている — 「登録の門はそれを検証したことがない(checkout はエントリの後に置かれうる)ので、宣言の不在を書くのが正直である」。**この正当化を撤回する。**

`repo` は ADR 0052 決定3 で**登録の瞬間の観測**として焼かれる宣言になった。対象が存在しなければ観測できず、書かれるのは観測に基づかない既定値である。人間が後から remote 付きの clone をそこに置いた瞬間、宣言と実態がずれて quarantine に落ちる — 「checkout を後から置く」運用は、ADR 0052 が名指しで拒否した推測の一種を門に残していた。

検査は `git -C <path> rev-parse --git-dir` の成否だけで、形は ADR 0040 の重なりガードと同じ(門でも弾き、床は pickup 側に残る)。issue #121 が単射性の検査を拒んだのは「人間の慣習であり検査が不正確になる」ためだが、これは exact な検査なのでその族ではない。`create` と `clone` は盤面自身が checkout を作るので、この穴を構造的に持たない。

### 8. 扉は3枚すべて。confirm は要求せず、`unpublish` は作らない

`publish` は `WorkspaceAdmin` バンドルの4つ目の動詞(`create` / `list` / `update` / `publish`)として WebUI・`/api`・管理MCP に開く。CONTEXT.md の管理MCP は「registry 管理(agent / profile / workspace の作成・編集)」を既に人間の手として開いており、workspace 系の動詞だけ非対称にする根拠がない(ADR 0032 の義手モデルの下では帰属はどちらも人間である)。

**確認(confirm)は要求しない。** ADR 0061 の「危険な値」は registry の値がエージェントの権限を広げる向きのものであり、`publish` はそこに当たらない。宛先 URL が毎回人間の入力であること自体が同意の形になっている。

**`unpublish` は作らない。** remote-backed → purely-local へ戻すのは registry の手編集(`repo` 欄の削除)で足り、扉を作るべき痛みは観測されていない。

## 将来の拡張候補: org を宛先の既定にする

本 ADR は org を採らないが、**採る道は閉じない**。拡張の形は「`publish` の宛先が省略されたとき、合成 root(`BoardComposition`)で宣言された org 内に盤面が repo を作る」であり、未宣言なら宛先の省略という選択肢ごと不在になる(ADR 0041「不在は宣言される」)。この形なら決定2 の「宛先は引数」は既定値を得るだけで、org 外への publish も従来どおり通る。

先に案1(宛先は人間が用意)を採るのは、拡張の向きが一方通行だからである。案1に org 既定を足すと org 案になるが、逆向き — org を既定かつ唯一の置き場として設計した上で「org 外の宛先も受ける」を後から足す — では、org は既定でありながら唯一の置き場でもない中途半端な地位になる。加えて、org はまだ存在せず作れるのは人間の Web UI だけ(制約2/3)なので、org を前提にすると着手から動くまでの間に盤面の外の作業が挟まる。案1は今日ある材料だけで完結する。

**この拡張が正しくなる条件は明確である** — workspace の新設頻度が上がり、repo あたり人間2手(作成 + bot の招待)が実際に摩擦になったとき。案2は repo あたり0手で、そこだけは案1が構造的に負けている。今日の N は 1(registry)、実環境動作確認の第3段で 2 になる。

## 根拠

**1. 「盤面が作る」と「ユーザーが所有する」の両立不能は、org でしか解けず、org は今日存在しない。** 制約1〜3 の合成である。したがって選べるのは「盤面が作るのをやめる」か「org を人間が用意して盤面に宣言する」の2つしかなく、前者は今日の材料だけで成立する。

**2. 決定1 は問題を移設せず消滅させる。** org 案は「盤面が repo を作る」を残したまま器を正しくする解であり、器の設定(base permission / team)が間違っていれば同じ穴が別の形で開く。決定1 の下では盤面が GitHub 上に永続的な資源を作る経路が1本も無くなるので、この族の穴は構造的に再発しえない。

**3. `publish` の値は repo の作成ではなく、遷移に扉を与えることである。** `repo` 欄は ADR 0052 で機械が読む宣言へ昇格したが、その欄を書く人間向けの経路は作られなかった(`updateWorkspace` は3フィールドしか触らない)。issue #212 が「promote」と呼んだものの本体はこの欠落であり、repo をどこに作るかはその中の一手にすぎない。この読み替えが、org 採否を独立の判断へ分離した。

**4. 並行 publish を許せるのは、危険な側に触れないからである。** ADR 0064 が守る不変条件は2つの層を持つ — ref の不変性(スナップショット比較)と checkout の専有(作業ツリーを奪わない)。`publish` は前者だけに触れ、後者には触れない。再基準化は前者のために既に存在する機構であり、6行目を足すことは新しい免除ではなく既存の族への1件の追加である。

**5. 決定7 は ADR 0052 の帰結の回収である。** `repo` 欄が散文から宣言へ変わった時点で、「宣言は観測に基づく」という要求が `register` の門に生じていた。#211(S3)は `origin` を読んで焼く実装を入れたが、読む対象が存在しない場合の門は据え置かれた。本決定はその積み残しを閉じる。

## Considered options

- **org を採り、盤面が org 内に repo を作る(案2)** — repo あたり人間0手で最も手数が少ない。採らなかったのは、拡張の向きが一方通行であること(案1 → 案2 は既定値の追加だが逆は地位が濁る)、org がまだ存在せず作れるのが人間の Web UI だけであること、そして盤面が再び「GitHub 上に永続的な資源を作る主体」に戻ることによる。将来の拡張候補として上に残す。
- **org を「取り込みの門」にする(org 内の repo しか workspace にできない)** — 動かせない repo(他人の repo・fork・別 org)が使えなくなるうえ、制約4 によりどのみち「読めない」経路の実装は要るので盤面は簡単にならない。読み取り権限1つのために repo の引っ越しを要求するのは釣り合わない。
- **`publish` を作らず、remote 正本が欲しければ人間が GitHub に repo を作って `clone` モードで取り込む一本にする** — 扉は増えないが、`create` で生まれた workspace が後から remote を得る道が registry の手編集だけになる。purely-local として実際に走ったタスクの履歴を捨てて clone し直すか、盤面の外で手作業を積むかの二択になり、ADR 0052 が宣言モデルを整えた意味が半分失われる。
- **`publish` を実行中のタスクがある間は拒否する** — ADR 0064 の carve-out を増やさずに済み、publish の同期ブロック先頭で slot を見れば競走もしない。採らなかったのは、人間面に新しい拒否状態が1つ増えるうえ、その拒否が守るものが無いからである(checkout に触れない以上、無実のセッションが失うものは再基準化1行で足りる)。長いタスク(`work` = 90分)の間 人間が待たされる代償も釣り合わない。
- **`publish` は保護ブランチだけを送る** — 動く ref が1本のままで ADR 0064 の記述が無傷になる。採らなかったのは、publish 後の workspace が「remote 正本を持つ」と宣言しながら、恒久記録(過去のタスクブランチ)の唯一の在処が盤面自身がキャッシュと呼ぶものになるためである。
- **`publish` の瞬間に、event log が知るタスクブランチのうち checkout に無いものを人間へ報告する** — 失われた記録の存在を知る機会にはなるが、人間に取れる行動が無い。状態遷移の動詞に監査の役を足すことになり、扉の目的が濁る。
- **`register` の門は現状維持し、quarantine に拾わせる** — 床は既に pickup 側にあるので害は限定的だが、「観測できない状況で宣言だけが書かれる」という形が門に残る。ADR 0052 が推測を拒否した理由がそのまま当てはまる。
- **モードを `create-local` へ改名する** — 何が起きるかは名前で明快になるが、対になる remote 直作成の動詞を作らない以上 `-local` は何とも区別しない接尾辞になり、`register` / `clone` が remote に出るかを名前に持たないことと不揃いになる。将来の扉は `create-and-push` のように合成を名前にできる。
