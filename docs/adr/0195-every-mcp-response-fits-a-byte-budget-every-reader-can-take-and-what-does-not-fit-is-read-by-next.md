# 盤面が返す MCP 応答は、どの読み手にも届くバイト予算に収め、収まらない分は続き(next)で読ませる

2026-10-05 の grilling(issue #1376、発端は #1317)で決定。管理MCP の `get_task` は task の event を全件返し、読み手の
応答上限を超えうる。読み手ごとに、上限を超えたときの振る舞いを実測した(Claude Code、Codex、ChatGPT、Claude のアプリ)。
測定表と、伸びる読み口の棚卸しは #1376 に置く。

## 決定

1. **盤面が返す MCP 応答すべてに、盤面側で応答予算を掛ける。** 管理MCP にも Worker MCP にも掛ける。管理MCP の読み手は
   人間がどこからつないでもよい(Claude Code、Codex、ChatGPT、Claude のアプリ)。上限を超えたときの振る舞いも読み手で違う。
   Claude Code はファイルに逃がして全文を残すが、Codex は中央を黙って切り詰め、全文は戻らない。読み手の逃げ道に頼ると、
   どこから読むかで届く中身が変わる。
2. **予算は UTF-8 で 40,000 バイト。盤面の定数とし、設定にはしない。** 既知の読み手で一番厳しいのは Codex で、Codex は
   トークナイザを使わずバイト数で判定する(実効 48,000 バイト)。40,000 バイトなら、Codex が足すヘッダ・決定5 の目印・
   続きの分を引いても収まる。字数を単位にしないのは、漢字が詰まると1字あたりのトークン数が大きく揺れるからである。
3. **予算を超えうる読み口は、item を丸ごと予算まで返し、続き(next)と残りの件数を付ける。** 小さい読みは今どおり1回で
   全部届き、大きいときだけ呼び出しが増える。件数で切るページング(既存の `page`)は大きさを保証しないので、この規則に
   寄せる。線を件数でなく大きさで引くのは、ADR 0122 が `read_memory_entries` に件数の上限を置かなかった理由と同じである。
   ADR 0122 追記が `list_memory_branches` を「全件を1応答」にした判断は、予算の内側ではそのまま成り立つ。続きが要る
   のは木が予算を超えるときだけで、呼び出し回数を数えた理由は変わらない。
4. **1件で予算を超える item だけは、長い欄を予算の位置で切り、続きがその欄の残りを指す。** 保存は逐語のままで、
   分けるのは届け方だけである。ADR 0189(`last_message` を逐語で持つ)とはぶつからない。
5. **出口では全応答を測る。予算を超えた応答は予算まで切り、本文に目印を付け、盤面全体の記録に残す。** これは読み口の
   欠陥の床であって、続きの読み方ではない。予算を超えうる読み口がここに落ちないことは不変条件になる。書き込み verb で
   error を返すと、済んだ書き込みが失敗に見えるので、error にはしない。
6. **続きは読み手が持ち回る印で、盤面は状態を持たない。カーソルとは呼ばない。** 既読の状態を持つ Decision log の
   未読カーソルと、同じ応答の中で取り違えさせないためである。
7. **読み手の上限は、測った値として残し、版上げのときに測り直す。盤面は実行時に読まない。** 予算に収まった応答は床に
   掛からないので、読み手の上限が予算より下がっても盤面には残らない。どちらの CLI でも、上限は版だけでは決まらない。
   Codex はサーバーから配られるモデルの metadata で決まり、Claude Code はサーバーの flag で上書きされる。実行時に読める
   のは盤面のホストの Codex の `models_cache.json` だけで、それは ADR 0116 の線(認証ファイルは存否だけ読む)の外になる。
   しかも管理セッションの読み手には届かない。版上げのときに測り直しても、版の間に起きる変化は拾えない。この穴は承知の
   うえで受け入れる。

## Considered options

- **読み口を変えず、読み手の逃げ道に任せる。** 文書化されている管理セッション(Claude Code)では何も失われない。しかし
  「どこからでも使えるように」という要件では、Codex で中央が欠ける。
- **読み手の設定を上げる手順を書く(Codex の `tool_output_token_limit`)。** ChatGPT とモバイルには設定が無い。
- **`get_task` だけを直す。** `read_decision_log` は盤面全体のログを返すので、もっと早く上限を超える。同じ欠陥を残す。
- **events を別の verb に分ける。** 小さい task の読みでも、呼び出しが毎回1回増える。

## 帰結

- 予算が既知のどの読み手の上限より小さいので、「盤面が返した」と「読み手に届いた」がほぼ一致する。#1229 に残る問いは、
  記録の扱いに絞られる。
- HTTP の `/api` は MCP の上限を受けないので、この ADR の外である。

## 追記(2026-10-05 の triage / grilling、issue #1403)

決定2 の「40,000 バイトなら Codex が足すヘッダ…を引いても収まる」は、code mode の Codex では成り立たなかった。0.147.0 の
gpt-5.6 系は `tool_mode: code_mode_only` で、MCP の応答は `exec` の出力として届く。その経路の上限は `truncation_policy` の
10,000 トークン(`ceil(bytes/4)`、×1.2 は掛からない)で、40,000 バイトになる。上限が掛かるのは盤面の本文ではなく、モデルが
exec の中で `text()` に渡したものである。canary では terra が本文を取り出して合格し、sol は CallToolResult を丸ごと JSON に
包んで本文の引用符の分だけ膨らみ、中央が欠けた(実測と包んだときの膨らみの表は #1403)。standard の worker は sol で、
盤面の Worker MCP の応答もこの経路に乗る。

1. **予算が測るのは、盤面が返す応答そのもの —— MCP の結果(CallToolResult)を丸ごとシリアライズした大きさである。** 本文の
   大きさではない。詰める処理・欄の分割・出口の床のすべてで同じ大きさを測る。値は 40,000 のまま変えない。Codex は
   バイトから決まった数え方でトークンを出すので、余裕を足す根拠が無い。包んだときの膨らみは中身の引用符しだい
   (実測で +1.4% 〜 +12.9%)で、本文を測ったまま定数を下げても保証にならない(引用符だらけなら約2倍)。本文だけを
   渡す形(terra)は常にこれより小さいので、一緒に覆われる。ヘッダは別の item で、上限は item ごとに掛かると読める
   (terra の合計 40,047 バイトが合格した表からの推論)。
2. **canary は、盤面の tier 表にある Codex のモデルを全部回す。** 合否はモデルが exec の中で書くコードで決まるので、
   モデルごとに違う(全モデルを回すのは #1391 の canary がすでにそうしている。ここで変えるのは埋め草)。埋め草は実際の応答に近い引用符の多い形にし、CallToolResult の大きさで予算ちょうどに詰める ——
   包み方が1段の形は合格し、それより多く包む形は不合格として見える。
3. **包み方が1段より多い形(二重の stringify・整形した出力)と、tier 表の外のモデルは覆わない。** 決定7 と同じく承知の
   うえで受け入れ、版上げのときの canary で見る。description で code mode の読み方を指示する案は採らない —— 読み手の
   一部のために全 verb の文を足し、従うかはモデルしだいで保証にならない。

Considered options の「読み手の設定を上げる手順(`tool_output_token_limit`)」は、code mode の exec の出力には効かなかった
(`-c tool_output_token_limit=2000` で実測)。

## 追記(2026-10-08 の grilling、issue #1399)

決定3 の続きは、境目の item を鍵で引き直していた。読む間に既読の範囲が変わると、黙って欠け・重複が起きた ——
未読の行が先頭へ移れば欠け(上限到達の中断と行の拒否は task を queue の先頭へ戻すので、欠けるのは今いちばん注目
すべき行になる)、既読の行が後ろへ移れば重複する。境目の item が抜けると、理由の分からない error になった。
先頭や途中への挿入・離脱は board 順に限らず、記憶の木・検索の順位・halted refire の行でも起きる(観測と棚卸しは #1399)。

1. **続きは、返した件数と、返した item の鍵の列の digest を持つ。** 続きを読むときは、今の列の先頭からその件数分の
   digest が一致すれば、その位置から返す。一致しなければ「最初から読み直せ」の error にする。境目の item そのものの
   離脱は error にしない —— 先頭の範囲が返したものと同じなら、残りは今の列の残りと一致する。盤面は状態を持たない
   (決定6)まま、欠けも重複も起こさないか、起きうるときは名指して止まる。
2. **行の中身の変化と、未読の範囲の中の並べ替えは検知しない。** どちらも欠けにも重複にもならない。一覧は生きている
   ものとして受け入れる。途中に新しい行が入りうる読み口は、読む間に行が入ると読み直しになる。これも受け入れる。
3. **新しい順に返す履歴(`get_task` の event、`read_decision_log`)は、この検査を掛けず、鍵で引き直す。** 新しい行は先頭に
   積まれるので、検査を掛けると動いている task を読み終えられない。event は書き換えも削除もできないので、鍵の引き直しが
   外れることはない。読み始めた後に積まれた分は返さない。これは決定3 の当初からの範囲である。
4. **1件を切って返す続きは、その欄の大きさと digest も持ち、食い違えば同じ error にする。** task の本文は編集できるので、
   切れをつなぐと新旧の継ぎはぎになりうる。

続きの鍵を列の位置で作ると、この追記の1 の digest が変化を表さなくなる。そのため鍵は、item ごとに変わらない識別子で作る。

### Considered options

- **今のまま「一覧は生きている」と description に書く。** 応答の完結を `next` の有無で判断できなくなる(#1387 US 13)。
- **境目を並びの位置(sort_key など)で持つ。** 離脱は救えるが並べ替えは救えず、読み口ごとに並びの鍵が要る。
- **先頭 N 件の digest を全読み口に掛ける。** 新しい順の履歴が毎回読み直しになる(この追記の3 がこれを外す理由)。
- **続きを読み手のセッションに縛る。** 盤面は管理MCP の呼び出し元のセッションを見ない。別の読み手に渡った続きも
  検査(この追記の1)を通るので、害が無い。

## 追記(2026-10-09 の grilling、issue #1413)

code mode の Codex では、canary の prompt(「呼んで DONE と答えよ」)に対してモデルが書くコードが揺れた。terra は呼ぶだけで
結果を捨てる回があり(`text("ok")`)、canary はそれを上限の観測でない「不合格」として出した。同じ版・同じ prompt でも
terra は本文だけを出す回と捨てる回に分かれ、sol は 0.147.0 では1段包んだが、0.161.0 では本文だけを出した(34,506 バイト。
予算いっぱいの上限を試さないまま合格する)。包み方はモデルの性質ではなく、版と回しだいだった(実測の表は #1413)。

1. **canary が Codex で測るのは、予算が覆う最悪の形 —— CallToolResult を1段包んだもの —— がそのモデルの exec の出力上限に
   収まるかである。** 形は prompt で exec のコードを逐語で指定して固定する。モデルの自然な包み方は観測しない。
   追記2 の「合否はモデルが exec の中で書くコードで決まるので、モデルごとに違う」は、全モデルを回す理由として
   成り立たなくなった。理由は決定7 の「上限はモデルの metadata で決まる」に置き換える。
2. **追記3 の「包み方が1段より多い形…は版上げのときの canary で見る」は撤回する。** 今の prompt でも当てにならない観測
   だった。1段より多い形は、どこでも観測せずに受け入れる。
3. **観測にならなかった回は「観測なし」とし、不合格と分けて出す。** 読み手の実行の失敗(usage limit など)、tool を
   呼ばなかった回、指定したコードを走らせなかった回がこれに当たる。門は満たしていないので exit は 1 のままである。
   指定したコードを走らせたかは、コードの一致で見る。本文の先頭やバイト数、Codex の切り詰め通知の文字列を見る案は、
   順に、頭だけ出した回を上限の観測と取り違える、上限が下がった回と区別できない、版で黙って外れうる、という理由で採らない。

Claude Code は exec を持たず tool の結果がそのまま文脈に入るので、prompt は読み手ごとに分け、Claude の行は変えない。

## 追記(2026-10-09 の grilling、issue #1393)

決定4 は最も長い欄を1つ切るだけだった。その欄を空にしても予算を超える object は、正しく作った続きでも出口の床に落ちた ——
長い欄を2つ持つ item(handoff と result がどちらも長い Exemplar の case)と、予算を超える封筒(item の列の外にあって
最初の応答にだけ載る欄。issue 由来の task の purpose は GitHub の issue 本文で、盤面は長さを決められない)である。床は応答の
末尾にある続きも切るので、残りの item も読めなくなる(経路と観測は #1393)。

1. **1欄を切っても予算に収まらない object は、収まるまで長い順に文字列の欄を切る。** 1つの切れに載せる断片は1つの欄の分
   だけにする。ほかの切る欄は空文字にし、切れの印で名指す —— 名指さないと、空にした欄と本当に空の欄を読み手が区別
   できない。1つの欄を読み終えたら、次の切る欄へ進む。
2. **封筒も、item より先に同じ規則で切る。** 封筒の切れは item の id を持たず、読み手はそれで item の切れと見分ける。欄の
   path は応答の根から数える。
3. **続きは切る欄すべての大きさと digest を持ち、どれかが変われば読み直させる。** 追記 #1399 の4 を複数の欄に広げ、欄ごとに
   新旧が混ざる継ぎはぎを防ぐ。切らない欄は今どおり毎回丸ごと載り、その変化は検知しない。
4. **決定4 の「1件で予算を超える」は、「その item と続きの印を合わせて1応答を超える」と読む。** 単独なら収まる item でも、
   続きの印の分で超えるなら切れで届く。続きの印が無ければ残りを読めないので、丸ごと返す手は無い。
5. **文字列以外の中身だけで予算を超える object は覆わない。** 今ある item と封筒の形に該当するものは無い。承知のうえで
   受け入れる。「文字列以外の中身だけで超える」は、この追記の4 と同じく、続きの印と1文字(escape 後に最も広い文字)の分を
   含めて読む —— 切れは1文字以上を載せないと進めないので、それが収まらない object は切らずに丸ごと返す(issue #1700)。
   この続きの印には、欄を読み終える最後の切れの続き(item の key を持つ)も入る(issue #1755)。

### Considered options

- **書き込み時に長さの上限を置く。** issue 由来の purpose を書くのは盤面ではなく GitHub なので、届かない。worker の handoff を
  拒むことにもなり、決定4 の「保存は逐語、分けるのは届け方だけ」に反する。
- **床に任せ、`response_truncated` の記録を待つ。** 作れる入力で決定5 の不変条件が破れることは確かめてある。床の記録は
  まだ人間の面に出ていない(#1386)ので、待っても気づけない。
- **1つの切れに複数の欄の断片を詰める。** 呼び出しは少し減るが、切れの印が列になり、つなぎ方が複雑になる。
- **空にせず、欄ごと省く。** 名指しはやはり要り、item の形が切れごとに変わる。
- **封筒の切れに固定の id(`"envelope"` など)を入れる。** item の鍵とぶつかりうる。
