# 無人 merge の読み直しは門を面より先に読み、門が閉じていれば面の変化もキューで待つ

2026-10-10 の grilling(issue #1720、発端は #1644 のレビュー)で決定。ADR 0217 決定1 は、無人 merge キューの読み直しで
門と着地の面を同じ2点で読むと決め、当たったときの結果 — 門ならキューに残る、面ならキューから外れる — を分けたが、
両方に当たったときの順は決めていなかった。tick は面を先に読んでいたので、門が閉じている間に面が question 側へ
変わった PR には merge question が立った。これは ADR 0092 決定1 が門を置いた merge question の登録そのものであり、
ADR 0217 決定1 が赤の枝で門を読む理由(修理が push する前の CI で問うことになる)の形でもある。経路と再現は #1720 に置く。

## 決定

1. **門が閉じていれば、面の変化はキューで待つ。** 面が question 側(`escalate`・保護・risk flag)へ変わった PR は、
   門が閉じている間はキューに残り、門が開いた後の tick で面と CI を読み直す。キューの行がそのまま門待ちを表すので、
   新しい状態も経路も要らない。いま着地を走らせても門で止まり何も立たないので、ADR 0217 決定2「いま開けば立つ
   question と同じ形」とも揃う。
2. **`external` への変化も門の後に読む。** question を立てない取り下げは着地の行為ではなく、ADR 0092 の門が待たせる
   ものではない。それでも面ごとに読む順を分けない — 1つの読み直しが面によって2通りの順を持つことになり、揃えて
   壊れるものが無い。代償は、取り下げの event が修理の間遅れ、その間 PR が着地を待つ完了タスクに数えられて
   agent / workspace の削除の扉が拒み続けることである。門は付帯子の決着で必ず開くので、永久には続かない。
3. **profile は門より先に読む。** 読む順は profile → 門 → 面で、PR を開く着地(門 → profile → 面)と違う。キューの PR は
   すでに開いており、門を閉じているもの — 修理子、review 子、未束ねの異議 — がその PR の agent を spawn するとは限らない
   ので、門の間に盤面の外で registry から消えた・壊れた agent を検出するのはこの読みだけである。門の後に回すと、修理が
   終わってから quarantine が立ち、registry を直す往復が着地の後ろに積まれる。PR を開く着地で門を先に読むのは、
   開く前なので待つ間に検出すべき PR が無いからである。

## Considered options

- **キューから外し、question だけ門の後に立てる** — 外した PR の question を門の決着で立て直す経路が要る。再発火は
  開いている PR へ push するだけで面を読まない。
- **今のまま(面を門より先に読む)** — ADR 0092 決定1 の登録時の門を改めることになる。
- **PR を開く着地と同じ順(門 → profile → 面)** — 決定3 の理由で退けた。

## 帰結

- 門が閉じている間、面が変わった PR は人間の面に何も出さない(今までは門待ちの印が付いた question が見えていた)。
  キューにいること自体が人間の面に出ない穴は #1735 が扱う。
