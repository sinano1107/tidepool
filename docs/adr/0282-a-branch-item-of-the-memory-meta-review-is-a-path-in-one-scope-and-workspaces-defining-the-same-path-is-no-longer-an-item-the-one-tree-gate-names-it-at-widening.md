# memory meta-review の枝の項目と判断の行は (path, scope) の単位で、「複数の workspace が同じ path を定義」は項目から外す —— 衝突は盤面全体へ広げる時に一木の門が名指す

2026-10-20 の triage / grilling(issue #2326、元 #2304 の /code-review)で決定。memory meta-review の判断の行が名指す枝は path だけで
(ADR 0278 決定5「複数 scope が定義した path」)、判断の行への異議で立つ修理子(ADR 0279 決定3)はその path の**どの scope の**枝にも
`define_memory` / `move_memory_branch` を通せ、被覆(ADR 0278 決定3)も path だけで数えるので、別 workspace に定義を書けば未定義のまま
の workspace の欠けが行なしで閉じた。実測(`file:line`)は #2326 のコメントに置く。

path 単位の根は ADR 0178 決定8 の「複数の workspace が同じ path を定義している」を見回りの項目にしたことで、その項目は「別の workspace
の同じ path は同じ話題である」に乗る。だがその同一性を要るのは**1人の読み手の中の重なり**(盤面全体 + 自分の workspace を重ねた1本の木、
ADR 0178 決定1・2)だけで、workspace どうしの同じ path はどの読み手も同時に見ない。ADR 0178 自身が「放置した重なりは広げるときに必ず門に
当たる」と置いたとおり、盤面全体へ広げる時には一木の門が衝突する定義をすべて名指して拒み、`supersedes` で畳む1手が通る。

## 決定

1. **「複数の workspace が同じ path を定義している」を memory meta-review の項目から外し、purpose の対処の文も外す**(ADR 0178 決定8・
   追記8 を改める)。衝突への対処は、その path を盤面全体へ広げる時に一木の門が名指した時点で行う。枝の一覧(ADR 0122 追記)の
   `definitions` / `scopes` の2欄は変えず、重なりは行から読める —— 人間が見れば直せる。
2. **枝の項目と判断の行の対象は (path, scope) で、scope は workspace か盤面全体(null)。** 残る構造の項目「配下にエントリを持つ定義の無い
   枝」は欠けている scope ごとに1項目、判断の行は「left_as_is: branch <path> in scope <workspace | whole board>」。異議された枝の
   再掲(ADR 0279 決定5)も同じ鍵。
3. **盤面全体のエントリがその path かその下にある未定義の枝は、項目を (path, 盤面全体) の1つだけにする。** 一木の門(ADR 0178 決定2)が
   そこへの workspace の定義を拒むので、workspace ごとの項目に届く verb は盤面全体の定義だけ —— 届く手が1つの項目は判断ではなく強制
   (ADR 0278 追記5 の routing のセルと同じ線)。workspace ごとの項目は、その path かその下に盤面全体のエントリが無いときだけ。
4. **被覆と修理子の射程は (path, scope) で見て、盤面全体への行為はどの scope の項目も覆う。** 定義の作成は (path, scope) が一致するか
   scope が盤面全体なら行為済み、移動は動いた行の scope で数える(盤面全体 → 盤面全体の移動が連れて行った workspace の行も、ADR 0177
   決定5)。判断の行の修理子が `define_memory` / `move_memory_branch` を通せるのは、名指された (path, scope) と、同じ path の盤面全体
   だけ —— 覆いの門(ADR 0161 決定6)の「盤面全体か同じ scope」と同じ形。

## 退けた案

- **path 単位のまま、ADR 0178 の一木の前提に乗って決定として残す** —— 修理子が人間の異議の意図と違う workspace の同名の枝を動かせる
  ことを機構で止められず、被覆の取りこぼし(別 workspace の定義で欠けが閉じる)を直すには別の分岐が要る。
- **衝突の項目を残したまま枝に scope を持たせる** —— 衝突には単一の scope が無く、項目の形が2種類になるか、枝の一覧の1行に判断の行が
  複数付く。
- **行為では覆わず項目が消えたかだけで被覆を見る** —— 異議で再掲された枝は path が変わらない限り消えないので、定義を書いた直後に同じ枝へ
  `left_as_is` を求め、ADR 0278 決定3「行為済みに二度申告させない」と食い違う。
- **衝突の前提を別の根 issue に分ける** —— 前提に乗っているのは衝突の項目1つだけで、削る変更なので同じ grilling で決める。

## 変えないもの

一木の門(ADR 0178 決定2)と、盤面全体の枝の改名が全 workspace の配下を連れて行く(ADR 0177 決定5)は、1人の読み手の中の重なりの
規則なのでそのまま。書き込みの行の修理の枝の射程(ADR 0281 決定2)は既に scope 一致で、本 ADR で判断の射程と揃う。

## 帰結

- 追記する ADR: 0178 決定8・追記8、0278 決定4・5、0279 決定5。
- 複数の workspace が同じ未定義の path に leaf を持つ盤面では、枝の項目は workspace の数だけ立つ(それぞれに自分の定義が要る場面)。
- 判断ログと注入の記録の `judgment` / `items` の形が変わるが、event payload の JSON であって列ではない。盤面は作り直す。
