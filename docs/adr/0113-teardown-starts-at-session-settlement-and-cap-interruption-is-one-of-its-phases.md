# 後始末の起点は session の決着であり、上限到達による中断もその局面である

2026-09-11 の grilling(issue #537)で決定。ADR 0109 決定5 が入れた後始末の backstop は「最終 verb は着地したのに root が exit しない」だけを見ており、上限到達による中断(ADR 0104)が回収済み観測を待つ区間はタスク種別の時間制限のまま残っていた。その梯子の底は failure question であり、ADR 0104 決定1 が消したはずの「retry 一択の問い」がそこから立つ。#531 の agent brief はこの拡張を項目に持っていたが、受け入れ基準が無く合意した seam の外の判断が要るため意図的に落とされた。現状調査と `file:line` は issue #537 のコメントに置く。

## 決定

1. **後始末の起点は session の決着であり、最終 verb の着地に限らない。** 上限到達による中断で root process が exit した瞬間も session の決着である(タスクのほうは決着せず、queue へ戻る) —— ADR 0109 決定2 が session の終わりを回収済み観測に置いた時点で、この区間は定義上 session の最後の局面だった。永続化する事実は `tasks.teardown_started_at` ひとつのままで、意味も「後始末に入った時刻」のまま変えない(ADR 0112 決定2 と同じ言い方)。違うのは、その時刻を書かせる事実が経路ごとに別だということだけである。cap の session でも `Slot.inTeardown` を立てる —— 待っている当のものは容器に残る子であり、その子が盤面に触れる口は決着と同時に閉じる。

2. **cap の梯子は1段である。** 完了経路の backstop は2段(起点 → 強制回収 → 回収 timeout)だが、cap では root の exit と同時に強制回収が撃たれている(ADR 0109 決定4)。残るのは「force は届いたのに空にならない」区間だけで、1段目が測る「root がまだ exit しない」は cap では既に確定した事実である。底は完了経路と同じ Containment quarantine で、**failure question は立てない**(ADR 0104 決定1)。そこでタスクは `in_progress` のまま留まり、確認回答の受理で後始末が完走して初めて `todo` 先頭へ戻る —— 行が動くのは後始末が完走したときだけ、という規則を経路で割らない。底で失敗の記録を残さない点は、ADR 0099 決定3(空を観測できないまま timeout したら失敗の記録は残す)に ADR 0109 決定4 が入れた例外を cap へ広げたものである。またここで行を `in_progress` に留めることは、ADR 0007 が退けた「`in_progress` のまま凍結する」とは別物である —— あちらは tree rule も queue 復帰も無いまま回復を待つ**既定の扱い**で、「動いているはずなのに何もしていない」曖昧な状態を作る。こちらは空を観測できなかった例外の底であり、tree rule はそもそも走れず(生きている process が書いているツリーは退避そのものが競合する。ADR 0099 決定3)、確認 question が立って人間を呼んでいる。question の文面が経路ごとに違うのは人間が確認すべきものが違うからであり(タスクは決着しているのか、queue へ戻る予定なのか)、プロセスについての断言の強さは ADR 0112 決定4 が揃えたとおりに従う。

3. **経路ごとの step は行に持たず、後始末中の status から1点で導く。** 後始末中の行の status は経路ごとに一意である(完了 `done` / エスカレーション・分解 `todo` / 上限到達による中断 `in_progress`)。経路を列に書くと status と食い違う行が表現でき、その食い違いは復旧経路でしか現れない —— 観測が最も遅い場所である(ADR 0112 決定2 が question の列を1つに留めたのと同じ理由)。導出は1つの関数に集め、3経路のテストで固定する。これは既存の穴も同時に閉じる: 復元規則は起動時復旧と確認回答の受理で2本に分かれており、後者はエスカレーション・分解を完了として扱って退避を飛ばしていた。

4. **後始末の未了は、再起動時の中断処理より先に読む。** 「再起動は実行中タスクを中断する」掃除(ADR 0001)は `in_progress` の行を拾って failure question を立てるので、cap の後始末はそこから除外し、ADR 0109 決定5 の起動時復旧へ渡す。除外しなければ、盤面を1回再起動しただけで ADR 0104 の無害化が失効する。これは ADR 0001 の掃除から `in_progress` の行を外す最初の例である —— ADR 0109 決定5 が拾う後始末の行は `done` で、掃除と競合しなかった。

## 退けた案

- **cap 専用の列 / イベントで起点を持つ** —— `sessionInTeardown` の「高々1つ」が2本に割れ、読み口・時限・起動時復旧がそれぞれ2経路を持つ。
- **cap でも2段の梯子を回す** —— 意味を持たない5分が1つ挟まる。1段目が測る事実は cap では既に確定している。
- **経路を列(`teardown_reason`)に書く** —— 復元は1点から読めるが、同じ事実が status と列の2箇所に載る。
- **cap を後始末とは別の待ちとして扱い、時限の尺度だけ共有する** —— 「session の終わりは回収済み観測」(ADR 0109 決定2)と「後始末は最終 verb から」の2文が矛盾したまま残り、時限・quarantine 文面・起動時復旧・読み口が2セットに割れる。
- **再起動のときだけ cap でも failure question にする** —— 盤面の再起動という盤面側の事情で、環境事象が失敗に化ける。
