# タスクブランチを失った task は着地が終わったと読む —— 終わりの記録は書かず、「諦める」が失われた event と一緒に着地の question を閉じる

2026-11-23 の grilling(issue #3582)で決定。ADR 0375 決定7 は「失われた根の着地はそこで終わる」と決め、終わりを別の記録に刻むか失われた
event から読むかを spec に委ねた。spec は刻む側を選び、ADR 0397 は刻む書き手を受理と収束の2人にした。失われた event(事実)と着地の
終わり(後から述語で書く記録)が別になり、その間に条件と時間の隙間ができた。終わりを書くには「根か」と種類の判定が要り、「根か」を
読むには git が要る。#3492(受理の後で根になった子)、#3581・#3714(系譜の読みが落ちる)、#3582(終える種類の列挙から漏れた、祖先の
記録で透明な根と PR を開いた根が、失われたブランチを git で読む着地に落ちる)は、どれもこの隙間から出ている。この grilling も最初は
列挙を完全にする形(全種類の終わりの記録、merge の扉ごとの床、回答ごとの扱い、書き手の順序)を積んだが、種類か扉が増えれば同じ漏れが
戻る。隙間そのものを無くす。実測・読み手の表・`file:line` は #3582 のコメントに置く。決定はコードの読みと fixture の実測に依り、
本番の盤面では観測していない。

## 決定

1. **効いている失われた event(ADR 0375 決定1・2)を持つ task は、着地が終わった task と読む。終わりの記録は書かない。** 「着地が終わったか」
   を読む箇所(収束の候補、着地を待つ数え、workspace の削除の扉、PR の根が子孫を外す読み)は1つの述語を読み、その述語が失われた event を
   読む。根かどうかも、失われた task の種類(死んだ・handoff だけ・透明、PR の有無)も条件にしない —— 根でない task はもともと自分では
   着地しない。失われた task は着地の候補に入らないので、失われたブランチを git で読む経路が無い。`landing_ended_branch_lost` は廃止し、
   handoff だけの根に `nothing_to_land` を書くこともやめる。
2. **「失われた ref を諦めて基準へ戻す」の受理は、失われた event と同じ transaction で、その task を指す開いた着地の question(local 着地、
   昇格失敗、merge question)を閉じ、無人 merge キューの行を取り下げる。** 同じ transaction は既に付帯子を倒している(ADR 0375 決定4・9)。
   着地の question は、その task のブランチを着地させる問いなので、ブランチが無ければ根かどうかによらず答えようが無い。閉じるのは人間自身の
   回答の帰結で、ADR 0240 決定2 の先回りには当たらない(ADR 0375 決定8 のまま)。閉じた question の id は失われた側の event が運ぶ。
   これで、失われた event が書かれた時点で、扉が読む状態(候補、question、キューの行)が全部正しくなる。merge の扉ごとの検査も、
   `retry`・`end landing` の回答の特別扱いも置かない。盤面がその根への執行の印を持っている間(無人 merge の tick、merge の回答、
   収束の push と PR の作成)は、受理を拒む —— question とキューの行の片づけが執行中の行為と競るからで、`end landing` が拒むのと同じ
   理由である(ADR 0399 決定6)。拒まれた受理は Quarantine を開いた
   まま残し、次の回答が通る。
3. **PR を開いた根も決定1・2 に入る。** ADR 0375 決定7 の末尾(PR を開いている根は対象にしない)を置き換える。その理由「内容は GitHub の
   head に在る」は、ADR 0380 決定4 が数える前に取り戻すと決めた後は、取り戻せなかった根にしか当たらない。「成果が捨てられた」の述語は
   PR の条件を既に外しており(ADR 0380 決定1)、同じ根のレビューを倒しながら着地だけを続けていた。続けると、push 前に失われた commit
   (修理子の merge back を含む)を欠いた古い head が、無人で merge される。未 merge の PR は GitHub に残し、盤面は merge も close もしない。
4. **死んだ・handoff だけ・透明の区別は、読むときに記録から導く**(ADR 0380 決定1)。ADR 0375 決定7 が終わりの記録を2つに分けた理由
   (「内容が失われた」と「運ぶものが無かった」を同じ記録にしない)は、失われた sha と作成時の sha が記録に在るので、導出で保てる。

ADR 0397 は、この ADR が全部置き換える(終わりを書く判定、受理と収束の2人の書き手、決定4 の順序)。ADR 0375 決定7 の「専用の記録」と
決定8・9 の「終わった根に」は、決定1・2 の形で読む。

## 退けた形

- **失われた根の全種類に終わりの記録を定め、merge の扉と回答ごとに検査を置く**(この grilling の前半の案)—— 種類5つ・扉6つ・書き手の
  順序の規則が並び、どれも「失われた event が効いているか」の写しだった。
- **終わりを書く判定の手前に、透明な根と PR の根の分岐を足す** —— 同じ列挙の漏れを3度塞いだ後の4度目になる。

## 帰結

- 画面の「ブランチを失って終了」は、終わりの記録でなく、効いている失われた event を持つ死んだ(透明でない)`done` の work に出す。根かどうかは
  問わないので、merge back が届かないまま失われた子にも出る。handoff だけの task と透明な task には出さない —— 成果は失われていない。
  PR の決着の記録がある根は、今どおり決着が先に出る(ADR 0265 決定7 に追記)。
- 記録だけを信じるので、「諦める」が記録を書いた後・git を書く前に落ちると、ref が無傷でも着地が終わったと読まれる(#3624)。その影響は
  PR の根にも及ぶ。倒れる向きは「merge しない」で、PR は GitHub に残る。
- 失われた tip が push 済みで PR の head が GitHub に残っていても、取りに行く先から object が消えていれば、着地は終わる。人間は GitHub 上で
  merge できる。直す場所は取り戻す側(ADR 0380 決定4)で、#3724 に送った。
- 確かめていない: キューの行を取り下げた後に人間が GitHub 上で残った PR を merge した場合、盤面がその merge を観測する経路が残るか。本物の GitHub が、branch を消した後の
  sha 指定の fetch に応じるか(ADR 0380 帰結のまま)。
- 失われていない `done` の子が、失われて透明な親の下で着地の根になる場合は、この ADR の範囲に入れていない(#3723)。
