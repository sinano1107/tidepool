# リフレッシュ未完了/失敗のマーカーが付いた /usage 画面は信頼できない観測 — parseUsage がゲートで観測不能へ畳む

`/usage` パネルの描画は**2段**である: まずこの端末に永続化された最終既知値(seed)が描かれ、その後サーバーリフレッシュが上書きする(issue #287 の (b) 判定の再検証、2026-08-14)。ADR 0074 の quiet debounce とタイムアウト安全床は「画面が描き終わったか」しか見ておらず「その画面がリフレッシュ後か」を見ていないため、slow refresh・リフレッシュ失敗・rate limit の画面では端末ローカルの stale 値がアカウント全体の真値の顔で最終観測になる(fail-open — 被害上限は次の成功スクレイプまでの1サイクル)。そこで **parseUsage にマーカーゲートを足す**: 合成後画面に `Refreshing…` / `Showing last-known usage` / `could not refresh` / `Failed to load usage data` / `(rate limited` のいずれかがあれば、スナップショット**全体**(session / week / fable)を null 化し、既存の fail-closed に乗せる(issue #334 の grilling、2026-08-14)。

置き場所がパーサなのは ADR 0074 の分業(scraper は画面を観測し、parser はテキストを読む)どおりマーカー検査がテキスト読みそのものだからで、本番の parseUsage 呼び出しは1箇所しかなく、ADR 0074 のタイムアウト安全床経路も合成→パースを通るため自動的に被覆される — scraper は無変更。効果範囲が全体なのは、リフレッシュがパネル一括の HTTP 1本でありウィンドウ別の鮮度という粒度が画面に存在しないから。ADR 0076 の idle 3分法そのものは変えない — ゲートが先に評価されるため、seed 由来の「0% + Resets なし」画面が idle=available を誤発火する経路は一括で閉じる。

Considered options:

- **debounce 延長で `Refreshing…` の消滅を待つ**(slow refresh を成功観測へ変換)— 失敗マーカーは待っても消えないためゲートは結局必須。Pi 実測ではリフレッシュは 2s 静穏内に完了しており slow refresh は稀、失うのは回復可能な1サイクルで fail-closed の既存の交換と同型。画面内容依存の状態を scraper に足す複雑さに見合わない。
- **ウィンドウ単位の null 化** — 存在しない粒度の発明。
- **発火マーカーの記録・可視化** — v1 は素の null。恒常的リフレッシュ失敗のうち認証原因は ADR 0077 の経路(使用量 null → 確定プローブ1発)が正しく人間に見せる。非認証の恒常失敗は未観測の痛みであり、痛みが出たら広げる。「区別しない」は本 ADR が明示的に選んだ判断である。

Consequences:

- **受け入れた残余は3つ。**(1) seed 描画後〜マーカー初描画前の1ティックに debounce が挟まる理論上の窓 — seed とインジケータは間にネットワークを挟まない連続ローカル描画(Pi 実測の再描画間隔 200〜500ms)で、2s debounce(実測最大の4倍)が間に落ちることは実質ない。(2) マーカー文字列の変更はゲートが**黙って外れる**(fail-open 方向)— ラベル変更が fail-closed に倒れるのと非対称で、ADR 0076 の3分法が持つ自己制限性はこのゲートには無い。外れた姿は今日の挙動そのものであり、被害上限(1サイクル + ペース線 + 100% キャップ)も同一。従来どおりスクレイパー破損イベントとして直す。(3) ゲート発火サイクル中、`windows.fable = null` は UI 上「個別制限の観測なし(Pro プラン)」の顔になる — session / week の観測不能表示が支配的な画面での化粧上のノイズとして受け入れる。
- マーカー文字列は CLI バージョン依存。CLI バンドル 2.1.232 の実読が根拠で、`Refreshing…` は 2.1.221(Pi)/ 2.1.232 の両キャプチャで確認済み。失敗系マーカーの 2.1.221 での実在は決定時点で未確認(Pi がオフライン)— 実装時にバンドルを grep で確認し、違えばリストを両版対応に広げる。
- テストの形: red fixture は**既存の生バイトフィクスチャの prefix cut**(新規素材不要 — `Refreshing…` 直後で切って合成すると「stale seed 65% + `Refreshing…`」画面になり現行パーサが最終観測として読むことを実測確認済み)。合成→パース経路を通すので ADR 0074 の生バイト原則どおり。失敗マーカー3種は実キャプチャが存在しないため合成後画面テキストへの文字列挿入(synthetic)で足す — 生バイト原則の目的である差分描画の再現性は prefix cut 側が本物で踏み、失敗マーカーのテストが検査するのはパーサのテキスト述語そのものなので、逸脱は検査対象を過不足なく覆う。既存の緑は無傷(フルキャプチャの合成後最終画面にはマーカーが一切残らないことを実測確認済み)。
- ADR 0074 の安全床の refinement: タイムアウト時パネルマーカー描画済みでも、リフレッシュ未完了/失敗マーカーがあれば fail-closed。床の趣旨は「再描画が止まらない入力での全体 fail-closed 退行の防止」であり、マーカー付き画面は再描画 churn ではなく信頼できない観測。
- 実装は issue #334。

## 追記: `(rate limited` はマーカーではなかった(2026-08-25、issue #492)

**全体ゲートのマーカー一覧から `(rate limited` を落とす。** 本文が実装時に課した「バンドルを grep で確認し、違えばリストを両版対応に広げる」を実行した結果、答えは広げるのではなく**狭める**ことだった。CLI バンドル(Pi の 2.1.221 と手元の 2.1.239 / 2.1.241 / 2.1.243 / 2.1.245 で同一)の実読で `(rate limited` の出現は2箇所しかなく、seed 全体が stale な変種は**必ず `Showing last-known usage` を伴う**。伴わないほうは `Per-model breakdown unavailable (rate limited — try again in a moment)` — per-model の内訳だけが取れなかった局所の一行で、同じ画面の session / week は端末ローカルの最終既知値ではなく**サーバー由来(直前レスポンスのヘッダ)の値**で描かれている。鮮度そのものは保証されない — headers seed が古い可能性は本文の被害上限(1サイクル + ペース線 + 100% キャップ)が受ける、受け入れた残余である。それを全体 null 化するのは、本文が退けた fail-open の逆側の誤りであり、本番 Pi を永続 fail-closed に落とした(issue #492 に実機画面と再現)。

残りの4つが揃って言っているのは**「端末ローカルの persisted seed がそのまま画面に出ている」**の一点で、`(rate limited` だけがそこから外れた唯一の項目だった。ゲートの粒度(画面全体)も置き場所(パーサ)も変えない — ADR 0030 の「per-model 行の不在は fail-closed の入力ではない」と同じ扱いに戻すだけである。

あわせて、受け入れた残余(2)「マーカー文字列の変更はゲートが黙って外れる」の実例が観測された: CLI の非 rate-limit 版は大文字の `Could not refresh usage data` で、小文字始まりの `could not refresh` には**今日すでに一致していない**。これも headers seed(サーバー由来の数字)側なので読む側に倒すのが正しく、直さない。
