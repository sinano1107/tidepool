# Subagentは労力の分割であって委譲ではない — 盤面はauthorityダイヤルを持たない

ハーネス(Claude Code等)内蔵のsubagent機能と盤面のdecomposeは、どちらも「分業」を解いており適用対象が重複して見える。両者は**説明責任の分割線**で区別する: decomposeは説明責任の分割であり、独立した完了基準・assigneeとauthority・risk・セッションを跨ぐ生存を持つ単位を生む。subagentは説明責任を分割しない労力の分割であり、同一セッション・同一slot・同一watchdog・同一タスクブランチの内側で走り、成果は親タスクの完了基準と完了時レビューに全部吸収される — 盤面から見て親エージェント本人の作業と区別されない(grepの並列版と同じ「思考の一部」)。

この線から2つの帰結が出る。第一に、registryの別エージェントをsubagentとして呼ぶことはカテゴリとして禁止 — registryエージェントの身元はauthority profileと不可分であり、subagent呼び出しは「別ワーカーの能力だけ借りて説明責任は親のまま」という身元と責任の分離になる。別ワーカーの能力が必要ならdecompose + `assignable_to`が既存の道。subagentに使えるのは盤面上の身元を持たないハーネスユーティリティ型のみ。第二に、盤面はsubagent利用を機械的に制御するauthorityダイヤルを**持たない**。`assignable_to`が委譲(説明責任の分割)を機械強制するのに対し、subagentはワーカー内部の道具でありauthorityの対象外。統治は規律の散文 + 監査で行う: 「説明責任を分割する作業をsubagentに流すことは盤面を素通りする委譲の密輸であり、decomposeせよ」という盤面教義をadapterがspawn時に全ワーカーへ注入し(全ワーカー共通の教義をregistryの各profileに複写するとdriftする。かつ「Agentツール」という具体語はvendor知識でありADR 0005に従いadapterが盤面の線をClaude Code語に翻訳する)、違反はstream-json監査ログ + 完了時レビュー + meta-reviewが捕捉する。

同じ線から第三の帰結が出る: ハーネス内蔵のオーケストレーション機能(Claude Code の Workflow ツール等)は **worker にはカテゴリ禁止**。Workflow は曖昧な要求を自律分割する装置ではなく、呼び出し側が事前に書く決定論的スクリプト(分割・検証・統合の計画の明示的な記述)であり、それが書けている時点で分割の判断は既に済んでいる — つまり workflow スクリプトとは **decision log に載らない decompose 計画**そのものであり、成果物が親に吸収可能かどうかに関わらず、盤面が統治対象として主張する行為(decompose は decision log に記録される1つの判断であり、統合復帰までがタスクモデル)を盤面の外で実行する。説明責任の分割そのもの。Agent ツール(親のターンごとの判断の内側で走る単発・並列の labor helper)との線は**規模ではなくオーケストレーションの有無**で引く — 「何並列から密輸か」という問いは発生しない。この禁止は「乱用が観測されてから絞る」方針(上記)と矛盾しない: 労力分割ツールへの予防ダイヤルではなく、registry エージェントの subagent 呼び出し禁止と同じ、線の向こう側に落ちるもののカテゴリ禁止である。

禁止の主体は worker に限る。盤面自身(Tidepool 名義)や人間が自らの機構としてオーケストレーションを使うこと — 例えば将来のレビュー層(issue #15)を多エージェント検証で実装すること — は線の外である: その分割の判断は盤面の上で行われるため密輸にならない。これは vendor 自身の先例とも同型(Claude Code の ultrareview は user-triggered / billed で、モデル自身には起動権がない。通常の Workflow 呼び出しも呼び出しごとの明示的な人間の opt-in を要求する — headless の worker セッションにはその人間がいない)。副次的な補強が2つ: (a) workflow は throttle の観測ループ(pickup 時 JIT、実行中タスクには決して触れない)を1タスク内で追い越して不可逆な予算を燃やせる加速装置であり、fail-closed の哲学(ADR 0008)とも整合する。(b) vendor 契約上も workflow は呼び出しごとの明示的な人間の opt-in を要求する機能であり、headless セッションにはその人間がいない — 禁止は盤面が standing opt-in を与えないという不作為でもある。enforcement は spawn 時のツール無効化フラグ + 注入教義への1行(issue #31)。

Considered options:

- **粗いon/offダイヤル(authority profileに真偽値、adapterがAgentツール無効化フラグに変換)** — 唯一機械的に強制可能な粒度だが、封じたい実害がまだ観測されていない。乱用パターンがmeta-reviewで実際に観測されたときに初めて足す(mergeダイヤルと同じ「absent is inert」の育ち方)。
- **ユーティリティ型のallowlist** — 「どのagentをsubagentに使えるかをtidepoolから管理する」という当初構想に最も近いが、列挙対象がvendor固有の型名になりvendor知識がregistryに漏れる(ADR 0005の緊張)。ユーティリティ間の差が説明責任上の差を生まない以上、盤面が区別する根拠も薄い。
- **全面無効化** — 線の運用を信用できるまで封じる案。探索subagentによる文脈管理(大量のファイルを読んで要約だけ返す)まで失い、長いタスクで親セッションの文脈消費が悪化する副作用がある。
- **判断の有無で線を引く(判断を含む作業はすべてタスク化、subagentは検索・要約のみ)** — 親エージェント自身がセッション内で無数のミクロ判断をしており(decision logに載るのは権限内判断の1行記録だけ)、subagentにのみ判断禁止を課す根拠が薄い。実際の関節で切っていない。
