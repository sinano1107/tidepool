# 要求の学習の宛先は task の文面の書き手であり、分解判断に乗る task ではその分解判断の書き手である

2026-10-05 の grilling(issue #1358、発端は #1357)で決定。ADR 0194 決定1 で登録者は「その task の存在を決めた判断の主」になり、
文面を書いた者とは限らなくなった。retrospective は登録者を文面の書き手の代わりに読み続けており、承認で実体化した子
(登録者は human、文面は分解した agent が書いた)への `task_ambiguity` は宛先が無く学習されない。ADR 0194 による悪化では
なく、承認で実体化した子が human 名義だった以前からの挙動である。登録ごとの宛先の表は #1358 に置く。

## 決定

1. **要求の学習の宛先は、登録者ではなく task の文面の書き手である。** 曖昧な文面を直せるのはそれを書いた者だけで、存在を
   認めた者ではない。ADR 0115 決定4 の `task_ambiguity` と `missing_information`(Behavior)の「宛先は登録者」、ADR 0164
   決定2 の「登録者が人間か盤面」を、この読みに改める。
2. **文面の書き手は、`based_on_decision` が指す分解判断の書き手、無ければ登録者である。** 承認で実体化した子は、元の分解判断を
   approve を越えて持ち越している。approve には文面を直す手段が無い(reject しか無い)ので、文面は分解した agent が書いたまま
   である。前提の破綻が「分解判断の書き手」を同じ記録から引いている(ADR 0121)ので、新しい列も印も要らない。変わるのは承認で
   実体化した子だけで、人間 decompose の子は分解判断の書き手が human なので今と同じく起草しない。
3. **盤面が書いた文面(RCA review・完了時レビュー・meta-review)への `task_ambiguity` は今のまま起草しない。** これらは分解判断に
   乗らず、文面の書き手は盤面である。盤面のテンプレートはコードなので、直すなら issue で直す。
4. **登録者 agent が task に書く申告(ティア・reviewer 指名)の学習も、同じく文面の書き手に宛てる。** 承認で実体化した子の
   申告も分解した agent が書いた。#584 の「登録者 agent」はこの読みで実装する。

## 退けた案

- **登録者のまま、ADR 0194 の後は「存在を決めた主が要求を渡し損ねた」と読み替える** —— 承認で実体化した子の曖昧さは、
  直せる者のいない human に宛たり、どこにも学習されない。
- **承認 question の登録者で書き手を引く** —— 実体化した子は承認 question への参照を持たない。`based_on_decision` は
  既に持ち越されており、承認を経ない子にもそのまま当たる。
- **申告の学習は #584 の grilling に回す** —— 同じ語が2つの読みで残り、#584 が字面どおり実装すると承認で実体化した子の
  申告が human に宛たる。
