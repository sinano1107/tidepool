# 登録の門は着地先とその出所を見せる — 配備の事実はソースコメントに書かない

issue #305 のグリリング(2026-08-15)で決定。ADR 0052 の実環境動作確認 第3段の準備で、Pi の
`/etc/default/tidepool` に `TIDEPOOL_WORKSPACES_DIR` が無いまま `clone` モードの登録直前まで進んでいたことが
見つかった。登録していれば checkout は SD カード側の既定 `~/tidepool-workspaces/<name>` に落ち、#205 未実装のため
盤面からは戻せなかった。止めたのは実験の準備で前提を1つずつ確かめていた人間であって、機構ではない。

## 破れの形 — エントリに書かないことと、人間に見せないことは別

ADR 0018 は `clone` / `create` モードのエントリから `path` を消し、着地先を「基点 + 名前」の規約導出にした。
エントリはホスト非依存になったが、その帰結として**登録の門は着地先を人間に一度も見せずに決める**ようになった。
`register` モードは人間がパスを打つので見えている — 見えていないのは規約導出の2モードだけ、という非対称である。
ADR 0040 のガード(盤面自身の状態パスとの交差)は正しく素通りする位置にあり、この穴を塞ぐものではない。

もう1つ、`src/workspace.ts` のコメントが「Pi の unit は `/mnt/ssd/tidepool-workspaces` を設定している」と
配備の事実を主張していたが、unit はそれを設定しておらず、直した後の値も別(`/mnt/workspaces`)だった。
ソースが配備の事実を主張すると、配備が変わるたびに黙って嘘になる。

## 決定

1. **登録の門(WebUI のフォーム、management MCP の `create_workspace`)は、規約導出モードの着地先を決定の瞬間に見せる。**
   WebUI は名前を打った時点で `will clone to <base>/<name>` を出す。基点は workspaces 一覧の読み口
   (`GET /api/workspaces` / `list_workspaces`)が一覧の属性として返し、client が `<base>/<name>` を合成する
   — 規約は「基点と名前の結合」の1本で名前は区切り文字を含まないから、これは解決の複製ではなく表示である。
   ADR 0018 の「解決は1点で」は実行の話であり、プレビューには及ばない。MCP は1回の呼び出しで登録まで進むため
   「見せてから決める」形が無い — 一覧が基点を返すことと、`create_workspace` の結果に着地したパスを返すことで代える。
2. **着地先には出所を添える。** `TIDEPOOL_WORKSPACES_DIR` 未設定時は「既定であり未設定である」ことを同じ行で言う。
   既定値は開発機で正当なので未設定を拒否も警告もしないが、パスだけ見せると「意図した設定」と「未設定の既定」は
   区別できず、規約導出のエントリが1つも無い間は誰も気づけない性質が残る。出所を言うことで初めて閉じる。
3. **規約導出の既存エントリも、一覧の行で着地先を見せる**(明示 `path` と混同しない別の1行)。門と同じ理由。
4. **配備の事実はソースコメントに書かない。** ソースは「既定は開発機の値、本番ホストは設定する」までを言い、
   Pi の値は deploy-pi skill(first-time-setup の `/etc/default/tidepool` 雛形)だけが持つ。
5. **`verify-deploy.sh` が `/etc/default/tidepool` の必須キーの存在を検査する。** 対象は「無いと盤面が黙って
   別の挙動になるキー」に限る — `TIDEPOOL_WORKSPACES_DIR` / `TIDEPOOL_PUBLIC_ORIGINS` / `TIDEPOOL_GITHUB_TOKEN_FILE` /
   `TIDEPOOL_REGISTRY` / `TIDEPOOL_DB` / `TIDEPOOL_WORKER_LOGS`。雛形だけ直しても実ファイルとの乖離は誰も検出しない
   (発見時点で既に2キー乖離していた)。`TIDEPOOL_AUDITOR` は雛形にだけ足す — 無くても既定(監査なし)で動く選択肢
   であり必須ではない。

## 退けた案

- **未設定のホストで規約導出モードの登録を拒否する / 起動時に警告する** — 既定は開発機で正当であり拒否は行き過ぎ、
  起動警告は決定の瞬間から遠く誰も読まない。決定2の「出所を見せる」で足りる。
- **プレビュー専用の口を server に持つ** — 表示のために解決点を増やす価値が無い。基点は一覧の属性として返す。
- **verify-deploy が「規約導出の workspace が registry にあるのに基点が未設定」を検査する** — 決定2が人間面で同じ穴を
  塞ぐので二重、かつ verify-deploy が registry の中身を読み始めるのは役割の拡張。
- **settings に基点の持続行を置く** — 基点が変わる頻度はゼロに近く、フォームのプレビューで同じ事実が読める。
