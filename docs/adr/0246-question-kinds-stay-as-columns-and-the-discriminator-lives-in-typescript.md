# question の種類は表の列のまま、判別子は TS に置く

2026-10-13 の grilling(issue #1895)で決定。`tasks` には question の種類ごとの system-internal 列が10本並び、種類は
「どの列が非 null か」で判別されている。列1つを足すと DDL・型・登録の入力・INSERT・fixture を書き写し、種類で分岐する
約11か所の更新漏れを tsc は教えない。門(#1879)の後は表の組み替えに migration が要るので、組み替えるかを門の前に決めた。
列ごとの書き手・読み手・分岐の箇所の実測は #1895 のコメントに置く。

## 決定

1. **表は組み替えない。** 種類別の列は今のまま残し、判別子の列も payload の列も足さない。種類で分岐する SQL の述語
   (着地・quarantine・CLI 認証の警告・abandon の範囲・親を塞ぐかの規則)は列を直接読むので、表に判別子を置いても
   分岐は減らない。痛みは TS 側にある。
2. **判別子は TS に置き、書く側と読む側の写しを1つのモジュールに対で持つ。** 書く側は種類ごとの payload を持つ union を
   受け取り、列へ写す —— 2つの種類の列を同時に書く道は型の上で無い。読む側は列から種類を導き、TS の分岐はその種類への
   網羅的な switch にする。種類を足す作業は union・DDL の列・写しの2本の腕に縮み、残る分岐は tsc が指す。`Task` の
   平らな欄と外へ出る形(JSON API・WebUI・管理 MCP)は変えない。
3. **どの種類にも当てはまらない列の組み合わせを読んだら、食い違う列を名指しして例外を投げる。** 書く側が union なので、
   この状態に届くのは写しの不具合か直接の SQL だけである。優先順位で黙って1つに決めると、abandon の範囲のような判断を
   別の種類のものとして下す。

## 退けた案

- **判別子の列と JSON の payload 1列に置き換える** —— 表の組み替えで門の前の作り直しを要し、SQL の述語が
  `json_extract` になって型の守りの外の範囲が広がる(`.out-of-scope/json-extract-payload-paths.md`)。TS で得られる
  網羅性は決定2 と同じ。
- **判別子の列だけ足し、種類別の列は残す** —— 足すだけで門の後でもできるが、判別子と埋まった列の食い違いという
  新しい状態が生まれ、どちらが正かを決める規則が要る。
- **種類ごとに別の表へ分ける** —— 列の型は保てるが、読み手の SQL が JOIN になり、これも表の組み替えである。
- **読む側だけに判別子を置く** —— 分岐の網羅性は得られるが、issue が観測した書き写しは減らない。
