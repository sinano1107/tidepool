# 通常完了の解放も回収済み観測を門とし、後始末は worker session の一部である

2026-09-09 の grilling(issue #531)で決定。ADR 0099 決定3 は slot の解放と再利用の前提を回収済み観測に置いたが、通常完了(`complete_task` / `decompose` / `escalate`)の解放だけがその門を通っておらず、final MCP call の中で同期に走っていた。穴の存在は既に記録に残っている —— ADR 0104 の実装は「回収済み観測を待つ間に session が自己申告して次のタスクが slot に入っていることがありうる」ことを前提に slot を再観測しており、通常経路が門を持たないことを局所的に自衛していた。現状調査・測定・実測ログは issue #531 のコメントに置く。

## 決定

1. **通常完了の解放も回収済み観測を門とする。** domain verb は final MCP call の中で同期に着地し、response はすぐ返る —— worker exit と回収済み観測を待つ循環待ちは作らない。workspace の解放(tree rule / merge-back / 休止位置)と slot の解放だけが回収済み観測の後ろへ移り、cap 中断・watchdog 強制回収と**1つの型**を共有する。ADR 0099 決定2 の「回収は再実装されない」がこの経路にも及ぶ。

2. **後始末(teardown)は worker session の一局面であり、session の終わりは root process の exit ではなく回収済み観測である。** slot を占めるのは task ではなく session であり、タスクが決着した後も後始末の間は session が握り続ける。`worker_exited` は root process の観測点として位置を変えない —— トークン消費はそこからしか取れず、session の終わりと観測点は別の瞬間でよい。後始末は**盤面全体の停止ではない**(止められるより狭い資源の話ですらなく、枠がまだ空いていないだけである)。ただし「今なぜ pickup が起きないか」に答える読み口は、停止の列挙と**並べて**後始末を報せる —— 「タスクは `done` なのに次が始まらない」は既存のどの語彙とも一致せず、説明が無ければ人間は古い停止と誤読する。

3. **完了経路では、後始末時に dirty なツリーは成果ではなく残存プロセスの露見である。** 完了の門(ADR 0084)が verb の手前で clean を要求している以上、そこに現れる変更は「done と報告した後に書かれたもの」でしかない。退避せず workspace quarantine に落とす —— WIP コミットにすれば次の行の merge-back がそれを祖先ブランチへ運ぶ。掛かる範囲は完了の門と同じ述語であり、review の完了・`escalate`・`decompose` は従来どおり退避する(タスクブランチに留まり merge-back しないので、失われるより残るほうが人間の修理材料になる)。

4. **root process の exit は、容器に残るものが孤児である証拠である。** 自己終了報告を観測した時点で盤面は強制回収を撃つ —— 行儀よく exit するのを待たない。ただしこれは**送達であって回収の完了ではなく**、ADR 0099 決定1 の語彙は不変である: 門は回収済み観測ただ1つで、後始末は依然としてその後ろでしか走らない。時限は「verb は着地したのに root が exit しない」だけを見る backstop に退き、そこから先は既存の梯子(強制回収 → 回収 timeout → Containment quarantine)がそのまま受ける。完了済み session がその梯子に落ちたときは failure question を立てない —— タスクの決着は host 側の事情で覆らない。

5. **後始末の未了は再起動をまたぐ事実である。** in-memory の callback は盤面の crash を越えないので未了は永続化し、起動時に容器機構の前提検査が「前の盤面のプロセスは残っていない」を証明してから残りを完走させる。issue #382 が sparse-checkout の復元で踏んだのと同じ形であり、理由も同じ —— 証明の前に進めば、生き残った process の居る workspace を盤面が書く。

6. **最終 verb の後に session が続かないことは機械の門が守り、protocol 文は補うだけである。** 追加 verb は門が拒み、ファイル書き込みは決定3 の検査が捕らえ、残存プロセスは決定4 が回収する。3つの verb の返り値に置く「即座にターンを終えよ」の一文が守るのはトークンだけで、不変条件は1つも預けない —— 締めのターンだけは機械で殺せないことが実測で確定しているからである(畳み込み停止は消費の報告を落とし、SIGINT は行こそ出すが全ゼロを記録する。issue #531)。

## Considered options

- **pickup の門だけを足し、解放は今のままにする** —— slot の再利用は止まるが、tree rule と merge-back は生存容器の中で走り続ける。守れるのが slot 側だけで、issue #382 が防御した重複と同じ根が残る。
- **最終 verb の着地と同時に強制回収する** —— 締めのターンを機械で殺せるが、消費の報告が届かず正常完了した全タスクが欠測に落ちる。畳み込み停止へ替えても同じで、信号を替えると今度は全ゼロが記録される(実測)。
- **完了経路の後始末でも dirty を WIP として退避する** —— 報告後に書かれたものが無検査で祖先ブランチへ入る。決定3 の門が守っているのは、まさにその1行先である。
- **後始末の未了を in-memory に留める** —— 完了した作業の着地が盤面の crash で静かに落ちる。静かであることが害で、失われる量ではない。

## 追記: 着地も後始末の中へ移り、再起動をまたいで完走する(#531 の実装中、2026-09-10)

決定1 は「workspace の解放と slot の解放だけが回収済み観測の後ろへ移る」と書いたが、実装すると**着地(PR 昇格 / merge)もその後ろへ移らざるを得なかった**。旧実装では `complete_task` の tool handler が slot 解放の直後に `landing.land` を撃っており(`src/mcp.ts:378`)、解放だけを後始末へ移すと着地が merge-back より**先に**走る。着地は帰り先を決めるために remote-tracking ref を読み、その ref を更新するのは merge-back 自身の fetch である。順序を保つには、着地も同じ後始末の中に置くしかない。

**枠を解放してから撃つ**という相対順序は旧実装のままである(変わったのは、その一組が回収済み観測の後ろへ移ったことだけ)。

この移設は2つの帰結を持ち、どちらも決定として引き受ける:

1. **完了と着地の間で盤面が落ちても、着地は失われない。** 後始末の未了は永続化されている(決定5)ので、起動時復旧が tree rule → merge-back → 休止位置 → slot 解放まで走らせた後、そのまま着地まで完走させる。旧実装では、この窓で crash したタスクの着地は二度と起きなかった —— 決定5 が「静かであることが害で、失われる量ではない」と言った穴が、着地にも開いていたことになる。

2. **着地の失敗は MCP の tool error ではなくなる。** 後始末の呼び口は全部 fire-and-forget なので、着地が投げても worker には届かない。届く先は既存の PR 昇格失敗 question であり(ADR 0092 / ADR 0106 の経路は不変)、そこへ落ちない想定外の例外だけが後始末の記録に残る。worker はどのみち最終 verb を撃った後で、着地の結果に対して打てる手を持たない。

決定1 の「解放だけ」という言い方はこの追記で広がるが、**門は変わらない** —— 回収済み観測ただ1つであり、着地もその後ろでしか走らない。
