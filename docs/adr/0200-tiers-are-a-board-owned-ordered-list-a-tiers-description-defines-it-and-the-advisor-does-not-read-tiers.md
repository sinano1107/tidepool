# ティアは盤面が持つ順序付きの段の一覧で、段の定義は説明が持ち、advisor は段を読まない

**Status 追記: 決定6 のフラグと「要るのは最上位だけ」は ADR 0208 で置き換え** —— advisor の上限は盤面設定の選択(`off` / `sonnet` / `opus` / `fable` / 窓で `opus` に下がる `fable`)で、既定は `off`。上限より上の main には advisor を付けず、adapter は系列ごとに「上限の alias が受ける世代の上限」を持つ。

2026-10-05 の triage / grilling(issue #1346)で決定。発端は、4段目(Haiku / Luna の帯)の再開条件が、記録されえない観測を
待っていたことである(#553 / ADR 0114 決定5)。問いは「段を固定の数にするか」に広がった。固定の3段のままだと、別の Provider が
飛び抜けたとき、登録者が新旧を書き分けるには行を段の間で動かすしかない。学習器のセルは段を持たないので、動かした行は元の段の
task で得た実績を移った先で数えられる。下ろした側の Provider からは frontier の行が消え、advisor・meta-review・振り返り
Board call が走れなくなる。段の名前を書いている配布物は tidepool 自身のコードだけだった(種の registry は1つも書いて
いない)。コードの照合は #1346 のコメントに置く。ADR 0110 決定2 の値域と決定3 の advisor の導出・検査、ADR 0114 決定4 の
advisor の行と決定5 を置き換える。

## 決定

1. **ティアは盤面が持つ順序付きの段の一覧である。** 種は3段(`economy` / `standard` / `frontier`)で、種の段と足した段に扱いの
   差は無い。段を足すのは、行を動かさずに新しい区別を作るためである。相対語(最下段・最上段)で段を指す規則は持たない ——
   盤面既定を「最下段」と書くと、下に段を足した瞬間に未指定の task が全部そこへ落ちる。
2. **段は盤面内部の id で同一とし、名前・説明・位置は編集できる。** ズレを起こすのは行を段の間で動かすことだけで、名前・説明・
   位置を変えても、行が付いたままなら実績は同じ行に数えられる。行・task の要求・盤面設定は id で段を指す。agent.md の `tier` は
   別のリポジトリなので名前で書き、改名は盤面が同じ操作で registry へ commit する(push の失敗は改名ごと成立しない —— ADR 0150
   決定5 と同じ扉)。削除できるのは、行が無く、設定から指されず、未決着の task が要求していない段だけ。編集面は settings タブと
   管理MCP の両方である。
3. **段ごとに1行の説明を必須にし、文面の書き手には「名前 — 説明」を順序どおりに見せる。** 説明は「1つ下の段では足りず、この段
   なら足りる仕事」を書く。種の3段の説明は配布物が持ち、編集画面は隣の段の説明を並べて見せる。
4. **コードが段の名前で固定していた箇所は、盤面設定が段を指す。** 盤面既定(種は `economy`)。下書きは盤面既定の段を読む
   (ADR 0192 決定1 の「コードに固定」を置き換える)。振り返り Board call と周期 meta-review は1つの設定を共有する(種は
   `frontier`。ADR 0111 追記4 の「未設定は frontier」と ADR 0150 決定7 を置き換える)。段の順序を読む規則は、agent の既定
   `tier` の「1段下」だけになる。
5. **表の主キーは (provider, model, effort) で、1つの段に同じ model は1行までである。** 行は (model, effort) の組の分類で
   (ADR 0192 決定1)、学習器のセルも Interview の対象も effort を持っていた。1つの組が属する段は1つである。同じ段の中の effort の
   比較は Interview が担い(ADR 0199 決定5)、同額の並びに3つ目の鍵は足さない。行の Quarantine の鍵は (provider, model) のまま。
6. **advisor は段を読まない。** 組み合わせの可否は Provider の序列が決める。序列は model だけに付き、運用者が並べる段((model,
   effort) の分類)からは導けない。フラグが立っていれば advisor は Provider の最上位の系列の alias(anthropic は `fable`)、
   立っていなければ main と同一である。advisor を宣言できるのは、正準経路が相談機構を持つ Provider の entry だけで(いまは anthropic
   だけ —— ADR 0097 決定3)、最上位の系列を持つのもその Provider だけである。alias にするのは、advisor が行でなく、分類も価格も持たないからである(ADR 0182 の理由が
   当たらない)。具体 id にすると、世代のたびに advisor つきの全セルが数え直しになる。main が最上位の系列の行のときは、advisor を
   main と同一の具体 id にする —— 行と alias は別々の時に進み、alias の指す世代が main より古いと黙って付かない。adapter は
   知っている系列の prefix の一覧を持ち、知らない系列の行は advisor を有効にした entry の候補にしない(付かない advisor を
   記録とセルに残さない)。ティアの水準の検査は導出に畳まれて消える。advisor は行でないので、行の Quarantine を見ない
   (ADR 0184 決定2 の「advisor の導出からも外れる」を置き換える)。
7. **段の定義は説明が持ち、申告のズレは routing meta-review が説明の書き換えとして提案する。** 根拠は、床を決めたのが task の
   申告だった配分評価で、書き手が人間でも数える(ADR 0111 追記2 の「`task` は読み物のみ」を置き換える)。pin は説明のいまの
   文面、承認の修正値は文面である。特定の workspace や書き手に偏った申告の癖は Behavior のまま残す —— 説明は盤面全体に1行で、
   宛先も scope も持てない(ADR 0197 決定4 は変えない。入力の問いは #584)。Behavior の起草側と memory meta-review の
   プロンプトに「段の定義を Behavior に書かない」を足し、検査は置かない。
8. **routing meta-review は「段を足して行を移す」を提案できる。** 同じ段の行どうしで結果が分かれ、合う段が無いときである。
   名前・説明・位置は根拠の episode から起草でき、承認の修正値になる(行の追加と違い、人間にしか書けない欄が無い)。pin は移す
   行の全欄と隣の段。順序の提案は足さない —— 段をまたいだ episode は申告された仕事が違い、順序の根拠にならない。
9. **4段目の帯は worker への要求としてだけ扱い、再開条件を Interview での実測に置き換える(#1415)。** 翻訳の都合で段は足さない。
   結果ごとの帰結は #1415 に置く。運用者が自分の盤面に段を足すことは、実測を待たない。表示時翻訳は alias `haiku` のまま残し
   (ADR 0192 決定4)、見直しの条件は #1415 に移す。

## 帰結

- 行を段の間で動かすと実績が段をまたいで数えられる。既存の行の提案(ADR 0150)にも決定8 にも当たり、#1414 で決める。
- 改名の直後、走っている session は古い名前を書きうる。未知の段として拒まれ、エラーがいまの一覧を返す。承認済みの Behavior の
  散文が古い名前に触れていても、盤面は追わない。
- 新しい最上位の系列が出ると、tidepool の release が adapter を直すまで、advisor を有効にした agent はその行で走れない。
- 種の表は、Sol が主力と廉価を effort で受け持つ形(`/implementation-delegation` §5)を写せるようになる(#1416)。

## 退けた案

- **固定の3段のまま、飛び抜けた model を frontier に並べる** —— 学習はズレないが、登録者が新旧を書き分けられない。
- **固定の段を release で増やす** —— 足した段を埋める Provider を使わない盤面では穴になり、足せるのも release のあとになる。
- **種の3段だけ名前を固定で残す** —— 根拠にした「配布物が書く綴り」が無かった。扱いの違う段が2種類できる。
- **段の名前を不変にする** —— 参照を id で持てば理由が消え、説明だけ編集できる線に根拠が無い。
- **ティア申告の学習を Behavior から全部外す** —— 特定の workspace や書き手に限った規則の置き場が無くなる。
- **advisor の序列を行の欄に書かせる / 運用者に advisor の行を名指させる** —— Provider の定義の写し間違いが、黙った未 attach に
  なる。**model ごとの序列の表を adapter に持つ** —— 要るのは最上位だけである。**いつも alias を渡す** —— 決定6。
- **VM の隔離盤面に economy の行として置いて測る** —— 採点の伏せ方も観測の数え方も Interview と別物になる。

## 追記(2026-10-05、issue #1421 の実装)

- **段の削除は論理削除である。** 決着済みの task は要求した段を id で指したままで、その task 行が要求の唯一の記録である(`task_registered` は段を持たない)。物理的に消すと FK に当たるか、記録を NULL で失う。削除は段を一覧から外す(`position` を NULL にする)。名前の一意は生きている段どうしで見るので、消した名前で段を足し直せる。決定2 の削除条件(行・設定・未決着の task)は変えない。
- **決定4 の「1つの設定」の名前は `judgement_tier` である。** 旧い名前 `retrospective_tier` は振り返り Board call だけを指すように読めた。周期 meta-review も同じ設定を読むので改めた。未公表なので旧い綴りは残さない。

## 追記(2026-10-06、issue #1431 の grilling)

- **決定2 の削除条件に「registry の agent.md の `tier` が名指していない」を足す。** 前の追記の「決定2 の削除条件は変えない」はこれで改める。agent.md は行・設定・未決着の task と同じく、段を消すと壊れる側にある —— 名指した agent の定義は未知の段として拒まれ、盤面既定の agent なら assignee の無い work が修理まで拾われない。壊れることは削除の時点で分かるので、pickup の Quarantine で直させず、削除の扉が agent 名を並べて断る。組み込み agent は `tier` を持たないので数えない(改名と同じ)。
- **読むのは手元の clone で、fetch しない。** 削除は registry に書かないので、書き込みの入口の refresh(ADR 0052 決定2)に当たらない。盤面自身の agent.md の書き込みは書く前に段を検査し、着地すれば clone に入るので全部見える。見落とすのは未取得の外部 commit だけで、削除の直後に外から書かれるものと同じく pickup の Quarantine が受ける。registry の無い盤面は照合しない。clone を読めなければ削除ごと断る —— 照合を飛ばす `settleStaleProposals` の線は poll で pickup を止めないためのもので、人間の撃つ削除には当たらない。
- **退けた案**: 移し先の段を持たせて agent.md を書き換えてから消す —— ほかの3条件は移し先を持たず、削除が registry への書き込みになる。改名と同じく fetch してから読む —— refresh 点が増え、拾える分は削除の直後の外部 commit と区別できない。
- 盤面の agent の書き込みの push が着地する前に削除が通る狭い競合は残す(改名の着地と transaction の間の競合と同じ種類)。

## 追記(2026-10-07、issue #1521 の grilling)

- **決定6 の「知っている系列」に、advisor を受けられない行を足す。** advisor を有効にした entry の候補から、次の行も外す
  (行は表に残り、advisor の無い entry の候補のままで、Quarantine もしない)。
  - **main として advisor を受けない世代の行**(Sonnet / Opus の 4.6 未満)。フラグに関係なく外す —— advisor が何であっても
    CLI が起動時に断る。
  - **advisor になれない系列の行**(Haiku)。フラグが無いときだけ外す —— advisor が main と同一になり、CLI が起動時に断る。
    フラグが立てば `fable` が付くので外さない。
  adapter は系列ごとに「main として advisor を受ける最小の世代」と「advisor になれるか」を持つ。序列ではないので、退けた案
  「model ごとの序列の表」は退けたままである。実測と導出の表は #1521 のコメントに置く。
- **ADR 0042 が退けた「ペアリング表を adapter に持つ」には当たらない。** 0042 が退けたのは、ホストの CLI 版で解決先が動く alias
  を表で judge することだった。ここで読むのは行の具体 id(ADR 0182)で、知るのは過去の世代について閉じた事実である。
- **帰結**: Haiku の新しい世代が advisor になれても、release が adapter を直すまで外れたままになる(安全な側に外れる)。
  Sonnet / Opus の新しい世代は下限より上なので、そのまま候補になる。フラグの無い盤面では、advisor を有効にした agent は Haiku の
  行を選べず、#1415 の Interview でも同じく対象から外れる。
- **退けた案**: Haiku の行にはフラグに関係なく `fable` を付ける —— フラグを立てていない運用者に main より上の消費を黙って足し、
  「いつも alias を渡す」を一部戻す。予測せず失敗 question に任せる —— pin は pickup ごとに決定論で選び直されるので、`retry`
  のたびに同じ pin で落ちる(Haiku は最安なので `cost` の優先では常に先頭)。起動時の拒否を観測して受ける —— stdout は空で、
  盤面は stderr で判定しない(ADR 0188)。同意の未了や `availableModels` の除外も同じ理由で失敗 question のまま残す(ADR 0184 の
  「報告なき exit」の線)。advisor の上限を運用者が選ぶ問いは #1538 に分けた。
