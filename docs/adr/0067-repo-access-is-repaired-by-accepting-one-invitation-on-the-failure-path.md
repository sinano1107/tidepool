# repo アクセスは、到達に失敗した瞬間に招待1枚を受諾して直す

**Status 追記: 修復の形は [ADR 0093](0093-the-boards-github-identity-is-one-app-and-a-token-broker-mints-per-repo-tokens.md) で「招待1枚の受諾」から「App を repo に install する」に置き換わった(2026-08-21)。** 決定2(ループは作らない・3つの扉)、決定3(「書けるか」)、決定5〜8 の線は生きている。受諾の seam(決定1)と `viewerPermission` の probe・`gh api user` の観測(決定4)は installation token では動かず、仲介の発行成否に代わる。

issue #213 のグリリング(2026-08-12)で決定。#209 の machine user 対応から派生し、#212 / ADR 0066(所有権と作成経路)とは独立 — org を採っても採らなくても要る。

盤面は GitHub に触れるとき常に tidepool-bot 名義で撃つ(ADR 0024)。したがって外部の repo を workspace として取り込むには、その repo に tidepool-bot のアクセスが要る。今日は `clone` モードが `authedGit(... "clone" ...)` で落ちるだけで、人間には git の生のエラーしか見えず、**何をすれば直るのかが示されない。**

**自動付与はしない。** collaborator の追加にはその repo の admin が要る。tidepool-bot に人間のリポジトリの admin を渡すと、盤面の到達範囲が「1つの machine user が書ける範囲」から「人間のリポジトリを再構成できる範囲」へ広がり、ADR 0024 が身元を境界にした設計と衝突する。加えて、bot が任意の repo に自分を追加できるならその付与はアクセス制御を表していない。

## 実測で確定した事実(すべて Pi 上の本物のボットトークンで)

issue #213 本文の「検証済み」は**人間のトークン**(`sinano1107`)での確認だった。ボットトークンで撃ち直した結果:

1. **トークンは classic PAT、scopes は `repo, workflow`、名義は `tidepool-bot`。** ADR 0024 が実装時に決めると保留した PAT 種別は、実物としては classic である。
2. **`GET /user/repository_invitations` はボットトークンで 200 を返す。**
3. **`PATCH /user/repository_invitations/<id>` は 204 で通る。** 受諾後 `viewerPermission` は `WRITE`、clone も push も成功し、受信箱は `[]` に戻る(受諾済みは消えるので、受諾は冪等に扱える)。
4. **`read` で招待されると、受諾も clone も成功し、`push` だけが後から 403 になる。** `viewerPermission` は `READ`。失敗が PR 昇格という遠い場所に出る形であり、ADR 0052 が名指しで拒否した症状そのものである。
5. **`gh repo view --json viewerPermission` は書き込み権限を直接読める。** 招待オブジェクトの `permissions` を読むより強い — repo 側の事実であって、招待が存在しないケース(すでに read の collaborator)も同じ問いで捕まる。
6. **すでに collaborator である相手への `PUT .../collaborators/<login> -f permission=push` は 204 で即時に権限を上げ、新しい招待を作らない。** したがって提示する一行コマンドは1つで両方の状況を直す — 未 collaborator なら招待が出て、READ の collaborator なら即時昇格する。
7. **アクセスの無い repo と存在しない repo は、`gh` も `git` も文言が完全に同一である**(`Could not resolve to a Repository` / `Repository not found.`)。probe は両者を区別できない。

## 決定

### 1. seam は1つの関数 — 「この repo 宛ての招待を受諾し、権限を返す」

`owner/repo` を受け、(a) 自分宛ての pending 招待のうち **その repo のもの**だけを受諾し、(b) `viewerPermission` を返す。**招待の掃除はしない。** 盤面は受信箱を揃える主体ではなく、今進めたい一歩のために1枚を受ける。

範囲を「いま到達したい repo」に絞るのは、任意の第三者からの招待を無条件に受ければ、盤面の到達範囲が盤面の知らない理由で黙って広がるからである。registry が知っている repo に絞る案は、**登録の門ではその repo がまだ registry に無い**ため clone モードを救えず、併用が要る。「いま到達したい repo」は3つの扉すべてで同じ規則がそのまま効く唯一の線である。

照合には URL から `owner/repo` を取り出す関数が要り、それがそのまま「**これは github.com か**」の門になる。ADR 0052 が拒んだのは URL の**綴りの照合**(ssh / https / ホスト名の別名を別物と読む誤検出)であって、owner/name の抽出は exact な操作なのでその族ではない。非 GitHub の remote(`clone` の入力欄は「anything git clone accepts」)では probe も受諾も発火せず、今日の生エラーのままである。

### 2. ループは作らない — 呼ばれるのは失敗経路だけ

issue #213 は「pickup ゲートに足すのか、probe 失敗中だけのポーリングか」と二択で問うたが、答えは**どちらでもない**。

| 扉 | 契機 | 失敗したとき |
|---|---|---|
| 登録の門(`clone`) | clone の**前**に1回 | WRITE 未満なら clone を撃たずに拒否し、案内を返す |
| pickup | `refreshWorkspace` の fetch が落ちた瞬間 | 通れば quarantine すら立たない。ダメなら案内込みで quarantine |
| quarantine の解除 | 確認 question の回答時の検証 | WRITE が見えなければ**回答を拒否**、question は開いたまま |

正常時のネットワーク呼び出しは1つも増えない。新しいタイマーも状態も増えない。

これが成立するのは、**3つの扉すべてに、人間の「もう一度」という行為がすでにあるから**である。登録の門では人間が目の前でボタンを押しており、pickup 側では確認 question への回答が**もともと必須**である(`quarantineWorkspace` の確認 question は「復旧しただけでは pickup は再開しない — 人間の承認が要る」という設計であり、`registry-reachability.ts` が同じ線を明文化している)。ポーリングはこの文法と衝突する: 人間の承認なしに quarantine を解除する経路を1本作ることになる。

**代償は正直に書く。** issue #213 本文の「人間の手数は『招待を1回出す』まで縮む」は、ループなしでは満たされない。招待を出して立ち去れば盤面は自力で再開しない。pickup 側では回答が元から必須なので実質増えないが、これは手数の削減ではなく**手数を増やさないこと**である。

### 3. 合格条件は「見える」ではなく「WRITE 以上が見える」

実測4 の read 招待は、受諾も clone も通してしまう。probe の合格条件を `viewerPermission >= WRITE` にすると、この失敗が PR 昇格という遠い場所に出ることが構造的に無くなる。

**登録の門は WRITE 未満を弾く。** read しか取れない repo を workspace にできなくなるが、read だけで完結する workspace は今のところ想像上のものである — 独立監査(ルート review)の発見も修理タスクになり、修理の成果は PR で着地するので push が要る。read だけの workspace という概念は作らない。

**非対称が1つ残る。** `register` モード(既にホスト上にある checkout の登録)は `origin` を読んで `repo` を焼くだけで probe を持たないので、read しか無い clone を登録すると同じ穴が別の扉から開く。ADR 0066 決定7 が git repo 検査を足した式で probe も足せるが、そうすると登録の門が全モードでネットワークを要求することになる。今は閉じず、痛みが観測されたときに閉じる。

### 4. 案内は3つを名指しし、盤面は自分の名前を実測で名乗る

- **目標 repo の名指し** — 「repo が存在しないか、`<login>` に見えていない」。実測7 のとおり両者は区別できないので、両方を言うのが唯一正直な形である
- `https://github.com/<owner>/<repo>/settings/access`
- `gh api -X PUT repos/<owner>/<repo>/collaborators/<login> -f permission=push`

一行コマンドが主で、リンクが従である。1回のペーストで終わり、GitHub UI で招待欄を探す必要がなく、実測6 により **READ からの昇格も同じ一行が直す**。

`<login>` は `gh api user --jq .login` の実測値である。今日 `tidepool-bot` という文字列は `TIDEPOOL_GIT_IDENTITY` の noreply email に埋まっているだけで(`src/workspace.ts:98`)、トークンの持ち主とは別物である。定数や合成 root の宣言にすると、ずれたときに人間は**違う相手を招待する**ことになり、症状は「招待したのに直らない」という遠い場所に出る。ここは宣言ではなく観測が正しい — 「実際に付与される身元」を知っているのは GitHub だけであり、ADR 0041 の「不在は宣言される」が守るのは選択肢の不在であって、観測できる事実の代用ではない。

### 5. 確認は要求せず、辞退はせず、org 招待は作らない

**confirm は要求しない。** ADR 0061 の「危険な値」は registry の値がエージェントの権限を広げる向きのものであり、招待の受諾はそこに当たらない。到達範囲を広げているのは**人間が出した招待**であって盤面ではなく、盤面は絞った1枚を受けるだけである(ADR 0066 決定8 が `publish` に confirm を要求しなかったのと同じ線)。

**招待の辞退(decline)は実装しない。** 受信箱の管理は盤面の仕事ではない。

**org 招待(`GET /user/memberships/orgs`)は作らない。** ADR 0066 が org を将来の拡張に回したままであり、org を採る日が来たら membership の受諾がこの seam の兄弟として要る(そのときも受諾は1回で済み、以後の repo 単位の付与は即時になる)。今日それを先に作る理由はない。

### 6. 新しい `gh` 呼び出しは時間上限つき

`execFileSync` は同期であり、pickup 経路で black-hole した接続を無制限に待つと event loop ごと止まって、ADR 0036 が復旧経路と定めた人間面まで応答しなくなる(`containment.ts` が fail-closed より悪いと呼ぶ状態)。既存の `GhCliClient` の呼び出しは上限を持たないが、**この issue が足す呼び出しはすべて上限つきにする** — 実ネットワーク往復なので `GIT_NETWORK_TIMEOUT_MS`(30秒)の側であり、ローカルのバイナリを叩く `CAPABILITY_PROBE_TIMEOUT_MS`(5秒)ではない。

### 7. 受諾の記録は既にある question に1行足すだけ

pickup 側では確認 question がすでに立っているので、受諾した事実をその question のイベントとして append する(既存の `quarantine_refired` と同じ形)。登録の門では何も足さない — 成功そのものが記録(workspace エントリの registry コミット)であり、失敗は何も残さない。**受諾専用の面は作らない。** 「なぜ bot が repo X に書けるのか」の正本は GitHub 側の collaborator 一覧であり、授権した行為(招待)は人間自身のものである。

### 8. `publish`(#285)はこの seam を呼ぶ。依存の向きは #213 → #285

ADR 0066 決定5 は「案1で最も起きる人為ミスは **repo は作ったが bot の招待を忘れた**」と名指しし、そのとき `publish` は `remote add` を巻き戻して**痕跡を残さない**。つまり `publish` は「なぜ落ちたか」を人間に残す面を構造的に持たない。

#213 を先に着地させれば `publish` の実装時点で seam は既に存在し、呼ぶだけで済む。逆順にすると、ADR 0066 が自分で名指しした最頻の人為ミスを、直せる材料が手元にあるのに開いたまま一度出荷することになる。

**PR 昇格の push 失敗はこの issue では扱わない。** 門で WRITE を確認する以上、昇格時点で書けないのは「人間が後から権限を下げた」ケースだけである。しかも**アクセスを剥奪**したなら pickup の fetch が先に落ちて既存の workspace quarantine が捕まえる。取り残るのは push → read への**降格**という一点だけで、これはまだ観測されていない痛みである。

## 根拠

**1. 受諾は便宜ではなく、外部 repo の取り込みが完結するための必要条件である。** 個人名前空間の repo への collaborator 追加は招待を作り、招待は受諾されるまで一切効かず、受諾できるのは招待された本人だけである。盤面に受諾の経路が無ければ、人間は Pi に入ってボットのトークンで `list` → `PATCH` を手打ちするしかない。ADR 0066 が org を将来に回したことでこの条件は残り続ける(org でも membership の受諾が1回は要る)。

**2. 検討事項の1つはすでに閉じていた。** issue #213 は「既に登録済みの workspace のアクセスが後から失効した場合はどうするか」を問うたが、remote 正本を宣言した workspace は pickup ごとに `refreshWorkspace` が fetch を撃ち、失敗は `prepareWorkspaceAtPickup` 経由でその workspace の quarantine に落ちる(ADR 0052)。資源単位で止まる形も確認 question も既にある。足りなかったのは新しい門ではなく、**打ち手の提示と解除の自動化**だけである。この読み替えが、設計を「新しい器」から「既存の器への2箇所の追加」へ縮めた。

**3. 決定2 が新しい機構を1つも足さないのは、issue が言った「quarantine の検証つき解除とまったく同じ文法」を文字どおり採ったからである。** 解除の検証は既に「回答を鵜呑みにせず検査を走らせ、まだ壊れていれば回答を拒む」という形で存在する。受諾はその検査の**中**に置かれる1ステップであり、外側に回る何かではない。

**4. 決定3 の合格条件は、実測が設計を変えた例である。** グリリング開始時の設計は「read probe で到達性を確認する」だった。read 招待を実際に受諾してみて初めて「受諾も clone も通るのに push だけ落ちる」が見え、`viewerPermission` がそれをその場で捕まえられることも同じ実測で分かった。

## Considered options

- **pickup ゲートに受諾を常設する** — 招待が出た瞬間に人間の介入なしで拾える。採らなかったのは、正常時の pickup にも `gh` 呼び出しが毎回1つ増え(同期呼び出しで event loop を塞ぐ側)、その代償で買えるのは「人間がもう一度押さなくてよい」だけだからである。押す行為は pickup 側では元から必須である。
- **probe 失敗中だけポーリングする** — 人間は「招待を出す」だけでよくなる。採らなかったのは、新しいタイマーと状態が増えるうえ、「復旧しただけでは quarantine を解除しない — 人間の承認が要る」という既存の文法と正面から衝突するためである。
- **到達失敗時に pending 招待を全部受諾する(受信箱を空にする)** — URL のパースが不要で実装は最小。採らなかったのは、第三者が出した招待もついでに受けて、盤面の到達範囲が盤面の知らない理由で広がるためである。
- **registry が知っている repo の招待だけ受諾する** — 絞りとしては自然だが、登録の門では対象 repo がまだ registry に無いので clone モードを救えず、決定1 の規則と併用が要る。規則を2本持つ理由がない。
- **受諾前に招待の `permissions` を読み、push 未満なら受諾しない** — 「受諾したのに使えない」状態を作らない。採らなかったのは、値の出所が repo 自身ではなく招待オブジェクトになり、**すでに read の collaborator**(招待が存在しない)というケースを同じ問いで捕まえられないためである。`viewerPermission` は両方を1つの問いで答える。
- **受諾するだけで権限は問わない** — 実装は最小。採らなかったのは実測4 のため(push が PR 昇格で 403 になる、ADR 0052 が拒否した「症状が遠い場所に出る」形)。
- **ログイン名をコード定数か合成 root の宣言にする** — ネットワーク呼び出しがゼロになる。採らなかったのは、ずれたときの症状が「違う相手を招待して、招待したのに直らない」になるためである。トークンの持ち主は観測できる事実であり、宣言で代用すべきものではない。
- **登録の門は WRITE 未満でも通し、警告だけ出す** — read 目的の取り込みを塞がない。採らなかったのは、read だけで完結する workspace が今のところ想像上のものであり(監査の発見も修理タスクとして PR で着地する)、「後で遠くで落ちる」を許す代償に釣り合わないためである。
- **`register` モードにも同じ probe を置いて非対称を今閉じる** — 扉が揃う。採らなかったのは、登録の門が全モードでネットワークを要求することになるためである。決定3 に名指しで残し、痛みが観測されたときに閉じる。
- **PR 昇格の push 失敗にも案内を出す** — push → read への降格という細い穴も閉じる。採らなかったのは、その穴がまだ観測されていない痛みであり、アクセスの剥奪(より起きやすい形)は pickup の fetch が先に捕まえるためである。
- **org 招待(`GET /user/memberships/orgs`)も同時に扱う** — ADR 0066 の将来の拡張に先回りできる。採らなかったのは、org がまだ存在せず、作れるのは人間の Web UI だけであり(ADR 0066 制約2/3)、受諾の形が repo 招待と同じであることは今日の実測からも導けるためである。
