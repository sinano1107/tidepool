# worker が1度も走らなかった pickup は失敗の瞬間に後始末へ入り、session は容器を開いた瞬間に始まる

2026-09-12 の grilling(issue #559)で決定。`worker.start` が投げた pickup は `console.error` だけで slot を握ったままになり、タスク種別の時間制限いっぱい待った末に watchdog の梯子の底で「時間制限に達し容器を回収した」という偽の failure question が立っていた。Node の `spawn()` が非同期に失敗する経路(issue #127)も event を1つ書くだけで同じ梯子に落ちる。scheduler のコメントはこの wedge を「再起動中断と同じ、watchdog スライス(#9)が来るまで」と正当化していたが、#9 は再起動中断を起動時の即時記録にしており、待つ理由はとうに消えていた。現状調査・再現・`file:line` は issue #559 のコメントに置く。

## 決定

1. **worker session は盤面が容器を開いた瞬間に始まる。spawn ではない。** slot を握るのは task ではなく session であり(ADR 0109 決定2)、容器は session ごとに盤面が spawn より**先に**作る(ADR 0099 決定2)。始まりを spawn に置くと、容器を開いて slot を取ったあと spawn に辿り着けなかった pickup の枠を誰も握っていないことになる。issue #127 の「spawn 不成立は worker session ではない」はこの読みに改める —— 実質(exit も消費も観測されたことにしない)は変えず、「process を1つも持たなかった session」と言い直す。

2. **worker が1度も走らなかった pickup は1つの族であり、失敗を観測した瞬間に記録する。** `start` の同期 throw も、adapter の内側で観測する非同期の spawn 失敗も、人間に届く症状(遅さと偽の文面)と直す先(記録の形と時点)が同一なので1つの決定で扱う。観測点が2つあるのは実装の事情である。時点は失敗の瞬間 —— 盤面は worker が走っていないことをそこで知っており、盤面自身の先例(再起動中断の即時記録)に揃える。梯子を待って文面だけ直す案は、原因を知らないハンドラに文面を書かせる形(ADR 0112 決定4 が退けたもの)へ戻る。

3. **経路は盤面自身のエスカレーションと同じ後始末の型である。** 失敗の瞬間に failure question を立て(行は `todo` になる)、そのうえで後始末へ入り、空の容器へ強制回収を撃ち、回収済み観測を経て tree rule・休止位置・slot 解放を走らせる(決定1 があるので、後始末が「session の最後の局面」であることと矛盾しない)。記録を回収済み観測の**前**に置くのは escalate verb と同じ順であり、watchdog が記録を観測の後ろに置く理由(殺した session の失敗は容器が空になって確定する)は process を1つも持たない session には当たらない。後始末中の status は `todo` なので、ADR 0113 決定3「status が経路を一意に定める」は無傷で、起動時復旧も確認回答も既存の規則のまま question を残す —— `in_progress` で入ると上限到達による中断の step に読まれ、復旧が question を立てずに queue 先頭へ戻す。待ちの上限は種別の時間制限から後始末の backstop(回収 timeout)へ縮み、空を観測できないホストでは他のどの後始末とも同じ Containment quarantine に落ちる(process の断言は ADR 0112 決定4 の「残っているかもしれない」。backstop の非 `in_progress` 側の前置き「作業を終えて報告した」は spawn 失敗には当たらないので、決着の事実だけを言う文面に揃える)。`failTask` 直呼びは採らない —— それは slot を解放せず(再起動中断で成立するのは起動時に slot が空だからである)、容器の帳簿を閉じる呼び口が scheduler にもう1本生える。

4. **記録は failure question(retry / abandon、推奨 retry)であり、quarantine ではない。** `start` が同期で投げる決定的な失敗(Provider entry 無し・非 openai・skill allowlist・資格情報の不在)はどれも pickup の gate が先に弾く二重防御であり(ADR 0116、封じ込め能力の検査)、そこまで届いたら盤面のバグである —— 資源が実行不能なのではないので6つ目の資源にはならない(ADR 0112 決定2 と同じ理由)。現実に残る fs / git の失敗は一過性でありうるので retry に判断価値がある。retry が無駄にするトークンは無い(process が起きていない)。question が断言するのは3つだけ —— どのタスクの worker が・1度も走らずに・盤面が捕まえた例外の本文。時間制限にも容器の回収にも原因の所在にも触れない。

5. **どちらの観測点も `spawn_failed` event を書く。** 族が1つなら証拠の形も1つである。question は回答で決着するが event は残る。

## 退けた案

- **梯子を待ち、文面だけ spawn 失敗のものに直す** —— watchdog に原因を運ぶ状態が要り、ADR 0112 決定4 の形へ戻る。
- **`failTask` を呼んでから slot と容器を別途閉じる** —— 回収の呼び口が2つになる(ADR 0099 決定2 の反対)。
- **`in_progress` のまま後始末に入り、記録は回収済み観測の後ろに置く(上限到達による中断と同じ形)** —— ADR 0113 決定3 が `in_progress` を cap に割り当て済みで、backstop の文面と起動時復旧が cap として読む。status に event の事実を足して導出を割る案も、決定3 を静かに弱めるので退けた。
- **確認 question 1枚・受理の検査 = start の再実行という gate 形(ADR 0112 決定3 と同型)** —— 落ち続けても question は積み上がらないが、abandon が消え、task に帰属しうる失敗を環境事象と決めつける。積み上がりはまだ観測されていない。
- **同期 throw だけを範囲にする** —— 同じ決定を2回書く。
- **session の始まりは spawn のまま、その窓を「pickup」という別語で握る** —— 問いを1つしか持たない語が増える。
