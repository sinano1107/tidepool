# 自動テストはサーバー境界で止め、ブラウザ駆動は受け入れ確認に限る

**Status: この ADR の線はブラウザとサーバーの間にある。サーバー境界の下の層(ドメイン層・schema 層)は ADR 0107 が名付け、主戦力は本 ADR のまま。**

自動テストの主戦力を「vitest の統合テスト(`tests/harness.ts` の `bootTidepool`)」に固定する。これは実 express + 実 SQLite + 実 registry クローンを起動し、HTTP `/api/*` と MCP verb を `fetch`/`mcpClient` で叩く — ドメインロジックからサーバー境界までを実物で通す、実質的な e2e 層である。UI 層(`public/index.html`)の自動テストは原則持たない。持つ場合も Playwright 等の**コード化された・CI に載る・再利用できる**スモークを、クリティカルパス(作成フォーム→API→登録、失敗トーストの表示)数本に限定する — 網羅は狙わない。claude-in-chrome によるブラウザ手動駆動は**テスト資産にしない**。issue の完了基準を実機で一度見ておく受け入れ確認(例: #73)にのみ使う。

理由: リスクの大半はドメインとサーバー境界にあり、`bootTidepool` が既にそこを実物で吸収している(#73 時点で 485 件)。claude-in-chrome 駆動は非決定的(トースト捕捉すらタイミングで落ちる)・CI に載らない・再利用できない・トークンが高い・**リグレッションを一切捕まえない**ため、テスト資産の要件を満たさない。受け入れ確認としては有効だが、積み上げる対象ではない。自動テストで守れていない空白は「UI 配線」の一層だけであり、`public/index.html` は in-browser Babel のビルドレス React で**型検査も効かない** — バックエンドの厚いテストで守れない唯一の層がここに集中する。実例として、`pushed:false` → warn トースト、`RegistryCloneBusyError`(409)→ danger トーストの配線は `bootTidepool` では捕まらず、#73 では DOM で実文言を目視確認するしかなかった。ただし画面が単一 `index.html` のうちは配線量が小さく、スモークの優先度は中〜低。UI が複数画面・複数コンポーネントに育つほどこの層のリグレッション価値が上がり、スモークを足す投資効率が良くなる。

Considered options:

- **UI もすべて claude-in-chrome で e2e 確認する** — 非決定的で CI に載らず、毎回 Claude が手で駆動するためリグレッションを捕まえない。トークン消費も大きい。受け入れ確認の道具であってテストスイートではない。
- **Playwright で UI を網羅的に e2e する** — ロジックは既に `bootTidepool` が実物で担保しており、UI は薄い(単一 `index.html`)。網羅的 e2e は維持コストが便益に見合わず、遅く脆いテスト群を抱えることになる。入れるならスモーク数本に絞る。
- **UI 層は一切テストしない(完全な現状維持)** — 大半は妥当だが、型検査すら効かない UI 配線のバグが無検出で残る。クリティカルパスのスモークを「将来 UI が育ったときの受け皿」として認める余地は残す。
