# 記憶の参照名(宛先・scope)は書く瞬間に registry で解決できなければ拒み、孤立は一覧で見せる

2026-09-28 の grilling(issue #1055、#634 を畳む)で決定。Behavior / Exemplar の宛先(agent 名)と人間の面の scope(workspace 名)は
schema が空でないことしか見ておらず、typo の宛先は誰にも注入されず黙って死ぬ。ADR 0083 追記3 の「旧名宛ての Behavior が孤立するのは正しい
挙動」は書いた時点で存在した名前の話で、存在しない名前を通す理由にはならない。meta-review の scope は ADR 0122 決定1 で照合済みだが、
人間の面と宛先には同じ門が無かった。経路の一覧と `file:line` は #1055 のコメントに置く。

## 決定

1. **人間と meta-review が記憶に書く参照名 —— 宛先の agent 名と scope の workspace 名 —— は、書く瞬間に registry で解決できなければ
   拒む。** null(全員 / 盤面全体)は常に可。registry の無い盤面では門は掛からない(assignee / reviewer と同じ姿勢)。組み込み agent は
   registry の合成エントリなので通る。
2. **門は選択の入る操作にだけ置く**: 直書き(settings / 管理MCP)、提案 question の回答の修正値、approve、meta-review の `consolidate`、
   人間の移動の行き先 scope。復元・移動が写す本文・帰責が導出する宛先は選択ではないので門を通らず、domain 層の関数は registry を知らない。
   approve に門があるのは「これを注入する」宣言だからで、宛先が解決できない candidate は付け替えるか reject する。
3. **削除済み agent 宛てのエントリの編集は拒む。** 編集は後継の新エントリを作る操作で、後継は誰にも注入されない。「宛先を変えない編集」を
   通す例外は、誰も読まないエントリの文言を直す操作だけを守るので置かない。編集の瞬間が付け替えか無効化の時点で、人間の面は削除済みの
   現在値を見せるが送信できる選択肢にはしない。復元だけが通るのは、復元は本文を選ばず、拒んでも人間にできる操作が無いから(復元してから
   付け替える編集はできる)。
4. **帰責の起草は、宛先の agent が registry に無ければ起草しない。** 「宛先の agent がいない起草は失敗ではなく起草しない」(登録者が
   人間・盤面のとき、ADR 0164)を削除済みの agent へ延長する —— 学ぶ相手がもういない。
5. **孤立 —— 宛先の agent や scope の workspace が registry に無いエントリ —— は一覧の印で見せる。** 一覧は WebUI と管理MCP が同じ
   読み口を共有するので印もそこに載る。ADR 0083 追記3 の「孤立は正しい挙動」は維持し、見えることだけを足す。meta-review の周期検査
   (ADR 0083 追記4)に孤立を足すかは、agent の削除で孤立が実際に生まれてから決める(派生 issue)。

## 退けた案

- **門だけ、または印だけ** —— 門は typo を防ぐが後から削除された孤立は防げず、印は孤立を見せるが typo を止めない。役割が違う。
- **門を domain 層(`recordBehavior` 等)に置く** —— 帰責の起草と移動・復元の写しまで同じ門で落ち、写しは選択ではないので拒む理由が無い。
- **印を WebUI だけクライアント側で照合** —— 管理MCP の一覧と食い違う実装を2つ持つことになる。
