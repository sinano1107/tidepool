# 動力の認証は長寿命トークンへ移し、その失効は cliAuth として盤面を止める

issue #318 のグリリング(2026-08-13)で決定。盤面は無人で回る前提だが、動力である claude CLI の資格情報は
対話ログイン前提で、refresh token がサービス側に reject されたり複数セッションの refresh が競合したりすると
**黙って**期限切れになる(#306 で観測)。切れると worker spawn・AI 下書き・表示時翻訳・使用量の読み取りの
すべてが落ちるが、盤面が気づくのは次に pickup を試みたときだけで、それまで人間の面は異常なしに見える。
#306 の修正は失敗が起きた後の説明を直すもので、本 ADR は**失敗そのものの検出と予防**を決める。

決定は実測に基づく(2026-08-13、Mac / CLI v2.1.228。Pi での再確認は移行 issue の受け入れ条件):

- 有効な setup-token でも対話 TUI の使用率%パネルは出て、`parseUsage` は完走する — ADR 0028 のスクレイプは
  移行後も生きる。ただしヘッダーは「Claude Max」でなく「Claude API」表示になる。**ヘッダーは認証の生死の
  判定材料にならない**(ADR 0028 の「API 課金表示 = %パネル不在」という対応関係はもう成立していない)。
- 無効なトークンでは TUI は**無言で**起動し(エラーなし、プロンプトも出る)、%パネルだけが出ない →
  `checkUsage` は null → 今日の機構では fail-closed throttle に化ける。
- `claude auth status` はトークンの**出どころ**を報告するだけで有効性を検証しない(無効トークンでも exit 0)。
- `claude -p` は無効トークンで exit 1、JSON エンベロープに `is_error: true`・`api_error_status: 401`・
  `result: "Failed to authenticate. API Error: 401 Invalid bearer token"`。
- `CLAUDE_CODE_OAUTH_TOKEN` は `/login` の保存済み資格情報より優先される(公式の優先順位 5 位 vs 7 位。
  有効な Keychain ログインがある Mac で無効な env トークンが認証を壊すことでも確認)。
- CLI は**自分の**ツール(Bash)の子プロセス env から `CLAUDE_CODE_OAUTH_TOKEN` を抜く(printenv で 0 バイト)。
  一般の変数(30 バイト)と `GITHUB_TOKEN` / `TIDEPOOL_GITHUB_TOKEN`(40 バイト)は素通しする。

## 決定

### 1. 資格情報は `claude setup-token`(1年有効)へ移す

`CLAUDE_CODE_OAUTH_TOKEN` を `/etc/default/tidepool`(systemd EnvironmentFile、600 root:root — VAPID 鍵と
同じ型)に置き、全呼び出しが env 継承で受け取る。無人運用の敵は「切れること」ではなく「**いつ切れるか
分からないこと**」であり、この移行は予測不能な失効(refresh の reject / 競合)を予測可能な年1回のイベントに
変える。課金はサブスクリプションのまま。

ADR 0028 の「認証・トークン管理は CLI が所有し、tidepool は一切触れない」は一部改訂する。あの教義が守って
いたのは共有 `credentials.json` 上の refresh ローテーション競合だが、setup-token には refresh が存在しない
ので、教義の前提ごと失効した — 矛盾ではなく前提の失効である。CLI の資格情報**ファイル**には引き続き一切
触れない: 対話ログインの残骸は消さなくてよく(env が優先)、tidepool が所有するのは自分の env に置いた
トークン1つだけである。

### 2. 秘匿の非対称 — 消費者が置き場所を決め、守る主体が厳重さを決める

GitHub PAT 型の隠蔽(呼び出しごと注入、継承 env に入れない — ADR 0024)は**このトークンには構造的に
不可能**である: PAT の消費者は盤面自身(git 操作)だから env から外せるが、このトークンの消費者は worker の
claude プロセスそのものであり、プロセスに認証させる以上そのプロセスの env からは消せない。

その代わり、守るのはベンダーである — CLI は自分の資格情報変数をツール子プロセスからサニタイズすることを
実測で確認した。逆に `GITHUB_TOKEN` 系は素通しなので、**ADR 0024 の PAT 隠蔽は今後も必要なまま立ち続ける**。
「CLI が守ってくれるなら PAT も env でよいのでは」は成立しない — CLI が特別扱いするのは自分の資格情報だけで、
一般のシークレットを守る仕組みではない。残る経路は Linux で CLI プロセスの `/proc/<pid>/environ` を同一 uid
から読む筋だけで、これは Pi のサンドボックスの pid 分離に依存するため、移行時に containment-canary の流儀で
1本検査を足して確かめる。

### 3. 失効は `cliAuth` — 列挙の5番目に入る board-wide halt

認証切れは「使用量が読めない」(throttle の fail-closed、ADR 0028)とは**別の答え**である — 前者は読めない、
こちらはそもそも喋れない。ADR 0058 / 0068 の列挙に `cliAuth` を1行足す。位置は `registryReachability` の後・
`throttle` の前: 認証が死ぬと使用量も観測不能になるため両方が同時に立ちうるが、`halts[0]` が人間に見せる
べきは**原因(cliAuth)であって症状(throttle fail-closed)**である。

形は quarantine 同型(封じ込め能力・レジストリ到達性の3人目の兄弟): Tidepool 名義の確認型 question が
1枚立ち、回答受理時に検査をもう一度走らせて検証つきで解除される。question に乗せることで push 通知は
**既存の通知対象定義(質問と human タスク)のまま**届く — board 状態の push を退けた ADR 0058 と矛盾しない。
理路は registry reachability と同じ(ADR 0052): 資格情報の失効は時間で自己回復しない故障であり、自己回復
する環境事象と同じ静かな skip で扱わない。

### 4. 検出は定期プローブ + 機会的分類。曖昧な観測は cliAuth を立てない

`claude auth status` は検証しないので、検出は**実際に認証を使わせて失敗を見る**形にする。定期プローブ
(既定30分 — 要件は「人間が1時間以内に知る」)を probe(Board call の観測系)として回し、加えて既存の
呼び出し(AI 下書き・表示時翻訳・checkUsage・worker exit)が認証エラーで落ちたときはその場で分類して
quarantine を登録する(機会的分類 — #306 の診断修正と同じ場所を触る)。判定は `api_error_status: 401` の
機械判定で、文字列マッチには頼らない。

**確定的な認証証拠だけが question を立てる。** `checkUsage` の null は多義的である(起動モーダル・レンダラ
変化・プロンプトマーカーの局所化・認証死 — 本 grilling 中に複数を実際に再現した)。曖昧な観測不能で人間を
呼び出すと、what's-new モーダル1枚で深夜に question が立つ。曖昧さは今日どおり fail-closed throttle に
留まり、cliAuth に化けるのは 401 のような確定的シグネチャだけである(ADR 0069 の「識別基準の確度が例外の
広さを縛る」と同じ線)。

### 5. 期限は記録し、30日前に1回だけ知らせる

setup-token の失効は発行日 + 1年で確定している。期限日を `TIDEPOOL_CLAUDE_TOKEN_EXPIRES_AT` としてトークンと
並置し、定期プローブが期限30日前を切ったら Tidepool 名義の質問を1回立てる。「切れてから知る」を「切れる前に
知る」に変える、日付比較1つの機構である。1年という寿命をコードに埋めず期限日を明示的に持つのは、将来
トークン寿命が変わっても壊れないためである。

追記(2026-08-13、issue #320): 期限 metadata の必須性と警告の単位は ADR 0075 で改訂した。

### 6. verify-deploy に項目7(認証プローブ)を足す

現状の verify-deploy.sh は `claude` に一切言及せず、認証が死んでいても全項目 pass する。デプロイ直後の
全項目 pass は人間が安心して離れるための儀式であり、動力が死んだままの pass はその儀式を裏切る。盤面と
**同じ判定**をサービスユーザー + サービス env で走らせる検査を足し、検査の二重定義を避ける。

### 7. 夜間の失効は朝に届く — 通知対象の定義は変えない

cliAuth の question は既存の通知経路に乗るため、quiet hours(既定 23:00–07:00)中の失効は**検出と halt は
即時、push は朝のダイジェスト**になる。「1時間以内に知る」が夜間は成立しないことを承知の上で、通知対象の
定義(質問と human タスクの2つ — ADR 0058 が守った線)を無傷に保つ方を採る意図的な決定である。夜間に
届いたところで人間は寝ており、halt が即時である以上、失うのは回復可能なアイドル時間だけである(ADR 0028 の
fail-closed と同じ交換)。

## 退けた対案

- **対話ログイン継続 + 検出強化** — 根本原因(失効の予測不能性)を放置する。検出はどのみち作るので、
  移行案はこの案を包含する。
- **`ANTHROPIC_API_KEY`(API キー課金)** — 期限が無く無人性は最も高いが、サブスクと別の従量課金に変わる
  (ADR 0062 でも言及した線)。
- **worker だけ対話ログインを残す**(トークンを worker から隠すため) — 資格情報の二重管理になり、worker に
  ついてだけ予測不能な失効が残る。CLI 自身のサニタイズの実測で、この隠蔽の動機自体が消えた。
- **`claude auth status` をプローブにする** — トークンを検証しない(実測)。出どころの報告と生死の検査は
  別物である。
- **TUI ヘッダー表示で判定する** — 有効な setup-token でも「Claude API」表示になる(実測)。
- **board 状態の push 通知を新設する** — ADR 0058 が退けた形の再導入になる。question に乗せれば通知対象の
  定義は無傷で済む。
