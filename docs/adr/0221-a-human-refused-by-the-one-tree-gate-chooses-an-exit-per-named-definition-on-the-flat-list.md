# 門に拒まれた人間は、名指された定義ごとに出口を選ぶ —— 記憶の viewer は作らず平らな一覧の上で

2026-10-09 の grilling(issue #1219)で決定。ADR 0178 の門は、人間が盤面全体へ置こうとしたエントリを、worker の書いた
workspace の Definition で拒みうる。#1212 の grilling はその出口を「記憶の viewer を作って解く」としたが、前提の「名指された
定義を畳む面が無い」は当時すでに崩れていた(畳む UI は ADR 0162 決定1 で入っていた)。現状の測定とコードの所在は #1219 の
コメントに置く。

## 決定

1. **記憶の viewer は作らない。** 平らな一覧の上で直す。木の viewer は、人間が枝の全体を見たい用途が別に出たときに起票し直す。
2. **名指された workspace の Definition ごとに、人間が3つの出口から選ぶ。既定は置かない。**
   - その本文のまま盤面全体へ広げる(Definition の1件の移動で scope だけを変える。同じ path を複数の workspace が定義して
     いれば、本文を1つ選んで盤面全体の Definition を書き、全部を畳む)
   - 盤面全体の文言を書いて畳む(`supersedes`)
   - その workspace の枝を改名する(枝ごとの移動)
   どれにも当たらなければ、人間は自分のエントリの path を変える。
3. **入れ子なら上の path から順に解く。** 盤面全体へ置く定義も盤面全体のエントリなので、上位に残った workspace の定義に門が
   当たる。改名は枝ごと動くので、同じ workspace の下の定義もまとめて解ける。
4. **拒まれた下書きは捨てさせない。** 文言を書く出口だけが書き込みのフォームを使い、そのときは下書きを退避して、保存が通ったら
   開き直す。
5. **「複数の workspace が同じ path を定義している」の印は人間の一覧に出さない。** 重なりを直すのは meta-review の仕事で
   (ADR 0178 決定8)、人間がそれに当たるのは拒まれたときだけ —— そのとき名指された定義として並ぶ。

ADR 0178 の帰結「出口は盤面全体の定義を書いて畳む1手」は、「名指された定義ごとに1手、入れ子なら上から順」に読み替える。

## なぜ出口を選ばせるのか

worker の定義が全 workspace に通じる意味かは本文を読んだ人間にしか決められない —— ADR 0178 決定8 も同じ意味なら畳み、違えば
改名と分ける。拒否の後に盤面全体へ上げる操作だけを用意すると、それが既定の出口に見え、workspace 固有の意味が判断を経ずに
全 workspace の注入に入る。

## なぜ広げる出口は移動なのか

畳みは新しい本文を書かせる。意味がそのまま通じる定義に人間が一文を書き直すのは、Knowledge を1件置きたかっただけの人間に
とって重い。移動は本文の側を継ぐので、書き手は worker のまま、人間は移した者として残る(ADR 0162 決定4)。

## 退けた案

- **viewer を作り、木の読み口 `listMemoryBranches` を人間の面へ出す** —— 拒否への対処に要るのは名指された数件で、木の全体ではない。
- **名指された定義を一覧で選択済みにして既存の畳みに任せる**(#1219 の triage 案)—— 定義の畳みは同じ path に限られるので、
  入れ子の拒否では選び直しと順番が人間の仕事になる。
- **「盤面全体へ広げる」ボタン1つ** —— 上の「なぜ出口を選ばせるのか」。
- **広げてから Edit で文言を直す** —— 直すまでの間、workspace 固有の文言が全 workspace の注入に入る。
