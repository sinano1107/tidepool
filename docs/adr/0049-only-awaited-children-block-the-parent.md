# 親を塞ぐのは親が待っている子だけであり、付帯子は塞がない

issue #181 で決定。`completeTask` のガード(`src/tasks.ts:691`)と blocked の導出は、同じ
`unfinishedChildSql`(`src/tasks.ts:1830`)— 「未決着の子が1つでもあるか」という**平坦な1本**を
共有している。この平坦さが、異議由来の子が走行中の元タスクに生えたときにその完了を塞ぐ
(issue #181 の報告)。

## 決定

**塞ぐ子と塞がない子を分ける。**

- **親が待っている子** — 親の作業を分けた子(`decomposeTask` / `humanDecomposeTask` が
  `based_on_decision` を刻む)と、親が答えを仰いだ question(`escalateTask` が登録するもの)。
  この2種だけが blocked を導出し、完了を塞ぐ。
- **付帯子(attached child)** — その補集合。親の作業のためではなく親の**結果に対して**後から
  付けられた子であり、親の完了も pickup も塞がない。今日の実例は4つ: 異議由来の修理タスク
  (ADR 0046)と RCA review、layer 1 の完了時レビュー、そして人間が親を名指して直接登録した
  review 子(`registerTaskSchema` は `parent_id` 付きでも `type: "work"` だけを
  `humanDecomposeTask` へ回す — `src/api.ts:571`)。

定義を補集合側に置くのは意図的である。閉じた列挙は新しい扉が開いた瞬間に黙って古くなり、そのとき
生まれる誤りは「**本物の分解子が親を塞がない**」— 親が未決着の実作業を残したまま完了する — という、
塞ぎすぎより悪い側へ倒れる。塞ぐ側を列挙し、それ以外を付帯子とする。

`based_on_decision` を持たない子のうち question type だけが「待つ」側に残る。親を持つ question は
例外なく `escalateTask` 経由であり(agent のエスカレーション、watchdog の失敗 question
`src/watchdog.ts:74`、issue 展開の確定的失敗 `src/scheduler.ts:227`、merge 失敗)、親を持たない
question は quarantine 族の3つ(agent / workspace / containment)だけで、いずれもルート。人間は
question を登録できない。したがって「親を持つ question = 親が答えを待つ子」は代理ではなく事実である。

## 根拠

**1. 異議の効果は、異議されたタスクの状態に依ってはならない。** `HUMAN_FACING_KINDS` は
`decision_logged` と `task_completed` の2つ(`src/events.ts:274`)であり、**完了エントリにも異議を
打てる**。そのとき `bundleObjections` は決着済みタスクの子として修理タスクと RCA を登録するが、
完了は取り消されない。むしろこれが異議の**通常ケース**である — 流し読みに並ぶエントリの大半は
既に決着したタスクのものだから。決着済みタスクへの異議が完了を取り消さないのに、走行中タスクへの
異議だけが完了を塞ぐ非対称に正当化は無い。それは ADR 0046 が親子リンクを**文脈の配線**として
使ったことの副作用にすぎない。

異議は完了基準への異議ではなく**判断への異議**であり、その効果は fix-forward(修理タスク)一本で
ある。完了ゲートを兼ねさせるのは二重計上になる。

**2. ADR 0003 の不変条件は無傷であり、本 ADR はそれが指していたツリーを精密化する。** 0003 の
根拠はこう綴られている:

> 完了基準はツリー全体を覆う

そこで覆われているのは**分解が作ったツリー**である。0003 が払うと決めたコスト(「親セッションが
もう1回走るコスト」)と、その対価(「子の成果が出揃った状態での検証・反復分解の機会」)の交換は、
付帯子に対して成立しない — 元タスクは修理を計画していないので、自分の計画に照らして検証するものが
無い。判断ゼロのセッションを1回丸ごと払うことになる。これは issue #181 の選択肢3が言う「不変条件に
穴を開ける」ではなく、不変条件の**主語を確定させる**変更である。

**3. condensation の入力を汚さない。** エージェントは渡されたブリーフに対して完了を判断した。その
判断こそが蒸留の入力であり、外から生えた子でそれを潰せば、記録に残るのは「エージェントが完了
しなかった」という事実でないものになる。fix-forward の信号は修理タスクの存在が既に運んでいる。

**4. 線は1本 — 完了ガードと blocked を割らない。** CONTEXT.md の blocked は「親子関係から機械的に
導出される」1つの規則である。完了ガードだけ絞ると同じ病理が pickup 側に残る: watchdog が元タスクを
殺して人間が retry と答えても、修理タスクに塞がれて **retry が効かない**。escalate 後に question へ
答えても、修理タスクが残る限り復帰できない。用語集が1つと言っているものを2つに割る理由は無い。

## ADR 0048 の分割とは一致しない

同じ `based_on_decision` を読むが、切り方が違う。**escalate の question が判別子である。**

| 子 | ADR 0048(abandon の巻き添え) | 本 ADR(親を塞ぐか) |
|---|---|---|
| decompose の子 | 巻き添えになる | **塞ぐ** |
| escalate の question | 巻き添えにならない | **塞ぐ** |
| 異議由来の修理・RCA | 巻き添えにならない | 塞がない |
| 完了時レビュー | 巻き添えにならない | 塞がない |

2本の線を1本に畳んではならない。決裁権外の子(承認 question 経由で実体化する子)は元の分解判断を
持ち越すので(`PendingChildSpec.based_on_decision`、`src/tasks.ts:141`。承認 question 自身も持つ —
`src/tasks.ts:1566`)、どちらの線でも「判断に乗る子」の側であり、付帯子ではない。

**held の射程は本 ADR の領分ではない。** failure question の held / abandon の範囲一致は ADR 0048 の
決定3が持つ。一般 question の held が付帯子まで凍らせること(元タスクが escalate している間、その
修理タスクが slot に入れない)は本 ADR の変更対象外であり、今日の挙動のまま残る。

## 実装

`based_on_decision` は今日 `task_registered` イベントの payload にしかない(`src/tasks.ts:574`)。
本 ADR の規則は `unfinishedChildSql` — `tasks` だけを見る純 SQL、`nextSlotTask` / `listQueue` が
毎ポーリング通す経路 — で表現される必要があるため、ADR 0048 の決定5(`based_on_decision` を
`tasks` の列にする)を前提とする。**したがって実装は issue #180 の後**であり、それまで issue #181 の
露出(逃げ道が escalate と watchdog だけ)は残る。判断は独立しており、順序だけが依存している。

`unfinishedChildSql` の消費者は2つではなく**3つ**である。完了ガードと blocked の導出に加えて、
abandon / question 回答の経路が `hasUnfinishedChildren(db, unblockTarget.id)`(`src/tasks.ts:1193`)で
親の先頭復帰を判定している。狭めれば、未決着の子が付帯子だけになった親はこれまで先頭復帰しなかった
ところで復帰する。本 ADR の規則の下ではこれが正しい — 親はそれらを待っていない — が、意図した
3つ目の挙動変化として記す。ADR 0048 の効果節も同じ `unblockTarget` を論じているので、実装時に
2つの issue が同じ行で衝突することを見落とさないこと。

## 受け入れる代償

元タスクが通常どおり完了する以上、`openHandoffPr`(`src/mcp.ts:398`)が走り、**異議された作業が
PR に乗る** — 保護 workspace でなく merge ダイヤルが許せば、修理タスクが走る前に merge されうる。
これは根拠1の対称性の帰結そのものである: 異議は今日も、決着済みタスクの PR も merge も塞いで
いない。異議が昇格を止めるべきなら、それは異議経路ではなく merge の門が持つべき判断である。

副産物として、ADR 0046 / 0047 が修理タスクに約束した「直すべき成果物の記録」は本当に届く —
元タスクが完了するので handoff doc が存在する。塞ぐ側に倒すと、修理が最も要る経路でこの約束だけが
空になっていた。

## Considered options

- **異議由来の子の登録を、元タスクが決着するまで遅らせる(issue の選択肢1)** — 「triage コミット =
  一括適用」の線(CONTEXT.md の Triage session)に手が入り、「コミット時に決まったことが後から
  効く」という新しい状態を持つ。元タスクが cancel された場合の扱い(RCA は要る・修理は要らない)も
  設計が要る。
- **コミット時に元タスクが in_progress なら子を登録せず、次の triage が引き取る(issue の選択肢2)** —
  異議イベントは既に永続化済みなので束ね直しの単位の設計が要る。より重いのは待ち時間で、**その間に
  元タスクは完了し PR まで昇格する** — 人間が今朝出した方向コメントが成果物の昇格に間に合わない。
- **完了ガードで差し戻す(エラーではなく `todo` へ戻して統合復帰させる)** — ADR 0003 の不変条件は
  文面どおり無傷(完了イベントは流れない)で、worker の詰まりも消える。しかし根拠2のとおり元タスクは
  分解していないので統合するものが無く、判断ゼロのセッションを1回払う。加えて完了しないため
  handoff doc が宙に浮き、ADR 0046 / 0047 が修理タスクに約束した文脈が空になる。
- **現状維持(issue の選択肢4)** — 「走行中タスクの判断行にその場で異議が付く確率は低い」は成り
  立たない。`listLog`(`src/events.ts:285`)はタスクの status で一切絞らず、`log_decision` は
  セッションの途中で流れる verb なので、**トリアージ時点で最も新しい未読エントリは、まさに今
  走っているセッションが書いた行**である。辺縁ケースではなく流し読みの最前列にある。
- **走行中タスクのエントリを流し読みから隠す / 印を付ける** — 隠す側は成立しない: 未読カーソルは
  単一の高水位マーク(`log_cursor.last_read`、前進のみ)なので、走行中タスクのエントリを飛ばして
  カーソルを進めれば、その行は二度と未読に戻らず異議の機会が黙って失われる。除外したければ
  カーソルの形そのものを取り替えることになる。印を付ける側は、人間に応答できる行動が無い —
  「決着を待ってから異議を出す」は選べない(沈黙 = 承認、カーソルは進む)ので、打てる手を1つも
  変えない情報になる。
