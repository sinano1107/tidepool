# ツール面の宣言は MCP 軸に及ばない: computer use を止めているのは `-p` 1枚であり、盤面はそれを観測する

issue #529 のグリリング(2026-09-09)で決定。ADR 0039 の**延長**である — 「worker のツール面は既定拒否の allowlist」は
セッションの面**全部**を覆っているように読めるが、ADR 0039 測定5 が既に書いているとおり `--tools` は MCP 軸に届かない。
届かない側に何が住んでいるかを、この文書が初めて数える。

**この文書が塞ぐ穴**: Claude Code は Computer Use を **MCP サーバとして配る**。盤面が MCP について宣言している姿勢は
board 所有の `--mcp-config` + `--strict-mcp-config` の2つだが、**CLI にはその姿勢を迂回して MCP サーバを session へ
注入する経路がある** — computer use はそこを通り、`--strict-mcp-config` は dynamic map を落とさない。実際に止めて
いるのは `-p`(headless)の短絡1枚だけである。`-p` は盤面が封じ込めのために選んだフラグではなく、worker を回す唯一の
形として選んだフラグであり、盤面はそれが門であることを宣言も観測もしていなかった。

測定(ゲートの全条件、strict が dynamic を落とさないことの静的追跡、attached-but-toolless の実測)は issue #529 が持つ。

## 決定1: 3つ目の封じ込め問いの射程を MCP 軸へ**非対称に**広げる

`checkToolSurface` は `mcp__` 接頭辞のエントリを照合対象から外している。ADR 0039 決定3 がそう決めた理由は
**欠落側にしか掛からない** —— MCP サーバが繋がらなかったセッションでは verb が丸ごと消え、含めると「盤面の MCP が
落ちている」が封じ込め能力の不成立に化ける。過剰側にはこの理由が無い。

よって過剰側だけを見る。**盤面が宣言していない MCP サーバが1つでも面にあれば不成立**、欠落は従来どおり一切見ない。
これは ADR 0039 の他の2方向(観測 ⊃ 期待 / 観測 ⊂ 期待)の非対称版であり、判定の意味は同じ —— このホストの CLI が
盤面の宣言を honor しなくなった。

## 決定2: 観測対象は init の `mcp_servers[].name` であって、`tools` の `mcp__` 接頭辞ではない

MCP サーバは**面に付いていながらツールを1本も出さない**状態を持つ(認証待ち、接続失敗、CLI 側で無効化)。
`tools` 配列だけを見る検査はその状態を取り逃がすが、ベンダー側の門が動いたとき最初に現れるのはまさにその状態である。

配管(`parseInitField` に2つ目のフィールドを通す)の代価を払う。「盤面のホストなら結局ツールも出るはずだ」で済ませる
ことはしない —— それは今 `-p` について問題にしているのと同じ形の推論である。

## 決定3: 正本の probe に `--strict-mcp-config` を足す

`TOOL_SURFACE_PROBE_ARGS` は `--mcp-config` を運ばない(タスク単位の生成物であり、spawn の外に存在しないため)。
そのままだと probe の MCP 面は**ホストのもの**になり、人間が持つコネクタが面に出て、worker の封じ込めと無関係な理由で
盤面全体が止まる。

`--strict-mcp-config` は**パスを含まない姿勢**であってタスク単位の生成物ではないので、probe が運ばないと決めた線に
抵触しない。probe(空)と実セッション(`tidepool` 1つ)が**同じ1つの規則**で通り、ADR 0039 決定3 の
「期待集合を2箇所に置かない」がそのまま保たれる。

**probe の MCP 面が空になる理由は1つではない**、と書いておく。strict が落とすのはホストのコネクタ(別バケツで、
source 側が自分を止める)であって、この ADR が問題にしている dynamic 注入ではない。後者を止めているのは probe でも
`-p` である。つまり probe は「宣言が honor されているか」と「`-p` の門がまだ立っているか」を同時に見ており、
前者は盤面の宣言、後者はこの ADR が観測対象にしたものである。strict が dynamic を落とすと読んではならない。

## 採らなかった道

- **盤面が設定層で名指しで閉じる** — ADR 0039 が組み込みツールについて却下した閉世界をそのまま持ち込むことになる。
  ベンダーが2本目を配れば開いたまま入ってくる。加えて `-p` が短絡している今、書いた off が効いていることを確かめる
  手段が無い(効いているのか、そもそも来ていないのかが区別できない)。
- **`-p` を床として宣言する** — 床の綴りをベンダーの print モードの定義に預けることになる。観測は宣言を要求しないので、
  こちらは取らずに済む。

## ハーネスの非対称は残す

Codex 側は `features.computer_use=false` を名指しで書き、preflight が観測と照合する **列挙 deny** である(ADR 0098 の
正準経路)。閉世界だが、代償統制として `CODEX_CLI_VERSION` の pin があり、ベンダーが増やした機能はそもそも到達しない。
Claude 側と形を揃えないのはこの差による。版 pin を上げる手続きに `CLOSED_FEATURES` の読み直しが無いことは別の問題で、
issue #532 が持つ。

## 追記(実装時、issue #533)

決定2 が「配管」と呼んだ形は `parseInitField` に2つ目のフィールドを通すことだったが、それでは**1回の呼びで配列が
1本しか返らない**ので ping を2本撃つことになる。この ping は起動時と pickup ごとに走り回数が盤面の応答性に直結する
ので、`runInitPing` は field 名ではなく**射影関数**を取る形にした。`parseInitField` は呼び手が消えたので削除
(ADR 0107 決定5)。決定そのものは動いていない —— 見るのは init の `mcp_servers[].name` である。

**正本は要素の形のドリフトを見られない。** probe は `--strict-mcp-config` を `--mcp-config` 無しで撃つので
(決定3)、その `mcp_servers` は構造上いつも空であり、要素が `name` を失っても空配列は空配列のまま通る。要素を
持つのは `tidepool` が付いた実セッションだけなので、**「`tools` は読めたのに `mcp_servers` が読めない」を不成立に
倒すのは深層防御側(実セッションの init 行)である**。決定1 が MCP 軸を過剰側だけに絞ったことと矛盾しない ——
これは「宣言外のサーバが居るかどうかを**測れなかった**」であって、欠落側の事象ではない。
