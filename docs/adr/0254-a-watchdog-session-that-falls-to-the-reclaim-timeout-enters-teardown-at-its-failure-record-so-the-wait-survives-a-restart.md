# 回収 timeout に落ちた watchdog の session は失敗の記録の瞬間に後始末へ入り、梯子の底の待ちは再起動を越える

**Status 追記: 決定2 の復旧が後始末を完走させる前提 —— 後始末の step は再実行安全である —— の持ち主は [ADR 0345](0345-a-teardown-step-is-idempotent-or-skipped-from-the-record-and-the-boards-own-head-move-goes-through-the-ref-gate.md) 決定1(2026-11-01、issue #2889)。tree rule は同 決定2・3 で再実行安全になる。**

**Status 追記: 決定2 の受理の門から走る復旧に、前の盤面が閉じ切らなかった session の記録を閉じる段が1つ増える(ADR 0315 決定1・3)** —— 対象は起動時点の event id 以下の spawn に限り、走行中の別 Harness の session には書かない。

2026-10-14 の triage / grilling(issue #648)で決定。watchdog の時間制限の梯子が回収 timeout に落ちると、failure question と
Containment question は立つが、延期した tree rule を「どの session のために待っているか」は watchdog の in-memory にしか無かった。
盤面を再起動すると起動時の復旧はその session を拾わず、確認回答は何も走らせずに受理され、tree rule の走っていない workspace へ
次の session が入る(issue #382 の形)。同じ受理の穴は、梯子の底に落ちた後始末中の session でも、再起動後の前提検査が落ちたときに
開いていた。現状調査と `file:line` は issue #648 のコメントに置く。

## 決定

1. **回収 timeout に落ちた watchdog の session は、failure question を立てた瞬間に後始末へ入る。** 後始末の印を書き、枠を後始末中に
   する —— 記録を先に置いてから後始末へ入る、ADR 0118 決定3 と同じ順である。tree rule は走らせない(ADR 0099 決定3 のまま、
   確認回答の受理まで待つ)。印の意味は「後始末に入った時刻」のまま変えない: 印はもともと容器の空を意味しておらず、上限到達による
   中断(ADR 0113 決定1)・1度も走らなかった pickup(ADR 0118)・報告なき exit(ADR 0145)はどれも空を観測する前に後始末へ入る。
   印を書かないのはこの経路だけだった。これで梯子の底に落ちた後始末中の session と同じ形になり、再起動を越える事実が1つに揃う。
2. **梯子の底の待ちは、どの経路から落ちたかを問わず再起動を越える。** 再起動後の前提検査が前の盤面の容器の空を観測できれば、起動時の
   復旧が後始末を完走させる。Containment question は開いたまま pickup を止め、回答は question を閉じるだけになる —— 再起動が
   空の観測を新しく持ち込んだのであって、question が解放の門であることは pickup について変わらない。観測できなければ、確認回答の
   受理が、後始末の印の残る session の後始末を、枠を握ってから走らせる。受理の検査は同じ前提検査を読み直すので、走らせる前提は
   受理の時点で満たされている。
3. **in-memory の `pending` は1回の run の中の述語として残す。** 再起動後の受理前の再検査は素通りではない —— 帳簿に無い前回の容器は
   前提検査の残骸検査(#463)が読み、まだ populated なら回答を拒む。行に写すべきだったのは「回収を待っているか」ではなく
   「どの session の後始末が未了か」であり、それは後始末の印がすでに持っている。

## 退けた案

- **待っている session を持つ列を足す** —— 同じ「後始末の未了」を印と2箇所で言い、片方だけ書かれた状態が表現できてしまう
  (ADR 0112 決定2・ADR 0113 決定3 と同じ理由)。
- **Containment の列に session を持たせる** —— 列の形を変え、同じ門を通る Board call の容器(ADR 0136 決定6)と主語が混ざる。
- **印が残る間は pickup を止め、次の起動を待つ** —— 人間がもう一度再起動しないと盤面が動かない。
- **前提検査に落ちた再起動の受理の穴を別 issue にする** —— 原因は同じ(受理の門が in-memory しか読まない)で、決定1 は #648 の
  経路をこの穴へ落とす。分けると #648 が半分しか直らない。

## 追記(2026-10-16 のトリアージ、issue #1936)

**再起動中断(ADR 0001)も、失敗の記録の瞬間に後始末へ入る。** 起動時の掃き出しは failure question と後始末の印を1つの
transaction で書き、tree rule はその場では撃たない —— 前提検査が通った起動では起動時の復旧が、通らなかった起動では確認回答の
受理が後始末を走らせる(決定2)。この掃き出しも印を書かずに tree rule を直接撃っており、前提検査の結果を見ないまま、前の盤面の
process が生き残っているかもしれない workspace を書いていた(ADR 0109 決定5 が禁じる形)。決定1 の「印を書かないのはこの経路
だけだった」は再起動中断も印を書いていなかったので当時から偽であり、これで失敗を記録する経路はすべて印を書く(ADR 0109 決定1)。
再起動中断は watchdog kill・報告なき exit と同じ「self-report なき終了」の失敗である(ADR 0145 決定2)。ADR 0145 決定3 と
ADR 0118 決定3 が再起動中断を「`failTask` を直接呼ぶ」経路として引く記述は、この追記の後は成り立たない。

印が書けなければ failure question も残らない(status は `in_progress` のまま、起動は落ちる)。2つを別々の文にすると、間で
落ちたとき status は決着したのに印の無い session が残り、どの門も tree rule を走らせない。

**`harnessContainment` を持たない盤面には決定2 の受理の門が無い。** その盤面の Containment question は修理を検査できず回答を
拒むので、前提検査が落ちた起動の後に tree rule を走らせるのは、前提検査の通る次の起動の復旧だけである。本番の合成 root は
常に `harnessContainment` を渡すので、この形はテスト盤面に限られる。

退けた案: **掃き出しを前提検査で囲み、落ちた起動では `in_progress` のまま残す** —— 「印が残る間は pickup を止め、次の起動を
待つ」と同じ帰結になる。確認回答を受理しても何も走らず、人間がもう一度再起動するまで tree rule が走らない。
