# Interview は表に無い対象を走らせられ、meta-review が提案できる対象は表の行の近傍だけである

2026-10-05 の triage / grilling(issue #1347)で決定。ADR 0182 で表の行が具体 id になり、spawn が行の綴りで pin されるように
なってから、表に無いセルは「走ったあとに消された・書き換えられた行」しか現れない。一方で #550 は Interview の子を表の行で
固定し、#921 の提案は「対象が表に無いまま」を pin にしていたので、2枚を合わせると meta-review 発の Interview には走らせ
られる対象が無かった。行に限ったのは #550 の本文だけで、ADR 0111 決定6 は「候補セル」としか書いていない。行に限ると、
測るには行を足すしかなく、足した行はその瞬間に本番の候補になる(`cost` の task では最安の行が先頭で走る)。effort の比較も、
本番の行を書き換えずには測れない。コードの照合は #1347 のコメントに置く。

## 決定

1. **Interview の子は、表の行でない対象で走れる。** 表は本番の候補だけを持ち、Interview は候補になる前に通れる場所になる。
   ADR 0181 決定1 が未観測のセルを最初に走らせるものとして名指した Interview を、表の編集とは別の入口にする。人間が
   第三者の測定を根拠に行を足し、それを Interview で測る道(ADR 0114 決定2 / ADR 0182 決定2)は残る。
2. **対象は (provider, model, effort, tier) で名指し、advisor は本番と同じ規則で導出する。** Interview が答える問いは「この
   model はこのティアの品質を満たすか」(ADR 0114 決定2)で、ティアは問いの一部である。子の要求ティアはこの tier になる。
   advisor を直接名指すと、行を足したあとの本番と別のセルになりえて、Interview の観測が同じセルに数えられない(ADR 0181
   決定4)。「対象が表にある」は4欄の完全一致で判定する。
3. **root review が対象の一覧を欄で持ち、子の pin はその一覧のどれかでなければ盤面が拒む。** 行に限っていたあいだは「表に
   ある」が歯止めだった。purpose の散文のままだと、何が走るかを review agent が決める。登録の扉は行を書く扉と同じ検査
   (既知の Provider、alias の拒否 —— ADR 0182 決定1)をする。走る対象は、人間が1つずつ承認したものだけになる。
4. **行でない対象を Provider が断ったら、対象を名指す Tidepool 名義の question を1枚立て、出口を2つ持たせる。** pin された
   子には別の候補が無いので、ADR 0184 決定4 の「判断が存在しない」は当たらず、`todo` の先頭へ戻すと断られ続ける。鍵は
   (provider, model) で、開いているあいだ子は走らない。「走らせ直す」は盤面が検査し直してから受理し(ADR 0184 決定5 と
   同じ検査)、「この対象は測らない」はその model の子だけを cancel する。兄弟は続く —— 対象は人間が1つずつ承認した
   もので、1つ外すのは分解判断の破棄ではない。openai は pickup 前に読んでいる一覧で対象も照合する。Quarantine の機構を
   借りるが、資源には数えない: 回答が修理の確認とは限らない。
5. **meta-review が提案できる対象は、表にある model の別の effort か別のティアだけで、根拠の episode を添える。** ADR 0150 の
   「根拠を持てるのは分類と effort だけ」をそのまま使う —— 既存の行の提案と同じ軸で、違いは本番を動かす前に測れること
   だけである。表に無い model を持ち込むのは人間だけ。pin は根拠の行の全欄と、対象と一致する行が表に無いこと。approve の
   修正値は purpose に加えて対象の effort / tier で、修正は question の中で行う線(ADR 0150 決定2)を保つ。
6. **Interview の結果を表に入れる提案種別は足さない。** 決定5 の対象の結果は、既存の行の提案(tier / effort の書き換え)に
   根拠として加わる。人間が持ち込んだ model は、findings を読んだ人間が行を足す —— 価格は人間にしか書けず、決める場面は
   Interview の完了であって次の周期ではない。ADR 0150 の「追加は Interview と人間」は変えない。

## 帰結

- ADR 0110 決定4 の新セルの出どころ「観測された未知の id」は、ADR 0182 以後は現れない。新しく観測されるセルは Interview が
  初めて走らせた行でない対象になり、行の提案と人間の行追加の読み物になる。#921 の発火事象「新セル」は消え、提案は根拠の
  episode から出る(ADR 0111 決定6 の「meta-review の要求」)。
- 未知の model への入口を開けるのは引き続き人間である。変わるのは、開けるのに本番を賭けなくてよいことである。人間の把握の
  外にある model に盤面が自分で辿り着くことは、この決定では解けない。
- 人間が足した未観測の行が Interview より先に本番で走ること(#1246)は決めていない。行を足す前に測れるので、行を候補から
  外す門の必要は薄れる。
- 同じ model を別の effort で2行並べられるか(表の主キー)は段の形の問いで、#1346 で決める。この決定は主キーに依らない。
- effort の値域は、行を書く扉も行の提案も検査していない(#1409)。Interview を通せば、走らない effort で落ちるのは本番では
  なく Interview の子になる。

## 退けた案

- **子を表の行に限る(#550 の本文のまま)** —— 冒頭のとおり対象が無くなり、測る前に本番の候補にするしかない。
- **対象をセルの4つ組 (provider, model, effort, advisor) で名指す** —— 決定2。
- **対象を purpose の散文に書く** —— 決定3。
- **断られた子を failure question に落とす** —— abandon は判断ごと破棄で、走れる兄弟の子も道連れになる。
- **断られたことを Interview の結果として黙って決着させる** —— 走れなかったことも、走らせ直す手段も人間に出ない。
- **meta-review に表に無い model を提案させる(Provider の model 一覧、外部の評価、agent の知識)** —— 根拠が「一覧にある」
  だけで、ADR 0110 が退けた一様な探索の代金を、人間の承認の時間と Interview の費用で払う。
- **行の追加の提案種別を足し、価格を修正値で必須にする** —— 決定6。

## 追記(2026-10-15、issue #1410 の実装)

決定4 の「この対象は測らない」に2つ足す。

- **最後の対象を外して root に done の pin の子も未決着の子も残らなければ、盤面がその場で root を cancel する。** ADR 0247
  決定1 の「人間の abandon / reject の答え」にこの回答も含める —— 0 にしたのは人間の答えで、起きた root に採点できる答案が無い
  形は同じ。出自はこの question。
- **前提の破綻の question の retry(ADR 0248 決定2)は、この回答で外した対象を新しい Interview に写さない。** retry が登録時
  の一覧をそのまま写すのは、途中で外れた対象が壊れた probe のせいだった可能性があるからで、Provider の拒否は probe と独立
  した理由である。写すと同じ拒否の question がもう一度立ち、人間が同じ答えを2度する。測りたくなったら人間が登録し直す。

## 追記(2026-10-15 の triage / grilling、issue #1992)

決定4 の question の主題は、断られた子ではなく対象(鍵)である —— 同じ対象を pin した子はどの Interview のものでもこの
question で止まり、前提の破綻の retry(ADR 0248 決定2)で写った対象の子も同じ question で止まる。これに1つ足す。

- **その対象を走らせうる未決着の Interview が盤面に残らなくなれば、question は回答なしで盤面名義に決着する。** 走らせうる
  とは、その対象の子が止まっているか、出題前の root の一覧にその対象があること。root の直接 cancel と前提の破綻の abandon
  は question に答えずに Interview を cancel するので、question が開いたまま残り、「この対象は測らない」は何も cancel しなかった。
  主題が盤面から消えたら回答なしで決着するのは、表から行が消えた行の question(ADR 0184 決定5 の門1)と同じ形で、記録も
  同じ `quarantine_released` に Interview の root を cancel した event を `observed_event_id` として付ける。誰も判断していない
  ので decision log には載せない。測定は #1992 のコメントに置く。

退けた案:

- **この question が開いている間は直接 cancel を拒む** —— 3経路(直接 cancel、前提の破綻の abandon / retry)のうち1つしか
  塞がない。残りを塞ぐと前提の破綻の回答を拒むことになり、probe が壊れたと人間が判断した Interview を、model の拒否が片付く
  まで畳めない。主題がタスクでないので、直接 cancel の門の族から外す。
- **止めている子が無くなれば決着する** —— retry の直後は写った対象の子が出題前で居ないので question が閉じ、新しい子が同じ
  拒否で question を立て直す。人間がまだ答えていない拒否をもう一度作る。
- **新しい event の種類を足す / question を cancelled にする** —— 回答で受理された解除との区別は `observed_event_id` が持ち、
  それ以上を読む読み手は居ない。question は subtree の外にあって Interview をまたぐので、どの cancel に巻き込まれたかの線も
  引けない。

## 追記(2026-10-18 の grilling、issue #2184 / ADR 0273)

決定2 の対象の綴り (provider, model, effort, tier) は (provider, model, effort) の3欄になり、段は Interview 1件の属性(root の `tier`)になった(ADR 0273 決定6)。「対象が表にある」の判定は3欄 + Interview の段で変わらない。決定5 の提案は対象の段でなく Interview の段を名指し、purpose の代わりに仮説・測る仕事・根拠の task を運ぶ(ADR 0273 決定9)。決定1・3・4・6 はそのまま。

## 追記(2026-10-18 の grilling、issue #1999)

追記(#1992)の門「その対象を走らせうる未決着の Interview が盤面に残らなくなれば、question は回答なしで盤面名義に決着する」は、
cancel の経路ごとに呼ぶ処理ではなく、**cancel を含む transaction の終わりに盤面が状態から導く1回の掃除**である。#1992 は2経路
(root の直接 cancel、受験者の failure の abandon)に呼び出しを付けたが、「この対象は測らない」(#1999)と probe の破綻の報告への
abandon / retry(#2132)は呼ばず、同じ model に model の鍵と effort の鍵の question が両方開いていると、model の鍵への回答が effort の
鍵の受験者も cancel して、effort の鍵の question が走らせうる Interview の無いまま開いて残った(実測は #1999 のコメント)。経路ごとに
付ける形は ADR 0267 が退けた「分岐を足し続ける」形で、root が残る場合(他の対象が生きている)も表現できなかった。

- **掃除の範囲は、その transaction で cancel された task が運ぶ鍵だけ。** 盤面に task の無い鍵の question は、無関係な cancel では
  閉じない(#1992 の線)。retry の新しい root は同じ transaction の内側で登録されるので、「retry の直後に閉じる」退けた案には当たらない。
- **`observed_event_id` は、その鍵を走らせうる最後の Interview を消した cancel の event。** その鍵をまだ走らせえた root ——
  その鍵の対象行に受験者が無いか、受験者が transaction の始めに未決着だった root —— が同じ transaction で cancel されたなら root の
  cancel の event(#1992 の文面どおり)。root が残る、またはその鍵の受験者が前に決着していて root は一覧に鍵を持つだけなら、その鍵の
  受験者の cancel の event —— 一覧に鍵があるだけの root の cancel を優先すると、別の Interview の受験者の cancel が実際に最後の
  Interview を消したのに観測がその root を指す(#2219 の実測)。原因(人間の答え)は cancel の event の `origin_question_id` から
  1手で辿れる —— 記録は直接の原因だけを指す盤面の他の記録と同じ形。

退けた案: **3経路目・4経路目に呼び出しを足し、引数を root id から鍵へ広げる** —— 次に cancel の経路が増えたときまた付け忘れる。
**人間の答えの event を観測に付ける** —— #1992 の2経路は cancel の event を指しており、経路によって指す距離が変わる。
