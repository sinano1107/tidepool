# 未回答 question は配下を held にし、abandon は計画ごと破棄して親を再計画に戻す

失敗 question の「abandon」に実効を持たせる(#20)にあたり、次の2つを盤面の実行ルールとして採用する。(1) 祖先に未回答の question を持つタスクは slot に入らない(**held** — blocked と同じく導出のみで保存しない)。一般の question は自分の親のサブツリーを、cancel を持ち得る failure question は失敗タスクの親のサブツリー(兄弟含む)を held にする。(2) abandon 回答は失敗タスクのサブツリーに加え、**親の未完了子孫すべて**(巻き込まれた未回答 question を含む)を一括で cancelled にし、親を先頭復帰させて再計画させる(計画ごと破棄)。親より上へは波及しない — 親自身は生きているため祖父の計画は壊れていない。

根拠は3つ。第一に、このモデルには兄弟間の依存エッジが存在しない(CONTEXT.md: 独立した blocking エッジはない)ため、「キャンセルされた子に依存する兄弟だけ」を選択的に止めることは原理的に不可能で、取れる立場は「計画全体を止めて親に再計画させる」か「走らせて安全弁に頼る」の二択になる。第二に、decompose の子は全員 `based_on_decision` で1つの判断に紐づく — 1子の放棄はその判断の前提を壊すので、残りの子を盲目に走らせるより判断ごと無効にして親の統合セッション(ADR 0003 と同型)に再計画させる方が一貫する。第三に、シングルスロットの下で failure question が発生した瞬間に in_progress の兄弟は存在し得ず、held が兄弟の新規着手も防ぐため、回答時のカスケードは todo のタスクにしか触れない — セッション kill なしで安全に一括 cancel できる。

親の復帰が**先頭復帰**なのは既存ルールの適用そのもの: question への回答は人間の操舵行為であり、unblock された親は先頭に入る(ADR 0003 の対比参照)。abandon も回答である以上、壊れた計画の再計画を放置せず即座に走らせる。

Considered options:

- **安全弁任せ(本体のみ cancel)** — 兄弟は走り続け、前提成果物の欠如に気づいたエージェントの escalation と親の統合検証を後ろ盾とする。実装は最小だが、壊れた前提の上の作業にトークンを消費し、エージェントが欠如に気づかず低品質な成果を出すリスクが残る。
- **人間の操舵で解決(cancel の API 露出)** — abandon 時に人間がボードで残りの兄弟を手動整理する。依存の有無を知っているのは人間だけという理屈は正しいが、「30秒の回答」で済むべき操舵がボード作業に膨らむ。
- **計画ごと破棄(採用)** — 未着手の独立な兄弟まで捨てるコストは再登録のみ(done の成果は保持される)で、計画の一貫性が構造的に保証される。

なお cancelled は blocked 導出上 done と同じ完了扱い(cancelled の子は親を塞がない)。これは本決定の前提であり、カスケード後に親の blocked が外れて再計画に復帰できるのはこのためである。
