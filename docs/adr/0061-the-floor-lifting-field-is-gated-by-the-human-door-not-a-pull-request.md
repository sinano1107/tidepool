# 床を持ち上げるフィールドの門は人間面であって PR ではない

issue #229 のグリリング(2026-08-10)で決定。`review_allowed_commands`(ADR 0035)に盤面側の書き込み経路が
1つも無い —— `updateWorkspaceSchema`(`src/api.ts`)にも管理MCP の `update_workspace` にも settings 画面にも
現れず、設定するには registry を帯域外で編集するしかない —— という報告から始まった。

## 先に訂正する事実

ADR 0035 と `src/registry.ts` の doc comment 2箇所は、このフィールドの門を「保護 workspace が要求する人間
merge」「a human reading the registry PR」と書いている。**これは人間発の経路を勘定に入れていない不正確な記述で
あり、書かれた時点で既に不正確だった。**

`CONTEXT.md` の Registry が述べるとおり、registry 変更の正規経路は2本ある —— agent 発(registry-edit タスク
→ PR → 人間 merge)と、人間発(WebUI / 管理MCP → 盤面がリモートの保護ブランチへ**直接コミット**、ADR 0052)。
PR が門になるのは前者だけである。したがって「PR が門」が事実だったのは、このフィールドに人間発の経路が
たまたま無かったからにすぎず、**設計された門ではなく経路の不在**だった。

その不在は意図された決定にも見えるが、どこにも書かれていない。今日の状態は「意図的に閉じている」と
「単に作り忘れた」を見分けられない。

## 決定

**`review_allowed_commands` の門は、人間面が要求する credential(ADR 0036)と、危険な値に対する明示の確認で
ある。** このフィールドは他のあらゆる registry フィールドと同じ3つの扉(WebUI / `/api` / 管理MCP)から編集
でき、扉の格は揃ったままにする。

### 1. 危険な値の確認は既存の `confirm` を一般化して担う

workspace 編集の `confirm` は今日「保護を外すことへの同意」だが、これを「**このペイロードに含まれる危険な値
すべてへの同意**」へ一般化する。ブールを2枚目に増やさない —— 呼び出し側が扉ごとに「どっちがどっち」を覚える
コストのほうが、区別から得るものより大きい。

「何に同意したか」はブールの枚数ではなく**拒否の本文**で表す。確認なしの保存は理由コードを列挙して拒む
(`unprotect` / `review_allowed_commands_set` / profile 側の3つ)ので、ダイアログは列挙をそのまま出せる。
人間が見たものと同意したものが一致する。

執行は**ドメイン側**(`updateWorkspace`)に1つ置き、API が 409 `confirm_required` に、管理MCP が
`registryToolError` に写す。profile が API 境界(`rejectUnconfirmedDanger`)と `management-mcp.ts` に
**二重に実装している**形は踏襲しない —— 扉が増えるたびに実装が増える形は、いずれ扉ごとにずれる。

### 2. 判定はペイロードの純関数。編集前の値は読まない

危険判定はペイロードだけを見る。盤面が現在値を読んで差分を取ることはしない。

これで摩擦が出ないのは、`updateWorkspace` が**部分パッチ**だからである(`undefined` = 触らない。profile の
全フィールド再送とは形が違う)。WebUI はこのフィールドを `protected` と同じく**変わったときだけ**線に載せる
ので、`notes` だけの編集ではペイロードに現れず、確認も出ない。**確認は人間がそのフィールドを実際に編集して
保存した瞬間にだけ出る。**

帰結。2つのうち1つを消す編集はペイロードに残り1つを載せるので確認が出る —— 減らす方向でも「今なお何が
開いているか」は人間の目を通る。全部消す編集は空配列なので確認は出ない(床を下げる方向に摩擦は置かない)。
空配列はキーの削除として着地する —— 不在が正規形であり、`protected: false` を書かないのと同じ形。

### 3. 書き込みは編集扉のみ。作成扉には載せない

workspace 作成が今日 `confirm` を持たないのは、**作成時に同意を求める対象が1つも無いから**である
(`protected: true` は強める向き、省略は「最初から無い」であって剥奪ではない)。ここに
`review_allowed_commands` を載せると、確認フローを1つも持たない登録経路に危険確認を新規に持ち込むことに
なる。そこで観測された痛みは無い —— #229 が報告しているのは既存 workspace への追加である。

## 根拠

**1. 「開けるべきでない」ではなく「見えない」が今日の状態である。** workspace の他のフィールドは、編集できない
ものも settings 画面に**表示されている** —— `repo` / `path` は "shown but never editable" という意図的な形で
コメントされ、`branch` も表示だけされる。`review_allowed_commands` は表示すらされない唯一のフィールドで、
「開ける/開けない」の前に「あることが分からない」。

**2. 一貫性の順序が逆立ちしていた。** 人間発の直コミット経路には、profile の無人 merge(`auto_if_ci_green`)と
workspace の保護剥奪という、レビューコマンド1本より遥かに広い widening が既に通っている。
`review_allowed_commands` だけを止めると、盤面は「レビューセッションに `npm test` を許す」を「workspace の
保護を外す」より厳しく守ることになる。

**3. このフィールドだけ PR 経由にする案は、ADR 0052 が統一したばかりの定義を二重化する。** PR を作るとは、
盤面が自分の書き込みを merge されるまで**効かない状態で待たせる**経路を1本作ることである。ADR 0052 決定1 は
「push 成功が『効いた』の定義」に統一した直後であり、フィールド1つのためにその定義を分岐させる取引には
見えない。

**4. 危険な接頭辞だけを確認対象にする案は、ADR 0035 が既に失敗を記録した列挙である。** `sh` / `node` /
`python` … を危険語彙として持つ設計は、deny ではなく確認トリガのリストになるだけで、漏れたときの帰結は
同じ形をしている —— `perl -e` が確認なしで通り、ダイアログの不在が「これは安全だ」という誤った信号になる。
ADR 0035 は「インタプリタとラッパは無限にある。塞げないまま『列挙した』という誤った安心だけが増える」と
書いてこの道を捨てた。確認の側で復活させる理由が無い。

**5. 文法検証の役割は弱まらず、むしろ広がる。** `assertValidReviewAllowedCommands` の根拠は「人間が読んだ
ものが CLI に届く」だった。読む人間が PR のレビュアから確認ダイアログの前の人間に変わっても、カンマが
`--allowedTools` トークンを1つ余計に注入する事実は変わらない。**これからは確認ダイアログの列挙も守る対象に
なる** —— 表示された1行が、実際には2つの allow として届くことがあってはならない。書き込み経路ができる以上、
検証は loader 側だけでなく**書き込み前にも再走**する(skill 許可リストが取ったのと同じ形 —— 不正な値が
次の `loadRegistry` を壊せないようにする)。

**6. #228 が閉じたことで、このフィールドは初めて意味を持つ。** 起票時点では review タスク自身のブランチが
保護ブランチから切られており、`npm test` を許しても走らせる対象が無かった。ADR 0053 でタスクブランチが
lineage から切られるようになり、その前提は解けている。

## Considered options

- **このフィールドを含む編集だけ PR 経由にする** —— ADR 0035 の記述を守るべき不変条件として読み直す道。
  一貫した設計ではあるが、根拠3の定義の二重化を招く。またその PR を誰が merge するかは、WebUI を触っている
  当の人間である —— 経路が長くなるだけで、判断する人間は変わらない。
- **UI 経路を作らないことを決定として明文化する(ADR + 画面上の表示)** —— 「意図的な省略か抜けか」という
  #229 の問いには答えるが、根拠2の順序の逆立ちが残る。
- **確認を差分ベースにする(既存値から増えたときだけ)** —— 摩擦は減るが、判定のために編集前のエントリを読む
  必要があり、「今そこに何が開いているか」が人間の目を通らないまま編集が積み重なる。決定2の部分パッチ +
  純関数で、差分ベースの利点(不要な確認が出ない)は差分比較なしに得られる。
- **`confirmDangerous` を2枚目のブールとして workspace に足す(profile と同じ綴り)** —— 「何に同意したか」を
  型で区別できるが、`confirm` と `confirmDangerous` が同じペイロードに並ぶ。区別は理由コードの列挙で足りる。
- **管理MCP の扉からは外す** —— worker の handoff / objection 本文に仕込まれた指示が、人間の対話エージェント
  経由で危険な値の確認として着地しうる、という懸念は実在する。ただしそれが正しいなら `merge:
  auto_if_ci_green` は今日すでにその扉から立てられる。フィールド単位で外しても経路は塞がらず、閉じたという
  誤った安心だけが残る。これは**扉単位の問い**として切り出した(issue #267)。
- **`branch` も同時に編集可能にする** —— 同じく UI から書けないフィールドだが、性質が違う(widening ではなく
  entry の指す先を変える、`repo` / `path` に近い)。観測された痛みも無いため据え置く。

## 実装

サーバ/ドメイン側は issue #264、settings 画面側は issue #265。決定2 の議論中に見つかった profile 側の確認摩耗
(この決定とは独立に残る)は issue #266 —— ADR 0086 で決定2 を profile 扉へ拡張して解消。
