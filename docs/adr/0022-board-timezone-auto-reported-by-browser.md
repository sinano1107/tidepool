# 盤面タイムゾーンはブラウザが自動報告する、ピッカーは作らない

2026-07-15 の grilling(「quiet hours のタイムゾーン修正 — 設定画面から tz を設定できるようにするべきか」)で決定。quiet hours の判定は UTC の壁時計で行われており(CONTEXT.md にもそう明記されていた)、JST のユーザーには昼間サイレント・深夜プッシュという真逆の挙動になっていた。修正にあたり「tz はどこから来るか」を決めた。

決定:

- **タイムゾーンは盤面に1つ、IANA 名で持つ(既定 Asia/Tokyo)。** quiet hours は「人間が寝ている時間」であり、tz は人間の属性 — 盤面がどのホストで動いていても同じ挙動になるべきで、ホストの TZ には依存しない(ADR 0018 のホスト非依存と同じ線)。既定を Asia/Tokyo とするのは、他ユーザーへの提供を考えてもまず日本からだという判断。既定が効くのは初回 PWA 起動までの間だけで、その期間まで真逆の通知挙動を残す理由がない。
- **PWA 起動時にブラウザが実測値(`Intl.DateTimeFormat().resolvedOptions().timeZone`)を自動報告し、DB と異なるときだけ更新する。** 人間が移動すれば quiet hours は現地の睡眠時間に追従する — 意味的に正しく、UI 追加ゼロで自己修復的。異なる tz の複数端末は last-write-wins で揺れうるが、シングルユーザー盤面では実質起きない。
- **設定画面の tz ピッカーは作らない。** シングルユーザーの個人盤面に IANA 全ゾーンのピッカーは過剰で、ブラウザは既に正しい答えを知っている。
- **受け口は独立エンドポイント `POST /api/settings/timezone`。** quiet hours の start/end とは送り手が違う — start/end は人間が意図して設定する値、tz は起動時に自動報告される実測値。quiet-hours API に相乗りさせると、自動送信が知る必要のない start/end を read-modify-write で送り直すことになり、将来設定 UI ができたとき競合の芽になる。

Considered options:

- **環境変数でデプロイ時固定** — ホスト非依存は満たすが、人間の移動に追従せず、変更にデプロイ作業が要る。
- **ホストの TZ に従う** — コード最小だが、ラズパイの OS 設定に通知挙動が依存する(ADR 0018 の方針に反する)。
- **設定画面のピッカーで人間が選ぶ** — ブラウザが知っている値を人間に手入力させる形。設定面(issues #46/#54/#55/#57)がまだ設計途上でもあり、バグ修正がそれに依存してしまう。
