# 完了は worker 自身のコミットを門で要求する — 盤面は本文を起草しない

issue #240 / #367 バケット B(2026-08-17)で決定。友人の repo にタスクの実行結果が git 履歴として残る形が、
実環境動作確認の第一印象に直結することが契機である。

## 破れの形 — 退避コミットが唯一の履歴になっていた

盤面がタスク workspace に作るコミットは slot-release tree rule の `WIP: task <id>` 1種類しかない。完了・
エスカレーション・分解・watchdog 失敗のどの解放でも同じ機械処理が走るので、worker が一度も commit しなければ
**成果の全量がこの無内容な1コミットに退避される**。git 履歴からは何を・なぜ変えたのかが一切読めない。

「完了時に盤面が別途コミットしている」という理解は誤りで、その正体はこの WIP コミットである。merge-back は
ff 可能ならコミットを作らず、作る場合も git 既定のメッセージになる。

worker セッションは `git commit` を**できる**(拒否リストは review セッション限定)し、名義は GIT_* env で
agent 名に固定済みである。欠けていたのは能力ではなく、コミットを**要求する場所**だった。

## 決定1: work タスクの完了はツリーが clean であることを要求する

worker MCP の `complete_task` は、work タスクのワークスペースに未コミットの変更(untracked を含む)が
残っていれば、**完了させずに拒否する**。ツール結果は「未コミットの変更がある。何を・なぜ変えたかが git
履歴だけで読める本文を付けてタスクブランチにコミットしてから呼び直せ」を英語で伝える。

これは handoff doc の欠落を返すのと同じ形の **domain error** であって、プロトコルエラーではない。拒否の
瞬間にセッション・slot・作業ツリーのどれも動かない —— 「domain error は session を生かす」の既存の線を
そのまま延長したもので、worker は同じセッションの中でコミットして呼び直せる。

門を機械で閉じるのは、**protocol 文の指示は追従されるとは限らず、字数にも限界がある**からである。protocol
には1行だけ触れる(コミットしてから完了しろ、と予告する)が、それを完了扱いの根拠にはしない。

門が `completeTask`(ドメイン層)ではなく worker MCP の verb 側に立つのは、`completeTask` を人間経路
(/api・管理MCP)と共有しているためである。人間タスクの完了はワークスペースを持たず、コミットを求める
相手もいない。

## 決定2: 掛からない場所を先に決める

- **review の完了** — review は書けない(ADR 0013 の床)。生成物が残っていれば従来どおり WIP へ退避される。
- **escalate / decompose** — どちらも「作業が終わっていない」解放なので、退避が正しい姿である。
- **workspace が無い / 解決できない / quarantine 中のタスク** — 門をスキップして現行どおり。
- **ツリーを観測できないとき**(git repository 自体が壊れている等)— 門は素通しする。「commit してから
  呼び直せ」は worker に実行不能なことを求める指示になり、直後の解放で tree rule 自身が同じ git に躓いて
  quarantine へ落ちる。盤面の資源の故障は完了を止めずに封じ込めへ回す、という `releaseWorkspace` の線を
  ここでも切らない。

## 決定3: dirty の判定は tree rule と同じ基準を1点から読む

ADR 0069 の3条件 —— 既知パスリストに一致し、untracked で、0 バイト —— をすべて満たす sandbox shadow 残骸
だけは dirty に数えない。判定を2箇所に複製すると、片方だけが残骸を数えて無実の拒否か取りこぼしを生む。
tree rule の退避除外と門の dirty 判定は同じ関数を読む。

観測は `git status --porcelain --untracked-files=all` で撃つ。既定の porcelain は丸ごと untracked な
ディレクトリを `?? .claude/` の1行に畳むので、パス一致による残骸の除外が効かなくなる。

## 決定4: 盤面はコミット本文を起草しない

LLM で本文を書く処理は入れない。理由は2つで、**財布**(退避は毎回の解放で走る機械処理であり、トークンを
焚く場所ではない)と**隔離境界**(tree rule は盤面が worker の外で撃つ最小の機械処理であり、そこに
モデル呼び出しという新しい失敗様式を持ち込まない)である。handoff doc や decision log からの起草も同じ
理由で採らない。

残る WIP コミットの subject には task title を添える(`WIP: task <id> — <title>`)。完了の門が入って以降
WIP が残るのは完了**以外**の解放だけなので、履歴を読む人間には「どのタスクの途中なのか」が id だけでは
足りない。issue-backed タスクの stored title は `#N` プレースホルダのままなので(本物は使用の瞬間に解決
される)、その場合は素の `WIP: task <id>` に落ちる —— 退避は同期の機械処理であり、GitHub を叩かない。

merge-back のコミットは変更しない。

## Considered options

- **(a) worker protocol に「必ずコミットしろ」と書くだけ** — 指示は追従されるとは限らない。守られたか
  どうかを盤面が観測しないので、破れは静かに履歴の質として現れる。
- **(b) 盤面が完了時に handoff doc から本文を起草してコミットする** — 履歴は埋まるが、書いたのは worker では
  ないので「何を・なぜ変えたか」は成果物ではなく報告の写しになる。財布と隔離境界の両方を削る。
- **(c) 門を `completeTask`(ドメイン層)に置く** — 人間経路の完了まで巻き込む。人間タスクにはワークスペースも
  コミットを求める相手も無い。
- **(d) 完了時も dirty を許し、退避コミットの本文だけを厚くする** — 「盤面が書いたコミット」が成果の唯一の
  記録である状態は変わらない。誰の判断でその変更が入ったのかが履歴から消えたままになる。
