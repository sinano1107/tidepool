# session を閉じる書き込みが投げたら閉じ切らなかった session の停止であり、鍵は枠ではなく session である —— 起動時の復旧は後の spawn がある session も閉じる

2026-11-01 の grilling(issue #2876、#2857 の派生。#2872 / #2880 と同じ族の根)で決定。ADR 0342 決定6 は session の `writes` の束(exit の
記録・一時領域の削除・投影・資源の停止の登録)を後始末の runner に乗せたが、runner の失敗の家(failedTeardown の行・memory の残り・受理の
撃ち直し)は「投げた手の持ち主は枠の今の主で、その容器は空」を前提に組まれている。ADR 0201 決定2 により `writes` は枠が次の session に
移った後にも届くので、前提の前半が破れる(#2872 は後半)。その結果、同じ手の同じ throw が届いた時刻で3つの底に割れていた —— 枠の主なら
failedTeardown、枠の外の live なら console、起動時の復旧の catch も console。分類するのは1つだけで、ADR 0342 が #2837 で根とした
「底が分類しない」形がここに残っていた。決定と写しの分離、底の表、釘の所在は #2876 のコメントに置く。

## 決定

1. **session の `writes` の束の手が盤面のバグ(ADR 0342 の B)で投げたら、閉じ切らなかった session の停止 `unclosedSession` である。**
   行の値は spawn event id、壊れているのは「session の記録が閉じられない」。`failedTeardown`(値 = task id、壊れているのは「枠が
   空かない」)とは別名にする —— 同じ kind では同じ task の2 session が `(kind, value)` で衝突し、値を spawn id に変えると spawn の無い
   never-ran の後始末が持てず、受理の検査も違う(片方は後始末の撃ち直し、片方は記録からの閉じ直し)。盤面全体の停止に数え、列挙の順は
   `failedTeardown` の直後 —— 先に直すべきは枠が刺さっている側。kind は**投げた手が束の手か**で選び、枠の主の `worker_exited` の INSERT が
   投げても `unclosedSession` である —— 枠の主かで分けると同じ throw が届いた時刻で別の家に落ちる。枠は決定の手が走らないので握った
   まま、残りの列に決定が後ろに継がれる。
2. **残りは session ごとに持ち、枠の解放で消えない。3つの底は同じ家に落ちる。** 枠の外の live の throw も行を立てる。起動時の復旧の
   session ごとの catch は分類する —— 盤面 DB の拒否(A)は投げて起動を拒み(ADR 0342 決定4 のまま)、それ以外は行を立てて起動は続く。
   ADR 0315 決定1 の「1件の失敗は記録して流す」は行に置き換わる。1つの原因で立つ行は最大2枚(死んだ session と走っている session)——
   pickup は1枚目で止まる。
3. **受理の検査は「その session を閉じ直す」で、冪等である。** process が生きていれば memory の残り(投げた手から、ADR 0342 決定6)、
   再起動を跨げば記録からの閉じ方(ADR 0316 決定2 の3手)を同じ spawn に撃つ。起動時の復旧が先に閉じていれば no-op で通る —— 行は
   人間の回答だけが閉じる(ADR 0112 決定3 と同じ門)。再起動を跨いだ閉じ直しは資源の停止の登録を撃たない(ADR 0316 決定3、帰結は live
   だけが撃つ)—— exit code と同じく失われる損失として受け入れる。question が断言するのは3つ: どの session(task と spawn id)が・
   いつから閉じられず・盤面のコードが投げた例外の本文。受理が閉じ直しであることは本文で予告する。
4. **ADR 0112 決定4 の門と残りの継ぎ先は、盤面全体の行ではなく枠の主の session の行を読む。** `tick`・回収 timeout・決定の門・起動時の
   後始末の再開・回収済み観測の保留・後始末の先頭の門のすべてで、死んだ session の行は走っている session の梯子を止めず、その観測や
   後始末を死んだ session の残りに継がない。読むのは行(kind は問わない)—— #2872 の後、枠の主の手が投げる時点は強制回収の後か回収
   timeout の書き込みで、後者は行が再入の門そのもの(ADR 0342 決定6)なので、「容器が空か」の別の読みは要らない。
5. **起動時の復旧は、同じ task に後の spawn がある session も exit(`exit_observed: false`)と投影を書く。** ADR 0315 決定3 が exit を
   書かなかった理由「窓が次の session に重なる」は、窓が次の spawn を越えない規則(ADR 0316 決定4 Status 追記、#2880)で消えた ——
   読み手は exit を `worker_spawned_event_id` で引く。一時領域の削除だけは、その task の spawn が watermark より後に無いときに限る ——
   session ごとの path は記録に無く、task 接頭辞の削除は走っている次の session の領域を消す。

## 退けた形

- **今のまま log し、次の起動の復旧に任せる** —— 記録を書く処理の欠陥に人間が気付く経路が無く、crash を console の1行に置き換えた
  ままになる。
- **枠に依らず `failedTeardown` を立て、残りを task ごとに持つ** —— 同じ task の2 session が衝突し、「枠が空かない」でないものに
  その名が付く。
- **梯子の門を「容器が空と観測したか」に読み替える** —— 再起動を越えず、梯子の手が投げた session の再入を別に止める機構が要る
  (#2876 の triage の測定で `quarantine_refired` が30分で30行)。決定4 の読み替えで同じ目的を行のまま満たす。
