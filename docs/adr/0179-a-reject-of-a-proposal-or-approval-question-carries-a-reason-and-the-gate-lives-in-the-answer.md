# 提案 question と承認 question の reject は理由を必須にし、門は回答の1か所に置く

2026-10-01 の triage / grilling(issue #1030)で決定。ADR 0159 決定3 は memory 提案の reject だけを理由必須にし、ほかの
reject 経路を #1030 に残した。回答の comment は issue #40 が「reject も選択肢名で足りる場合がある」として任意にしたものだが、
その #40 が痛みに挙げていたのは承認 question の reject だった。現状のコード調査と実測は #1030 のコメントに置く。

## 決定

1. **提案 question の reject は、種別を問わず理由の comment を必須にする。** 読み手は同主題の次の meta-review。routing の
   reject は「今は違う」で、同じ提案を機械で塞がない(ADR 0150 決定2)。だから空の reject では「根拠が足りない(増えれば
   再提案してよい)」と「根拠によらずこの設定にしたい(再提案は毎回ノイズ)」を読み分けられず、分けるものは理由しか無い。
   meta-review は理由を読み、それがもう当たらないときだけ再提案する。
2. **承認 question の reject も理由を必須にする。** 読み手は復帰した分解の書き手。question には盤面が承認を求めた理由は
   載るが、人間が断った理由は記録のどこにも無く、親は「どの点が駄目か」「子そのものが不要か」を推測して動く。#40 の
   「30秒の回答」より、外れた推測が使う1 session を重く見る。worker 向けの文面は足さない —— history には answer と comment が
   並び、理由そのものが指示になる。
3. **`abandon` / `hold` / `abandon promotion` の comment は任意のまま。** abandon は失敗の事実が記録にあり、理由が
   「失敗したから」で足りる場合が多い。reject は断った理由がほかのどこにも無い。hold と abandon promotion には読む
   エージェントがいない。
4. **門は回答の domain 関数の1か所に置き、「この question でどの選択肢が理由必須か」は盤面が決めて question の読み口に
   載せる。** ADR 0159 決定3 が reject の domain 関数に、ADR 0165 決定3 が defer に置いた検査はここへ移る(必須であることは
   変わらない)。経路ごとに置くと規則の定義が3つになり、人間の面が「どの種別のどの選択肢か」の写しを持つ。人間の面は
   載った一覧を描画するだけにする(承認 question の注釈と同じ分担)。
5. **人間の面は全 question に comment 欄を出す(任意)。** #40 の伝達路は API と管理 MCP にしか入口が無く、WebUI からは
   memory 提案以外で理由を書けなかった。理由必須の選択肢を選んだときは、欄が空の間は送信できない。

## 退けた案

- **routing / registry 提案は任意のまま** —— 決定1 の読み分けができない。
- **承認 question は任意のまま、worker 向けの文面で補う** —— 理由が無ければ、文面があっても親は推測する。
- **abandon も必須にする** —— 決定3。理由が記録に既にある答えに1文を強いると、「失敗したから」が並ぶ。
- **経路ごとに門を置く** —— 決定4。
