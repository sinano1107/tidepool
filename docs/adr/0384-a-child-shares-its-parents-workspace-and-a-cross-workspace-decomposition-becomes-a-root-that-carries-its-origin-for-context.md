# 子は親と同じ workspace に居て、別の workspace への分解は文脈を運ぶ分解元つきの根になる

2026-11-19 の grilling(issue #1796)で決定。`parent_id` は性質の違う3つの仕事を1本で運んでいる —— ① 親の文脈を子の worker に渡す、
② 親が子を待ち、決着した子の成果を受け取る、③ 子の中身を親のタスクブランチへ返す。ADR 0372 決定4 の後、別の workspace の子には③が
成り立たず、子の中身は自分の保護ブランチへ着地する。子のまま残すと、中身について判断する読み手 —— 完了時レビューの根、cancel が
捨てる範囲、着地が待つ祖先の PR(`openPrRootAbove`)、親の着地の門 —— のすべてに例外が要る。別の workspace の子を許した根拠の
ADR 0031(委譲の木は場所を跨いでよい)は系譜(ADR 0053)より前の決定で、例に挙げた registry-edit の分解は帰り先の無い系譜では立たず
(ADR 0301 決定7)、別の workspace の子が使われた観測も無い。読み手の数え上げと `file:line` は #1796 に置く。コードと ADR の読みで決めていて、
盤面は走らせていない。

## 決定

1. **workspace を選べるのは根だけで、子は workspace を入力に持たない。** 子を登録する扉(人間の分解、agent の分解、`parent_id` つきの登録、
   WebUI の子を足す form)は workspace を受け取らず、子の Edit にも workspace の欄が無い。子は親に従い、列は場所の固定でだけ書かれる
   (ADR 0372 決定1)。付帯子の review の「違う明示は拒む」(ADR 0290)は、入力が無いことに畳まれる。同じ workspace の中では、①〜③は
   これまでどおり `parent_id` が運ぶ。入力があると、保存するか・何と比べるか・Edit をどうするか・既定が無いときどうするかの規則が扉ごとに
   要り、既定の差し替えや未着手の親の Edit の後に、子が親と別の workspace に残る。
2. **issue つきの子は、親の場所が固定されていて、issue の workspace と一致するときだけ子になる。** issue の参照は workspace を身元の半分に
   持つ(ADR 0016)ので、子の workspace は入力でなく参照から決まる。固定されている = pickup の event か `task_branch_created` を持ち、
   workspace の Edit が凍結されている(ADR 0372 決定5)。それ以外 —— 親が未固定、または一致しない —— は決定3 の根になる。親の場所を止める
   仕組みは足さない。
3. **別の workspace に置く仕事は、分解元つきの根として登録される。** 子を足す操作とは別の操作で、agent の分解では承認 question を経て
   (今ある `allowed_workspaces` 外と保護 workspace の承認と同じ扉)approve で根になり、人間の操作では承認なしで根になる。根は自分の
   workspace の保護ブランチから切られて自分で着地し、レビュー・着地・系譜のどの読み手にも根として扱われる。親はこの根を待たず、親の
   risk flag も引き上げない。
4. **分解元は、分解した task とその分解の判断を指し、委譲の側の読みだけに使う。** 読み手は次のとおりで、中身の読み手(レビュー・着地・
   系譜・登録の床)は分解元を読まない。
   - 文脈: pickup で凍結する分解元の文面(ADR 0321)、`get_current_task` が渡す分解元の `handoff_doc` と history(分解の理由と兄弟の結果)、
     文面の書き手(帰責と学習の起草が分解した agent を書き手として読む)。
   - cancel: 分解元の cancel の cascade(abandon・直接 cancel・redecompose)は、その分解の判断から生まれた未決着の根を子と同じに倒し、
     走っていれば cancel 全体を拒む(ADR 0304)。完了済みの根は動かさない —— 中身は自分の保護ブランチへ運ばれている。
   - 統合: 分解元の worker の history に、根の状態・handoff・着地したかを、決着した子と同じ形で見せる(ADR 0045)。分解元は根を待たず、
     分解元の完了時レビュアーには見せない —— 根の中身は分解元に入っていない。

## 帰結

- ADR 0372 決定4 の「別の workspace に固定された祖先を飛ばす」は、同じ workspace の子しか居ないので当たる場面が無くなる。系譜の規則は変わらない。
- 別の workspace への分解でできる根は自分の帰り先を持つので、ADR 0301 決定7 が理由に挙げた「帰り先を work 自身の workspace で読むか」は
  問う必要が無くなる。ただし帰り先の無い系譜の RCA の下では、その根を立てる承認 question 自体が登録の床で拒まれる(承認で work を立てる
  question は宛先がブランチに依存する、ADR 0301 決定2)。そこを開くかは #2510 が決める。
- 親は別の workspace の仕事の完了を待てない。順序が要るなら人間が、根の着地の後に続きを登録する —— 子の完了は着地ではないので、待っても
  「その変更が使える」は保証されなかった。人間が走り出す前の木に issue つきの仕事を足すと、それも根になり、親のブランチで統合されない。
- 同じ workspace の中で系譜に飛ばされる祖先(未固定の human の祖先、着地済みの祖先、失われて透明な祖先)の下の子は `parent_id` を持ったまま
  自分で着地する。この形の完了時レビューと cancel の読みは #3225 / #3270 が持つ。

## 退けた形

- **子のまま残し、委譲の木と中身の行き先を読み分ける**(この grilling の最初の着地)—— merge back で中身を運んだ先を記録し、完了時レビュー・
  cancel・登録の床・着地の門をその記録と「導出が同じ祖先」の述語で読む形だった。独立の見直しを5回回すたびに、同じ「中身はどこへ行ったか」の
  読みに穴が出た(試行の全記録は #1796)。源の③を閉じれば読み手の例外は要らない。
- **別の workspace の子を分解元の無い根にする** —— registry-edit の worker が「なぜ直すのか」(親の文面・分解の理由・兄弟の結果)を失い、
  帰責の書き手が承認した人間になる。
- **子の workspace の明示を受け、親と比べて保存しない / 拒む** —— 比べる相手(親の導出か、列の埋まった祖先か)・既定が無いとき・Edit の
  規則が扉ごとに要り、比べる相手が後で動くと分類が古くなる。
- **issue つきの子を足すとき親の場所を止める**(空の列に書き、親の workspace の Edit を凍結する)—— 走り出す前の木の親を Edit できなく
  なる。未固定の親の下では根にすれば足りる。
- **分解元が cancel されても根を残し、知らせるだけにする** —— 死んだ計画の文面の上で worker が走り続け、redecompose や retry で根が二重にできる。
