# 失われたと数えるのは「無い」と分かった ref だけ —— 在るか無いか分からなければ回答を拒み、origin の「無い」は fetch への相手の答えで知る

2026-11-24 の triage と grilling(issue #3607。#3562 の仕様レビューの派生)で決定。

ADR 0373 決定5 の give-up は、戻す先の object が無い ref を失われたと数える。ADR 0380 決定4 は、remote-backed なら数える前に origin から取りに行き、origin に届かなければ拒むと決めた。spec #3273 はこれを「2回の `ls-remote` probe の間で落ちた fetch は、origin に無い」と近似し、その窓での誤読は受け入れていた。

実測では、origin が sha を持ったまま fetch だけが stall すると、give-up が受理されて取り消せない `lost_refs_accepted` を書いた。窓は「probe の間に origin が落ちる」よりずっと広い。probe が通る間に fetch だけが落ちる失敗は全部入る —— stall、転送中の切断、5xx、手元の hop2 の失敗、容量不足。手元の判定(`cat-file -e`)も、読めない dir や切れた alternates を「無い」と読んでいた。実測と code の読みは #3607 に置く。

1. **失われたと数えるのは、「無い」と積極的に分かった ref だけである。** 在るか無いか分からない失敗では、何も書かずに回答を拒む。give-up と `restore the baseline` の両方に当たる。上書きの選択肢は足さない —— 相手が無いと言わない内容を捨てる道を常設すれば、取り消せない記録を誤って書く入口を作り直すことになる。
2. **手元の「無い」とは、git がその object を `missing` と答え、ほかに何も報告しないことである。**
   - `missing` と答えて何かを報告すれば「分からない」になる —— 読めない、alternates の先が無い、loose の header が読めない。
   - 型を答えれば、何かを報告していても「在る」とする —— その時点で読めているからである。
   - replace と lazy fetch は切って読む。replace ref は、在る object を何も報告せずに `missing` と見せる。lazy fetch は、手元の読みを網に出す(ADR 0339 決定5)。
   - 手元を読む3つの読み手(失われたかの判定・取りに行く対象・keep-around に持つ値)は、同じ判定を使う。header の読めない loose へ戻す `restore the baseline` は、通る側から拒む側に変わる。
   - ADR 0398 決定3・4 とは食い違わない。読むのは戻す先の数個の sha だけで費用は repo に比例せず、気づいたときに盤面にできること(書かずに止まる)がある。
3. **origin と出元 repo の「無い」とは、その sha の fetch に相手が `upload-pack: not our ref <sha>` と答えたことである。**
   - それ以外の失敗は、すべて「分からない」として拒む。
   - 照合するのは相手の文とその sha だけである。手元の git が前に付ける部分は、翻訳されうるので見ない。
   - 相手を問わない —— GitHub、GitHub でない origin、身元の無い盤面が読む public repo。相手が出さないと答えた sha は、盤面にとっては取り戻せないので「無い」に入る。
   - タスクブランチの sha(出元 repo の写しを含む)は、出元 repo で取れなければ、答えを問わず origin にも聞く。取れれば戻し、両方が `not our ref` と答えたときだけ「無い」とする。
     - 出元 repo は差し替えうる(ADR 0395 決定2)。新しい fork が古い sha を持たないことは、盤面にとって「無い」ではない。
     - sha で引くので、origin から得た object の中身は同じである。ADR 0395 が避けた「宣言 repo で branch を読むと『無い』と読める」は、ここでは起きない。
   - 2回の probe は外す。spec が ADR 0376 決定1 から借りた「git の拒否文を解析しない」は、ここには当たらない —— 0376 の理由は push の拒否文では non-fast-forward と網の失敗を見分けられないことで、この答えは見分けられる。
4. **「分からない」は、取り消せない側への案内より先に出す。**
   - token を待つ前に、戻す先と keep-around の値のすべてを読み、分からなければその場で拒む。この読みは早く拒むためだけのものである。
   - 書き込みの同期区間(spec #3273 の受理の 7b)は、同じ判定で読み直す。失われたと数えるのは、今手元に無く、かつ非同期の段で「無い」と分かった sha だけである。そうでない sha が手元に無ければ、答え直させる(例: await の間に人間が動かした ref)。
   - 在るか無いか分からない sha が1つでも残る間は、「失われた ref が無い」(B4a)、「戻せない」(B3)、「保護ブランチが無い」(B4b)の拒否を出さない。読みは、最初の書き込みより前にすべて済ませる。
5. **拒否文は、壊れているものごとに分ける。** 次の4つで、直す手がそれぞれ違う。
   - 届かない(今の B4c): token が取れない、または出元 repo が宣言されていない。直す手は「待つ、宣言する」。
   - 取れたが「無い」とは言われていない: 直す手は「fetch の原因を直す」。出元 repo が答えないままなら、出元 repo を差し替える。
   - 手元で分からない: 直す手は「名前の場所を直す」。
   - 答えた後に手元が変わった: 直す手は「答え直す」。

## Considered Options

- **spec のまま受け入れる** —— 窓は前提より広い。取り消せない記録の側へ倒れる。
- **stall だけを「届かない」に回す** —— 切断・5xx・手元の失敗が窓に残る。
- **GitHub の GraphQL で object を照会する** —— 使えるのは GitHub の origin だけで、身元も要る。照会は在ると答えるのに相手が出さない object では、回答を拒み続ける。
- **REST の commit の照会** —— GitHub が持つ annotated tag や tree の object にも「無い」(422)と答える。

## Consequences

- ADR 0373 決定5 の「object が無い」と、ADR 0380 決定4 の「origin に届かない」の読みが変わる。spec #3273 の "Unreachable versus not on origin"(2回の probe)と pin B24 の probe の行は、この ADR が置き換える。
- 限界:
  - 相手の答えの文が変わると、本当に無い sha も「分からない」として拒み続ける。誤った記録は書かない。
  - protocol v0 の相手は、unadvertised な object に別の答えを返し、それは「分からない」になる。`allowReachableSHA1InWant` などを付けた v0 の相手は、手元に残っているが ref から届かない commit にも `not our ref` と答え、決定3 の「出さない = 無い」に入る。盤面は `protocol.version` を固定していない。
  - `GIT_NO_LAZY_FETCH` は git 2.45 から効く。それより古い git では、partial clone の名前の場所は「分からない」で止まり続ける。
  - 差し替える前の古い出元 repo にだけある sha は、盤面が古い repo を覚えていないので、失われたと数える。
  - 中身だけが壊れて header は読める loose は、在ると読む(ADR 0398 決定3 の外からの損傷)。
- GitHub と local の bare が `not our ref <sha>` を返すことは、個人の `gh` login で測った(git 2.47)。盤面の App の身元では測っていない。違う答えなら拒む側に倒れる。
- 保留中の設計 #3535 の項4「読めなければ届かなかったと読み、記録せずに数える」は、この ADR と食い違う。
