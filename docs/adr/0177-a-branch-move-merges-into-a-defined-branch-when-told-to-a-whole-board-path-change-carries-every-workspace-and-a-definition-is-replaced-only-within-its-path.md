# 枝の統合は枝ごとの移動が一度に行い、盤面全体の枝の path の変更は全 workspace を連れて行き、定義の置き換えは同じ path の中だけ

2026-09-30 の triage / grilling(issue #1185)で決定。ADR 0176 は枝の改名を枝ごとの移動に寄せたが、統合は「定義を畳む →
配下を移す」の2手のままで、間で配下が定義の無い旧 path に残った(枝ごとの移動は両方に定義があると拒む —— ADR 0162 決定4)。
実測で、盤面全体の枝は単なる改名でも workspace の leaf が旧 path に残ると分かった(枝ごとの移動が運ぶのは1つの scope だけ)。
実測・今の実装・文面は #1185 のコメントに置く。

## 決定

1. **枝の統合は枝ごとの移動が持つ。** 移される定義の行き先(同じ scope・path)に生きた定義があるとき、移動元の定義を
   行き先の定義の `superseded` にし、残りを `path_moved` で移すのを 1 transaction で行う。ADR 0162 決定4 の「両方に Definition が
   あれば拒否する」を改める。
2. **統合は移す者が `merge` を明示したときだけ。** 無ければ今までどおり全体を拒み、衝突する定義の組をすべて名指す。`merge` を
   付けて衝突が1組も無いときも拒む —— 引数は許可ではなく「行き先に定義がある」という申告。
3. **子の枝の定義どうしの衝突も、同じ規則で一度に畳む。** どの定義がどれに畳まれたかは返り値に載る。
4. **残るのは行き先の定義で、統合は文言を取らない。** 文言を変えるなら、統合の前か後に同じ path で書き直す。
5. **盤面全体の枝の path だけを変える移動は、全 workspace の同じ path の配下も同じ行き先へ移す。** 各エントリの scope は
   変わらず、workspace 自身の定義も動き、統合なら衝突はその workspace の中で畳む。scope を変える移動と workspace の枝の移動は、
   今までどおり移動元の scope のエントリだけを運ぶ。
6. **定義の書き込みと畳みが置き換えられるのは、同じ path の定義だけ。** 定義の書き込みの `supersedes` も既にある定義への
   畳みも、別 path の定義は拒んで枝ごとの移動へ案内する(同じ path で scope が違う定義は今のまま)。path を跨ぐ定義の
   `superseded` を書くのは統合だけ。ADR 0176 決定6 を改め、人間の面にも掛ける。
7. **meta-review も統合を直接できる。** 新しい門は無い —— meta-review の移動は同じ scope か広げる向きだけなので、行き先の定義は
   畳まれる定義を必ず覆い(ADR 0161 決定6)、配下には ADR 0176 の門がそのまま掛かる。
8. **人間の面は settings と管理MCP の両方が `merge` を取る。** 決定6 で定義の畳みが path を跨げなくなるので、settings に
   口が無いと WebUI から統合が消える。

## なぜ移動の側か

配下を動かす口が1つなら、ADR 0176 の移動の門(scope の向き・approved の Behavior / Exemplar の scope・提案が名指すエントリ)も
1か所で済む。定義の置き換えが配下を連れて行く形だと、同じ門を定義の書き込みと畳みにも写すことになり、ADR 0176 決定7
(定義の path を変えるのは枝ごとの移動だけ)も反転する。

## なぜ明示が要り、許可でなく申告なのか

統合は戻しにくい —— 畳まれた定義は後継が生きている間は復元できず(ADR 0163)、混ざった leaf は1件ずつ戻すしかない。改名は
移し戻せる。許可として読むと、常に付ける呼び方が通って門が空になる。申告なら行き先の path の打ち間違い(統合のつもりが
定義の無い path への改名になる)も拾う。

## なぜ盤面全体の path の変更は全 workspace を運ぶのか

読み手の INDEX は盤面全体と workspace を重ねた1本の木で、盤面全体の定義は自分の定義を持たない workspace の枝も定義している。
盤面全体の分だけが動くと、その workspace の leaf は定義の無い旧 path に残る。どのエントリの scope も変わらないので届く相手は
変わらず、ADR 0176 の門に触れない。

## なぜ定義の置き換えを同じ path に限れるのか

ADR 0176 が「同じ path に限る」を退けた理由は2つ —— 新しい文言での統合が1手で書けなくなることと、既にある後継への畳みが
path を跨げるままで規則が揃わないこと。前者は決定4 の2手になり、どちらの順でも間の状態は割れていない。後者は決定6 で揃う。
残せば「定義だけ畳んで止まる」割れがそのまま作れる。

## 退けた案

- **別 path の定義の置き換えが配下を連れて行く** —— 配下の移動が3つの口から起き、移動の門を書き込みの verb にも写す。
- **定義を残して配下だけを先に一括で移す** —— 間に未定義の枝は出ないが手数が減らず、子の衝突ごとの畳みも残る。
- **統合を別の verb にする** —— 引数も返り値も移動と同じで、違うのは申告だけ。
- **門なし(行き先に定義があれば統合)** —— 改名の打ち間違いが統合になる。
- **子の衝突は拒んで先に畳ませる** —— 消したい割れを子の枝に残す。
- **統合が新しい文言を取る** —— 移動が定義の書き込みの欄(原文と言語)を持ち、効くのは根だけで子は結局行き先が残る。
- **盤面全体の定義に頼っている workspace の分だけ運ぶ** —— workspace が根に自分の定義を持ち、子の枝は盤面全体の定義に頼るとき、
  残しても運んでも未定義の枝が出る。
