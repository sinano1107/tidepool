# 人間担当の work もタスクブランチを持ち、完了の扉が作業台の tip を取り込んで merge back を撃ち、人間の根は常に merge question で着地する

2026-11-13〜15 の wayfinder(map #3178、入口は #3158)で決定。人間担当の work は盤面にブランチを持たなかった —— ブランチを作るのは pickup の
準備だけで、pickup は人間担当の task を除く。人間の完了の扉は担当と状態だけを見て記録を閉じ、内容は盤面の外で名前の場所に書かれるか、
どこにも残らなかった(#3158 の表の H20)。人間が根の木では、子の系譜が存在しない `task/<親>` を読んで workspace が Quarantine に落ちる
(#1796 の人間版)。この ADR は、人間担当の work がタスクブランチを持つ契機、人間の「書き始める」、取り込みと完了の扉、着地、完了時
レビュー、cancel の面を決める。書く場所(作業台)と受け取る行為(取り込み)は ADR 0371、列・系譜・`task_branch_created` は ADR 0372、
in-flight の守りと最初の撮りの前の確認は ADR 0373 が持つ。場面・読んだコード・`file:line` は ticket に置く(#3207・#3213・#3214・#3215・
#3251・#3245)。コードと ADR の読みで決めていて、人間担当の work がタスクブランチを持つ盤面は走らせていない。走らせたのは、今の着地の面が
dial の無い根と `escalate` の根をどう扱うか(#3243)だけである。

以下、H は人間担当の work、「タスクブランチを持つ」は event `task_branch_created` を持つこと(ADR 0372 決定2)を指す。

## 決定

### タスクブランチと「書き始める」

1. **人間担当の work もタスクブランチを持ち、扉の動作は「担当が人間か」でなく「タスクブランチを持つか」で分ける。** 人間は (workspace,
   `task/<H>`) の作業台で書き、完了の扉がその tip を取り込む。タスクブランチを持たない H は今どおり記録だけを閉じる。人間の成果が agent の
   task と同じ merge commit / PR で履歴に残り、人間が割り振った agent の子は `task/<H>` で統合されて1本で着地する。task と commit を結ぶ
   専用の記録は足さない。
2. **`task/<H>` を作る契機は2つ —— 人間の「書き始める」(`start_work`)と、同じ workspace の子孫の場所の固定(ADR 0372 決定3)。** 登録も
   decompose も契機ではない(workspace が空でありえ、調べ物だけの task にもブランチが立つ)。「書き始める」は pickup と同じ準備(門の検査、
   remote-backed は origin の保護ブランチの fetch、基準の比較か最初の撮り)を通してから、その時点の系譜を fork 元に `task/<H>` を作り、
   作業台を開いて path を返し、event `task_work_started` を残す。準備が落ちれば pickup と同じ扱い(workspace の Quarantine)にして行為を
   拒み、場所を導出できなければ「workspace を Edit で指定してから」と拒む。通さないと、remote-backed では古い保護ブランチから切り、一度も
   pickup されていない workspace では基準を撮らない最初の書き込みになる。2回目以降は同じ path を返すだけで、作業台が disk から消えて
   いれば `task/<H>` から開き直す(取り込んでいない commit は戻らない)。作業台は task の checkout と同じ基点の下に置く —— 盤面の一時
   ディレクトリは boot で空になりうる。path を言う面は「書き始める」の応答、開いている間の task の表示(移動するコマンドと、自前の clone
   から git remote に足すコマンドを出す)、完了の扉の拒否文の3つ。status は `todo` のままで、「着手済み」は `task_work_started` から導く ——
   `in_progress` は DB の制約・人間の扉・後始末が「session が slot を握っている」と読む。
3. **祖先が人間担当でも、固定は同じ1つの規則に乗る。** ADR 0372 決定3 の固定は祖先の担当を問わず、「書き始める」も pickup と同じ固定の
   瞬間になる —— 自分の空の列を書き、タスクブランチを持たない未決着の work の祖先を上から固定する。agent の親が人間に割り振った子も
   `task/<親>` の今の値から切られる。系譜が人間担当の祖先を飛ばす形だと、人間が根の木で子が別々に着地し、子どうしが着地まで見えない。
4. **assignee の Edit の凍結に鍵を1つ足す —— pickup の event か `task_work_started` を持つ task では拒む。** `task_branch_created` は鍵に
   しない(ADR 0372 決定5)ので、子の pickup でタスクブランチだけ先にできた未着手の親は、担当を替えられる(agent ↔ agent、agent ↔ 人間)。

### 取り込みと完了の扉

5. **完了を伴わない取り込みの操作を1つ持つ(`take_in_work`)。完了の扉は「同じ取り込み + `done` + 撃つ」である。** 子の fork 元は名前の
   場所の `task/<H>` だけで、作業台で commit しただけの内容は子に見えない。agent の親は decompose の解放で書きかけが `task/<親>` に運ばれる
   ので、人間の親だけ土台を子に見せられない食い違いを消す。取り込みだけの操作は handoff を取らない。この2つは verb が取り込みの入口に
   なる —— ADR 0371 決定2 の「入口は今ある回答」と ADR 0351 決定4 の「verb は作らない」は conflict を受ける入口についての決定で、
   verb も sha や path は運ばない。
6. **検査は ADR 0371 決定3〜5 をそのまま当てる。** 作業ツリーが tip と違う・gitlink・隠せない形・人間しか書けない path を拒み、全部通って
   から書き、拒まれた操作は何も書かない。内容の検査は、入力の tip(`task/<H>` の今の値と、決定8 で merge した帰り先の値)のどれとも違う
   entry に当て、帰り先から入った変更を人間の変更に数えない。書く前の準備は「書き始める」と同じ。人間しか書けない path を根でも通さない
   のは、通すとその path が保護ブランチへ入る道が2本になるからである。tip が `task/<H>` の今の値と同じなら取り込まずに進み、根なら今の
   `nothing_to_land` が受ける。ADR 0084 決定1 が人間の完了を門の外に置いた理由(ワークスペースを持たず、commit を求める相手がいない)は、
   タスクブランチを持つ H には当たらない。
7. **子の成果への追いつきは人間が merge する。** 盤面は作業台の branch と作業ツリーを動かさず、「書き始める」の再実行と拒否のたびに
   `task/<H>` の今の値を作業台の ref に引き直す。人間の tip がその値を祖先に持たなければ拒む。包む commit の tree は人間の tip のもの
   なので、子の成果を含まない tip を通せばそれを落とす。解決は採点しない(ADR 0371 決定3)—— 子の成果を tree で捨てた merge も通り、
   「落とすには commit を書く必要があり、履歴に残る」で要件を満たす。盤面が clean な merge を代行する形は、取り込みの規則が2通りになる。
8. **帰り先との conflict は `done` の前に拒む。** 帰り先は `parent_id` でなく系譜で決まる —— 非根は系譜の `task/<P>`、根は保護ブランチで、
   別の workspace の親の下の H は根である。拒否のときに盤面が帰り先の値を作業台の ref に引き、人間がそれを merge して完了し直す。作業台を
   持たない H(同じ workspace の子だけが走った)なら、盤面がその拒否の中で開く(ADR 0371 決定7 と同じ形)。このとき `task_work_started`
   は残さず、assignee は凍らない。H の作業台は、子の merge back が `task/<H>` で conflict したときに開く作業台と同じ1つで、既に在れば
   盤面は branch を動かさない —— `task_work_started` の無い作業台がある。その conflict の Quarantine の回答が取り込む tip には、人間の
   書きかけの commit も入る(検査は決定6 と同じ)。先に `done` にして conflict を Quarantine で解く形は、拒まれた完了が書き込みを残す。根で `done` から着地までに保護ブランチが動いた分は、今の着地の question に残る。
9. **順は、検査 → `task/<H>` を書く → `done` → H の1件の merge back → 収束を突く。** 根の着地は収束が拾う。撃つのは後始末と同じ merge
   back を H の1件にだけで、分解ツリー全体の撃ち直しは `retry` と受理に残す(ADR 0371 決定10)—— 扉が撃ち直しを呼ぶと、兄弟が1つ走って
   いるだけで完了できなくなる。`done` の後に merge back が落ちれば積み残しになり、同じ2つが拾う。作業台を持たない H でも撃つ ——
   撃たなければ、子が門を通した成果が `task/<H>` に取り残される。「書き始める」・取り込み・完了は ADR 0373 決定8 の in-flight の鍵に入り、
   走行中の session の有無は見ない。完了の扉は、H の子孫に後始末が済んでいない task があれば拒む(取り込みだけの操作は拒まない)——
   「未完了の子」は status だけを見るので、子が `done` になってから merge back を撃つまでの間に完了すると、子の成果が H を飛ばす。
10. **タスクブランチを持つ H の完了は、agent の work と同じ handoff の全欄を必須にする。** 読み手が agent の側に実在する —— 親の統合復帰
    session、根の PR の本文、完了時レビュー。タスクブランチを持たない H の免除(ADR 0278 決定6)は変えない(#3224)。
11. **cancel は取り込まず、ブランチも作業台も動かさない。** 取り込みは拒みうるので、cancel が取り込むと cancel が詰まる。`task/<H>` に
    集まった子の成果はブランチに残り、運ばれない(agent の cancel と同じ)。`done` では扉が作業台を消し(そこを指す開いた question が
    ある間は消さない)、cancel では disk に残して片付けを後の契機に乗せる(#3057)。

### 着地

12. **着地の候補は、人間担当の work についてはタスクブランチを持つものだけを数える。** これまでは担当が人間の work を候補から外していた
    (内容を盤面のブランチに持たないため)。この除外を決めた ADR は無く、ここで初めて書く。
13. **人間の根は profile なしで着地し、常に merge question を立てる。** purely-local は `local_merge` の question、remote-backed は PR を
    開いた同じ transaction で `pr_merge` の question を立て、CI は `merge` の回答の時点に検査し、`hold` はいつでも答えられる(`escalate` の
    根と同じ手順)。無人 merge キューには入らない。着地の面の判定に「人間の根」を4つ目の入力として足し、読む順は 保護 → 人間の根 → dial、registry の無い盤面でも立つ。profile の解決は `human` を
    agent として引かず、profile なしで返す(agent 名の Quarantine に落とさない)。CI が赤・未報告のときに盤面が自分から立てる経路は足さ
    ない。question なしに着地する経路は作らず、「書き始める」の有無でも子の assignee でも分けない —— 「書く」と「保護ブランチに入れて
    よいと決める」は別の行為で、盤面が記録できるのは「誰が決めたか」だけである。dial を `escalate` と読み替える形は、持っていない dial を
    持つことにするので採らない。

### 完了時レビュー

14. **タスクブランチを持つ H は、agent と同じ統合点(根・risk flag の子・個別に出すと選んだ非根の子)で完了時レビューが立つ。** 運ぶ内容の
    有無は見ない —— handoff もレビューの対象で、決定10 により必ず在る。起票は `done` と同じ transaction。ADR 0111 決定1 は「登録者の宣言に
    よらず」統合点を見ると決めていて、保護ブランチへ着地する内容に担当者で例外を置く理由が無い。人間の根の下の flag の無い agent の子の
    内容は、この根のレビューが読む。着地は今どおりレビューを待たない(所見を待つ人間は merge question を `hold` する)。タスクブランチを
    持たない H には今どおり立てない(その handoff を誰が読むかは map の外、#3226)。
15. **reviewer の指名は完了の扉だけで受ける。** 根と risk flag の子は `review_by` / `review_tier`、非根の子は「個別にレビューに出す」
    (`review_flag`)の選択とその指名を、handoff と一緒に受ける。値は task の列に保存しない。タスクブランチを持たない H の完了は、指名を受けずに
    拒む。登録と Edit は、人間の task の3欄を今どおり拒む。扉は完了の時点でタスクブランチの有無を知るので、効かない値を受ける場面が無い。登録と Edit が掛ける検査(reviewer の門、段が
    生きていること)は扉が書く前に掛け、落ちれば完了ごと拒む。起票の条件だけが、欄の述語(拒否と WebUI の出し分け)から分かれる。
16. **修理子に専用の規則は足さない。** 異議由来は ADR 0237 決定3 のまま人間に戻り、レビュー由来の宛先は agent の根と同じく reviewer の
    選択である。どちらも agent の修理子と同じ系譜に乗る。人間担当の修理子は、場所が固定されなければ(「書き始める」も同じ workspace の子孫の
    固定も無ければ)タスクブランチを持たず、今どおり記録だけを閉じる。

### cancel の面

17. **cancel が見せる「捨てられる done の work」に、タスクブランチを持つ人間担当の done の work を入れる。** 判定は「実行者が人間でない」
    から「ブランチに成果を持つ」に替わる。一覧の目的は cancel で消える成果を見せることで、決定11 により `task/<H>` の内容は運ばれない。

## 退けた形

- **完了の扉は記録だけを閉じ、内容は保護ブランチへ直接入れる** —— 履歴に task の名前が出ず、purely-local しか救えない。
- **人間の根の完了を着地の承認として扱い、merge question を挟まない** —— 「人間が内容を見た」ことを盤面は確かめられず、条件の代用
  (作業台の有無、`task_work_started`)が場面ごとに破れた。agent の子孫の成果を含むときだけ立てる形は、承認と品質の関門を1つに畳む。
- **タスクブランチができた時点で assignee も凍らせる** —— 木を登録して子が1つ走った時点で、根の担当を替えられなくなる。
- **`in_progress` を人間に開ける** —— session が slot を握っていると読む箇所の全部に「人間なら別」の枝が要る。
- **reviewer の指名を Edit でも受ける / 登録時から常に受ける** —— 同じ値の入口が2本になるか、タスクブランチを持たずに閉じた H に効かない
  値が残る。
- **運ぶ内容が無ければレビューを立てない** —— 一度採って取り消した。handoff の誤りも指摘の対象である。

## 帰結

- `review_flag` と reviewer の指名の宣言者は、人間担当の task では登録者でなく完了する人間になる(ADR 0021)。人間担当の子には、登録者が
  レビューを予約する道が無い。
- 「書き始める」の対象は type が work の人間担当の task で、人間面からだけ届く(提示して異論が出なかった帰結)。
- registry の無い盤面では agent の根は「盤面の外」のまま、人間の根だけ merge question が立つ。全 agent が `external` の盤面でも同じで、
  GitHub の側で merge すれば観測が question を閉じる。人間には `external` を宣言する場所が無い。
- 決定8 の拒否の中で開いた作業台に解決の commit を置いたまま、完了せずに H を agent へ振り直すと、その commit は使われない。agent は
  `task/<H>` から始めて同じ conflict に当たるので、内容は失われない。
- 実装の順: 列と系譜(ADR 0372)が先に入る間、人間担当の祖先は固定されず、系譜から飛ばされる。先に固定すると、子の成果が `task/<H>` に
  集まった後、今の完了の扉は何も撃たないので取り残される。
- spec が決める: 取り込みの後に盤面が作業台の branch を進めるか、未取り込みの commit があるまま decompose したときの知らせ、扉が tip を
  読んでから作業台を消すまでに届いた commit、`task_work_started` を持つのに作業台が disk に無い H の完了、兄弟のブランチなど第3の ref を
  merge した tip の扱い、task の表示の review の行、レビュー由来の修理子の宛先を `human` に固定するか(#3178)。
- map の外: 根の判定がレビュー(`parent_id`)と着地(系譜)で食い違う(#3225)、全ての人間担当の task の `outcome` 必須(#3224)、人間
  担当の work を origin 経由で受ける扉(#3232)。
