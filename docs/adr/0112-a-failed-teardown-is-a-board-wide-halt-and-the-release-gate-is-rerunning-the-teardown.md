# 落ちた後始末は盤面全体の停止であり、解放の門は後始末の再実行そのものである

2026-09-10 の grilling(issue #538)で決定。ADR 0109 決定1 が通常完了の解放を後始末へ移した際、`runTeardown` の呼び口は全部 fire-and-forget になり、unhandled rejection で盤面ごと落とさないために全例外が `console.error` へ流れるようになった。固着そのものは持ち込まれていない(変更前も `releaseWorkspace` の throw は slot 解放より手前で経路を切っていた)が、そこへ新しく足された人間向けの signal に2つの欠陥が残った —— 偽の文面の Containment question が1度だけ立ち、回答後は盤面が無言で固着する。現状調査と `file:line` は issue #538 のコメントに置く。

## 決定

1. **落ちた後始末は盤面全体の停止である。** ADR 0109 決定2 は後始末を停止に数えなかった —— 止まっているのではなく枠がまだ空いていないだけ、という理由だった。その理由は**想定どおりに走る後始末にしか当たらない**: 想定外の例外で止まった後始末は人間が来るまで終わらないので「枠がまだ空いていない」ではなく「枠が空かない」であり、停止そのものである。列挙が1行増え、pickup ゲートは配線ではなく列挙から自動でつく(ADR 0068 決定3)。表示順は containment の直後 —— 両方立ったときに先に直すべきはホスト全体の側である。

2. **記録は既存 quarantine 族の機構を借りるが、6つ目の資源ではない。** 実行不能なのは資源ではなく盤面自身のコードであり、「実行に必要な資源が実行不能」という quarantine の定義に当たらない。借りるのは形だけ —— 行に持つのは question の列1つ、1件につき確認は最大1枚、解放は確認回答ただ1つ。`teardown_started_at` は「後始末に入った時刻」のまま意味を変えない(「落ちた」は question の存在が言う)。列を2つに割ると、行と question がずれた状態が表現できてしまう。

3. **解放の門は後始末の再実行そのものである。** 既存の quarantine は例外なく受理の直前に資源を検証し、まだ壊れていれば回答を拒んで question を開いたまま残す。後始末には検証すべき資源が無いので、検査は後始末をもう一度走らせることに一致する。これで「一度回答すると二度と鳴らない」という欠陥は、**鳴らし直す機構を足さずに**消える —— question は後始末が完走するまで閉じない。逃げ道(諦めて枠を解放する2つ目の選択肢)は置かない: tree rule が走っていない workspace へ次の session が入るのは issue #382 の形であり、ADR 0109 決定5 が永続化までして防いだものを人間が1クリックで踏めるようにしてしまう。盤面のコードが直って再デプロイされるまで盤面が動かないことは、この場合ちゃんと正しい答えである。

4. **落ちた後始末は梯子に入らない。** 梯子(強制回収 → 回収 timeout → Containment quarantine)は ADR 0109 決定4 が「最終 verb は着地したのに root が exit しない」だけを見る backstop に退かせたものであり、後始末のコードが投げたことは別の観測である。原因を知らないハンドラに文面を書かせると偽の断言になる —— 容器はもう空なので強制回収は no-op で、続く Containment question は「その session のプロセスがこのホストに残っている」と断言するが実際には残っていない。門は**行に持ち**、`teardownTick` と起動時復旧の両方が読む: in-memory の門は再起動を越えないので、越えなければ再起動のたびに偽の question を1枚ずつ刷る。あわせて、本当に空を観測できなかったときの文面も `in_progress` 側と同じ「残っているかもしれない」へ揃える —— 同じ観測に対する断言の強さが2箇所で違う理由は無い。

5. **question が断言するのは3つだけ。** どのタスクの後始末が・いつから未了で・盤面のコードが投げた例外の本文。原因の所在(バグか環境か)とホストのプロセス状態は断言しない。受理が後始末の再実行であることは本文で予告する —— 予告が無ければ、拒まれた人間は盤面が壊れたと読む。

## 退けた案

- **catch を外して投げさせる** —— unhandled rejection で盤面ごと落ち、未了は行に残るので次の起動でも同じ所で落ちる。
- **既存の Containment quarantine を原因つきで再利用する** —— ADR 0099 決定4 が相乗りさせたのは「このホストに残存 process が居るかもしれない」という**同じ主題**だった。盤面コードの失敗はその主題ではなく、相乗りさせると `containment` の列挙行が封じ込めの健全なホストで立ち、この ADR が直している偽の断言を場所を変えて再生産する。
- **marker に原因を足して読み口だけで言う** —— 読み口は既に後始末を報せている。枠が永久に刺さっているのに能動的に鳴るものが無い状態こそが症状である。
- **受理を検査なしにし、落ち直したら question をもう1枚立てる** —— 既存5族と形が割れ、question が積み上がる。
- **`settled` に解除点を足す** —— in-memory の門なので再起動を越えない。壊れていたのは解除点の位置ではなく、越える門が無かったことである。
