# advisor は opt-in で、配布される既定 agent は持たない —— 費用は per-model 内訳を観測のまま記録する

issue #307 のグリリング(2026-08-21)で決定。worker セッションのトークン内訳を初めて測った結果(測定表は
#307 のコメント)、接頭辞 34.8k のうち盤面が動かせる大きな要素は無く、費用の主因は別にあった ——
`advisor: opus` の相談が1回 $0.26〜0.40、**セッション費用の 30〜40%** を占め、7 セッション中で実バグを
捕まえたのは1回だった。CONTEXT.md の Advisor 項は issue #33 以来「運用上は原則すべてのエージェントに付与
し、外したい特殊ケースだけ無効化する(fix-forward のほうが高い)」としていたが、それは**運用者の見解**で
あって、配布する既定に課してよい線ではなかった。

## 決定

1. **advisor は agent 単位の opt-in のままとし、種(`templates/registry/agents/*.md`)の agent からは
   `advisor:` 行を外す。** 配布される既定は最小の床と、運用者が足せる余地を提供するものである。運用上は
   付与が有利だという見解は撤回しない —— ただし「黙って全員に適用する」ことを正当化するには費用が重すぎた
   (上記の実測)。付与は運用者がその registry で決める。kill switch(ADR 0043)と記録の2枚(spawn 時の
   ピン留め / 終了時の観測)は無傷。
2. **`worker_exited` に CLI の per-model 内訳(model id → tokens / cost)を観測のまま載せる。** 既存の
   `usage.advisor.usage` は7セッション全てで null だった —— CLI が advisor の model id を名指しするのは
   最終ターンに相談があった場合だけで、それ以外に帰属の根拠が無い。内訳の「main でも helper でもない残り」
   を advisor と読む規則は 7/7 で一致したが採らない: helper が走ったかどうかに意味が依存する推論であり、
   盤面の記録は機械観測に限る(Advisor 項 / Remote 操作の経路記録と同型)。内訳をそのまま残せば、読み手が
   `worker_spawned.advisor` と突き合わせて1相談の費用を事後に確定でき、main と同一モデルに解決した場合も
   「分離不能」が数字の形でそのまま残る。`advisor.usage` の意味は変えない。
3. **組み込みツール面(ADR 0039)は触らない。** 接頭辞の 62% がツール定義だが、役割のあるツールだけで
   約 17k、vendor の system prompt 9k は盤面から触れない。todo 族(`TaskCreate` 等、約 3k)は Subagent と
   同じ側 —— 説明責任を分割しないセッション内の足場 —— であり、短いセッションで未使用だったことを
   「役割が無い」とは読まない。

## Considered options

- **tako だけ外し fugu(review)には残す** —— review は判断の重さで opt-in に値するが、それは運用者の
  判断であって種が先取りする理由にならない。種は両方外す。
- **`WORKER_PROTOCOL` に「相談は判断点でのみ」を足して反射を抑える** —— 「毎回ちょうど1回」が反射か
  どうか未検証のまま指示を足すことになり、指示を足す方向は本 issue が警戒していた力そのもの。
- **todo 4本 / `NotebookEdit` を費用で落とす**(約 9%)—— 床の決定(ADR 0039)に「費用」という第2の
  理由を持ち込む対価に見合わない。`NotebookEdit` の agent 単位 opt-in も、床をデータに依存させ
  (ADR 0013)vendor のツール名を registry に持ち込むので採らない。
- **ターン数を減らす指示の効果測定(#307 作業項目3)** —— 費用以外の動機が無く、効く根拠も無いので
  issue にせず取り下げ。
- **WebFetch の egress 残余を再検討** —— ADR 0034 / 0072 が受容済みの既知の残余で、新しい事実は無い。
