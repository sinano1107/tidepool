# ベンチマークは使い捨て VM の盤面で課題集を構成ごとに走らせる器であり、最適化プロセスの様子見はその読み方の1つである

**Status 追記: 決定5 の費用の列は ADR 0299 決定5 で支出の目的で分けた** —— 課題の行の費用は記録から学ぶ支出(RCA・修理子)を除いた分に
なり、学ぶ支出・人間面・観測は走行の節に出る。課題は仕事の課題と最適化の課題(Interview)の2種類で、後者は期待解を持たない
(2026-10-22 の grilling、issue #2447)。

2026-10-22 の triage → grilling(issue #1880)で決定。#1880 は ADR 0244 決定6 が名指した「自律最適化プロセスの隔離環境での様子見」の設計
だったが、欲しいのは門の前の1回の様子見ではなく、tidepool がどんな仕事を対処でき、構成(版・model の組)で何が変わるかを定量的に、
繰り返し測る器だった。4つの最適化プロセス(memory / routing meta-review、Interview、学習器)の判断の質を読むのは、その器の最初の読み方。
材料の出どころ・読み口・既存の道具・列の表は #1880 のコメントに置く。

## 決定

1. **ベンチマークは1つの骨格で、様子見はその読み方の1つ。** 骨格は「使い捨ての盤面 + 人間が期待解つきで書いた課題集 + 走る前に固定した
   基準で記録を読む」。課題を実運用の盤面で走らせる案は退ける —— 課題の episode と Precedent が本番の学習に混ざり、ADR 0273 決定7 が
   受験者を集計から外した問題をもう一度作る。Interview とは別物で両方残す: Interview は盤面が自分の候補 model を段に対して選別する機構、
   ベンチマークは人間が外から盤面を製品として測る機構。
2. **場所はベンチマーク用の Lima VM 1台で、走行ごとに状態を消す。** host の Mac には立てない(ADR 0100 決定2)。見たい行で走らせるには
   自前の `/login` が要る(ADR 0262)ので VM の寿命に1回 login し、走行ごとに DB・worker-logs・workspaces を消して checkout を測る commit
   に動かす。門の盤面(#1879)と同じ VM には立てない —— 本番の記録を汚す経路を残さない。
3. **種は課題を実際に走らせて作る。** memory の材料の異議の帰責は Board call だけが、routing の材料の worker の終了と配分評価は実 session
   だけが書くので、DB への手書きは材料にならない。本番 DB の写しは面接室の絶対 path が焼き込まれて移せない。
4. **構成の軸は4つで、走行の記録が外側で持つ**: tidepool の commit、CLI の pin(ADR 0186)、実行設定の表の行、registry の commit。
   registry の既定は template の種で、ref を引数に差し替えられる —— 本物の registry を既定にすると自分の環境の測定になる。
5. **「対処できた」は課題が持つ期待解(テスト)で決め、盤面の決着は列として記録するだけ。** テストは land question の後の保護ブランチで
   走らせる。定量の列は課題ごと、4プロセスの判断の質は人間が読む列のまま。
6. **走行中の question と異議は人間が盤面の面で入れる。台本は持たない。** 実運用でも人間を待つのは同じで、待つことは棄却の理由にならない。
   課題の README が手順で書き、harness は課題の登録・決着待ち・抽出だけを持つ。
7. **読み口は盤面の WebUI と、抽出した走行記録の2本。専用のビューは作らない。** 記録は `docs/experiments/benchmark/results/` に構成を鍵に
   置く。走行後の状態は harness が消さず、人間が消す。
8. **契機は3つ(CLI の pin を上げる、表の行を変える、release)で、人間が Mac から走らせる。** 既定は全課題 × 表の既定行、総当たりは明示時
   だけ。スケジューラは作らない(#361)。
9. **meta-review の初回の登録の時点はここで決めない(#2437)。** 今の機構では最初の材料の次の poll で初回が登録され窓が閉じるので、1走行で
   meta-review が読める材料は最初の課題だけになり、memory の初回は店を直接書き換えて以後の課題に効く。ベンチマークの初回走行は #2437 の
   決定の後に走る —— 実運用でも初回の meta-review は真っ先に動く機能で、門の前に決まっている必要がある。

## 退けた案

- **様子見を `docs/real-environment-trial.md` に段を足す形で組む** —— Pi の v1 立ち上げの配管の確認で、主題が違う(ADR 0244 と同じ)。
- **`bootTidepool` を実 provider で in-process に走らせる** —— 前例が無く、clock・容器・Board call client・MCP URL を手で配線することになる。
- **meta-review を今すぐ登録する扉 / 周期登録の保留スイッチ / pause に登録も止めさせる** —— 初回の登録の時点への継ぎ当て(決定9)。
- **課題の question に harness が台本で答える** —— 走行のたびに台本を書く手間に対して読み手が無い(決定6)。
- **ベンチマーク専用の時系列ビュー** —— 読み手が人間1人で、盤面の面が既にある部分を二重に作る(決定7)。

## 帰結

- CONTEXT.md に ベンチマーク / 課題 / 走行 を足し、Interview の項に境を1文足す。
- GitHub の PR 面(ADR 0265)は測らない。PR 経路の確認は #1879 の close 条件1 が持つ。
- #2437 が着地したら同じ課題集を新しい commit で走らせる。commit 間の比較がこの器の最初の使い道になる。
