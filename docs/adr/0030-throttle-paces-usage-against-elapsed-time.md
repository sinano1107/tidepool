# Throttle は一律閾値ではなく経過ペースとの差で絞る — オフセットは人間の取り分の予約、解除は catch-up 時刻

ADR 0008 / 0028 の一律閾値(デフォルト80%)は「上限の手前で止まって守る」線だったが、実運用の目的は守ることではなく**ウィンドウ全体で一定ペースを保ち、予算を使い切ること**にある。一律閾値は序盤に守るべきでないもの(まだたっぷりある予算)を守らず、終盤に使うべきもの(もうすぐ失効する残り)を止める。そこで判定式を `throttled ⟺ 使用率% > 経過時間割合% − オフセット(pt)`(strict 比較)へ転換する。経過割合はウィンドウ開始時刻から出すが、開始は観測できないため `リセット時刻 − ウィンドウ長` で逆算する — ウィンドウ長は session = 5時間 / week = 7日の**ハードコード定数**(Anthropic のプロダクト事実であり盤面の運用ノブではない。仕様が変われば /usage 書式変更と同類のスクレイパー破損イベントとして定数を直す)。逆算の不整合は既存の fail-closed(観測不能 → throttled)に落とす。

**オフセットの向きは「遅れ」であり、意味は人間の取り分の予約。** 使用率はアカウント単位で、人間自身の対話利用も同じ予算を食う。盤面が常にペースからオフセット分だけ遅れて走ることで、空いた分が人間の取り分として残る。ウィンドウ開始直後のオフセット相当時間は使用率ゼロでも throttled になるが、これは予約の意味論そのものであり床(floor)の特例は足さない。オフセットはウィンドウごとの盤面設定(DB + WebUI、既定 session = 20pt / week = 10pt / fable = 10pt。不正値は入口で弾いて既定へ)。環境変数 `TIDEPOOL_USAGE_THRESHOLD` は廃止。

**throttled の解除タイマーはウィンドウのリセット時刻ではなく catch-up 時刻**(`経過割合 = 使用率 + オフセット` になる瞬間、複数線超過時は最大値)に張る。リセット待ち + 毎時 tick のままだと、ペースが追いついてから次の tick までの遊休(最大約1時間)が毎サイクル累積し、後半ほど理想ペースから遅れてウィンドウ末に使い切れない — 「一定ペースで使い切る」の実装上の急所はこのタイマーである。

**fable ウィンドウ(週次・リセットは week と同時刻)はタスク単位の絞り。** fable の週予算の逼迫は fable を使うタスクにしか関係ないため、pickup 候補の assignee を registry に解決して agent 定義の `model` が fable のタスクだけを skip し、他は流れ続ける(Quarantine が確立した「資源単位の停止」の前例に沿う。盤面全体で止めると sonnet タスクまで道連れになり、使い切りの目的と矛盾する)。**fable 行の不在は fail-closed にしない**: session / week が健全にパースできているパネルに fable 行が無い場合は「個別制限のないプラン」(Pro — fable 制限自体が存在しない)と読み、fable タスクは全体線だけで流す。不在を観測失敗と誤読すると Pro プラン運用時に fable タスクが恒久 skip になる。パネル全体が読めないときだけ従来どおり全体 fail-closed。per-model 行だけ書式が変わった場合に「制限なし」と誤読する残リスクは、全体線と100%キャップが被害上限を抑え、UI の可視化(ADR 0028 の「fail-closed は可視化とセット」の延長 — ウィンドウ別の状態と再開見込み時刻を表示)で人間が気づける道を確保する。パーサは推測書式に書かず、**実機 PTY キャプチャで fable 行のラベルを確定してから**実装する(issue #79 の教訓)。

**Spend-down(使い切り)**: 終盤に残り予算を盤面で燃やし尽くすための人間専用の盤面状態。対象ウィンドウ(session / week)を選んで有効化し、**対象のペース線だけ**を外して100%ハードキャップ(全ウィンドウ常時有効の唯一の上限)に切り替える。原則は「**使い切ってよいのは、もうすぐ失効する予算だけ**」— 燃やしたトークンは他方のウィンドウにも同時に算入されるため、失効しない側の線(人間の予約含む)は Spend-down 中も生き続ける。この帰結として session 使い切りが week の線で途中停止することはあり得るが、それは失敗ではなく「余りだと思ったトークンは week の生きた予算だった」という正しい教示である。Spend-down(week) は fable の線も外す(同じ瞬間に失効する予算)。対象ウィンドウのリセットで自動失効(取り残された状態は必ず放置 — Pause の純手動解除とは逆の線)、手動取り消し可、再起動を跨いで維持、Pause とは独立で Pause が勝つ。100%付近で spawn したタスクが走行中に上限を踏んで強制終了されるリスクは Spend-down に内在するが、既存の watchdog / failure question 経路が受ける。

Considered options:

- **一律閾値の維持(値だけ調整)** — どの値を選んでも「序盤に緩く終盤に厳しい」か逆かにしかならず、時間軸に対する一定ペースを表現できない。
- **乗算係数(`使用率 > 経過 × 係数`)** — 経過とのマージンが終盤ほど膨らみ(150%なら経過10%で+5pt、経過90%で+45pt)、一定ペースにならない。加算形はマージンが全期間一定。
- **先行許容オフセット(`使用率 > 経過 + オフセット`)** — 序盤のまとまった先行消費を許す向き。盤面が常に人間より先に予算を取る形になり、Tidepool 以外の対話利用の取り分を確保できないため逆向き(遅れ = 予約)を採用。
- **fable 行不在を fail-closed にする** — Max プランでは書式変更の検知として働くが、Pro プランでは fable 行が正常に存在しないため fable タスクの恒久 skip を製造する。「session / week の健全パース」を読み取り健全性の証拠に使う読み方に変えた。
- **fable 逼迫で盤面全体を止める** — 実装は現行機構のままで済むが、fable と無関係なタスクまで道連れに止め、使い切りの目的と真っ向から矛盾。
- **Spend-down が全ウィンドウの線を外す** — 「使い切り」の字面には忠実だが、失効しない側の予算(翌日以降の盤面の稼働分 + 人間の予約)まで燃やす。失効時刻を共有する線(week と fable)だけを束ねる形にした。

Consequences:

- throttle_state は単一の throttled/resetsAt からウィンドウ別の状態(どの線に当たっているか・fable の観測状態・再開見込み時刻)へ拡張され、UI 表示も同様に拡張される。resets_at の意味は「リセット時刻」から「再開見込み時刻」へ一般化される(fail-closed 時は従来どおり null)。
- fable 判定のために pickup 時に assignee → registry → `model` の解決が入るが、これは spawn 時と同じ経路の前倒しであり新しい観測は増えない。
- Pro プラン時に fable モデルのタスクが絞りを素通りして spawn し CLI レベルで失敗する経路が残る。事前ブロックではなく quarantine 族の事後隔離(spawn 失敗の観測 → 資源 needs-human)として別イシューで扱う(issue #124)。
