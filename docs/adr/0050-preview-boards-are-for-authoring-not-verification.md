# プレビュー盤面はオーサリングのための面であり、検証ではない

WebUI を直している最中に自分の目で画面を見たい、という需要(発端は設定画面の改修)に対して、ローカルに**プレビュー盤面**を立てる口を持つ。`bootTidepool` の上に、このリポジトリにコミットされた既定値フィクスチャの registry を載せた盤面を起こし、実ブラウザで触る `scripts/preview-<画面>.ts` を画面ごとに置く。

**ADR 0029 は反転しない。** 0029 が廃止したのは**検証** — 「この導線は動くか」という判定行為で、成果物(spec)が残り、エージェントが Playwright で担う — であり、本 ADR が足すのは**オーサリング** — 「直している最中にどう見えるか」を人間が自分の目で見る反復で、成果物は残らない — である。0029 はこの行為を一度も扱っていない。受け入れ確認のゲートは廃止されたままで、プレビュー盤面は何のゲートでもない。

## 安全は4つの不在で定義される

プレビュー盤面は、worker を spawn せず(`ScriptedWorker`)、GitHub 身元を持たず、本番 registry を読まず、push の行き先を指定するつまみを持たない。

4つ目は push を**禁じているのではない**。remote はフィクスチャが自分で作る一時的な bare repo で、そこへの push は成功し、平常の `pushed: true` の見え方がそのまま出る — 本番で push は成功するのだから、失敗側の劣化表示しか見られないプレビューは「本番と同じ見た目」を名乗れない。不在なのは行き先を**変える口**のほうで、env でもフラグでも指定できない。誰かがデバッグのために一行書き換えれば本番 remote を指せてしまう、という余地を残さないための不在である。

この4つが揃っているから、人間が本番の運用状態を一切気にせず触れる。

## 既定値はフィクスチャであって本番 registry ではない

プレビューが読む registry は `tests/registry-fixture.ts` が組み立てる使い捨てのクローンで、内容はこのリポジトリにコミットされたコードである。本番 registry(`tidepool-registry`)のクローンは読まない。理由は、**確認のために実運用の設定を歪めないため** — 「エージェントカードが5枚並んだときの折り返し」を見るために本番へ5体登録するのは本末転倒であり、逆に本番を読む設計はその歪め方しか提供しない。副作用として、プレビューは本番 registry のクローンが手元に無いホストでも動く。

盤面は**起動のたびに既定値から作り直される**(一時ディレクトリの git repo と一時 DB)。永続にしないのは、使うほど歪んで「常に同じ既定の見え方」という存在理由そのものを壊すからであり、見たい状態はフィクスチャへの追記としてコミットされる — その形なら再現でき、レビューでき、次に見る人にも同じものが出る。

## 腐らせない配線を1箇所に集める

前例の `scripts/preview-issue-states.ts` は、ADR 0036 / issue #153 で人間面に credential が入ったときに沈黙のうちに壊れた。`e2e/fixtures.ts` は `bootstrapUrl()` を踏む形へ直されたが、スクリプトは直されず、出力される URL は 401 を返し、必要なトークンはプロセス内で生成されて表示すらされない状態のまま数週間放置された。`scripts/` は `tsconfig.json` の `include` の外で、誰も走らせていなかった。

したがって: 盤面を起こして bootstrap URL を返すまでの配線は `tests/` 側の1箇所(`bootPreview()`)に集め、`scripts/preview-*.ts` は「呼んで出して待つ」だけの殻にする。vitest が `bootPreview()` を起こして `/` が 200 を返すことを主張し(今回の壊れ方はこれで落ちる)、`tsconfig.json` の `include` に `scripts` を足す。型検査だけでは足りない — 壊れたのは配線の形ではなく意味だった。

## Consequences

- **保存の失敗系は見られない。** 保存は本物として動き(使い捨て registry への実コミット + 一時 bare repo への push)、平常の `pushed: true` の見え方が出る。コンフリクトや権限エラーの文言は、常に成功する以上ここでは再現できず、e2e の scratch spec の領分に残る。
- **プレビュー実行中はワーキングツリーの `_ds_bundle.js` が書き換わる。** `components/` を watch して再ビルドするため(ビルドは 0.2 秒・決定的なので、変更検出は持たず無条件に走らせる)。本来あるべき状態を保つ方向の変化だが、git の差分は増える。
- **画面ごとにスクリプトが要る。** 全画面を1つの盤面で賄う形は採らない — `e2e/fixtures.ts` が `boot(opts)` を関数として配っているのと同じ理由で、必要な seam が画面ごとに違う。
- **`scripts/preview-issue-states.ts` は削除する。** 壊れてから誰も困らなかったこと自体が需要の不在の証拠であり、腐った実装を蘇生させるより新しい土台の上に書き直すほうが安い。

## Considered options

- **本番 registry のクローンを読む** — データのドリフトが構造的に起きない点は魅力だが、見たい状態を作る手段が「実運用を歪める」しか無くなる。棄却。
- **永続のプレビュー盤面**(`~/.tidepool-preview/` などに registry と DB を置く)— 触った状態が残る代わりに、誰がいつ何のために作ったか分からない状態が「既定の見え方」の顔をするようになる。リポジトリルートに残っている出所不明の `board.sqlite` が実例。棄却。
- **実合成の staging をローカルに立てる**(`npm run start:live` の系統)— 実 worker が spawn され、保存が本物の registry へコミットされ、credential ファイルが本番盤面と衝突する。将来の需要としては正当だが別物であり、本 ADR は `bootTidepool` 側にしか触れないので独立に検討できる。
- **スクリーンショットだけで済ませる**(エージェントが scratch spec で撮って人間に送る)— 今日そのまま動き維持コストもゼロ。レイアウトの微調整には足りるが、ホバーやダイアログを自分で開いて手触りを決める反復には負ける。
- **Makefile で `components/` の更新を検出してからビルドする** — 検出が節約するのは 0.2 秒で、代償は新しいビルドシステムと二重化した導線。棄却。
