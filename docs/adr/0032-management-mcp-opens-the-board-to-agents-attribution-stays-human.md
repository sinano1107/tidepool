# 管理MCP は盤面をエージェントに開くが、操作の帰属は常に人間

issue #131(管理用 MCP の作成)の grilling(2026-07-27)で決定。出発点は「盤面を人間だけでなくエージェントにも開く」— これまで盤面の操舵入口は WebUI(人間が直接操作)しかなく、人間が対話しているエージェントセッション(Claude Code 等)から盤面を触る道がなかった。素朴には「エージェントが盤面を管理する新しい主体クラス」を作りたくなるが、それは question 回答・cancel・triage・最終監査といったドメインの土台(最終監査者 = 人間)に張られた「人間」の線をすべて引き直す大改定になる。

**管理MCP は WebUI と同格の「もう一つの人間向け UI」であり、操作の帰属は常に人間(義手モデル)。** 呼び出しの主体がエージェントセッションであっても、そのエージェントは人間の手の延長として盤面を操作するにすぎず、question 回答・cancel・Edit・登録・人間 decompose・人間タスクの完了・issue コメント追記・registry 管理は**すべて人間名義**で永続化される。この一点で、盤面をエージェントに開きながらドメインの不変条件を1つも書き換えずに済む — 「question 回答 = 人間の判断」「registry の人間発変更 = 盤面が main へ直接コミット」「保護 workspace への変更は常に人間承認」はそのまま成立し、推奨受理率も MCP 経由の回答を人間として算入する。

**Worker MCP とは別の面で、worker session からは届かない。** 既存の Worker MCP は slot 帰属の worker session が使う道具で、authority profile が権限を縛る前提の上に立つ。管理MCP はその外側 — 人間向けリスナーに mount し、worker には Worker MCP の URL しか渡さない。新しい credential は作らない: WebUI と同一の信頼域に揃えるのが最小の設計であり、認証を足すなら /api を含む人間向け app 全体で一括すべき別の工事になる(v1 のブロッカーではない)。worker が Bash で localhost の人間用 /api を curl で叩ける既存の柔らかい穴はこの設計とは独立の hardening として別 issue に切り出し、#60(OS サンドボックスによる worker の読み取り封じ込め)と同じ post-v1 の線に置く。

**経路(webui / mcp)を操作イベントに機械記録する。** 帰属は人間でも「どの手から入ったか」はイベント履歴に残す — エージェントが人間に確認せず question に回答するような事故を、推奨受理率などの統計を汚染源まで遡って追跡できるようにするため。自己申告ではなく機械観測で、Advisor の実効構成を機械記録するのと同型。

**ログ読取は純読取。** Decision log を管理MCP から読んでも、未読カーソル(前進のみ)も Displayed も一切動かさない。「ログが人間の視界に入った」は盤面が直接観測できる WebUI だけが記録できる事実であり、エージェントが人間に伝えたかどうかは自己申告になる — 観測として扱えば異議率の分母(表示済みのみ)が「人間が見ていないかもしれない表示」で膨らみ、「未観測 ≠ 承認」の原則が壊れる。代償として MCP でいくら読んでも未読は減らず、同じログが次の triage に現れる。

Considered options:

- **エージェントを盤面管理の新しい主体クラスにする(操作をエージェントに帰属させる)** — question 回答・cancel・triage・最終監査に張られた「人間」の線をすべて引き直す必要があり、最終監査者 = 人間という土台を揺るがす。義手モデルはこの土台を一切触らずに盤面をエージェント駆動へ開く。
- **管理MCP に専用 bearer token を張る / 人間向け app 全体に認証を入れる** — 前者は /api が無認証のままなので worker は /api 経由で同じ操作ができてしまい防御として片手落ち、後者は WebUI / PWA 側の認証実装を伴う大きめの工事で issue #131 の範囲を超える。v1 は WebUI と同一信頼域への mount で成立させ、curl 穴は別 issue の hardening に送る。
- **経路を記録しない(WebUI と MCP を完全に無差別化する)** — シンプルだが、経路起因の事故(勝手な question 回答)が起きたとき遡って調べる手段がない。イベントは追記型で後から経路を埋められないため、記録するなら最初から。
- **MCP のログ読取で未読カーソルを進める / Displayed を発行する** — 二度読みは減るが、「人間の視界に入った」をエージェントの自己申告で成立させることになり、異議率の分母が膨らんで「未観測 ≠ 承認」が壊れる。
