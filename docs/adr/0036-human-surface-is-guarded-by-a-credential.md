# 人間面は credential で守る: worker のネットワーク到達を塞ぐ設計をアプリ層の認証に置き換える

issue #140 の再グリリング(2026-07-29)で決定。**ADR 0034 を supersede する** — 不変条件の枠組みは受け継ぐが、執行の主機構・極性・二段構造のすべてが実機実験の結果で置き換わった。0034 は却下オプションの記録として無傷で残す。ただし却下理由が全部生き残るわけではない — pf / nftables と WebFetch 丸ごと deny の却下理由は今も有効だが、**netns の却下理由(「macOS に無く dev/prod 乖離原則に正面衝突」)は実測が逆を示した**。Linux backend の netns は本番 Pi の不変条件を追加設定ゼロで支えている当のものであり、本 ADR の canary 節もその事実に依存している。生き残るのは「tidepool が**自前で** netns 層を足す手は採らない」という狭い主張だけである。

**不変条件は 0034 のまま宛先で定義する** — 「worker セッションからは、ツール・経路を問わず人間面(WebUI / /api / 管理MCP)に到達できない」。**ただし 0034 が割った二段(操作 = 完全閉鎖 / 読取 = 監査つき受容)を一段に戻す**。読取も閉じる。credential は経路を問わないので、WebFetch 経由の読取残余も同じ一枚で消える — 0034 が読取を受容したのは「Bash はフィルタで塞げるが WebFetch はサンドボックスの外を通る」という機構の非対称が理由であり、認証にはその非対称が無い。

## 転換の根拠(実機実験、2026-07-29、macOS 2.1.220 / 本番 Pi 2.1.207)

0034 は「サンドボックスのネットワークフィルタが宛先 host:port 単位の deny を表現できるか」「netns 相当の意味論が取れるか」を実機で確定する変数に挙げていた。答えは**プラットフォームで割れ、macOS 側はどちらの枝にも着地しなかった**。

1. **loopback 宛の deny は macOS の設定語彙に存在しない。** Seatbelt profile は `(deny default)` から始まり、`allowLocalBinding: true` のときだけ `network-bind` / `network-inbound` / `network-outbound (remote ip "localhost:*")` の3行が**一括で**入る。loopback 宛は OS レベルで許可され proxy に到達しないため、`deniedDomains` は `host` 表記でも `host:port` 表記でも効かない(陽性対照の `example.com` は同じ機構で 403 になるので、キーが死んでいるのではない)。`allowLocalBinding` を落とせば人間面は塞がるが**同時に bind も死ぬ**(#146)ので、「bind は許すが人間ポート宛は塞ぐ」は現行 CLI で表現できない。
2. **Linux は極性 (ii) を追加設定ゼロで既に満たしている。** bwrap backend は `--unshare-net` による本物の netns で、sandbox 内 loopback はホストと別世界。人間ポートにも Worker MCP ポートにも届かず(`ss -tln` はブリッジの 1080/3128 しか見せない)、自前サーバーを立てて自分で叩く npm test / webui-e2e のパターンは無傷。
3. **したがって 0034 の「主機構 = サンドボックスのネットワークフィルタ」は macOS で成立しない。** 守れているのは本番 Pi だけで、弱いのは開発機という非対称になった。ADR 0033 の乖離原則が最も嫌う「本番が弱い側」とは逆向きだが、乖離そのものは残る。
4. **帰属訂正**: ADR 0033 の #146 追記が「本番 Pi でも `allowLocalBinding` は効く」と読んだ測定は、実際には netns により**キー無しでも bind が成功する**ことの観測だった。キーの帰属が実測で立っているのは macOS 側のみ(0033 に反映済み)。

## スコープ: 不変条件は全ホストで維持する

「弱いのは開発機だけだから受容する」は採らない。**dev 盤面は本番と registry を共有している** — 開発機の `~/tidepool-registry` のリモートは本番 Pi と同じ `sinano1107/tidepool-registry` の main であり、人間面には `POST/PATCH /api/agents` `/api/workspaces` `/api/profiles`(= 共有 registry への直接コミット)が生えている。0034 が本丸に据えた資産のうち registry は、dev 盤面経由でも本番と同じ物に届く。「弱いのは開発機だけ」はホストの所在を見ており、資産の所在を見ていない。加えて、将来 Mac に盤面をデプロイしたくなったときに破綻する設計を今選ぶ理由が無い。

## 主機構: 人間面の credential

**ホスト・プラットフォーム・経路のいずれも問わない唯一の手**であり、Bash も WebFetch も loopback も tailnet も同じ一枚で閉じる。盤面が worker に取れない秘密を持つこと自体は新種ではない — GitHub token(ADR 0024、`TIDEPOOL_GITHUB_TOKEN_FILE`、mode 600 強制、fail-closed)の二例目である。ADR 0032 の「新しい credential は作らない」も覆らない: あれは**管理MCP が自前の鍵を持たず人間面リスナーに相乗りする**という意味であり、人間面全体に認証を足しても管理MCP は依然として自前の credential を持たず、人間面の1つを提示するだけである。

形は以下。

- **守る範囲は人間用リスナー全体** — 静的資産・`/api`・そこに mount される管理MCP を1本のミドルウェアが守る。**Worker MCP は守らない**。`server.ts` は人間用の `app` と Worker MCP の `mcpApp` を別ポートで立てており、後者に credential を掛けると全 worker が死ぬ。Worker MCP のアクセス制御は `?task=` が slot の現在タスクと一致すること(concurrency = 1 なので、ある瞬間に有効な id は自分のものしか無い)+ 各 verb 実行時のサーバー側 authority 解決のままで、ここは escalation 経路になっていない。
- **ブラウザは cookie、道具は bearer ヘッダ、両方受ける。** 静的資産まで守ると決めた以上、ヘッダ一本は原理的に選べない — ブラウザのトップレベル遷移にヘッダは付けられないからである。cookie は `HttpOnly` / `SameSite=Lax`。`Strict` は採らない: スマホでメッセージアプリから bootstrap URL を開くというクロスサイト起点のトップレベル遷移で cookie が送られず、導線が壊れる。CSRF は `SameSite=Lax`(クロスサイト POST には付かない)と `/api` の JSON content-type 要求(クロスオリジン fetch に preflight を強制し CORS で落ちる)の二重で閉じる。`Secure` は付けない — loopback は http であり、tailnet 側は tailscale が TLS を終端している。
- **盤面はハッシュだけ保存する。平文はディスクに残さない。** 初回起動時に生成してその場で表示し、以後は `hash(token)` だけが残る。理由は #151: **work プロファイルの worker は `Read` ツールで cwd 外の任意の絶対パスを読める**(Bash は同じファイルを OS に拒否されるのに、Read は素通しで読む。review が塞がるのは床ではなく `manual` が未承認のツール呼び出しを一律拒むため)。平文をどこに置いても worker に読まれるので、**盤面側の複製については credential の秘密性をどの床にも依存させない**形を採る。

  **ただしこれが切るのは盤面側の依存だけである。** 管理MCP は bearer ヘッダで認証するため、その平文は `claude mcp add --header` により `~/.claude.json` に保存される — MCP が自動で認証する以上、**クライアント側の複製のどれか1つは必ず平文でディスクに存在し、その秘密性は #151 の読み取り床に依存する**。設計で回避できる箇所ではない。今これが潜在的なのは、対話セッションが Mac に、worker が Pi にあって同じホストに同居していないからにすぎず、**顕在化するのは本 ADR がスコープを全ホストに広げた動機そのもの、すなわち Mac に盤面をデプロイする場面である**。したがって #153 には「worker を走らせるホストでは管理MCP を設定しない」という運用制約が付き、**#151 が解決した時点でこの段落ごと消える**。Mac に盤面を立てるなら #151 が先、という条件もここから出る。

  副産物として `npm run token` の意味は「再表示」ではなく**ローテーション**になり、道具側も平文を持たなくてよくなる — deploy-pi のスモークは token を運ばず「無認証で叩いて 401 が返ること」を主張すればよく、これはリスナーの生存と認証の作動を同時に測るので従来の「200 が返ること」より強い。
- **bootstrap はオリジンごと・端末ごと。** cookie はオリジン単位なので、Pi では `127.0.0.1:4589` と `raspberrypi.tailc0084f.ts.net:8443` の両方が要る。`npm run token` は盤面が知る全オリジンぶんの URL を出す必要があり、そのために公開 URL を設定として持つ(自力では導出できない)。
- **401 の見え方**: HTML のルートには **token 入力欄を持つ小さな静的ページ**を返す — インストール済み PWA はアドレスバーが無く、「この URL を開いてください」と書くだけでは端末が復旧できない。このページは盤面の状態を持たないので無認証で返してよい。`/api` と管理MCP には素の 401 JSON。

## ネットワークフィルタは多層の一枚へ格下げ

`deniedDomains: ["*.ts.net"]` を両プロファイルに入れる。主機構ではなくなったが、入れる理由は残る — **同じ Pi の `:443` に、アプリ層の認証をまったく持たない context-vault(将来のタコツボ)が tailnet 公開されている**(#150)。tidepool 側をいくら固めても、worker から見て隣に無防備な個人ナレッジストアが立っている状態は消えない。CIDR エントリ(`100.64.0.0/10`)は**その帯に解決される名前宛のリクエストを塞がない**(実測)ので、0034 の「CGNAT 帯は全帯 deny」は名前パターンでしか表現できない。MagicDNS の短縮名が `*.ts.net` にマッチするかは未測定で、canary で恒常的に測る。

**追記(#152 実装時、実機で測り直した結果、2026-07-29)**: MagicDNS の短縮名は `*.ts.net` にマッチ**しない**。`src/sandbox.ts` の `buildSandboxSettings` から実際に emit した settings を使い、実 worker と同じ spawn フラグ(`--allowedTools` なし)で計測した — 完全名 `raspberrypi.tailc0084f.ts.net:8443` への `CONNECT` はプロキシが `403 Forbidden` / `X-Proxy-Error: blocked-by-allowlist` で拒否する一方、短縮名 `raspberrypi:8443` への `CONNECT` は `200 Connection Established` でトンネルが通ってしまう(その先の TLS ハンドシェイク失敗はプロキシ層とは無関係)。`deniedDomains` に短縮名の生文字列 `"raspberrypi"` を列挙すると両方とも `403` になることを確認した(独立した2回の invocation で再現)。したがって `deniedDomains: ["*.ts.net", "raspberrypi"]` を両プロファイルに入れる。短縮名には共通の suffix がないため、パターンではなく既知のホスト名を列挙する形を採った。deploy-pi の canary(#154)は、この完全名 + 短縮名の両方を撃つ形をそのまま引き継ぐ。

**tailnet は信頼境界ではない。** `tailscale serve` は身元ヘッダを注入できるので「tailnet 経由は身元があるから素通し」にしたくなるが、worker が走るのは開発機や Pi という tailnet ノードそのものであり、worker の WebFetch から出た要求も人間と同じノード身元を持って到着する。認証は経路を問わず一律に効かせる。

## fail-closed は ADR 0033 に相乗りする

ゲートが答える問いを「このホストでサンドボックスに**入れるか**」から**「このホストで worker の封じ込めが成立しているか」**に広げる(概念としては**封じ込め能力**)。停止も question も1つのまま — 人間から見た結果が同じなのに停止機構が2つあると「今どちらで止まっているのか」を読み解く仕事が増える。認証側の検査は「token が読めた」ではなく、**自分の人間ポートへ無認証で1回リクエストして 401 が返ること**を測る(前者は自分のコードを信じるだけ、後者は組み上がった実物を測る)。現在 `sandboxPickupBlocked` は `app.listen` より前に呼ばれているので、自己検査は listen 後に回す。

**人間面は fail-open、pickup ゲートは fail-closed** — この非対称は意図的である。認証が立たない盤面では worker が1つも走らないので、開いている人間面に対する敵が存在せず、開いていること自体が「question を読んで直す」という人間の復旧経路になる。Pi で起動そのものを拒むと ssh するしかなくなる。将来の読者がこの fail-open を「バグ」として塞がないよう、ここに書いておく。

**追記(#154 実装時、2026-07-30): 上記の設計どおりに入った。** #153 の時点では対になる pickup ゲートが無く、人間面だけを開けると裸の盤面になるため暫定で fail-closed(全部 401)に倒してあったが、#154 でゲートが入ったのでその暫定は消えた。現在:

- 使えるハッシュを持たない盤面は人間面を**開ける**(`isAuthorized` が true を返す)。
- 同じ状態を封じ込め能力の自己検査が捕まえる — 無認証の `GET /api/tasks` に 200 が返るので不成立になり、盤面全体の pickup が止まって確認 question が1枚立つ。
- 実装は `src/containment.ts`(検査とゲート)と `src/auth.ts`(fail-open)に分かれ、両方に「この非対称は意図的、統一するな」と書いてある。

**fail-open 中は `/api` の JSON content-type 要求が CSRF の唯一の壁になる。** 二重に閉じるうちの一枚目 `SameSite=Lax` は cookie の属性であり、cookie を1枚も使わない盤面では何も守っていない。「認証があるのだから content-type 検査は冗長」という理由でそこを畳むと、認証が立っていない盤面 — つまりこの検査が単独で立つべき唯一の盤面 — が無防備になる。

**復旧の順序に落とし穴が1つある。** `npm run token` は既存の cookie を殺すので、人間は**先に**新しい bootstrap URL を開かないと、ゲートを解除する question に回答できない。この一文は doc だけでなく question の本文にも入れてある。

## e2e canary は結果で主張する

同じ不変条件が3つの見え方で守られる — macOS の loopback は**到達したうえで 401**、Pi の loopback は netns により**接続不成立**、tailnet は deny により **403**。したがって canary は「入れないこと」を、`401` / `403` / 接続失敗の**3つに限定して列挙**した許容結果で主張し、プラットフォームごとに期待値を書き分けない(ADR 0033 が読み取り床で取った立場と同じ)。「200 でなければ合格」にはしない — 404 や 500 は穴が別のパスに移っただけの状態を通してしまう。撃つ先は認証があれば 200 を返すパスとし、tailnet は完全名と短縮名の両方を撃つ。**認証層そのものは canary からは測れない**(Pi では接続が成立しないため)ので、そこは上記の盤面自己検査が担う — canary はネットワーク層を、自己検査は認証層を測る、という分担になる。

**追記(#154 実装時、2026-07-30): canary は「測れなかった」を合格にしない。** 許容結果を3つに限定しても、**撃つ前にその宛先が生きていたか**を見ないと同じ穴が裏口から入る — 盤面が動いていない macOS で撃てば、サンドボックスの中でも外でも接続失敗になり、何も守られていなくても3つの許容結果の1つが返る。しかも macOS の loopback は「到達したうえで 401」という形を出せる**唯一**の盤面である(Pi は netns で接続自体が成立しない)ので、そこが黙って空振りすると canary の情報量はほぼ消える。したがって実装(`.agents/skills/deploy-pi/scripts/containment-canary.sh`)は宛先ごとに**サンドボックスの外から先に1回撃って基準線を取り**、判定を4値にする: PASS(基準線が生きている ∧ 中からは 401/403/接続失敗)、**VACUOUS**(基準線が死んでいる = 結論を出せない)、**DECLINED**(セッションがプローブの実行を断った — これも封じ込めについて何も語っていない)、FAIL(それ以外)。後ろ3つはいずれも非ゼロ終了。

**「接続失敗」の判定でもう一度同じ穴が開きかけた。** 短縮名の実際の形は `CONNECT` が **`200 Connection Established`**(= トンネルは開いた = worker は外に出た)で、その後 TLS が SNI 不一致で落ちるというものである(#152)。curl の終了コードだけを見ると「接続に失敗した」に見えるため、素直に書くと**穴そのものが許容結果の1つとして緑になる** — `deniedDomains` から `raspberrypi` を消しても canary が通ってしまう状態だった。判定は `http_connect == 200` を「到達」として**プロキシ層で先に**確定させる。TLS がその後どう転んだかは封じ込めではない。この分岐は `scripts/containment-canary.test.sh` が固定している。

Considered options:

- **不変条件を本番のみに縮め、dev の弱さを監査つきで受容する** — dev 盤面が本番と registry を共有している以上、資産の所在を見ていない。0034 が「経路単位で塞ぐと issue を増やし続ける」として宛先で切った判断を、ホスト単位で緩めることになり、同じ形の綻びを別の軸で作る。
- **fail-closed で止める(macOS 盤面は agent タスクを pickup しない)** — 新しい機構を作らず ADR 0033 の器にそのまま乗る最も安い手で、「守れない場所では worker が走らない」という形で不変条件を満たす。将来 Mac に盤面をデプロイしたくなった時点で破綻するため主機構には採らないが、**認証が成立しなかったときの受け皿として本 ADR に残っている**(上記 fail-closed 節)。競合ではなく層である。
- **人間面を unix socket に退避する** — macOS のサンドボックスは AF_UNIX を既定で拒否する(`network.allowUnixSockets` / `allowAllUnixSockets` を書かない限り)ので床としては成立する。しかし**ブラウザは unix socket を開けない**ため、dev の玄関を tailnet に出す必要があり、今 loopback に閉じている dev 盤面をクロスホストの読取面に晒す。操作の穴を塞ぐ代わりに読取面を広げる取引になる。Linux の unix socket 遮断は seccomp 依存(`@anthropic-ai/sandbox-runtime` 不在なら素通し)で、socket パスを読み取り床の裏に置いて fs 床に肩代わりさせるという層をまたいだ依存も生む。
- **平文の token をファイルに置き、読み取り床で守る** — #151 により work プロファイルの Read ツールに床が無く、成立しない。ハッシュ保存はこの依存を切る。
- **tailnet の身元ヘッダを信頼する** — worker が走るノード自身が tailnet ノードなので、人間と worker を区別できない。
