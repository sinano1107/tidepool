# エージェントのレビュー要請は flag で開き、type では開かない

2026-07-15 の grilling(「review flag の opt-in を誰が宣言できるか」)で決定。実装上 `review_flag` は人間の登録経路にのみ存在し、decompose の `ChildSpec` には無かった — エージェント発のレビュー要請はゼロ経路であり、それが意図した線なのか未実装の穴なのかが未記録だった。

決定:

- **`review_flag` の宣言者は登録者であり、人間・エージェントを問わない。** decompose の子に宣言でき、検査も承認変換も一切ない。review flag は監視への opt-in であって権限を1ミリも広げない — 害のある方向は「外す」であって「付ける」ではなく、escalation の「上方向は決して制限されない」と同じ側の操作である。生成される review は Auditor(独立レビュー)に解決されるため、自分の子に付けても身内に甘い審査にはならない。乱発のコストは登録時に塞がず、meta-review が蒸留すべき統治パターンの側に置く(ADR 0010 の線)。
- **review type の登録はエージェントに開けない。** flag が「完了物のレビュー要請」を、escalation が「独立監査の提案」をカバーし、独立監査の入口は人間の2つ(scratchpad の meta-review 振り分け / Register 直接登録 — issue #61)のまま。
- **flag は登録後不変**(risk_flag と同型 — 登録時宣言のみ)。外す経路は監視の骨抜きなので開けない。後から付けたい人間にはルート review(独立監査)という既存の道がある — 対象は purpose の散文が運ぶので「タスク X の成果物をレビュー」と書けばよく、完了時レビューとの差は自動性だけ。実需が観測されたら編集の再検討はあり得る。

この非対称は権限の理屈では説明できない: review type は spawn 時にコード定数の reviewer profile で上書きされる(ADR 0013)ため、work の子より権限が**狭い**。狭い方向の委譲を塞ぐ根拠は入口の管理 — 独立監査は人間の操舵チャネルであり、ルート/親なし review の対象は purpose の散文が運ぶ(issue #61)ため、人間の目を経ない散文が Auditor の行動指針になる経路は flag より一段慎重に扱う。

Considered options:

- **エージェントにも review type の子を開ける** — reviewer profile は work より狭いので権限では塞げないが、入口を「2つ」と閉じた直後(issue #61)に第3の入口を開くことになる。escalation という安全弁で足りるかを観測してから開けても遅くない(additive で可逆)。
- **flag も塞ぐ(レビュー要請は常に人間の判断)** — 慎重になりたいエージェントの道が escalation だけになり、設問化のコストが review 1本より高くつく。監視の**追加**を塞ぐ理屈が立たない。
- **flag を可変にする(後から付ける・外す)** — 外す方向は骨抜き。付ける方向はルート review が既にカバーする。risk_flag(登録時宣言・変更経路なし)と可変性の規則が割れ、語彙が濁る。
