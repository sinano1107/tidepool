# 答えを取りに行く盤面呼び出しは空のツール面を宣言する —— 翻訳はさらに推論の不在を宣言し、自前のシステムプロンプトを持つ

issue #224 で決定。ADR 0044 が Board call について引いた「不在は呼び出しごとに明示的に
宣言される」という線を、advisor から**ツール面と推論**へ延長する。

## 発見の経緯と実測

decision log 画面で「訳をそえる」を有効にすると表示が遅い、という観察(ADR 0052 の
実環境動作確認 第1段)から。1件の翻訳に入力 18.6k・出力 4.5k を払っていた。

### フラグの比較(開発 Mac / haiku-4-5 / 英語 ~640文字の decision-log 風テキスト)

共通フラグは本番と同じ `-p --output-format json --model haiku --effort low
--max-turns 1 --safe-mode`、共通 env は `CLAUDE_CODE_DISABLE_ADVISOR_TOOL=1`。

| 構成 | 追加した手 | input | cache_read | cache_create | output | cost |
|---|---|---|---|---|---|---|
| A | (当時のまま) | 10 | 17,794 | 4,181 | 1,314 | $0.0175 |
| B | `--tools ""` | 3,922 | 0 | 0 | 1,349 | $0.0114 |
| C | B + 素朴な `--system-prompt` | 378 | 0 | 0 | **3,626** | $0.0193 |
| D | B + `MAX_THINKING_TOKENS=0` | 3,892 | 0 | 0 | 286 | $0.0061 |
| E | D + 素朴な `--system-prompt` | 348 | 0 | 0 | 296 | $0.0026 |
| F | B + `--effort max` | 3,922 | 0 | 0 | 1,262 | $0.0110 |
| G | D + `--exclude-dynamic-system-prompt-sections`、同一プロンプトを2連続 | 3,716 | **0** | **0** | 308 / 301 | $0.0060 |

### 本番 Pi での再現(2026-08-10 / claude 2.1.221 / markdown 入りの原文)

| | input | cache_read | output | cost | 実時間 | peak RSS |
|---|---|---|---|---|---|---|
| 当時のまま | 10 | **17,536** | 1,274 | $0.0163 | 14.0s | 301MB |
| 採用案 | 457 | 0 | 172 | **$0.0021** | **7.4s** | 302MB |

`cache_read` 17,536 は issue #224 本文が本番で観測した値と一致する —— 同じ現象を
測っている。コスト −87%、実時間 −47%。

読むべき点は6つ。

**1. `--allowedTools` ではなく `--tools` である。** issue の仮説(ツール定義が
システムプロンプトに載ったまま)は正しかったが、綴りが違った。`--allowedTools` は
permission 面を絞るだけで、**定義は載ったまま**である。定義そのものを積まないのは
`--tools ""`(CLI ヘルプ: 「Use "" to disable all tools」)。入力 22k → 3.9k。

**2. `--effort` は haiku 4.5 で観測可能な差を生まない。** low と max で出力
1,349 vs 1,262(各 n=1)。サーバ側が effort をどう扱っているかはここからは確認
できないので、記録するのは**差が観測されなかった**ことまでである。翻訳のコストを
effort で下げようとしても徒労であり、下げる口は推論の側にある。

**3. 出力側の本体は推論である。** `MAX_THINKING_TOKENS=0` で出力 1,349 → 286。
訳文自体が ~290 トークンなので、当時の出力の8割は捨てられる推論だった。
対応する CLI フラグは存在せず(`claude --help` を `think` / `budget` / `reason` で
検索、いずれも該当なし)、env がこの CLI における唯一の綴りである。

**4. `--system-prompt` は文言次第で毒にも薬にもなる。** 素朴な1文(C)は入力を
378 まで落とす一方で出力を 3,626 に爆発させ、**当時より高くつく** —— 既定の
システムプロンプトが推論の量を抑えていた側面がある。要求を書き下した版は安いだけ
でなく訳文の質も既定版より**上**だった(既定版は「ペーシング スロットル」に不要な
空白、「5 時間」「41 分」と数字前後に空白が入る。書き下し版はいずれも出ない)。
既定のシステムプロンプトはコーディングエージェントの人格であり、翻訳者としては
雑音である —— 3,600 トークン払って翻訳に不利な指示を積んでいた。

**5. prompt cache は使えない。** `--tools ""` を撃つと `cache_creation` /
`cache_read` がどちらも 0 になり、**完全に同一のプロンプトを2連続で撃っても
効かない**(G)。`--exclude-dynamic-system-prompt-sections` が削るのは 176 トークン
で誤差である。当時 17.8k が cache_read に乗っていたのはツール定義が大きかったから
であって、キャッシュが翻訳のために働いていたわけではない。

**6. プロセスの重さはトークンと無関係である。** peak RSS は構成に依らず ~300MB。
この事実は本 ADR ではなく ADR 0063 が扱う。

## 決定

**1. Board call のうち「答えを取りに行くもの」は、空のツール面を明示的に宣言する。**
`--tools ""` を渡すのは AI 下書き(`ClaudeDraftClient`)と表示時翻訳
(`ClaudeTranslationClient`)の2本。ADR 0044 が数えた5本のうち残る3本 —— skill 列挙
ping(ADR 0025)・ツール面 probe(ADR 0039)・使用量スクレイプ(ADR 0028)—— には
渡さない。

線は「モデルターンが立つか」ではなく **probe か否か**で引く。残る3本はいずれも
CLI の状態を**観測しに行く**呼び出しであり、観測対象の環境を観測者が削るのは
自己矛盾である。とりわけツール面 probe は `--tools spawnTools("work")` を意図的に
渡して観測された `tools` 配列を盤面の宣言と照合しているので、ここを `""` にすると
照合が常に「観測 ⊂ 期待」へ倒れ、**封じ込め能力の不成立 → 盤面全体の pickup 停止**
になる。skill 列挙 ping に足さない理由も ADR 0039 が既に一度書いている(「skill 列挙は
user tier の skill を見るのが目的で、そこに足すと集合が壊れる」)—— そこにトークンの
節約は無く、「この ping は何を観測しているのか」を読みにくくするだけである。

この決定は新しい機構ではない。`--tools` は ADR 0039 決定1 が worker spawn のために
既に置いた語彙であり、**init イベントの `tools` 配列を読めば観測できる**ことを理由に
選ばれていた。同じ理由が Board call 側でもそのまま働く —— 空のツール面は宣言であり、
宣言どおりかは観測できる。

**2. 表示時翻訳は、さらに推論の不在を宣言する。** `MAX_THINKING_TOKENS=0` を渡す。
env 変数名は `claude-worker.ts` に定数として1回だけ置き、`ADVISOR_DISABLE_ENV` と
並べる。ADR 0044 がその定数に書いた理由 ——「『このセッションには advisor がない』は
綴りが厳密に1つでなければならない。typo は fail open して、しかも静かに失敗する」——
が文字列 env である本件にもそのまま当てはまる。

**`boardCallEnv()` には畳み込まない。** 「推論しない」は全 Board call について真では
ない —— AI 下書きは brain dump からタスクを組み立て、issue の登録可否を判定する
生成タスクであり、推論が仕事の一部でありうる(sonnet で走っており、effort が効く
世代でもある。計測は別 issue)。畳み込めば ADR 0044 が防いだ失敗 ——「Board call だから」
で括って個別の性質を潰す —— を別の軸でやり直すことになる。`boardCallEnv` に真偽値の
引数を生やす案も同じ理由で採らない: あの関数は「Board call である」という1つの事実
から env が決まる形をしており、引数が付いた瞬間に呼び出し側が毎回2軸を判断させられる。

**3. 表示時翻訳は自前のシステムプロンプトを持つ。** 翻訳の要求(訳文のみを返す・
markdown 構造を保つ・識別子とコードスパンは訳さない・翻訳調にしない・省略や
並べ替えをしない)を `--system-prompt` として渡し、user prompt は対象言語と原文だけ
にする。文言は `src/claude-translation-client.ts` の定数として置く —— これは翻訳という
機能の**実装**であって設定ではなく、registry や workspace が触れる値ではない。
外部ファイルへ切り出すと「設定に見えるもの」が1つ増える。

引き受けるものが3つある。(a) CLI 既定システムプロンプトの今後の改善から翻訳だけが
外れる。裏返せば CLI の変更で翻訳の挙動が勝手に変わることも無くなり、再現性は上がる
—— ADR 0005 が「ホストの最後の選択が run に漏れてはならない」と言ったのと同じ向き
である。(b) `--safe-mode` の役割が変わる。`--system-prompt` を渡した時点で CLAUDE.md は
載らないので、`--safe-mode` は hooks / plugins / MCP を止める役として残る。(c) この
数行がそのまま盤面の翻訳品質の仕様になる —— issue #48 の「翻訳調は不採用」という
基準を、機械が読める場所に初めて書き下すことになる。

**4. `--effort` は残す。** 効果が観測できないことは、ピン留めをやめる理由にならない。
ADR 0005 は「CLI はホストが最後に選んだ model/effort を覚えていて、無関係な
ディレクトリでの切り替えが実行に漏れ込む」からピン留めしろと言っている。外すことは
ピン留めをやめることであり、翻訳のモデルが Claude 5 系へ移った日にホストの最後の
effort 設定が翻訳へ漏れ込む。`pinnedModelFlags` が worker / draft と共有されている
以上、翻訳のためだけに分岐させれば「ピン留めの形は1つ」という設計意図が崩れる。

**5. 翻訳を CLI 以外の口へ移さない。** issue #224 の未決事項「そもそも翻訳を CLI
セッションで回すのが妥当か」への答え。理由は2つ。**回避する対象が残っていない** ——
入力 457 トークンの中身はシステムプロンプト ~200 + user prompt ~250 で、ほぼ全部が
翻訳そのものである。当初 22,000 あった「CLI だから乗るもの」は数十トークンまで落ちた。
**CLI は非効率な経路ではなく subscription への唯一の口である** —— 盤面は OAuth
subscription 認証で走っており(`--bare` を使わない理由がまさにそれ)、生の API へ
移せば `ANTHROPIC_API_KEY` の従量課金になる。すると ADR 0030 の pacing が見ている
同じアカウント予算から翻訳が抜け、`/usage` scrape も翻訳の消費を報告しなくなる。
issue #224 が問題視した構図 ——「盤面が自分の記録を人間に読ませるためのコストが、
盤面が働くための予算を削る」—— は**解消されるのではなく、見えなくなるだけ**である。
安さと引き換えに観測可能性を捨てる取引であり、ADR 0041 / 0043 が積み上げた線と
逆を向いている。

## Consequences

**空のツール面は観測できるが、推論の不在は観測できない。** 決定1 は init イベントの
`tools` 配列に現れるので、効かなくなれば見える。決定2 の env は未文書のつまみであり、
CLI が名前を変えるか無視するようになれば**何も壊れずにコストだけ静かに 2.5 倍へ戻る**
—— ADR 0039 が「deny 層は黙って効かなくなりうる」と警戒したのと同じ失敗の形である。
救いは翻訳の usage が1件ずつ `translation_cache` に保存されていること(`input_tokens` /
`output_tokens` / `estimated_cost_usd`)で、回帰は事後には見える。

**計器は新設しないが、既にある読み口に顔をつける**(issue #273)。`GET /api/translate/usage`
は `translation_cache` の全行を返す実装が既にあり、そのコメントは issue #47 の意図を
そのまま書いている ——「record it the same way worker sessions do, make it observable」。
にもかかわらず**どの画面もそれを叩いていない**。記録も読み口もあって、顔だけが無い。

ADR 0044 決定5 が「盤面呼び出し側に計器を作らない」と決めたのは**存在しえない状態**の
計器についてであり、ここで検知したい状態 —— ベンダーが env の名前を変えて推論が戻る ——
は構造的に起こりうる。盤面には防げず、検知しかできない。そして issue #224 自身が代償を
実演した: 1件 $0.03〜0.05 という消費は最初から保存されていたのに、数か月のあいだ誰も
気づかず、人間が「訳がなかなか出ない」と言うまで見つからなかった。**記録があることと
検知されることは別である。** 足すのは顔だけで、新しい API も新しい記録も増えない。

**能動的な検知(閾値を超えたら decision log に出す等)は作らない。** それは新しい機構で
あり、ADR 0044 決定5 が拒んだ側に入る。顔をつけても人間が settings を見に行かなければ
検知は起きない —— この限界は自覚のうえで受け入れる。

**prompt cache が使えないことは受け入れる。** 457 トークンを毎回定価で払う。キャッシュ
に乗せるためにツール定義を積み直すのは本末転倒であり(A の実測がその値段である)、
`--exclude-dynamic-system-prompt-sections` で稼げるのは 176 トークンにすぎない。

## Considered options

- **`--allowedTools ""` を渡す(issue の当初仮説)** —— permission 面しか動かず、
  ツール定義は載ったままである。この案は「`--allowedTools` で足りるのでは」という形で
  再提案されやすいので、上の表を残す。
- **`--system-prompt` を渡さず、既定のシステムプロンプトに乗る** —— 入力 3,855 で
  $0.0058(採用案の 2.5 倍)。かつ訳文の質は**下がる**(上の点4)。当初この案を
  推したが、要求を書き下したシステムプロンプトとの比較で覆った。
- **素朴な `--system-prompt` を渡す** —— 出力が 3,626 へ爆発し、当時より高くつく(C)。
  「システムプロンプトを短くすれば安くなる」という直感が成り立たないことの実測である。
- **`MAX_THINKING_TOKENS=0` を `boardCallEnv()` に畳み込む** —— 決定2 のとおり。
- **`--effort` を外す** —— 決定4 のとおり、ADR 0005 のピン留めをやめることになる。
- **翻訳を生の Anthropic API へ移す** —— 決定5 のとおり、subscription の外へ出る。
