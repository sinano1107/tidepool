# 軌道修正は checkpoint 機構ではなく文脈の可視化で賄う

issue #171 で決定。懸念は「decompose された子タスクが順に処理される間、親の想定どおりに
進まなくても、親には統合復帰まで軌道修正の機会が無い」だった。調査で判明したのは、
問題の核が判断機会の不足そのものではなく、**記録は在るのに届いていない**ことである:
子は決着済み兄弟の handoff doc を読めず、親の分解理由(decision log)も渡らず、
統合復帰・retry したセッションは自分自身の decision log すら読めない。worker が
文脈を得る唯一の窓 `get_current_task` の視界が「自タスク + 親1ホップの内容 +
自分の settled 子」に限られていたためである。

## 決定

**1. 子完了ごとの親 checkpoint 機構は作らない。** 壁は3つ: (i) 未決着の子を持つ親は
blocked であり走れない — checkpoint は「blocked 中の親の spawn」という新セッション
種別を要求する。(ii) checkpoint で親が残りの計画を修正しように も、エージェントに
子を cancel する権限は無い(cancel は人間の判断のみ)— 修正権限の新設は権限モデルの
大工事になる。(iii) 判断点が無くても毎子1セッションを燃やすポーリング型のコスト。
これらを越えるべき痛みはまだ観測されていない(observed pain over speculation)。

**2. 子が親 agent に question して完結する機構も作らない。** 親のセッションは子の
実行時点で既に死んでおり、「親に聞く」の実体は「同じ記録を読んだ別のモデル
インスタンスを spawn する」ことでしかない。生きた記憶は存在せず、親の知識は
decision log / purpose の記録が全てである。Question =「人間の判断を求めるタスク
type」の線(義手モデル・異議率の分母など複数の不変条件が乗る土台)も守られる。
権限内判断の質は advisor が既に担う。親の agent 定義(専門性レンズ)だけは記録に
還元されない実在の差だが、**計画の正否がレンズの未記録の側面に依存しているなら、
それは decompose の記録が不十分だという説明責任の穴**であり、修理は相談機構ではなく
外化の作法(決定4)が担う。

**3. 代わりに、既に在る記録を届くようにする(文脈の可視化)。** 1つの拡張 —
**親1ホップの視界に「親の settled 子」を加える** — が二役をこなす: work 子から
見ればそれは決着済み兄弟の handoff doc(先行結果との食い違いに気づいた子は既存の
escalation で人間を呼べる)、review タスクから見れば被レビュータスクが decompose
した子たちの handoff doc(「子のレビューは親に委譲される」の統合点レビュアーが、
統合された部品の記録を初めて読める)。合わせて: 自タスクの decision log を全タスクに
(統合復帰・retry の意図継承)、親の decision log を review 限定から全子に開放
(分解理由の伝達)、settled 子の文脈に question の purpose を追加(watchdog 失敗の
状況説明が復帰セッションに届く)、そして再開の合図。合図は spawn 文言の per-task な
変化ではなく **WORKER_PROTOCOL の静的な1行**で綴る — 再開の事実は注入される記録
(自分の decision log・回答済み failure question)から導出可能であり、盤面が
別途宣言すると briefing とずれうる第2の情報源になる。プロンプト層は全タスク不変の
まま、タスクの状態は `get_current_task` 一本に揃う(WIP コミットの存在だけは
briefing に映らないため、doctrine の1行が `git log` の確認を課す)。注入は**全文・切り詰めなし**: 統合復帰する親は
既に全子の handoff を全文受け取っておりその量は受容済み。肥大するほど子が多い計画は
注入の問題ではなく分解の粒度が粗すぎる兆候である。

**4. 外化の作法: 親のレンズにしか無い判断材料は decompose 時に外化する。** 実行に
効く制約・意図は子の purpose と分解理由(decision log)へ書き落とす。外化の失敗は
子の escalation や統合時の手戻りとして観測され、fix-forward → 親 agent の
instructions 改善のループが拾う。相談機構を作ると、書き落としを構造的に許す方向に
圧が掛かる — 機構の不在自体がこの作法の執行装置である。

**5. 逐次 decompose は可能なまま残るが、作法としては推さない。** 親が次の1歩だけを
decompose すれば統合復帰が毎子後に起こり、checkpoint 相当は今日の機構で表現できる。
しかし計画の全体像がボードから消え(生きている計画を映すというボードの存在意義と
衝突)、親の意図はセッション分断のたびに記録経由の継承に晒される。不確実性が
極端に高い計画で worker が自ら選ぶことは妨げないが、既定の作法は「確信のある
計画を一括 decompose + 文脈の可視化 + 統合点での再 decompose」である。

## Considered options

- **毎子完了後に親を checkpoint spawn する(issue の原案)** — 決定1 の3つの壁。
  再提案されるとしたら「(iii) のコストは許容できる」という形だろうが、(i)(ii) は
  コストではなく構造の変更であり、痛みの観測が先である。
- **逐次 decompose を正式な作法にする** — 本 grilling の中間案。ボードの可視性と
  意図継承の脆さ(決定5)で退けた。
- **子→親 question 機構** — 決定2。「親はシステムプロンプト(専門性レンズ)を
  踏まえて考えられる点で advisor と違う」という反論は正当だが、その差が効く場面は
  文脈の可視化後には狭く、レンズの task 関連部分はそもそも外化されているべき(決定4)。
- **兄弟 handoff の要約注入(全文ではなく1行 + 取りに行く verb)** — 「読める記録が
  在るのに届かない」を形を変えて再生産する。handoff doc は文脈のみを運ぶと定義された
  セッション間文脈の乗り物であり、痩せさせるのは存在意義と矛盾する。

## 追記(2026-08-05、issue #179 / ADR 0047)

決定3 が挙げた注入は「親の decision log」と「親の settled 子」という**2つの別々の束**を
渡す形だったが、子の側からそれを噛み合わせる手段が無かった — 同じ「記録は在るのに届いて
いない」の穴が処方箋自身の中に残っていた。ADR 0047 が実装スコープを次のとおり改める。

- **項目1** — 親の子は settled に限らず全て届き(未決着の兄弟は title / purpose /
  completion criteria / status)、依頼内容(purpose / completion criteria)も運ぶ。決定4 が
  定めた外化のチャネルは2本あるのに、届く配線が分解理由の1本しか作られていなかったため
- **項目2 / 項目3** — decision log と子は `history` という1本の年表に織られ、自タスクにも
  親にも同じ形で当たる。あわせて親の `handoff_doc` の review ゲートを外す
- **項目4** — 決定5(内容三つ組)に吸収される
- **項目5** — 影響なし

決定5 の「親1ホップ」の線は維持する(ADR 0047 決定8)。決定4 の外化の作法は、人間 decompose の
分解理由が任意から必須へ変わることで1段強くなる(ADR 0047 決定7)。
