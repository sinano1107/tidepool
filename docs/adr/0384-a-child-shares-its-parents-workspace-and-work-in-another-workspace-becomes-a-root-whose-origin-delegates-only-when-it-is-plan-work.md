# 子は親と同じ workspace に居て、別の workspace への分解は分解元つきの根になり、分解元は計画の work なら委譲の親、それ以外なら文脈だけを運ぶ

2026-11-19 の grilling(issue #1796)で決定。`parent_id` は2種類の読み手に読まれている —— 委譲の読み手(親の文脈を子に渡す、親が子を
待ち完了を拒む、決着した子の成果を受け取る、分解の判断ごとの abandon・前提の破綻・cancel の cascade)と、中身の読み手(子の中身を親の
タスクブランチへ返す系譜、完了時レビューの根、着地、登録の床)。ADR 0372 決定4 の後、別の workspace の子の中身は親のブランチに入らず自分の
保護ブランチへ着地するので、子のまま残すと中身の読み手のすべてに例外が要る。別の workspace の子を許した根拠の ADR 0031(委譲の木は場所を
跨いでよい)は系譜(ADR 0053)より前の決定で、別の workspace の子が使われた観測も無い。読み手の数え上げと `file:line` は #1796 に置く。
コードと ADR の読みで決めていて、盤面は走らせていない。

## 決定

1. **workspace を選べるのは根だけで、子は workspace を入力に持たない。** 子を登録する扉(人間の分解、agent の分解、`parent_id` つきの登録、
   WebUI の子を足す form)は workspace を受け取らず、子の Edit にも workspace の欄が無い。子は親に従い、列は場所の固定でだけ書かれる
   (ADR 0372 決定1)。付帯子の review の「違う明示は拒む」(ADR 0290)は、入力が無いことに畳まれる。入力があると、保存するか・何と
   比べるか・Edit をどうするか・既定が無いときどうするかの規則が扉ごとに要り、既定の差し替えや未着手の祖先の Edit の後に、子が親と別の
   workspace に残る。
2. **issue つきの子は、木の根の場所が固定されていて、issue の workspace と一致するときだけ子になる。** issue の参照は workspace を身元の
   半分に持つ(ADR 0016)ので、子の workspace は入力でなく参照から決まる。子の場所は木の根の場所で決まり、根の場所が固定されている =
   根が pickup の event か `task_branch_created` を持ち、workspace の Edit が凍結されている(ADR 0372 決定5)。それ以外は決定3 の根になる。
   根の場所を止める仕組みは足さない。
3. **別の workspace に置く仕事は、分解元つきの根として登録される。** 子を足す操作とは別の操作である。agent の分解では、権限の内外を問わず
   承認 question を経て approve で根になる(今ある `allowed_workspaces` 外と保護 workspace の承認と同じ扉)。人間の操作では承認なしで根に
   なる。根は自分の workspace の保護ブランチから切られて自分で着地する。分解元は、分解した task とその分解の判断を指す。
4. **分解元が計画の work —— type が work で、自分にも `parent_id` をたどった祖先にも付帯子が居ない —— のとき、分解元は委譲の側の親である。** 委譲の
   読み手は `parent_id` の子と分解元つきの根を同じに読み、中身の読み手は分解元を読まない。分解元が計画の work である段が続く限り、委譲の
   読み手は子孫として読む(根の根も cancel で倒れる)。
   - 委譲の読み手: pickup で凍結する親の文面(ADR 0321)、`get_current_task` の親の `handoff_doc` と history、文面の書き手(帰責と学習の
     起草)、親が未決着の子を待ち完了を拒むこと、統合に戻った親の history に決着した子として並ぶこと(ADR 0045 / 0047)、分解の判断
     ごとの abandon と、その question が開いている間 pickup を止める範囲(ADR 0048 決定3)、前提の破綻とその届け先、cancel の cascade が
     未決着の子孫を倒すことと走っている task による拒否(ADR 0304)。
   - 中身の読み手: 系譜(ADR 0053 / 0372)、完了時レビューの根(ADR 0111)、着地と着地の門、登録の床(ADR 0301)、cancel の cascade が
     done の work の付帯子を倒すかを決める「成果が捨てられたか」(ADR 0271)、親の risk flag の引き上げ。根はこれらに根として読まれる ——
     親の完了時レビュアーは根の中身を読まず、done の根のレビューは分解元の cancel で倒れない(中身は自分の保護ブランチへ運ばれる)。
   中身の読み手は `parent_id` だけを読み、`parent_id` は workspace を跨がないので、中身の読み手に例外は要らない。
5. **それ以外 —— 付帯子(レビュー・RCA・修理)とその `parent_id` の子孫、work でない type —— が分解元のとき、分解元は文脈だけを運び、根は
   独立した根である。** 分解元の文面・`handoff_doc` と history・文面の書き手は決定4 と同じに渡すが、待ち・完了の拒否・abandon・前提の破綻・
   cancel は根として読む —— 根の失敗の abandon は根の木だけを倒し、根の前提の破綻は root と同じ escalation になり(ADR 0121 決定1)、分解元や
   その祖先の cancel は根に届かない。根そのものは根なので、根が計画の work として別の場所へ分解すれば、それは決定4 の委譲の親になる。
   付帯子は計画の一部ではなく、親の結果に後から付いたものである(ADR 0049)。付帯子自身が親の cancel で倒れるのは、自分の中身の行き先が
   親のブランチで、親の計画と一緒に死ぬからで(ADR 0271 決定3)、別の場所に置いた根の中身は自分の保護ブランチへ運ばれ、親の生死に依らない
   (RCA が cancel から外れるのと同じ線)。待てば、その workspace の Quarantine や未着手で親の着地が止まり(付帯子の待ちは親の結果を判定して
   着地を通すためのもの、ADR 0049)、待たずに委譲の親のままにすると、根の失敗や前提の破綻を判断する分解元が先に決着して居ない。type で
   分けると、付帯子の下の修理の work から1段下で同じ待ちが戻る。

## 帰結

- ADR 0372 決定4 の「別の workspace に固定された祖先を飛ばす」は、同じ workspace の子しか居ないので当たる場面が無くなる。系譜の規則は変わらない。
- 計画の work の分解元は `parent_id` の外にある待ちの辺だが、独立した root どうしの順序(ADR 0121 決定2 が退けた依存の辺)ではなく、分解から
  生まれた委譲の親である。root どうしの順序は今どおり人間が持つ。
- 計画の work は分解元つきの根の完了を待つが、完了は着地ではないので、その変更が親の workspace から使えることは保証しない(今の子と同じ)。
- 付帯子の下で分解の判断が abandon されて分解し直されても、走っている文脈だけの根は残るので、同じ提案が二重になりうる。agent の別の
  workspace への分解は必ず承認 question を経るので、二重は人間の承認の手前で見える。
- 別の workspace への分解でできる根は自分の帰り先を持つので、ADR 0301 決定7 が理由に挙げた「帰り先を work 自身の workspace で読むか」は
  問う必要が無くなる。帰り先の無い系譜の RCA の下では、その根を立てる承認 question を登録の床が今どおり拒む(ADR 0301 決定2 の表が承認で
  work を立てる question を宛先がブランチに依存する側に置く)。根は自分の帰り先を持つので、この拒否の理由はこの決定で当たらなくなるが、
  開くかは #2510 が決めるまで今の床を残す。人間の操作は承認 question を経ないので、この床を通らない。
- 人間が走り出す前の木に issue つきの仕事を足すと、分解元つきの根になり、親のブランチで統合されない。
- 同じ workspace の中で系譜に飛ばされる祖先(未固定の human の祖先、着地済みの祖先、失われて透明な祖先)の下の子は `parent_id` を持ったまま
  自分で着地する。この形の完了時レビューと cancel の読みは #3225 / #3270 が持つ。

## 退けた形

- **子のまま残し、委譲の木と中身の行き先を読み分ける**(この grilling の最初の着地)—— merge back で中身を運んだ先を記録し、完了時レビュー・
  cancel・登録の床・着地の門をその記録と「導出が同じ祖先」の述語で読む形だった。独立の見直しを5回回すたびに、同じ「中身はどこへ行ったか」の
  読みに穴が出た(試行の全記録は #1796)。中身の読み手が `parent_id` だけを読み、`parent_id` が workspace を跨がなければ例外は要らない。
- **計画の work が分解元のときも、分解元を文脈だけに使う** —— 同じ判断の兄弟の abandon で根が残って分解し直すと二重になり、止められていない
  根が走っていると abandon が ADR 0304 で拒まれ(ADR 0048 決定3 は、question が開いている間 pickup を止める範囲が倒す範囲を覆うことに乗る)、
  根の前提の破綻が分解した側に届かない。委譲の読み手を1つずつ決めると、決めていない読み手から穴が出る。
- **付帯子が分解元のときも委譲の親にし、待ちだけを外す** —— 根の失敗や前提の破綻を判断する分解元が先に決着して居らず、親の cancel が
  付帯子を経て、中身の行き先が親に依らない根まで届く。
- **分解元の種類を type で分ける** —— 付帯子の下の修理の work(type は work)が別の場所に分解すると委譲の親になり、親の着地が別の workspace の
  Quarantine で止まる。
- **別の workspace の子を分解元の無い根にする** —— registry-edit の worker が「なぜ直すのか」(親の文面・分解の理由・兄弟の結果)を失い、
  帰責の書き手が承認した人間になる。
- **子の workspace の明示を受け、親と比べて保存しない / 拒む** —— 比べる相手・既定が無いとき・Edit の規則が扉ごとに要り、比べる相手が
  後で動くと分類が古くなる。
- **issue つきの子を足すとき親の場所を止める**(空の列に書き、親の workspace の Edit を凍結する)—— 走り出す前の木の親を Edit できなく
  なる。未固定の根の下では分解元つきの根にすれば足りる。
