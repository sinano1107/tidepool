# WebUI はサーバ応答を、新たに宣言する wire の契約を通して読む

2026-09-21 の grilling(issue #759)で決定。ADR 0133 で `webui/` の全ファイルが tsc の射程に入ったが、サーバ応答が
入る境界は `type ServerJson = any` の1行で素通しのままだった。`any` は何も主張しないので、欄の綴り違いも消滅も
実行時まで見えない。実測(応答ごとのサーバ型の所在、型の閉包の大きさ、leaf 制約を破ったときの挙動)は
issue #759 のコメントに置く。

## 決定

1. **型はサーバ側に立つ。** 捕まえるのは WebUI の綴り違いだけでなく、サーバとの食い違いである。応答の形を
   WebUI 側に手で書くと、検査されない写しがもう1枚増える(ADR 0133 決定4 が design-system の型で断った形)。
2. **正本は依存ゼロの leaf module に新しく宣言する wire の契約である。** 載せるのは WebUI が読む欄だけで、
   エラー応答(確認ダイアログの 409、登録の門の 422)を含む。import してよいのは leaf の語彙(`HaltKind` 等)だけ。
   サーバは `res.json(x satisfies ...)` で同じ契約に照らす。宣言は2箇所に見えるが食い違いはコンパイル時に赤くなる。
3. **契約は `'METHOD /path' → 応答型` の表1つで引く。** WebUI は型付きの取得関数だけを通して応答を受け、
   サーバの `satisfies` も同じ表の同じ行を指す。パスと型の対応を呼び出し側のキャストに預けない。
4. **分岐に使う欄はリテラル union で契約に書く。** WebUI の綴り違いは tsc が、サーバ側の値の追加は `satisfies` が
   赤くする。値集合そのものを leaf へ移すのは issue #352 の仕事で、ここではしない。
5. **抜け道は機械で塞ぐ。** WebUI では `Body.json()` を `Promise<unknown>` に宣言し直し、表を通らない読み取りを
   型検査で落とす。サーバでは表の各キーに `satisfies` が現れることを test が検査する。`ServerJson` は名前ごと消し、
   `webui/**` に `noExplicitAny` を効かせる。
6. **送信側の body はサーバから引かない。** 形が違えばサーバの zod が 400 で拒む —— 黙って壊れる応答側とは
   失敗の見え方が違い、zod スキーマを leaf へ移す対価に見合わない。

## Considered options

- **既存のサーバ型を leaf へ移す(`halt-kind.ts` の先例)** — 閉包が65宣言・約855行に及び、半分は WebUI が
  3欄しか読まない `EventPayload` から来る。しかもサーバ型は wire の形ではない(`ThrottleState` は送出時に欄名が
  変わり、参照先に `Date` を持つ型もある)。契約が約束すべきは WebUI が依存する欄であって、サーバの内部型ではない。
- **ADR 0133 決定3 を撤回して非 leaf から直接引く** — tsc のエラーは0件で、`@types/node` が推移的に入り
  `Buffer` / `process` が WebUI で型検査を通るようになる。決定3 が防ぐ破れ方が、黙って起きる。
- **ルート登録そのものを型付けして handler が値を返す形にする** — サーバ側の付け忘れも構造で消せるが、
  `api.ts` 全体の書き換えを契約という主題に抱き合わせることになる。
