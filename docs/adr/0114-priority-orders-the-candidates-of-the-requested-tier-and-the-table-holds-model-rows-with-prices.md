# 優先順位は要求ティアの候補を並べる鍵であり、表は価格つきのモデル分類の行である

2026-09-11 の grilling(issue #556、従属して #553)で決定。ADR 0110 決定2 が置いた task の優先順位(quality / cost / speed)は、
#544 の selector が読める材料を持たず記録だけの列になっていた —— 表が `Provider × ティア → model` しか持たず、価格も速度も軸に
無い。ティアは価格で揃えて作られているので、同ティアの候補間に cost が区別できる差もほぼ無かった(価格・速度の実測表と出典は
#556 のコメントに置く)。一方で、OpenRouter のような多モデル Provider が入ると「金額と性能で自動的に配置してほしい」需要は
生まれる。この ADR は ADR 0110 決定2 の優先順位の値域と、決定3 の表の形・穴の扱いを置き換える。ティアが床であること、
選択が pickup 時の決定論であること、学習器の位置(決定4)は動かさない。

## 決定

1. **優先順位は selector が読む。値は `quality` / `cost` の2値、既定は `quality`。** `speed` は落とす —— 締め切りはティアの
   申告で表すのが正直で(「今日は economy で足りる」)、人が worker を待つ場面でも所要時間を支配するのは思考と tool 呼び出しで
   あって出力速度ではない。所要時間は学習器の outcome として観測され続けるので、落として失う記録は無い。

2. **表は「モデル分類の行」である: (provider, model, tier, effort, 価格 in / out)。** 同じ (provider, tier) に複数行を許し、
   「LLM を足す」は行を1つ足すこと。行は「その model はそのティアの品質を満たす」という分類であり、**分類は価格帯ではなく性能で
   行う** —— 根拠は第三者が同一ハーネスで測った指標を優先し、vendor 自身のハーネスの数字は参考に留める(Kimi K3 は公式の
   Terminal-Bench 2.1 では Sol の隣だが、独立の同一ハーネス測定はすべて Sonnet 5 / Terra の帯に置く)。「ティア = 価格帯」は
   担保すべき性質ではなくなり、価格は行の属性になる。種の表はスキル `/implementation-delegation` §4 / §5 と同じ内容・同じ鮮度
   管理のまま、moonshot は kimi-k3 を economy の1行にする(旧・3ティアに同じ model を写した行は、穴を spawn 失敗にしていた
   機構の副産物であって品質判断ではなかった)。economy の champion より弱い行(K2.6 / K2.7-code)は種に入れない —— 配布物が
   cost の economy task をそこへ流す賭けをしない。足すのは運用者、測るのは Interview(ADR 0110 決定4)。

3. **ティアは床で、候補は要求ティアと同じ行だけ。** 上位の行へ繰り上げる規則は持たない —— 上げたいなら登録者が tier を書く。
   要求ティアの行を持たない Provider は、その task では entry ごと除外される(Throttle と同じ語)。全 entry が除外されて初めて
   skipped で、これは既存の枝である。「行が無い = 運用者の設定漏れ = spawn 失敗」の例外は退役する —— 「moonshot に frontier 級が
   無い」は設定漏れではなく事実で、除外が正しい語である。

4. **並べ方は2つの鍵の順序を入れ替えた対称な規則。** `quality` = Provider 順位、同順位なら価格。`cost` = 価格、同額なら
   Provider 順位。温存の強制は Throttle オフセット(除外)が担い、順位は好みなので、cost を選んだ task では価格に譲ってよい。
   価格の鍵は out 単価、同額なら in 単価 —— 現在の全行で in と out は比例していてどちらを鍵にしても順序は変わらず、本当の費用は
   学習器の session 合計が持つ。advisor の行は同 Provider の frontier 行、複数なら最安。選んだ Provider の出所に「価格で選んだ」が
   1値増え、`worker_spawned` に刻まれる。

5. **4段目のティアは作らず、Haiku 4.5 / Luna は種に入れない(#553 は却下)。** 行を足すことは「worker session の品質を満たす」
   という分類であり、スキルが rename・機械的置換・大量処理に置くモデルはそれを満たさない。価格が行の属性になった今、4段目の
   障壁は「価格帯を壊す」ではなく「要る場面が観測されていない」ただ1つで、再開条件は `.out-of-scope/` に置く。

## 退けた案

- **表に cost / speed 列を足すのではなく、外部(OpenRouter endpoints API / Artificial Analysis API)から定期取得する** —— 両方
  とも機械可読と確認したが、数行の値を年に数回更新する作業に取得経路・キー管理・出典表示義務を足す価値が今は無い。OpenRouter が
  Provider になり行が増えたときの更新経路として残す(#139)。
- **task 種別で価格の鍵を切り替える(review は in 優先、実装は out 優先)** —— 順序が変わる行が1つも無く、効かない規則は観測
  できない。review task には優先順位の列がそもそも無い(要求は `review_tier` のみ)。再開条件: in の順序と out の順序が食い違う
  行が表に現れたとき。
- **優先順位でティアを下回る(締め切りなら standard の作業を Sonnet で)** —— 「standard を申告して sonnet で走った」episode が
  難易度の申告(学習の文脈変数)を濁す。同じ1列でティアを下げるほうが記録として正直。
- **列ごと落とす** —— #548 の文脈変数を1つ減らし、Q2 で確認した需要(多モデル Provider での自動配置)に「学習器の昇格まで」と
  答えることになる。
