# 盤面全体の停止は1つの読み口が答え、その答えは観測の鮮度を伴う

issue #225 / #227 のグリリング(2026-08-09)で決定。

実機で2つの症状が同じ日に出た。1つは、未コミットの triage セッションが pickup を止めている最中に queue 画面の ↑ を6回押しても、6回とも「immediate poll fired」という成功トーストが返ったこと。`GET /api/pause` が答えるのは Pause と throttle の2つだけで、**triage の在否はサーバの口にも無かった**。もう1つは、spend-down を有効化しても再開見込み時刻がその場で更新されず、画面を2回開き直すまで反映されなかったこと。ルートは正しく即時再評価を撃っているが `void poll()` の撃ちっぱなしであり、その中身は PTY 上で `claude --safe-mode` を起こして `/usage` をスクレイプする数秒〜数十秒の処理だったので、**応答は必ず更新前に返っていた**。

原因は別々に見えて1つである。**盤面は「今なぜ pickup が起きないか」に対する正準の答えを持っておらず、必要になった順に個別配線を生やしてきた。** その結果、答えを持たない停止が黙って増え、答えられる停止についても「いつ観測した値か」を言えなかった。

## 決定

### 1. 盤面全体を止める停止は、1つの読み口が列挙で答える

線は「**止められるより狭い資源が存在するか**」で引かれる — CONTEXT.md の Quarantine が既に持っていた基準であり、抽象的な但し書きではなく判定基準として働く。今日の列挙は5つ:

- triage セッション
- Pause
- throttle の session / week 線
- 封じ込め能力の不成立
- レジストリ到達性の不成立

**資源単位の停止はここに入らない** — workspace / agent の quarantine、fable 線、issue 展開の一時的失敗は、候補ごとの性質であって盤面の状態ではない。同じ読み口に混ぜると、線そのものが次の追加で溶ける。

### 2. 答えは、それが基づく観測の鮮度を伴う

読み口は throttle について `{throttled, resumesAt, observedAt, 再評価中か}` を返す。**「表示は観測に基づく」という ADR 0028 の線を守ったまま遅延を扱える形はこれ1つである** — 応答を待たせれば PTY の数十秒が人間の HTTP に乗り、楽観的表示は盤面が見ていない値を UI に主張させる。`throttle_state` は今日、観測時刻の列を持たない。`webui/app.jsx` のコメントは既に「走行中は stale でありうる」と自覚していたが、**どれだけ古いかを盤面自身が知らなかった。**

UI は応答を待たず、「再評価中」の間だけ短間隔で同じ読み口を叩いて追従する。ポーリングは「人間が今結果を待っている数十秒」に限定され、常時ポーリングにはならない。

### 3. 露出の面は事実の寿命で分かれる

- **瞬間の事実 → トースト。** ↑ を撃った直後、同期で読める停止(triage / Pause / 封じ込め能力 / レジストリ到達性)はその場で名指しする。throttle だけは「再評価中」と言う。
- **持続する事実 → slot 行。** 消えないので、再評価の結末を引き取れる。
- **人間の行動を待つ停止のうち、確認 question を持たないもの → 全タブ常設バナー。** 今日これに該当するのは **triage セッションだけ**である: Pause は人間自身が押した明示的な意思、throttle は自己回復する環境事象、封じ込め能力とレジストリ到達性は Tidepool 名義の確認 question が人間を呼ぶ。triage だけが人間の操作の**副作用**として生まれ、確認 question も立たず、queue 画面にも出ていなかった。バナーには commit を乗せる — 人間がその場で解ける唯一の停止だからである。

## Consequences

- `throttle_state` に観測時刻の列が要る。副産物として「走行中の stale」が初めて定量化される。
- 新しい盤面全体の停止が生まれたとき、増えるのは配線ではなく**列挙の1行**になる。
- トーストと slot 行の役割が分離する — 前者は瞬間の通知、後者は持続する真実。両者が矛盾する道は、同じ読み口を読む限り構造的に閉じる。
- ↑ が「発火した」と「pickup が起きた」を区別して語るようになる。今日この2つは同じ文で名乗られていた。

## Considered options

- **`/api/pause` に triage を1つ足すだけ** — 今回の実害は確実に消える。却下したのは、封じ込め能力とレジストリ到達性が引き続き不可視のまま残るため。どちらも盤面全体を止めるので、同じ「20分原因不明で止まる」が別の顔で戻る。
- **応答を再評価の完了まで待たせる** — 押した直後の refresh が必ず新しい値を読む。却下したのは、PTY スクレイプの数十秒を人間の HTTP 応答に載せることになるため。Tailscale 越しのスマホではタイムアウトやプロキシ切断の範囲で、「押しても変わらない」が「押したら壊れる」に化ける。
- **push で UI を追わせる** — 待たせずに確実に届く。却下したのは、CONTEXT.md の Quiet hours が通知対象を「question と人間宛てタスクの2種」と明記しており(どちらも人間がボトルネックで親を塞ぐ)、盤面状態の変化をそこへ入れるのは通知対象の定義そのものの変更になるため。
- **楽観的表示** — spend-down の意味論はクライアント側でも計算できるので即座に反応する。却下したのは、盤面が観測していない値を UI が主張することになり、ADR 0028 の「fail-closed は可視化とセット」= 表示は観測に基づく、と正面から衝突するため。
- **列挙はまとめるが用語化はしない** — 実装は同じ。却下したのは、「なぜこの5つだけが並ぶのか」を説明する場所が無くなり、次に資源単位の停止がここへ混ざるのを防げないため。
