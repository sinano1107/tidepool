# コミットはトリアージの終端であって、セッションの動詞ではない

issue #278 のグリリング(2026-08-11)で決定。ADR 0059 が「セッションは操舵で開き、流し読みでは開かない」と決めたとき、**フローの終端がセッションの存在を前提にしたまま残った**。ADR 0004 の語彙(トリアージセッション = 一本道フロー1回分)と ADR 0059 の決定(フローは走っているがセッションは無い状態が正規)が両立しないことが、実機のバグとして表に出た形である。

ステージングの意味論、タイムアウトでの自動クローズ、コミットが「run now」である線、front-insert と異議の束ねがセッションに属することは、いずれも無傷である。

実機で観測されたのは、流し読みだけのトリアージが**必ず**赤いエラーで終わり、既読カーソルが進まないため未読カウントが永久に消えない、という事象だった(#278)。同じ穴から 3/3 のキュー確認画面が空になる、回答が生んだログエントリがコミット後に新しい未読として現れる、引き継がれた scratchpad 行が UI に一生現れない、バナーからのコミットが未読ログ全体を黙って既読にする、が同時に出ていた。

## 決定

### 1. フローとセッションを2語に分ける

**Triage(トリアージ)** は人間がたどる一本道フロー1回分(質問 → ログ流し読み → キュー確認 → コミット)。**Triage session(トリアージセッション)** は操舵が始まったときだけ開くサーバ側の窓であり、pickup を止め、front-insert をステージし、異議を束ねる。

ADR 0004 の「トリアージセッション = 一本道フロー1回分」という定義を、この2語に割る。新語は作らない —— 既存語の再配分だけで済み、DB テーブル名(`triage_sessions`)も API パス(`/api/triage/*`)もそのまま正しくなる。包含関係が読みのままである: **トリアージの最中に、操舵が始まればトリアージセッションが開く。**

`steering` は Objection の方向コメントで既に埋まっているため、セッション側の名には使えない。

### 2. コミットはトリアージの終端であり、セッションを閉じるのはその一部

**Commit(コミット)** はトリアージの終端であって、次の3つを1つの行為として行う。

1. scratchpad の振り分けを適用する
2. トリアージセッションが開いていれば閉じる(ステージされた front-insert の適用と異議の束ねを含む)
3. 既読カーソルを進める

セッションが無いトリアージ —— ADR 0059 が正規にした状態 —— でも、1 と 3 は走る。**セッションの不在は失敗ではない。** 従来「コミット失敗」として扱っていた 409 は、pending なものが存在しえないことの表明であり、失われるものは何もない: 回答は即時 durable、異議は raise 時点で append 済み、front-insert はセッションを閉じた時点で適用済みである。

`auto-commit` という語は退場させる。watchdog がするのは「タイムアウトでセッションを**閉じる**」であって、コミットではない。

### 3. セッションの不在はサーバが吸収し、3状態を応答で区別する

`POST /api/triage/commit` はセッション不在でも 200 を返す。人間に届く結果は3つに割れる。

1. **セッションを今閉じた** —— ステージされた操舵を適用し、即時ポーリングを発火した
2. **セッションは既にタイムアウトで閉じられていた** —— 「セッションは HH:MM に閉じられ、ステージした操舵は適用済み」と明示する
3. **セッションは開いていなかった** —— 流し読みのみ。やったこと(既読 N 件・scratchpad N 件)だけを述べる

②と③の判別はサーバに閉じる。トリアージセッション行が「**閉じた主体**(コミット / タイムアウト)」と「**タイムアウトで閉じた事実を人間に伝えたか**」を持ち、次のコミットが1度だけ伝えて印を付ける。

クライアントに「このフロー中に操舵した」という信念を持たせる形を却下したのは、リロードで消えること(②が黙って③に退化し、再現しない挙動になる)、面を跨げないこと(スマホでトリアージ → タイムアウト → デスクトップでコミット、では誰も伝えられない)、そして「タイムアウトで閉じられた」が盤面の事実であってブラウザタブの事実ではないこと(帰属が逆になる)による。

伝える面はコミットの瞬間だけでよい。**盤面が動いていることは正常状態であって、知らせるべき持続する事実ではない。** 伝える価値があるのは「今押したコミットは、実は30分前に適用済みだった」という瞬間の事実である(Board-wide halt の「事実の寿命で面が分かれる」線の適用)。印が要るのは、翌日のコミットで同じ通知を蒸し返さないためである。

### 4. scratchpad の行はセッションに帰属しない

行は盤面の「振り分け待ちの行」の列であり、セッションの持ち物ではない。`triage_scratchpad.session_id` と、`startTriage` が全行を新セッションに付け替える `UPDATE`(WHERE 句を持たない)は、両方とも消える。**削除であって追加ではない** —— このカラムは常に最新セッションを指すため絞り込みの情報を何も持っておらず、実際の効果は「開いているセッションが無いと1行も返せない」ことだけだった。

帰結として:

- **振り分けはセッションの生死に依らず適用される。** 振り分けは行1本ごとの始末であって、キューの操舵ではない —— pickup を止める理由を持たないのだから、セッションの生死に依らせる理由もない。人間の判断が黙って消えない。
- **`GET /api/triage` はセッションの有無に依らず全行を返す。** コミット画面に持ち越し行が現れる。ADR 0004 が書いた「振り分けられなかった行は次のセッションが引き取る」という安全網は、これまでサーバ側でのみ真で UI には現れていなかった。
- **同じく S3 のキュープレビューもセッションを要求しない。** セッションが無ければステージされた front-insert が無いだけで、ライブキューはそのまま返る。

### 5. scratchpad への書き込みはセッションを開かない

ADR 0059 決定1 を改訂する。セッションを開くのは**回答と異議の2つ**であり、判定基準は「**セッションに預けるものがある行為か**」である。回答は front-insert をステージし、異議は `session_id` で束ねられてコミット時に修理タスクになる —— どちらもセッションが実際に何かを預かっている。決定4 の後、scratchpad は何も預けない。

これは ADR 0059 の線(操舵で開く)の忠実な適用であって逆行ではない。苛立ちを1行書き留めるだけで盤面が30分止まる道が消える。

流し読みと同じく、**書き込みは開いているセッションの activity には数える**(ADR 0059 決定3 と同型)。「放置」は不在であって沈黙ではない。

### 6. 人間が書いたログエントリは未読に数えない

`worker_id` が human のエントリは、その人間にとって最初から既読である。Decision log の目的はエージェントが権限内で下した判断を人間が流し読むことであり、**自分が書いた判断を読み返す対象にする理由がない。** 単一人間の系なので「人間が書いた」は「自分が書いた」と同義である。`origin` は問わない —— WebUI 経由でも管理MCP 経由でも、読み返す理由の無さは同じ。

これが解くのは、トリアージ中に人間自身の操作が生んだログエントリ(PR 昇格の abandon が積む `decision_logged` など)が、凍結されたスナップショットの先にあるために未読のまま残り、コミット後に新しいトリアージ対象として現れる、という事象である。**スナップショットの凍結自体は正しい** —— フロー中に足元でスナップショットがずれないためにあり、フロー中に届いたエージェントのエントリを読まずに既読化してはならない(カーソルは前進のみで戻せない)。

記録は何も消えない。視界からの退場だけであり、既読エントリは畳まれて残る —— 自分が書いたエントリへの異議も、畳みを開けば従来どおり打てる。

### 7. 人間の回答は Decision log に載せないまま

`question_answered` を `HUMAN_FACING_KINDS` に入れない。Decision log は権限内判断の1行記録と完了報告が流れる面であり、人間の回答はエスカレーションへの**応答**であって権限内判断ではない。回答は question タスクに残る。

### 8. 常設バナーはセッションを閉じるだけ

全タブ常設バナー(ADR 0058)のボタンは既読カーソルにも scratchpad の振り分けにも触らない。バナーの役割は「止まっていることに気づき、そこから解除できる」ことであって、トリアージを終えることではない。決定2 でコミットを終端の語に確定したので、ラベルからも `commit` を外す。

これが解くのは、Queue タブからバナーを押すだけで、読んでいない Decision log 全体が黙って既読になる(前進のみのカーソルなので戻せない)という事象である。

### 9. 即時ポーリングはセッションを今閉じたときだけ発火する

発火の理由は「止めていた pickup を再開する」ことであって、タスクが増えたことではない。②は閉じた時点で発火済み、③はそもそも何も止めていない。振り分けから生まれたタスクは、通常の登録と同じく次の自然な契機(走行中タスクの終了、毎時のティック)を待つ —— 登録経路によって pickup の急ぎ方が変わる非対称を作らない(`src/api.ts` の move が「さもないと並べ替えが黙って pickup 要求を兼ねる」として発火条件を絞っているのと同じ線)。

## Consequences

- 流し読みだけのトリアージが正常に完結する。未読カウントが消え、3/3 にライブキューが出る。
- セッションレスのトリアージでは **3/3 のプレビューはライブキューであり、途中で変わりうる**。止める理由が存在しないのだから設計通りである(「止まっていない」は不具合ではない)。
- タイムアウト30分は変えない。超過が無害になる —— 振り分けは適用され、既読カーソルは進み、文言は事実に基づく —— ため、時間で削る動機が消えた。
- 「コミット失敗」を人間が見るのは、本物の失敗(通信・サーバエラー)のときだけになる。そのときは何も適用されず、カーソルも進まない、という従来の不変条件がそのまま生きる。
- トリアージセッション行が「閉じた主体」を持つことで、人間のコミットで閉じたセッションとタイムアウトで閉じたセッションが記録上区別できるようになる。実機の直近4セッションはすべて後者だった。
- `/api/triage/commit` は決定2 で終端の動詞になったが、バナー(決定8)も同じエンドポイントを呼ぶ。エンドポイント名を `close` に寄せ、「Commit = close + cursor」をクライアントの合成として明示するのは別 issue とする —— 改名のコストはスキーマではなくテストと e2e の呼び出し箇所の機械的な差分であり、今回の修正と混ぜると差分が膨らむ。

## Considered options

- **終端をセッションの有無で2つのボタンに割る**(セッションがあれば「Commit」、無ければ「ログを既読にする」)—— 却下したのは、`triageActive` がポーリング時点のスナップショットであるため、判定とボタン押下の間にタイムアウトが割り込めば同じ失敗に落ちること、そして一本道フローの終端が状況で名を変えるとテンポが落ちることによる。
- **既読カーソルを流し読みセクションの離脱時に進める** —— 読んだ事実と操舵の確定を完全に分離できる。却下したのは、モバイルの画面オフやアプリ切り替えによる途中離脱で既読が確定する道が開き、前進のみのカーソルなので戻せないため。
- **カーソルをやめ、displayed 済み集合で既読を決める** —— 最も正確。却下したのは、Decision log の「未読カーソル(前進のみ)」というモデル自体の置き換えになり、影響範囲がこの issue を超えるため。
- **終端時点のログ末尾までカーソルを進める** —— 実装は最小。却下したのは、フロー中に届いたエージェントのエントリを読まずに既読化してしまい、取り戻せないため。
- **人間の回答を Decision log に載せる** —— 決定6 により載っても流し読みを汚さないので、ほぼ無料に見える。却下したのは、`HUMAN_FACING_KINDS` の変更が異議の対象集合と異議率の分母に波及するため。
- **scratchpad の帰属を残し、UI に載せる配線だけ足す** —— 変更は最小。却下したのは、意味を持たないカラムと WHERE 句を持たない全行 UPDATE が残り、セッション不在時は依然として行が見えないため。
- **フローにサーバ側の identity を与える**(何も止めない「トリアージフロー行」)—— ②③を完全に区別できる。却下したのは、決定1 で言葉として分けたフローがエンティティとして増え、開ける契機と閉じる契機をまた一から議論することになるため。決定3 の「未通知のタイムアウトクローズ」で、フローの存在を知らずに同じ問いに答えられる。
