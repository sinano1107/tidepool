# 認証の検出は実害の瞬間に行い、定期プローブは廃止する

issue #332 のグリリング(2026-08-14)で決定。ADR 0070 決定4 の改訂である。

ADR 0070 決定4 は認証失効の検出に定期プローブ(既定30分、実 haiku 呼び出し)を置いた。要件は「人間が
1時間以内に知る」。ところが Pi の実測(2026-08-14)で、無人・キュー空の盤面でもこのプローブが30分ごとに
実モデル呼び出しを飛ばし続けることの副作用が判明した:

- 5時間セッション窓が失効する前に必ず次のプローブが入り、**窓が連鎖して閉じない**。実測: 8/14 08:54 の
  /usage で session 窓の開始は 05:19。その間 Pi で走ったのは認証プローブだけ(worker ゼロ、キュー空)。
- ADR 0076 の「アイドル窓 = 観測された不在」の分岐が本番で永久に踏まれない。
- ADR 0030 のペース線の起点(窓の開始時刻)が、仕事の有無と無関係にプローブ都合で決まる。人間が使い
  始めた時点で経過割合が進んでいるぶん、絞りが実質ゆるむ。

コスト(1回 haiku で input 10 / cache read 21,334 / output 41)自体は微少で、本体は**他の機構の正しさを
壊す副作用**である。さらにこのプローブはコスト構造が倒錯している: 認証が死んでいれば 401 で即拒否され
0トークン・窓も開かない(タダ)。健全なときだけ実呼び出しが成立し、窓を開け続ける。**役に立たないときは
無料で、無用なときだけ支払う**機構だった。

グリリング中の裏取りで前提が2つ確定した:

- `pickupBlocked()` は末尾で `nextSlotTask` の不在を見て短絡するため、**キューが空だと hourly poll は
  `checkThrottle`(= checkUsage と null→401 分類)に到達しない**。無人・空キューの盤面では定期プローブが
  唯一の検出経路である — 廃止は「冗長の削除」ではなく「アイドル中は検出しない」という交換である。
- 決定5 の期限30日前警告(`warnCliAuthExpiry`)はプローブのタイマーに同居している。警告は0コストの
  日付比較なので、タイマーだけ残しモデル呼び出しを外す分離は自明に可能である。

## 決定

### 1. 要件を置換する — 「1時間以内に知る」から「実害の最初の瞬間に確定診断つきで halt」へ

「1時間以内」が守っていたのは ADR 0070 執筆時の脅威 — refresh の reject / 競合による**予測不能な黙った
失効**である。setup-token 移行(ADR 0070 決定1)でこの脅威は消えた。残る失効シナリオを分解すると:
(a) 年1回の期限切れは決定5 の30日前警告が守る。(b) デプロイ時のオペミスは決定6 の verify-deploy 項目
(#319)が守る。残余は (c) サービス側の revoke / アカウント異常だけで、稀かつ予測不能である。

この残余に壁時計保証を張り続ける価値はない。要件は「**失効が実害を持つ最初の瞬間**(pickup・AI 下書き・
表示時翻訳・worker)に、確定診断つきで halt + question が立つ」に置き換える。アイドル中は誰も認証を
必要としておらず、検出しないことの損失は「仕事が来た瞬間に修理待ちが入る」だけ — 決定7 が夜間について
既に受け入れた交換(halt は即時、失うのは回復可能なアイドル時間だけ)を、アイドル時間帯全体へ一貫適用
するだけで、新しい譲歩ではない。

### 2. 定期プローブと起動時プローブを廃止する

`startCliAuthMonitor` の30分ごとの実プローブと、サーバ起動時の1回(`probeNow` のモデル呼び出し)を落とす。
残る検出経路は3つで、いずれも「実害の瞬間」または「人間起点」である:

- **JIT 分類**: pickup 候補があるときの `checkThrottle` — `checkUsage` が null なら確定プローブを1発撃ち、
  401 なら quarantine(現行のまま)。認証が死んでいればこのプローブは 401 拒否でタダである。
- **機会的分類**: AI 下書き・表示時翻訳・worker exit の 401 をその場で分類(現行のまま)。
- **回答受理時の再検査**: cliAuth question の回答を受ける前の検証(現行のまま)。

`unknown` の扱いも現行どおり(console.warn + fail-closed throttle に留まる)。これは ADR 0008「usage は
pickup 判断の瞬間だけ、background poll はしない」と同じ形であり、認証検査が教義の例外だった状態を解消する。

### 3. タイマーは期限警告専用に縮退して残す

決定5 の30日前警告はプローブではなくタイマーが担っていた。タイマー(現行30分間隔のまま — 0コストの
日付比較なので周期を変える理由がない)と起動時の警告チェックは残し、モデル呼び出しだけを外す。

### 4. 決定6 は不変、決定7 は一般則に吸収される

verify-deploy の認証プローブ(ADR 0070 決定6、#319 の未チェック項目)は変更しない — デプロイは人間起点の
イベントで、着地すれば**唯一の能動検査**になるぶん重要度はむしろ上がる。決定7(quiet hours 中の失効は朝の
ダイジェスト)は「1時間以内」の前提ごと消え、夜間特例ではなく決定1 の一般則 — 検出は実害の瞬間、通知は
question 経由 — に吸収される。交換条件の理路はそのまま本 ADR の根拠として引き継がれる。

## 受け入れる損失

アイドル中に失効が起きても、仕事(または人間の AI 動詞)が来るまで誰も気づかない。以前は事前に修理できた
ケースで、修理待ちの遅延が仕事の先頭に乗る。残余シナリオ (c) の稀さと、失うものが回復可能な待ち時間だけ
であることから受け入れる。

## 退けた対案

- **間隔延長(例: 6時間)** — 窓の連鎖は切れるが「健全なときだけ支払う」倒錯は残る。中途半端。
- **0トークンスクレイプの定期実行 + null のときだけ実プローブ** — `checkUsage()`(0トークン・窓を開けない)
  をタイマーで回し、%パネル不在のときだけ確定プローブを撃つ案。壁時計保証を窓コストなしで維持できるが、
  スクレイパが退行すると(#323 の Pi レンダリングバグが先例)every tick が null → 実プローブ発火で、除去した
  はずの窓連鎖へ**静かに回帰**する。ADR 0008 の教義に背景スクレイプを再導入する点も含め、要件の置換
  (決定1)を選んだ以上この保証自体が不要になった。
- **モデル呼び出しを伴わない 401 観測の新設(非公式 API エンドポイント直叩き)** — 非公式依存で脆く、
  「認証プロトコルは CLI が所有する」の線を破る。
- **現状維持(窓開放の受け入れ)** — コストは微少だが、ADR 0076 の分岐が本番で踏まれない・ADR 0030 の
  ペース線の起点が歪む、という他の機構の正しさを壊す副作用が残る。
